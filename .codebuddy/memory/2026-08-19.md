- 基于项目真实表结构（task_event_log 等）+ 实体类，给用户写了完整 JPA vs MyBatis 对照教学：
  - MyBatis 版完整 CRUD：Mapper 接口（@Mapper + @Param）+ Mapper XML（insert/update/delete/findById/findAll/count/方法名查询 7 段 SQL）
  - 关键差异：save() 自动判断 INSERT/UPDATE vs 手动 if 分派 insert/update；findById 返回 Optional vs null；分页内置 vs 手写 LIMIT；枚举/JSON 列 @Enumerated/@JdbcTypeCode vs 自定义 TypeHandler；map-underscore-to-camel-case 配置
  - 总结：JPA 全包 SQL（代价=失控），MyBatis 手写 SQL（回报=可控）；项目全单表简单查询，JPA 是最优解

## 新增知识点：双 ORM 共存 + 配置切换（用户提问）

- 用户问"能否同时写两套方法，根据配置决定用哪一套"→ 可以，核心是三层：① 抽象接口（如 TaskEventLogStore）让 Service 只依赖接口；② 两个实现类用 @ConditionalOnProperty(name="app.persistence.mode", havingValue="jpa"/"mybatis", matchIfMissing=true) 条件装配；③ yml 加自定义配置 app.persistence.mode=${APP_PERSISTENCE_MODE:jpa}
- 另一开关方式：@Profile("jpa")/@Profile("mybatis") + spring.profiles.active（项目已有 dev profile 先例）
- 关键坑：两个 starter 同时存在时自动配置冲突，需 @SpringBootApplication(exclude={MybatisAutoConfiguration.class}) + 手动 SqlSessionFactory bean
- 实践定位：双 ORM 用于迁移过渡/A-B 对照学习，不长期维护；JPA 本身可用 @Query(nativeQuery=true) 覆盖复杂 SQL

### 实测踩坑（重要）
1. **MyBatis 3.5.19 核心包无内置 UUID TypeHandler**（连 UuidTypeHandler/UUIDTypeHandler 都没有），INSERT `#{id}` 报 "Type handler was null"→ 需自定义 @Component TypeHandler（@MappedTypes(UUID.class)）
2. **H2 JSON 列读回是带引号的字符串字面量**（如 `"{\"k\":\"v\"}"`），readTree 得到 TextNode 而非 ObjectNode → TypeHandler 需对 TextNode 做二次 readTree 还原（PostgreSQL 原生返回 JSON 文本不受影响）
3. **两个 @SpringBootTest 上下文共用默认 H2 内存库导致 schema 重复初始化报"表已存在"** → 每个测试类指定独立 `spring.datasource.url`（research-agent-jpa / research-agent-mybatis）
