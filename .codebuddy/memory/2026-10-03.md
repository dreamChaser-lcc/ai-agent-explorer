- **J8 追问：execute 能否"直接传方法名"（像 JS 传函数）✅ 已讲（10-07）**：三层面——① **Java 没有"裸函数"**（方法不是值、必须依附对象）——`execute` 要的精确说是"**实现 Runnable 接口的对象**"（任务包）；但"函数式接口 + lambda/方法引用"就是 Java 的"传函数"官方姿势（形式极像 JS）；② **能直接传方法名——它叫"方法引用" `::`**（J3 学过：`taskResponseMapper::toTaskSummary`），**但有形状要求**：方法必须"零参零返回"才能直接当 Runnable（`this::cleanUp` ✅）；`this::executeTask` ❌ **形状不匹配**（它要一个 UUID 参数，Runnable 给不了）——所以项目必须 `() -> executeTask(taskId)`：**箭头的作用 = 现场把 taskId 绑进包裹、把"有参方法"适配成"零参包裹"**；③ ★ **JS 其实也分流（完全同构三行）**：`setTimeout(doSomething)` ✅（零参直接传引用≈Java 方法引用）/ `setTimeout(() => executeTask(taskId))` ✅（要绑参用箭头≈Java lambda）/ `setTimeout(executeTask(taskId))` ❌（立刻执行）——"形状匹配直传、绑参用箭头"两边同一规律。④ 补：Java 8 前原貌 = 匿名内部类 `new Runnable() {@Override run(){...}}`，lambda 是简写；**函数式接口家族**（只有一个抽象方法）：Runnable（零参无返回）/**Supplier**（零参有返回）/**Consumer**（一参无返回）/**Function**（一参有返回）/**Predicate**（一参返回 boolean——★ J5 的 filter 参数就是它）。**计划：J8 下半场 ThreadPoolLab 里加"两种提交方式对比"小实验（this:: 零参方法 vs 箭头绑参）**。
- **J8 思考题答案讲解（10-07）✅**：**题 1**（`() ->` 为什么必须包）双层——① **编译层**：`executeTask(taskId)` 带括号=方法调用表达式（**求值即执行**）、类型是 `void`——void 不能当参数传给 `execute(Runnable)`，编译直接报错；② **语义层**："**把活干了**"（立刻、主线程、跑 5 分钟）vs "**把活的说明书递进包裹**"（打包成 Runnable 延迟执行、班组拆包才跑）——lambda = **把一段代码"冻"成对象传递**（"代码即数据"）；★ **前端同构坑**：React `onClick={handleClick}`（对——递函数）vs `onClick={handleClick()}`（错——渲染时立即执行）、`setTimeout(fn)` vs `setTimeout(fn())`——**一模一样**。**口诀：带括号=现在干；箭头包=装进包裹等会干**。**题 2**（ASYNC vs SYNC）——对比表：HTTP 响应等待（全程挂几分钟 vs 毫秒级秒回 taskId）/ 超时风险（浏览器+网关+LB 任一环超时即断 vs 无）/ 用户看到（转圈干等甚至报错 vs 秒开+SSE 实时进度）/ 进度获取（无 vs `/api/tasks/{id}/stream`）/ **任务与连接的关系（绑死 vs ★ 解耦）**——深层：**任务状态存 DB、独立于 HTTP 连接** → 所以能暂停/取消/查历史（PAUSED/CANCELLED 枚举 + StepExecutionEntity 时间线才有意义）；**HTTP"请求-响应"模型与长任务八字不合** → 异步任务模式（202 Accepted + 轮询/SSE）是行业标配；SYNC 按代码注释仅"测试和简单场景"。**下一站：J8 下半场动手实验**（exampleJavaGrammar 加线程池实验：提交多任务看线程名/排队/复用）。
