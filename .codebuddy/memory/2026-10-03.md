**场景⑥ 追问：offset 原理（10-11，用户"代码里没看到 offset 读取"）✅ 已讲**：① **为什么代码里看不到**——offset 的读取/提交**全在 Kafka 客户端内部**（`KafkaConsumer`），应用代码是"**乘客层**"（"乘客睡觉，司机记里程"）；② **原理**：offset = **分区内**消息的单调递增序号（0,1,2...）——消费者组进度 = 一组 `<分区, offset>` 对（"书签"）；③ **存哪**：旧版 ZooKeeper → 新版 **`__consumer_offsets` 内部主题**（50 分区——Kafka 用"自己的消息机制"存"消费进度"——自举妙点）；★ **组间隔离**（不同组各自书签、互不干扰）；④ ★ **提交时机=重复的根源**：原生客户端默认 `enable.auto.commit=true`（每 5 秒）→ "至多一次"（**可能丢**）；**Spring Kafka 容器默认 `enable.auto.commit=false` + `AckMode.BATCH`**（"**处理完才提交**"）→ 处理中崩 → 重读 → **至少一次**（可能重，不丢）——★ 价值观："**宁重勿丢**"（丢=任务永久消失；重=守卫兜底）；⑤ **"避免重复"的真相**：投递层**不可能**完全避免（恰好一次是神话）——Kafka 负责"不丢"，**"不重复"是业务守卫的事**（思考题 2 再钉）；⑥ **眼见为实命令**已给：`docker exec -it kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group research-agent-backend`——三列：**CURRENT-OFFSET（书签）/ LOG-END-OFFSET（车道尽头）/ LAG（=堆积量——消费者监控第一指标）**；我们 yml 没写 ack 配置=用的就是默认（处理完才提交——正是要的 at-least-once）。
- **场景⑥ 追问 2：offset 怎么排查丢/重 + 能否回退读取（10-11）✅ 已讲**：**① 排查三层观测窗**——(a) **生产层**："有没有发"：`[MQ] 已发送` 日志 + **LOG-END-OFFSET**（车道尽头涨没涨）；(b) **消费层**："发了有没有读"：**LAG**（积压=LOG-END−CURRENT；持续 0 且业务没执行=疑似跳过/没发；长期>0=慢不是丢）+ CURRENT-OFFSET 轨迹（**注意 BATCH 模式书签按批前进——不能简单以"跳号=丢"**）；(c) **业务层（最硬的对账法）**："读了有没有干成"：数 Kafka 消息数 vs 数 `[MQ] 收到` 日志行数 vs 数业务数据（task 状态/事件）——**丢**=消息数>处理数；**重**=处理数>消息数（grep 同一 taskId 的"收到"行出现两次）——★ 但"重"未必有害（守卫跳过=设计目标）；生产监控=**LAG 告警**+消费延迟（JMX/lag-exporter/Burrow 一句带过）。**② 回退读取=支持（Kafka 招牌能力）——三种方式**：**(1) 旁路查看（最安全）**：`kafka-console-consumer.sh --from-beginning`【不指定 --group → 随机新组 → 不碰生产组书签——**只看不干**】；**(2) 重置原组书签（真重放执行——影响业务）**：`kafka-consumer-groups.sh --group X --topic Y --reset-offsets --to-earliest --execute`（档位：--to-earliest/to-latest/--to-offset N/--shift-by -N/--to-datetime——★ 前提：**消费者必须停止**（组 inactive 否则报错）——姿势：停应用→reset→重启；★ 后果警示：重放=重复消费（守卫兜底=宁重勿丢的另一面；哪些状态被拦去读 shouldStop=重复无害的保证书）；**(3) 按时间回退**（事故恢复利器）。**③ 根原理**：Kafka 把"**消息生命周期**"与"**消费进度（书签表）**"**解耦**（消息存磁盘+书签可改写）——传统 MQ 读走即删两者焊死——**这就是"可重放"的根**。
- **场景⑥ 追问 3：回退的"两条路"确认（10-11）**：用户确认"常规回退=用 --reset-offsets 操作"——✅ 对，**措辞校准**：不是"操作 kafka 应用"，而是【用 Kafka 自带的**命令行管理工具**（kafka-consumer-groups.sh）→ 本质通过管理接口改写**服务端**（`__consumer_offsets`）里消费组的**书签**】——不动你的 Spring 应用代码（只需停/启进程让组 inactive）。**补充另一条路（用户没看到）**：**代码层 `seek()`**——消费者程序运行时主动拨书签（`KafkaConsumer.seek()` / Spring 的 `ConsumerSeekAware` 接口）——**不停机、程序内控制**（典型用途："处理失败想重读这条/延迟重试"）——取舍：**运维排查/事故恢复 → 外部工具 --reset-offsets（标准姿势）；程序内精细控制 → seek()（要写代码）**；★ 为什么回退要"外部工具"：书签**存在服务端**（`__consumer_offsets`）——消费者停掉后没人能"内部"操作它——管理工具直接改服务端记录，是**唯一的非代码路径**。
- **场景⑥ 追问 4：代码层 seek 的场景 + 何时需要改 offset（10-11）✅ 已讲**：**定性**："**正常会手动改 offset 吗——不会**"（99.9% 时间自动管理=常态；改 offset 是**例外态**：要么出事【运维恢复】要么设计【代码 seek】）。**代码层 seek 四个真实场景**：① **失败重试原形**（catch 时 `seek(partition, record.offset())` 把书签拨回当前条——"无限重试直到成功"的朴素实现；进阶=重试主题/死信队列 @RetryableTopic 一句带过）；② ★ **跳过"毒药消息"**（坏消息永远处理失败、卡死车道→seek 跳过——生产最常见的干预；★ 我们 consumer 的 `UUID.fromString(taskIdText)` 就是隐患点：收到坏消息会重试后跳过=真实案例）；③ **程序化"时间旅行"**（Spring `ConsumerSeekAware.onPartitionsAssigned` 里 seek——"每次启动从某时间点读起"——如每日对账消费者——**不是排查是设计**）；④ **新组起点的主动版**（对应 yml 的 auto-offset-reset）。**"何时需要重读"全景**——**事故类**：修完消费 bug 重放重算（最典型——"代码修了数据要重算"）/ 消息过期后 offset out of range（retention 7 天——只能回 earliest/latest——没得选）/ 误操作跳过（--to-latest 手滑→reset 回去）/ 数据回填；**设计类**：程序内重试（seek）/ 跳毒药 / 定期重放对账 / ★ **测试演练**（模拟重放验证幂等性——场景⑥ 思考题 2 的验证方式）。**校准**：**代码 seek 主要不是排查工具**（它是业务逻辑的一部分、"设计时写进去的"）；**排查/恢复用外部工具 reset**（运维姿势"事后出手"）；排查时"**看** offset（describe/LAG）远比"**改**"常用——改是"看了之后决定要重来"的动作。
- **场景⑥ 追问 5：事故后重启如何保证幂等（10-11）✅ 已讲**：**核心校准**：① **"重启≠重复"**——正常重启**从服务端书签续读**（不重复——这正是不丢的机制）；重复只来自三个口子：**(a) 提交前崩溃**（重读"没提交的那几条"——小范围常态容忍）；**(b) ★ offset 记录过期**（`offsets.retention.minutes` 默认 7 天——组离线超期→书签被清理→回来当"**新组**"→按 auto-offset-reset【我们配的 earliest】**从头全量重放**——"事故停机很久"的典型风险！对策：**调大该配置**）；**(c) 人为重置**（reset/seek）。② ★★ **"不要重复操作"物理上做不到——能做到的是"重复了也无害"（效果幂等）**——"恰好一次投递"神话的又一次现身。**保证幂等的三板斧**（诚实标注现状）：**(1) 状态守卫**（已有——executeTask 开头 shouldStop——拦暂停/取消/终态；但【必要条件非充分条件】：重复时若任务处于"可执行状态"（RUNNING 等）可能被再驱动）；**(2) 断点续跑**（executeTask 本就是"从 DB 状态接着干"设计——但**精度（哪些步骤会跳过）需读代码确认**——已布置查证作业"幂等保证书的下半页"）；**(3) 唯一约束兜底**（写副作用处撞索引——场景④ 武器）；**(4) 升级选项：messageId 去重表**（生产端给每次执行请求生成唯一 id → 消费端去重表/SETNX——"消费幂等"的正规军；当前 taskId 轻消息+状态约束**够用于现语义**但非严格）。**针对本次事故重启的实操**：调 offsets.retention.minutes + 现役守卫 + 查证 executeTask 细节。

- **J8 追问：execute 能否"直接传方法名"（像 JS 传函数）✅ 已讲（10-07）**：三层面——① **Java 没有"裸函数"**（方法不是值、必须依附对象）——`execute` 要的精确说是"**实现 Runnable 接口的对象**"（任务包）；但"函数式接口 + lambda/方法引用"就是 Java 的"传函数"官方姿势（形式极像 JS）；② **能直接传方法名——它叫"方法引用" `::`**（J3 学过：`taskResponseMapper::toTaskSummary`），**但有形状要求**：方法必须"零参零返回"才能直接当 Runnable（`this::cleanUp` ✅）；`this::executeTask` ❌ **形状不匹配**（它要一个 UUID 参数，Runnable 给不了）——所以项目必须 `() -> executeTask(taskId)`：**箭头的作用 = 现场把 taskId 绑进包裹、把"有参方法"适配成"零参包裹"**；③ ★ **JS 其实也分流（完全同构三行）**：`setTimeout(doSomething)` ✅（零参直接传引用≈Java 方法引用）/ `setTimeout(() => executeTask(taskId))` ✅（要绑参用箭头≈Java lambda）/ `setTimeout(executeTask(taskId))` ❌（立刻执行）——"形状匹配直传、绑参用箭头"两边同一规律。④ 补：Java 8 前原貌 = 匿名内部类 `new Runnable() {@Override run(){...}}`，lambda 是简写；**函数式接口家族**（只有一个抽象方法）：Runnable（零参无返回）/**Supplier**（零参有返回）/**Consumer**（一参无返回）/**Function**（一参有返回）/**Predicate**（一参返回 boolean——★ J5 的 filter 参数就是它）。**计划：J8 下半场 ThreadPoolLab 里加"两种提交方式对比"小实验（this:: 零参方法 vs 箭头绑参）**。
- **J8 思考题答案讲解（10-07）✅**：**题 1**（`() ->` 为什么必须包）双层——① **编译层**：`executeTask(taskId)` 带括号=方法调用表达式（**求值即执行**）、类型是 `void`——void 不能当参数传给 `execute(Runnable)`，编译直接报错；② **语义层**："**把活干了**"（立刻、主线程、跑 5 分钟）vs "**把活的说明书递进包裹**"（打包成 Runnable 延迟执行、班组拆包才跑）——lambda = **把一段代码"冻"成对象传递**（"代码即数据"）；★ **前端同构坑**：React `onClick={handleClick}`（对——递函数）vs `onClick={handleClick()}`（错——渲染时立即执行）、`setTimeout(fn)` vs `setTimeout(fn())`——**一模一样**。**口诀：带括号=现在干；箭头包=装进包裹等会干**。**题 2**（ASYNC vs SYNC）——对比表：HTTP 响应等待（全程挂几分钟 vs 毫秒级秒回 taskId）/ 超时风险（浏览器+网关+LB 任一环超时即断 vs 无）/ 用户看到（转圈干等甚至报错 vs 秒开+SSE 实时进度）/ 进度获取（无 vs `/api/tasks/{id}/stream`）/ **任务与连接的关系（绑死 vs ★ 解耦）**——深层：**任务状态存 DB、独立于 HTTP 连接** → 所以能暂停/取消/查历史（PAUSED/CANCELLED 枚举 + StepExecutionEntity 时间线才有意义）；**HTTP"请求-响应"模型与长任务八字不合** → 异步任务模式（202 Accepted + 轮询/SSE）是行业标配；SYNC 按代码注释仅"测试和简单场景"。**下一站：J8 下半场动手实验**（exampleJavaGrammar 加线程池实验：提交多任务看线程名/排队/复用）。
