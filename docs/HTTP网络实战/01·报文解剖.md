## 一、请求的三段式

```http
POST /api/tasks HTTP/1.1              ← ① 请求行（方法 路径 协议）
Host: localhost:8080                   ← ② 头（Key: Value，元数据）
Content-Type: application/json
Authorization: Bearer dev-token
                                      ← 空行 = 分隔符（写死的规则）
{"title":"调研AI","goal":"..."}         ← ③ 体（业务数据）
```

## 二、响应的三段式

```http
HTTP/1.1 201 Created                   ← 状态行（协议 状态码 短语）
Content-Type: application/json
Location: /api/tasks/f84b...           ← 头（Location：新资源在哪）

{"id":"f84b","taskNo":"TASK-123",...}  ← 体
```

## 三、头部的三大金刚（后端最常打交道）

| 头 | 方向 | 管什么 | 项目联想 |
|---|---|---|---|
| **Content-Type** | 双向 | 体是什么格式 | @RequestBody 的 json 解析靠它 |
| **Authorization** | 请求 | 身份凭证 | TokenAuthFilter 校验的 dev-token |
| **Cache-Control** | 响应 | 缓存策略 | 静态资源（scalar.html）的 max-age |

## 四、一次对照实测（项目里跑）

```powershell
curl.exe -v -X POST http://localhost:8080/api/tasks `
  -H "Content-Type: application/json" `
  -d '{\"title\":\"t\",\"goal\":\"g\",\"executionMode\":\"SYNC\"}'
# -v 会打印完整的请求/响应头——亲眼看到三段式
```

## 面试速答

```text
Q：GET 能有 body 吗？ A：规范不建议、很多实现忽略——业务参数放 URL。
Q：头和体的分隔？ A：空行（CRLF）——解析器见到空行知道后面是体。
```

## 一句话

```text
HTTP 报文 = 行（干什么）+ 头（元数据）+ 体（数据），空行分界。
Content-Type 决定"怎么解析"，Authorization 决定"你是谁"。
```
