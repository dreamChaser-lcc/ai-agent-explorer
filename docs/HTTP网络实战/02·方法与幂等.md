## 一、四个方法的语义与幂等

| 方法 | 语义 | 幂等？ | 项目例子 |
|---|---|---|---|
| **GET** | 读资源 | ✅（读百次结果不变） | 查任务详情 |
| **POST** | 创建/触发 | ❌（发两次=建两个） | 创建任务——所以要幂等键！ |
| **PUT** | 全量替换 | ✅（覆盖成相同值） | 更新配置 |
| **DELETE** | 删除 | ✅（删了再删还是没） | 删除任务 |

```text
幂等的本质：同样的请求【重发 N 次】，服务端状态的最终影响
与【发 1 次】相同——这是"重试安全"的前提！
```

## 二、为什么 POST 天生不幂等 + 工程解法

```text
网络重试无处不在（超时重发/用户双击/MQ 重投）：
  POST /api/tasks 被重发 → 建两个重复任务 ✗

工程三解（项目场景④ 走的第三条）：
① 前端防抖——防用户，防不了网络重试
② 唯一索引仲裁——DB 层兜底（uk_idempotency_key 撞了返回已有结果）
③ 客户端生成幂等键——请求头带 Idempotency-Key，
   服务端"同 key 重放首次结果"
= 网络世界的"至少一次投递 + 幂等消费"（Kafka 消费者同一思想）
```

## 三、PUT vs PATCH（容易被追问）

```text
PUT：全量替换（缺的当空值）——幂等
PATCH：部分更新（只发变化的字段）——严格说 PATCH 不保证幂等（但实践中常做成幂等）
项目风格：更新接口其实都是"POST 心智"——用唯一键/状态机保护
```

## 面试速答

```text
Q：哪些方法幂等？ A：GET/PUT/DELETE 天然幂等；POST 不幂等 → 幂等键补。
Q：幂等键方案？ A：客户端生成 UUID → 服务端唯一索引仲裁 →
   重复请求返回首次结果（项目场景④ 的活体）。
```

## 一句话

```text
幂等 = 重发 N 次结果不变 = 重试安全的前提。
POST 不幂等是天性，工程用幂等键把它"补成幂等"——场景④ 全程实录。
```
