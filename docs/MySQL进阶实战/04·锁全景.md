# 04 · 锁全景——行锁、间隙锁与死锁

> **状态**：⬜ 未学习 ｜ **下一课**：05·三大日志

---

## 一、锁的分层地图

```text
全局锁（FTWRL，备份用）
├── 表锁（DDL / 表级意向锁）
└── 行锁（InnoDB，加在【索引项】上！）
    ├── Record Lock 记录锁：锁一行
    ├── Gap Lock 间隙锁：锁一段"空隙"（防插入 → 防幻读）
    └── Next-Key Lock = 记录 + 间隙（RR 级别的默认形态）
```

## 二、关键认知三条

```text
① 行锁锁的是"索引"，不是"行"
   → WHERE 没走索引的更新 = 锁全表（扫描到哪锁到哪）
② 间隙锁只在 RR 级别存在（RC 没有 → RC 会有幻读）
③ 锁冲突的表现就是"等"：innodb_lock_wait_timeout（默认 50s）后报错
```

## 三、死锁：两个事务各持一锁互等对方

```text
T1: 锁 A → 想锁 B（B 被 T2 持有）
T2: 锁 B → 想锁 A（A 被 T1 持有）
→ MySQL 检测到环路 → 选一个"代价小"的回滚（SHOW ENGINE INNODB STATUS 看）
```

**工程上怎么减少死锁**：

```text
① 多行更新按固定顺序（统一按 id 升序处理）
② 事务尽量短（别在事务里做 RPC/IO——SP2 场景⑤ 的教训）
③ 索引建对（避免扫描加锁放大范围）
④ 冲突极端激烈改用"乐观重试"（项目场景⑨ 的路线）
```

## 四、项目关联

```text
场景② 状态机：状态流转 UPDATE ... WHERE status='RUNNING'
→ 行锁天然仲裁"两个请求同时推进同一任务"
场景④ 幂等：并发撞唯一索引 → DuplicateKey
→ InnoDB 用"插入意向锁"实现排他，比应用层 try-catch-锁 更硬
```

## 五、面试速答

```text
Q：为什么更新没走索引会锁全表？
A：行锁挂在索引项上；没索引只能沿聚簇索引全扫，扫到哪锁哪（近似全表锁）。
Q：死锁怎么排查？
A：SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段：
   看两个事务各持什么锁等什么锁 → 对照代码的加锁顺序。
```

## 一句话

```text
行锁锁的是索引；间隙锁防幻读（RR 专属）；死锁靠"顺序统一+事务短"预防，
排查靠 INNODB STATUS。项目的唯一索引/状态机/乐观锁都是锁思想的应用层变体。
```
