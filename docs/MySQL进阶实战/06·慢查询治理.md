# 06 · 慢查询治理——从慢日志到改写

> **状态**：⬜ 未学习 ｜ **下一课**：07·分库分表

---

## 一、治理三步法

```text
① 开慢日志（先有数据）
   SET GLOBAL slow_query_log = ON;
   SET GLOBAL long_query_time = 0.5;      -- 超过 0.5s 记录

② 定位 TOP N（别看单条，看"总耗时"）
   pt-query-digest slow.log
   → 按"总耗时×次数"排序，揪出"量大且慢"的
   （一条 0.6s 但每秒跑 100 次的，比一条 10s 一天一次的更优先）

③ 单条优化（01/02 课的功夫上场）
   EXPLAIN → type=ALL？→ 索引 or 改写
```

## 二、改写套路五连

```sql
-- ① SELECT * 改具体列（可能吃到覆盖索引）
SELECT id, task_no, status FROM research_task WHERE ...;

-- ② 深分页：LIMIT 1000000, 20 是灾难（先扫 100 万再丢）
-- 书签法：记住上一页最后一条的 id
WHERE id > '上一页末尾id' LIMIT 20;

-- ③ 大 IN 改 JOIN 临时表 / 分批
-- ④ 子查询改 JOIN（老版本 MySQL 子查询会被优化得很差）
-- ⑤ COUNT(*) 估算：报表场景用 EXPLAIN 的 rows 或缓存计数
```

## 三、项目关联

```text
场景⑩ 数据清理：批量 DELETE 分批 + LIMIT——就是"改写套路③"的活用
  （一次性删百万行 = 长事务 + 大锁 + 主从延迟三杀）
场景③ 分页列表：PageRequest 固定 page.size —— 深分页防护
```

## 四、面试速答

```text
Q：慢查询怎么治？
A：先开慢日志拿到事实 → pt-query-digest 找"总耗时"大户 →
   EXPLAIN 看 type/Extra → 建索引或改写（列裁剪/书签分页/分批）。
Q：深分页为什么慢？
A：LIMIT 1000000,20 要扫过前 100 万行再取 20 条；书签法直接定位起点。
```

## 一句话

```text
慢查询治理 = 慢日志找事实 → 按总耗时排优先级 → EXPLAIN 定位 → 索引/改写。
深分页用书签；大批量操作用分批——项目场景③⑩ 都是这个思想。
```
