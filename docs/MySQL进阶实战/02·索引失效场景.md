# 02 · 索引失效的八种场景

## 八大罪（背下前五个就赢一半）

```sql
-- ① 对索引列用函数/计算（索引存的是原值，函数后对不上）
WHERE YEAR(created_at) = 2026      ✗
WHERE created_at >= '2026-01-01'  ✓ 改写成范围

-- ② 隐式类型转换（列是 varchar，传数字）
WHERE task_no = 123                ✗（被转成 CAST(task_no AS INT)，等价①）
WHERE task_no = '123'              ✓

-- ③ 前导通配 LIKE
WHERE title LIKE '%调研%'          ✗
WHERE title LIKE '调研%'           ✓（后置 % 能走索引）

-- ④ 违反最左前缀（联合索引 a,b,c 只用 b）
WHERE b = 1                        ✗
WHERE a = 1 AND b = 1              ✓

-- ⑤ OR 连了非索引列
WHERE a = 1 OR no_index_col = 2    ✗（整条放弃索引）

-- ⑥ NOT IN / != / <>（大概率放弃，取决于优化器成本评估）
-- ⑦ 索引选择性太差（status 只有 2 个值，优化器直接全表扫更划算）
-- ⑧ 优化器算成本后"自己放弃"（表太小，全扫更快）
```

## 最左前缀的本质（[数据结构 08](../数据结构实战/08·B树与B+树.md) [网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/docs/数据结构实战/08·B树与B+树.md) 的复习）

```text
联合索引 (a, b, c) = 先按 a 排序，a 相同再按 b，再按 c（字典序）
→ 查询条件必须从最左列开始连续命中
   a ✓ / a+b ✓ / a+b+c ✓
   b ✗（跳过 a，相当于在"乱序"里找 b）
   a+c：a 能走，c 用不上索引序（但 index condition pushdown 能救一点）
```


## 一句话

```text
索引失效五宗罪：函数包裹、类型隐转、前导%、丢最左、OR 串坏列。
记忆锚点：索引是"排好序的"——一切让"序失效"的写法都会翻车。
```
