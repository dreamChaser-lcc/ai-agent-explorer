# 05 · 三大日志——redo / undo / binlog

> **状态**：⬜ 未学习 ｜ **下一课**：06·慢查询治理

---

## 一、三本日志各管一摊

| 日志 | 层 | 管什么 | 一句话 |
|---|---|---|---|
| **redo log** | InnoDB | 崩溃恢复（持久性 D） | "我改到哪了"——先写它再刷数据页 |
| **undo log** | InnoDB | 回滚 + MVCC（原子性 A） | "我改之前是什么" |
| **binlog** | Server | 复制 + 数据归档 | "改了什么，给从库和备份用的" |

## 二、一次 UPDATE 牵动三本账

```text
UPDATE t SET x = 5 WHERE id = 1;

① 写 undo log（记旧值 x=3）        → 可回滚
② 改内存 Buffer Pool 的数据页      → 快
③ 写 redo log（物理页变更）        → WAL：先写日志，崩了能重放
④ 提交时【两阶段提交】：redo prepare → 写 binlog → redo commit
   （两本账必须一致——主从数据不丢的关键）
```

**为什么两阶段提交**：redo 和 binlog 各写各的会"主库有从库无"——
用"prepare → binlog → commit"保证要么都成、要么都回。

## 三、WAL（Write-Ahead Logging）思想

```text
磁盘太慢 → 数据页先改内存，日志先落盘（顺序写，快）
= "先记账后搬货"——崩溃后按账本重放
（和 Kafka 的思路同源：顺序写日志是存储系统的万能解）
```

## 四、项目关联

```text
SP3 / 场景② 的 @Transactional 提交链路：
  commit → redo/binlog 两阶段 → 从库复制
K8s 环境的 PG + Flyway（场景⑧/微服务线）：DDL 版本化走的是另一种"日志"思想
H2 开发库没有这一套（内存/文件模式简化）——生产 PG/MySQL 才是全量三件套
```

## 五、面试速答

```text
Q：redo 和 binlog 区别？
A：层次不同（InnoDB vs Server）、目的不同（崩溃恢复 vs 复制归档）、
   内容不同（物理页变更 vs 逻辑变更）。
Q：为什么 redo 是物理日志、binlog 是逻辑日志？
A：物理（页+偏移）重放快，适合恢复；逻辑（SQL/行变更）通用，适合跨引擎复制。
```

## 一句话

```text
redo 保命（崩溃恢复）、undo 保退路（回滚+MVCC）、binlog 保队友（主从/归档）。
提交 = 两阶段协调两本账；WAL = 先记账后搬货。
```
