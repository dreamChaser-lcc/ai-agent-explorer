## 一、ACID（一句话版）

| | 全称 | 靠什么实现 |
|---|---|---|
| **A** 原子性 | 全做或全不做 | **undo log**（回滚日志） |
| **C** 一致性 | 约束不被破坏 | A+I+D 的结果 + 应用层 |
| **I** 隔离性 | 并发互不干扰 | **MVCC + 锁** |
| **D** 持久性 | 提交即落盘 | **redo log**（先写日志再刷盘） |

## 二、四个隔离级别与三种病症

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 RU | ✗会 | ✗会 | ✗会 |
| 读已提交 RC | ✓防 | ✗会 | ✗会 |
| **可重复读 RR**（MySQL 默认） | ✓防 | ✓防 | 基本防（间隙锁） |
| 串行化 SER | ✓防 | ✓防 | ✓防（性能崩） |

```text
脏读：读到了别人【还没提交】的数据（它可能回滚）
不可重复读：同一个事务里两次读，值变了（别人改了并提交）
幻读：两次读，行数变了（别人插了并提交）
记忆：脏读是"读错"，不可重复读是"改了"，幻读是"多了"
```

## 三、MVCC——不加锁怎么做到并发读

```text
每行藏着两个隐藏列：创建版本号 / 删除版本号（trx_id）
读时对比"我的快照"决定这行可不可见 → 各读各的历史版本（ReadView）
→ 普通读（快照读）不加锁也不阻塞写——读写两不误
SELECT ... FOR UPDATE 才是当前读（要加锁）
```

## 四、项目关联

```text
场景⑨ 乐观锁（@Version）：
  并发确认靠 version 仲裁，冲突抛 OptimisticLockingFailure → 409
  = 应用层的"隔离"手段（比 DB 锁更轻，适合冲突少的场景）
SP4 事务实验：@Transactional 边界与传播行为（REQUIRED / REQUIRES_NEW）
场景④ 幂等：唯一索引 = 数据库层的原子仲裁
```

## 五、面试速答

```text
Q：MySQL 默认哪个级别？为什么不是 RC？
A：RR（可重复读）。历史原因 binlog 早期 format 与 RC 不安全；
   现在 RC 也安全（很多大厂改用 RC 减少间隙锁冲突）。
Q：@Version 乐观锁和 DB 悲观锁（SELECT FOR UPDATE）怎么选？
A：冲突少选乐观（重试成本低）；冲突激烈选悲观（一次锁住不空转重试）。
```

## 一句话

```text
A 靠 undo、D 靠 redo、I 靠 MVCC+锁——ACID 不是四个功能，是两本日志+一套快照。
RR 是 MySQL 默认；项目用 @Version 乐观锁在应用层做了更轻的隔离。
```
