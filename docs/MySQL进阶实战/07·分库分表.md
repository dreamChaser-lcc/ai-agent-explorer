# 07 · 分库分表——何时分、怎么分

> **状态**：⬜ 未学习 ｜ **本目录收官课**

---

## 一、先回答"何时分"（[数据结构 08 的推导回顾](../数据结构实战/08·B树与B+树.md) [网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/docs/数据结构实战/08·B树与B+树.md)）

```text
单表三层 B+ 树 ≈ 2000 万行（按行 1KB 算）
超过 → 树变 4 层 → 每次查询多一页 IO，写放大也上来

但行宽不同阈值不同：1KB/行 ≈ 2000 万；500B/行 ≈ 4000 万
真实信号不是行数，是【慢日志里这张表的查询开始劣化】
```

**分之前的三板斧（往往是更优解）**：

```text
① 索引/改写优化（06 课）—— 80% 的"性能问题"到这就解决了
② 冷热分离：历史表归档（场景⑩ 清理的进阶版——活表瘦身）
③ 读写分离：读多的场景加从库
都不够 → 才分。
```

## 二、分的两个维度

```text
垂直分（按列）：
  垂直分表：大字段（TEXT/BLOB）拆出去 → 主表行变窄 → 一页装更多行
  垂直分库：按业务域拆（订单库/用户库——微服务的库边界）

水平分（按行）：
  同构的 N 个表：research_task_0 / _1 / _2 ...
  按 key 取模或范围路由
  ★ 分表键选谁？——高频查询条件（项目会选 task_no / user_id）
```

## 三、分了之后的四大代价（面试展示深度）

```text
① 跨分页：LIMIT 全局排序要"各分片查→归并"（性能急剧下降）
② 跨事务：单库事务变成分布式（要 seata/最终一致）
③ 唯一约束：uk_idempotency_key 在单库才唯一 → 引入全局 ID（雪花）
④ Join 失效：跨库 join 全废 → 业务层组装或宽表
一句话：分库分表是"用一切便利换容量"的最后手段
```

## 四、项目关联

```text
research_task 当前体量（33 行）——离分库分表十万八千里 ✓ 不用焦虑
真实架构的顺序：优化 → 读写分离 → 缓存 → 归档 → 最后才分
场景⑩ 的"批量清理"就是"归档瘦身"思想的定时版
```

## 五、面试速答

```text
Q：单表多少行要分？
A：先看树的推导（约 2000 万/1KB 行），但真实标准是慢日志劣化；
   分之前先三板斧：优化索引、冷热归档、读写分离。
Q：分表键怎么选？
A：最高频的查询维度（避免大部分查询跨片）；一旦定了极难换。
```

## 一句话

```text
分库分表 = 最后手段：先优化/归档/读写分离三板斧，
分则选准分片键，代价是分页/事务/唯一性/Join 全要重做。
```
