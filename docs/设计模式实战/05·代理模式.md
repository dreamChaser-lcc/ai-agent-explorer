## 一、是什么：替身+增强

```text
代理 = 你调的还是"那个接口"，但接线员换成了中间人，
      中间人可以【前面加点事 → 调真身 → 后面加点事】。

结构：
  调用方 → [代理对象] --转--> [真实对象]
                 ↑
        前置/后置增强（日志/事务/锁/翻译）
```

## 二、两大流派

```java
// ① JDK 动态代理：基于【接口】
Proxy.newProxyInstance(loader, new Class[]{Dao.class},
    (p, method, args) -> {
        before();
        Object r = method.invoke(realDao, args);
        return after(r);
    });

// ② CGLIB：基于【继承】——生成真实类的子类（子类重写方法做增强）
//   所以 final 类/方法不能被 CGLIB 代理！
```

| | JDK 动态代理 | CGLIB |
|---|---|---|
| 要求 | 必须有接口 | 类不能 final |
| 生成 | 接口的实现 | 目标类的子类 |
| Spring 使用 | 有接口时（默认策略已变） | **Boot 默认**（proxyTargetClass） |

## 四、代理的经典自问（面试高频）

```text
Q：为什么同类内部方法调用 @Transactional/@Cacheable 不生效？
A：内部调用是 this.xxx()——走的是【真身】不是代理！代理只拦"从外面进来"的调用。
   （J8 附二 / SP2 都踩过这个点）
Q：为什么 CGLIB 不能代理 final 方法？
A：它靠"生成子类重写"增强——final 禁止重写，直接被绕过。
```

## 五、面试速答

```text
Q：JDK 代理和 CGLIB 区别？
A：接口 vs 继承；JDK 生成接口实现，CGLIB 生成子类；final 是 CGLIB 的死穴。
Q：装饰器和代理的区别？
A：装饰器强调"叠加增强"（可多层），代理强调"控制访问"（通常一层，框架用得多）。
```

## 一句话

```text
代理 = 中间人接管调用权，前后做增强。
Spring 的 AOP/事务/缓存/异步/异常翻译全是代理；
"this 调用绕过代理"是所有 Spring 增强失效的第一原因。
```
