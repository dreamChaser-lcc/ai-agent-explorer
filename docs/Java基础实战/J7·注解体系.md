## 1. 注解的本质：贴给"读者"看的标签

**注解（annotation）= 元数据**——"贴在代码上的说明性文字"。它**不执行任何逻辑**，只负责"**被某些读者读取，读者按它做事**"。

理解注解要拿住**两个维度**（J2 立了第一个，本课补第二个）：

| 维度 | 问题 | 关键 |
|------|------|------|
| **读者**（J2 立） | 谁在读它？ | 编译器 / Spring / JPA / 你自己写的反射代码 |
| **寿命**（本课补） | 它活到什么时候？ | `@Retention` 三档——决定"读者在哪个阶段还能看到它" |

---

## 2. `@Retention`：标签的"寿命档位"

| 档位 | 活到哪 | 谁能读到 | 典型例子 |
|------|--------|---------|---------|
| `SOURCE` | **编译完就扔**（不进 class 文件） | 只有编译器 | `@Override` |
| `CLASS` | 进 class 文件（**不加就是默认本档**） | 只有编译器 | （少见特意使用的） |
| `RUNTIME` | **活到运行时**（反射读得到） | 编译器 + 框架 + 你的反射代码 | `@Service` / `@GetMapping`——**框架注解的标配** |

**关键推理链**：框架靠**反射**读注解（J2）→ 反射发生在**运行时** → 框架注解**必须**是 RUNTIME 档。

---

## 3. `@Target`：标签能贴在哪

`METHOD`（方法）/ `TYPE`（类、接口、枚举）/ `FIELD`（字段）/ `PARAMETER`（参数）/ `CONSTRUCTOR`（构造器）……

**贴错地方 = 编译报错**（比如把只允许贴方法的 `@GetMapping` 贴到类上）。

## 5. 自定义注解三件套（`AnnotationLab`）

```java
// ① 声明（元注解：寿命 + 靶点）
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface LogExecution {
    String value() default "";
}

// ② 使用（贴标签）
@LogExecution("创建任务")
public void createTask() { ... }

// ③ 反射读取（"框架视角"）
if (m.isAnnotationPresent(LogExecution.class)) {
    LogExecution ann = m.getAnnotation(LogExecution.class);
    System.out.println("... value=" + ann.value());
}
```

**三段式心智**：**声明**是"造图章"→ **使用**是"盖章"→ **反射读取**是"验章"——框架的一切注解能力，都是这三段。

## 6. 注解的参数：`String value() default ""` 逐字拆

| 片段 | 意思 |
|------|------|
| `String` | 参数类型 |
| `value()` | 参数**名**（带括号是 `@interface` 语法要求——写法像方法但**不是方法**） |
| `default ""` | **默认值**：不写就用它（有了它才能"裸贴" `@LogExecution`；没有它则该参数必填） |

**★ `value` 特权规则**：**单参数且名叫 `value`** 时，使用时**可省略名字**：

```java
@GetMapping("/x")              // 简写
@GetMapping(value = "/x")      // 全称——完全等价
```

——全 Java 世界注解爱用 `value` 命名，就是为了换这行简写。**多参数时名字必须都写**（`@ConditionalOnProperty(name=..., havingValue=..., matchIfMissing=true)`）。

**J2 谜题补完**：`matchIfMissing = true` 是"给参数赋值"；其声明侧 `boolean matchIfMissing() default false`——**"不写时默认 false"**正是"默认不上场"的来源。

**写入端与读取端的对接**：贴标签时填进 `value("创建任务")`，反射时 `ann.value()` 读出来——**靠同一个名字对接**。

## 7. ★ 反射小课堂（下半场补课）

### 7.1 反射是什么——让静态 Java 获得 JS 的能力

```javascript
service.createTask();          // 平时：方法名写死
const name = "createTask";
service[name]();               // 动态：用字符串调方法——JS 天生就会
```

Java 方法名必须写死在源码里——**反射是官方后门**：运行时"翻看自己、按名字干活"。

**两类能力**：**自省**（看结构/读标签）+ **动态操作**（按名字调方法/造对象）。

### 7.2 反射五件套逐件拆（★ 档案室类比）

```text
TaskService.class              ① 去档案室，拿"TaskService 的档案"（说明书）——不是造对象！
  .getMethod("createTask")     ② 翻目录查名字 → 拿到"岗位职责书"（Method 对象）——活还没干
  .isAnnotationPresent(...)    ③ 看职责书上有没有盖 LogExecution 章？（true/false）
  .getAnnotation(...).value()  ④ 把章揭下来细看刻的字 → "创建任务"
  .invoke(service)             ★ ⑤ 指定 service 这位员工，照职责书开工——到这里才真执行
```

| API | 一句话 | 细节 |
|-----|--------|------|
| `Xxx.class` / `getClass()` | 拿类的"说明书" | **每类仅一份**；两条路通向同一个 Class 对象；**不是创建对象** |
| `getMethod("名")` | 照名字查目录 | 返回 `Method`= "名片/职责书"——**≠ 执行结果** |
| `isAnnotationPresent(...)` | "有章吗？" | boolean——**Spring 扫描的动作本身** |
| `getAnnotation(...)` | "把章拿下细看" | 能读参数（`ann.value()`） |
| `invoke(service)` | "指定执行者，开工" | **执行者必须当参数传**（Method 是"类级岗位职责"，不属于具体对象）；≈ `service.createTask()`；前端对照 `service["createTask"]()` |

**为什么框架离不开反射**：框架**先写**、你的类**后出生**——它不可能提前写 `new 你的类()`——只能运行时：扫描 class 文件 → 读标签 → 反射造对象 → invoke 调方法。**IoC/"没人调用却自动执行"/"Spring 怎么发现 @Service"——同一套答案。**

### 7.3 动态调用为什么"必须"用它（教具设计本意）

```java
for (String name : new String[]{"createTask", "plainMethod"}) {
    m.invoke(service);      // name 是【字符串变量】——service.name() 这种语法不存在
}
```

**方法名"运行时才知道"（来自字符串/配置/反射读到的东西）→ 唯一的路：先查（getMethod）再按（invoke）。**

## 8. ★ 概念校准：注解**不加功能**——功能来自"读标签的人"

**常见误解**："注解是为了给类加扩展的方法"——**半对半不对**（"运行时"沾边；"加东西"是主客颠倒）。

**校准核心**：

> **注解 = 标记（便利贴），本身零功能**——不加方法、不改类、不执行逻辑。
> **一切效果来自"读标签的人"**——谁读了它，谁去干活。

**反证（可动手）**：把 `AnnotationLab` 里读标签的 `if` 段**删掉**，只留 `m.invoke(service)` → 方法照跑，但"开始记录执行"**永不再打印**——注解瞬间变死文字。

> **注解是"墓志铭"，不是"发动机"——它只"说"，从不"做"。**

**类比**：快递便利贴"易碎"不管搬运（快递员的行为）/ 工牌不干活（门卫看工牌放行）/ 菜单 ⭐ 不做好菜（厨师的行为）。
**前端锚点**：`class="btn-danger"` 属性零功能——CSS/JS 读了才有效果；**`class` 属性 ≈ 注解**。

**同一份标签，不同读者不同活**：`@Override` 编译器读（核对）/ `@Service` Spring 启动读（注册）/ `@GetMapping` 请求时读（路由）/ `@Entity` JPA 读（映射）/ `@LogExecution` 你自己读（打印）——**没有"读者"的注解 = 废纸**。

## 9. ★ 框架读了标签后能做什么：操作全谱（九类）

**核心心智**：**框架不改你的类——改的是"它自己与你打交道的方式"**。"你没变，变的是你和框架的关系。"

| # | 操作 | 框架内部干什么 | 真实注解 | 你的代码变了吗 |
|---|------|--------------|---------|--------------|
| ① | **收养**（注册） | 替你 new、收进容器、注入给别人 | `@Service` `@Component` | ❌ 没变——只是"被别人用上了" |
| ② | **挂路由** | 记"URL → 你的方法"进路由表 | `@GetMapping` | ❌ 没变——HTTP 能找到你了 |
| ③ | **套戏服**（代理） | CGLIB 造代理，方法前后插逻辑 | `@Transactional` `@Cacheable` | ❌ 没变——请求先撞代理（J2 彩蛋！） |
| ④ | **送料**（参数装配） | 决定参数值**从哪来** | `@PathVariable` `@RequestBody` | ❌ 没变——参数被"喂进来" |
| ⑤ | **卡表**（校验） | 进门先查，不合规**到不了方法体** | `@Valid` | ❌ 没变——前面多了道岗 |
| ⑥ | **编排时机** | "什么时候调你"交给时钟/启动流程 | `@Scheduled` `@PostConstruct` | ❌ 没变——调用器换人了（IoC 钩子） |
| ⑦ | **建档**（映射） | 记"类↔表、字段↔列"翻译词典 | `@Entity` `@Column` | ❌ 没变——JPA 懂怎么翻译你 |
| ⑧ | **剪裁**（序列化） | JSON 出入时字段改名/隐藏 | `@JsonProperty` `@JsonIgnore` | ❌ 没变——JSON 里的样子被改了 |
| ⑨ | **隔墙塞值**（字段注入） | 反射 `setAccessible`——**private 也能塞** | `@Autowired` | ❌ 没变——值被"翻墙投递" |

**注意每一行的"没变"**——框架的强大在于：**不动你的代码，就能把你的代码"编排"进它自己的机制里**（容器/路由表/拦截链/映射词典都是框架**自己的**数据结构）。

**复合解剖**（真实世界的样子）：

```java
@PostMapping("/api/tasks")                          // ② 路由
public TaskResponse create(
        @Valid @RequestBody CreateTaskRequest req)  // ⑤ 卡表 + ④ 送料
{
    return taskService.create(req);                 // ① 收养：taskService 不是自己 new 的
}
```

**四五个注解、方法本体一行没改**——但"HTTP 能找到、参数被灌、非法被拦、依赖被塞"全发生了。

**★ 演员/导演类比**：你的类 = 演员（演技=方法本体，一字未改）；注解 = 简历标签；框架 = 导演组（读了标签：决定进哪个组、何时上台、从哪个门出场、穿不穿戏服、台词从哪来）——**导演从不改演技，只改"出场方式"**。

## 10. "加方法"的正名：主流框架不改你，但有两处例外

| 技术 | 什么时候"加代码" | 例子 |
|------|----------------|------|
| 主流 Spring 全家 | **不加**（"用你"≠"改你"——无侵入才是高境界） | 上面九类操作全是"编排"而非"修改" |
| **Lombok**（★ 真的加方法） | **编译期生成** | `@Data` → 生成 getter/setter/equals/toString（源码看不见，class 文件里有） |
| 字节码增强（ByteBuddy 等） | 运行/加载时改字节码 | APM 监控——高级、少见 |

**结论**：你理解的"加方法"不是错——**Lombok 正是这么干的**（它是**编译器**的活）；Spring 选了另一条路：**"不改你，也能用你"**。

## 12. 补充：思考题与答案（课堂问答收录）

**题 1**——`@Override` 为什么不需要 `RUNTIME`（它也是"重写标记"啊）？

**答（含一处理解校准）**：**"重写"本身不靠注解**——只要方法签名相同，Java 语法上**自动就是覆盖**（这是语言规则）；`@Override` 的真正身份是"**验收章**"——编译器拿它核对"**真有一个可覆盖的目标方法吗**"（名字/参数写错，当场拒收）。而"重写关系"在编译后进的是**方法表**（J2 多态的运行机制）——**运行时找方法不靠标签**——所以编译完就可以把它扔掉（SOURCE 档）。
**类比**："此页已校对"的章——内容不是被章改对的，章只是**验收凭证**（验收完即可丢弃）。

**题 2**——Spring 靠什么"发现"你的 `@Service` 类？

**答（用户已自答骨架，补全细节）**：四步全在**启动时**、全靠**反射**：

```text
① 贴标：@Service 是 RUNTIME 档（不贴 RUNTIME，运行时读不到——改档实验证明）
② 扫描：遍历 classpath 下所有 class 文件（找出"可能带标签的类"）
③ 读标：反射 classObj.isAnnotationPresent(Service.class) → true 的留下
④ 注册：反射创建实例（newInstance/构造器）+ 存进"Bean 大 Map"
⑤ 注入：别人需要时，从 Map 里取出来塞过去（J2 三步裁判）
```

**一句话**：扫描=遍历 class；读标签=反射；注册=反射造对象+存 Map；注入=从 Map 取——**全程都是反射**。

## 14. 补充：Component 家族五兄弟（2026-10-27 课堂问答）

> 学员提问："`@Component / @Service / @Repository / @Controller / @RestController` 我有点搞不清这几个的用法"

### 14.1 一句话总纲

```text
这 5 个本质是【同一个注解】的"语义化别名"——95% 功能相同（都是"注册为 bean"）
真差异只有两处：@Repository 的异常转换、@Controller 的路由识别
```

### 14.2 继承关系（元注解机制）

```text
@Component                        ← 根源
   ├── @Service                   = @Component + 业务层语义（零功能差异）
   ├── @Repository                = @Component + 数据层语义 + 异常转换 ★
   └── @Controller                = @Component + Web层语义 + 路由识别 ★
          └── @RestController     = @Controller + @ResponseBody
```

**组合注解原理**：`@Service` 的定义里"贴着" `@Component`（元注解），Spring 扫描时递归查元注解 → 按 bean 注册。

### 14.3 仅有的两处真功能差异

| 注解 | 附加功能 | 不用的后果 |
|---|---|---|
| **`@Repository`** | 异常转换（`PersistenceExceptionTranslationPostProcessor` 把 JPA/Hibernate 专有异常翻译成 Spring 的 `DataAccessException` 体系） | 上层 `catch DataAccessException` 接不住数据库异常 |
| **`@Controller`** | 被 `RequestMappingHandlerMapping` 识别，`@RequestMapping` 才生效 | 路由不注册，接口 404 |
| `@RestController` | = 上者 + `@ResponseBody`（返回值直接写响应体） | 同上 |
| `@Service` | 无（纯语义） | 只有可读性/按层切面的损失 |

### 14.4 项目实测（2026-10-27）

```text
@Component = 32   AuditAspect / RetentionCleanupJob / TaskExecutionConsumer / TaskResponseMapper
@Service   = 19   ResearchTaskOrchestrator / ResearchTaskCommandService / RetentionCleanupService
@Repository = 4   RetentionCleanupDao / JpaTaskEventLogStore / MyBatisTaskEventLogStore
@RestController = 10（6 个 Controller）
@Controller = 1（项目前后端分离，基本不用）
```

**反直觉的点：Spring Data JPA 接口不标 `@Repository`**

```text
ResearchTaskRepository extends JpaRepository  →  @Repository 标注数 = 0
原因：Spring Data 用 JpaRepositoryFactoryBean 动态生成实现并注册 bean，
     注解扫描不参与它的创建（加了不报错，但无意义）
对照：RetentionCleanupDao 是手写类 → 必须自己标 @Repository
```

### 14.5 决策表

| 类的职责 | 注解 |
|---|---|
| HTTP 接口返回 JSON | `@RestController` |
| 传统 MVC（返回视图名） | `@Controller` |
| 业务逻辑 | `@Service` |
| 手写 DAO | `@Repository` |
| Spring Data 接口 | **不标** |
| 切面/过滤器/定时任务/映射器 | `@Component` |
| 配置类 | `@Configuration` |

### 14.6 三个误区

```text
① "@Service 和 @Component 功能不同"      → ❌ 完全一样（纯语义）
② "反正都能注入，随便用"                  → ❌ 两个损失：@Repository 丢异常转换；
                                            语义乱后 AOP 没法按层切（@within(Service)）
③ "5 个是 5 套独立机制"                   → ❌ 一套机制 + 语义化别名 + 二次组合
```

### 14.7 组合注解（企业常见做法）

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@RestController
@RequestMapping("/api/v1")
public @interface ApiV1Controller { String value() default ""; }
```

`@RestController`、`@SpringBootApplication` 就是框架作者这样造出来的。

### 14.8 一句话

```text
@Component = "我是 bean"（通用）
@Service   = "我是 bean，干业务的"
@Repository = "我是 bean，干数据的，异常会被翻译成 Spring 的"
@Controller = "我是 bean，处理 HTTP（返回视图）"
@RestController = "我是 bean，处理 HTTP（返回 JSON）"
按层选型；真差异只有异常转换和路由两处；Spring Data 接口不标。
```

## 15. 补充：@Configuration 带/不带 @Bean（2026-10-27 课堂问答）

> 学员提问："`@Configuration` 为什么有的 +@Bean 有的又没有加"

### 一句话答案

```text
带 @Bean 的方法 = 这个类【生产 bean】（造对象给别人注入）
不带 @Bean       = 这个类【只做配置行为】——开开关（@EnableXxx）、
                  实现扩展接口（WebMvcConfigurer）、绑定属性，不生产 bean
两种都对，看职责是"生产"还是"配置"
```

### 项目两种形态

| 形态 | 实例 | 在干什么 |
|---|---|---|
| @Configuration + @Bean | LlmClientConfiguration / CacheConfiguration / AsyncExecutionConfiguration / KafkaTopicConfiguration | 生产 LlmClient、线程池、CacheManager、Topic |
| @Configuration 光秃秃 | WebCorsConfiguration / Sp8InterceptorConfiguration / CleanupConfiguration / PropertiesConfiguration | 跨域/拦截器（实现 WebMvcConfigurer）、@EnableScheduling、属性绑定 |

### J7 视角的补充知识

```text
@Bean 是 Component 家族里唯一的【方法级】注解（@Target(METHOD)）
其余（@Component/@Service/@Repository/@Controller）都是类级（@Target(TYPE)）
类级 = "把这个类注册为 bean"；方法级 = "把这个方法的返回值注册为 bean"
—— @Bean 自己没有宿主能力，所以必须住在配置类里
另：@Configuration 自身也被 @Component 元注解标记 → 配置类自己也是 bean
```

## 16. 补充：@Repository 异常转换详解（2026-10-27 课堂问答）

> 学员提问："`@Repository` 的异常转换是什么意思我不太理解"

### 一、问题背景：三套异常体系

```text
同一个"唯一键冲突"错误，不同技术抛的异常完全不同：
  Hibernate/JPA → org.hibernate.exception.ConstraintViolationException
  JDBC 原生     → java.sql.SQLIntegrityConstraintViolationException
  MyBatis       → PersistenceException（包装）
上层 catch 哪个？→ 与技术绑死，换技术 = catch 代码全部重写
```

### 二、Spring 的解法：统一异常字典

```text
DataAccessException（根）
 ├── DuplicateKeyException               ← 唯一键冲突
 ├── DataIntegrityViolationException     ← 完整性违规
 ├── ObjectOptimisticLockingFailureException ← 乐观锁失败（@Version）
 ├── EmptyResultDataAccessException      ← 期望 1 行得 0 行
 └── DataAccessResourceFailureException  ← 连不上
同一个错误 → 无论底层什么技术 → 翻译成同一个 Spring 异常
```

### 三、机制：翻译发生在代理层

```text
启动时：
  PersistenceExceptionTranslationPostProcessor（BeanPostProcessor）
  发现标 @Repository 的 bean → 织入翻译代理

运行时（伪代码）：
  try { dao.save(task); }
  catch (RuntimeException e) {
      throw translator.translate(e) ?? e;   // 能翻译→抛 Spring 的
  }
DAO 代码一行不用改——翻译在代理层完成
```

**前端类比**：各浏览器错误对象格式不同 → 写一个 `normalizeError(e)` 统一格式 → 业务代码只处理统一格式。`@Repository` = Spring 自动给 DAO 加 normalizeError。

### 四、项目铁证：场景⑨ 的 409 就是它救的

```text
场景⑨ 并发确认（@Version 乐观锁冲突）：
  底层抛：Hibernate 的 StaleObjectStateException
     ↓ @Repository 翻译代理
  变成：Spring 的 OptimisticLockingFailureException
     ↓ ApiExceptionHandler（已实测 catch 该类型）
  → HTTP 409 CONFLICT

反证：去掉 @Repository → 抛 Hibernate 原生异常
  → OptimisticLockingFailureException 类型不匹配接不住
  → 落到 Exception 兜底 → 500（前端语义从"冲突请重试"变"服务器错误"）

实测统计：OptimisticLockingFailureException 引用若干处（含 Handler）；
         Hibernate 的 StaleObjectState 全项目 0 处引用——上层从未感知过它。
```

### 五、两个澄清

| DAO 形态 | 翻译来源 | 要不要标 @Repository |
|---|---|---|
| Spring Data 接口 | 框架内置 translator | 不需要（标了无害） |
| **手写 DAO 类** | **注解触发织入代理** | **必须标**（本项目 RetentionCleanupDao 标了） |

### 六、一句话

```text
异常转换 = 各家专有异常 → 统一翻译成 Spring 的 DataAccessException 体系
触发 = @Repository → BeanPostProcessor 织入翻译代理
证据 = 场景⑨ 并发 409（Hibernate 异常被翻译后才能被全局处理器接住成 409）
不标代价 = 手写 DAO 异常不被翻译，上层 catch Spring 异常扑空 → 500
```
