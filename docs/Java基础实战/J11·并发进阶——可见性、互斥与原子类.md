## 1. 为什么 J8 不够——三大并发问题

J8 讲了"怎么把活交给别的线程干"，但没有回答：**当两个线程同时读写同一份数据，会发生什么？**

答案：三种经典的并发事故。

```java
// 一段看似无害的代码
int count = 0;
// 线程 A 和线程 B 同时执行 1000 次：
count++;   // ★ 结果不是 2000，可能 1738——"丢失更新"
```

**为什么 `count++` 会出错？** 它在 CPU 层面是**三步**：

```text
① 读：从内存读 count 到寄存器（比如读到 100）
② 改：寄存器里 +1（变成 101）
③ 写：写回内存（101）
```

两个线程交错执行：

```text
线程A：读到 100 → 改成 101 → 写回 101
线程B：读到 100（★ A 还没写回！）→ 改成 101 → 写回 101
结果：加了两次，只涨了 1——一次更新"丢失"
```

这就是并发三大问题的入口：

| 问题 | 现象 | 解决工具 |
|------|------|---------|
| **可见性** | 一个线程改了变量，另一个线程"看不见"（一直用旧值） | `volatile` |
| **原子性** | 一个操作被切成三步，中间被打断 | `synchronized` / 原子类 |
| **有序性** | 编译器/CPU 为优化偷偷调整指令顺序 | `volatile`（禁重排） |

> **前端类比**：JS 单线程 + event loop，**天然没有这些问题**——这就是为什么前端工程师初见 Java 并发会懵。心智迁移：Java 的每个线程 ≈ 一个独立的"迷你 JS 世界"，各自有变量副本，需要机制保证它们对"共享数据"的看法一致。

**而你的项目里，多线程无处不在**：Tomcat 请求线程（每个请求一个）+ Kafka 消费线程 + `@Async` 线程池 + 定时任务线程——**任何一个共享变量都可能被它们同时摸到**。

## 2. 可见性——volatile

### 2.1 复现一个"永远停不下来"的 bug

```java
public class VisibilityDemo {
    private static boolean running = true;          // ❌ 不加 volatile

    public static void main(String[] args) {
        new Thread(() -> {
            while (running) {
                // 空转……期望 main 线程把 running 改成 false 后退出
            }
        }).start();

        try { Thread.sleep(100); } catch (InterruptedException e) {}
        running = false;                             // main 线程改成 false
        System.out.println("已发出停止指令");
    }
}
```

**实际运行**：`main` 打印了"已发出停止指令"，但子线程**永远停不下来**。

原因：为了性能，每个线程可能把变量**缓存到自己的工作内存**（CPU 缓存/寄存器），子线程一直读的是自己缓存里的 `true`——main 的修改对它**不可见**。

### 2.2 解法：加 `volatile`

```java
private static volatile boolean running = true;    // ✅
```

`volatile` 的两个作用：

| 作用 | 说明 |
|------|------|
| **保证可见性** | 写 volatile 变量 = 立即刷回主内存；读 = 从主内存读（不走线程缓存） |
| **禁止指令重排** | 编译器/CPU 不会把 volatile 前后的读写乱序（单例 DCL 靠这个，见 2.4） |

**注意**：volatile **只保证可见性和有序性，不保证原子性**——`volatile int count` 的 `count++` 照样丢更新（它还是三步）。原子性要用 §3/§4 的工具。

### 2.3 项目实例：单例模式的 DCL（设计模式 01）

你学过的单例模式（设计模式实战 01）里就有它：

```java
public class Singleton {
    private static volatile Singleton instance;    // ★ 为什么需要 volatile？

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查（不加锁，快速路径）
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查（加锁后确认）
                    instance = new Singleton();    // ← ★ 这一行不是原子的！
                }
            }
        }
        return instance;
    }
}
```

`new Singleton()` 实际是三步：**分配内存 → 初始化对象 → 引用指向内存**。CPU 可能重排为"分配 → 指向 → 初始化"——另一个线程在第一次检查时拿到"已指向但未初始化"的半成品对象。`volatile` 禁止这个重排。

**为什么 Lombok/框架代码里到处是 volatile**：所有"状态标记"（停止开关、初始化标记）都该加——可见性问题是静默的，加了没坏处。

> **前端类比**：SharedArrayBuffer + Atomics——浏览器给多线程（Web Worker）共享内存时，也要求用 `Atomics` 原子操作、否则同样有可见性问题。**一旦引入真多线程，JS 世界就要面对 Java 的老问题**。

## 3. 原子性——synchronized

### 3.1 用法三种

```java
public class Counter {
    private int count = 0;

    // ① 修饰实例方法：锁的是 this（当前对象）
    public synchronized void inc() {
        count++;
    }

    // ② 修饰静态方法：锁的是 Class 对象（全类共用一把）
    public static synchronized void staticInc() { ... }

    // ③ 修饰代码块：锁的是括号里的对象（最灵活）
    private final Object lock = new Object();
    public void inc2() {
        synchronized (lock) {          // ★ 锁的是 lock 这个对象
            count++;
        }
        // 只有 count++ 这几行是互斥的，其他代码不受影响（锁粒度小 = 性能好）
    }
}
```

**本质**：`synchronized(锁对象)` —— **多个线程拿同一把锁才能互斥**；拿的不是同一把，互不干扰。

### 3.2 最容易翻车的点：锁错了对象

```java
// ❌ 错误：每个请求 new 一个新对象 = 每个线程一把新锁 = 完全没有互斥
public void handleRequest() {
    Object lock = new Object();
    synchronized (lock) { count++; }    // 锁了个寂寞
}

// ❌ 错误：用 String 字面量当锁（字符串池共享，全 JVM 谁都可能锁到它，容易死锁）
synchronized ("myLock") { ... }

// ✅ 正确：锁对象必须是 final 的成员（大家共用同一把）
private final Object lock = new Object();
```

### 3.3 项目对照：为什么 backend 里几乎没有 synchronized

审计结果：**backend 主代码里没有一处 `synchronized`**——不是遗漏，是架构决策：

```text
本地 synchronized 只能锁"同一个 JVM 内"的线程；
你的服务是 K8s 多实例部署 → 两个 Pod 各有各的 JVM，synchronized 拦不住对方
→ 跨实例互斥必须用分布式锁（场景⑨⑩：Redis SET NX EX）
```

**本地锁 vs 分布式锁的边界**（详见 §8）：单机内的并发（比如同一个请求里的多线程操作同一集合）用 `synchronized`/原子类；**跨实例的资源竞争**用 Redis 锁。

> **前端类比**：JS 单线程天然原子（`count++` 不会被切断）——所以 JS 里没有 synchronized 这个概念。但 Node.js 开 cluster 多进程后，"内存锁"同样失效，得用 Redis——**和 Java 后端走上同一条路**。

## 4. 原子类——CAS 无锁方案

### 4.1 用法

```java
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger count = new AtomicInteger(0);

count.incrementAndGet();        // ++ 并返回新值（原子）
count.addAndGet(10);            // += 10（原子）
int old = count.getAndSet(0);   // 读旧值并清零
count.compareAndSet(100, 200);  // CAS：是 100 才改成 200（★ 底层核心）
```

### 4.2 原理：CAS（Compare-And-Swap）

```text
CAS(期望值, 新值)：
  CPU 指令级原子操作——"如果内存里的值 == 期望值，就改成新值；否则失败"
  失败不自阻塞，而是【自旋重试】：

  循环 {
      old = 读内存;
      next = old + 1;
      if (CAS(内存, old, next)) break;    // 改成功了（说明中间没人动过）
      // 失败 → 说明别人先改了 → 重读 → 再试
  }
```

| 方案 | 原理 | 适用 |
|------|------|------|
| `synchronized` | 阻塞：抢不到锁就**挂起等待**（有上下文切换开销） | 竞争激烈、临界区有复杂逻辑 |
| **原子类（CAS）** | 非阻塞：抢不到就**重试**（自旋） | 简单计数/标志位，竞争不极端 |

> **前端类比**：`Atomics.add(sharedArray, 0, 1)`——SharedArrayBuffer 上的原子加法，同一套 CPU 指令。

### 4.3 项目对照：Redis INCR 也是同一个思想

你学过的 Redis `INCR`（Redis 08 §7.3 计算型）就是 Redis 服务端的原子计数——**和 AtomicInteger 解决同一个问题，只是位置不同**：

| 位置 | 工具 | 场景 |
|------|------|------|
| 单 JVM 内多线程 | `AtomicInteger` / `synchronized` | 内存里的计数、状态标记 |
| 跨进程/跨机器 | **Redis INCR / SET NX**（场景⑨⑩、限流） | 限流计数、分布式锁、多实例共享计数 |

**原则**：单机内解决的不出进程；跨进程才上 Redis（网络有开销）。

## 5. 线程安全集合——ConcurrentHashMap 实战

### 5.1 为什么 HashMap 不能多线程用

J3 学过 HashMap 本身（数据结构 04 讲了底层）：多线程同时 `put` 会互相覆盖数据（1.7 版本甚至可能死循环）；`size()` 也可能算错。解法不是"HashMap + synchronized"（锁粒度太粗，全部串行），而是专用的并发容器。

### 5.2 项目真实教材：[`TaskProgressStreamService`](../../backend/src/main/java/com/aiexplorer/researchagent/application/service/TaskProgressStreamService.java)（[网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/backend/src/main/java/com/aiexplorer/researchagent/application/service/TaskProgressStreamService.java)）

这是你项目里最真实的多线程场景——**SSE 实时推送**：

```text
谁在并发访问这张表？
  · HTTP 请求线程：前端建立 SSE 订阅 → subscribe() 往表里加连接
  · Kafka 消费线程：任务进度事件 → publish() 遍历表广播
  · 容器回调线程：连接断开/超时 → removeEmitter() 清理
——三类线程同时读写同一张 Map，没有 ConcurrentHashMap 就会乱套。
```

关键代码逐行：

```java
// ① 线程安全的 Map：多线程读写不用额外加锁
private final Map<UUID, List<SseEmitter>> emittersByTaskId = new ConcurrentHashMap<>();

// ② "不存在就创建"——★ 原子的组合操作（等价于 if(!map.containsKey) put，但不会竞态）
emittersByTaskId.computeIfAbsent(taskId,
        key -> new CopyOnWriteArrayList<>()).add(emitter);
//   ❌ 如果拆成两步：get 判空 → put 新列表 → 两个线程同时判空 → 一个列表被覆盖，emitter 丢失

// ③ CopyOnWriteArrayList：写时复制——读完全不加锁，适合"读多写少"（订阅后大部分时间在读）
```

**为什么 value 用 `CopyOnWriteArrayList` 而不是普通 ArrayList**：publish 广播时在遍历列表，同一时刻另一线程可能 remove 一个断开的连接——普通 ArrayList 遍历中被修改会抛 `ConcurrentModificationException`；CopyOnWriteArrayList 写时复制新数组，遍历的是旧快照，永不抛错。

### 5.3 三个"原子组合操作"（比 get+put 高级且必要）

| 方法 | 等价的非原子写法 | 意义 |
|------|-----------------|------|
| `putIfAbsent(key, v)` | `if (!map.containsKey(k)) map.put(k, v)` | 不存在才放（Redis `SET NX` 的 Java 版！） |
| `computeIfAbsent(key, k -> new ...)` | get 判空 → put 新对象 → 再操作 | **计算一次并保证原子**（§5.2 的场景） |
| `compute(key, (k, old) -> next)` | get → 修改 → put | 读改写原子化（如"给某任务的列表追加"） |

> 你已经认出来了：`putIfAbsent` ↔ Redis `SET NX`、`INCR` ↔ 原子类——**"组合操作必须原子"是贯穿本地并发与分布式并发的同一根主线**。

### 5.4 并发集合家族速查

| 集合 | 适用 | 场景对照 |
|------|------|---------|
| `ConcurrentHashMap` | 通用键值并发读写 | SSE 连接注册表（项目） |
| `CopyOnWriteArrayList` | **读多写少**的小列表 | 订阅者列表（项目） |
| `ConcurrentLinkedQueue` | 无界队列 | 任务缓冲 |
| `ArrayBlockingQueue` | 有界队列（配合线程池） | J8 线程池内部就是它 |
| `BlockingQueue`（生产者消费者） | 阻塞等待 | 简易任务管道 |

## 6. 线程协作——CountDownLatch

场景：**主线程要等 N 个子线程都完成，再汇总**。

```java
CountDownLatch latch = new CountDownLatch(3);   // 计数器=3

// 3 个子线程各自干活，干完减 1
for (int i = 0; i < 3; i++) {
    executor.submit(() -> {
        try {
            doWork();
        } finally {
            latch.countDown();                   // ★ 必须放 finally，防止异常导致永不放行
        }
    });
}

latch.await();                                   // 阻塞直到计数归零（也可 await(5, SECONDS) 带超时）
System.out.println("全部完成，开始汇总");
```

**项目真实用法**：[`LlmCallGuard`](../../backend/src/main/java/com/aiexplorer/researchagent/infrastructure/llm/LlmCallGuard.java)（[网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/backend/src/main/java/com/aiexplorer/researchagent/infrastructure/llm/LlmCallGuard.java)）——场景⑧ 的"治理层"：

```java
// 用 CompletableFuture 起一个异步 LLM 调用，主线程最多等 3 秒
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> llmClient.complete(prompt));
String result = future.get(3, TimeUnit.SECONDS);   // ★ 类似 latch.await + 超时——等不到就抛 TimeoutException 进重试
```

`CompletableFuture`（J8 提过的异步编排）的 `get(timeout)` / `thenApply` / `allOf` 是"等结果"的现代写法——**CountDownLatch 适合"多个任务的完成计数"，CompletableFuture 适合"单任务结果编排"**。

> `wait/notify`（Object 的老式线程通信）：能用 CountDownLatch/BlockingQueue/CompletableFuture 替代就别用——裸的 wait/notify 极易写错（忘记 while 判断、忘记 notifyAll）。

## 7. ThreadLocal——线程的"私有口袋"

### 7.1 是什么

```java
private static final ThreadLocal<String> currentUser = new ThreadLocal<>();

currentUser.set("lcc");          // 线程 A 存的
currentUser.get();               // 线程 A 读到 "lcc"
// 线程 B 读到的是 null——每个线程有自己的独立副本，互不可见
```

**前端类比**：≈ 每个线程自己的 `localStorage`（同 key 不同值）。

### 7.2 谁在用

```text
Spring 事务：@Transactional 靠 ThreadLocal 保存"当前线程的数据库连接"——
             同一线程里的多个 DAO 操作才能共享同一个事务（场景⑤ REQUIRES_NEW 新建连接 =
             换了新 ThreadLocal 值）
Spring Security：当前登录用户存在 ThreadLocal（SecurityContextHolder）
日志 MDC：traceId 打进每条日志（排查链路）
```

项目里 [`AuditLogService`](../../backend/src/main/java/com/aiexplorer/researchagent/application/service/AuditLogService.java) 的注释也预留了它："正式方案 = 从用户/安全上下文（如 ThreadLocal）取操作者"。

### 7.3 坑：用完必须 remove

线程池的线程**用完不销毁**（复用）——ThreadLocal 的值跟着线程活着，下一个任务会读到上一个任务残留的值（脏数据），且可能内存泄漏。**规范：`finally { threadLocal.remove(); }`**。

## 8. 本地锁 vs 分布式锁——边界（串联场景⑨⑩）

| 工具 | 锁住的范围 | 适用 | 项目 |
|------|-----------|------|------|
| `synchronized` / `ReentrantLock` | **单个 JVM** 内的线程 | 单机内共享资源（内存集合、本地文件） | 本地并发场景 |
| **Redis SET NX EX**（场景⑨⑩） | **跨实例**（所有 Pod 共享 Redis） | 多实例部署的任务互斥、定时清理 | [`DistributedTaskLock`](../../backend/src/main/java/com/aiexplorer/researchagent/infrastructure/lock/DistributedTaskLock.java)（[网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/backend/src/main/java/com/aiexplorer/researchagent/infrastructure/lock/DistributedTaskLock.java)） |
| Redisson（T7 已学） | 跨实例 + 看门狗续期/可重入 | 生产级分布式锁 | 技术栈补齐实战 T7 |
| 数据库唯一约束/行锁 | 跨实例（重量级） | 强一致场景 | — |

**决策链**：先想部署形态——**单实例** → 本地工具（synchronized/原子类）；**多实例** → Redis/数据库锁。你的 K8s 部署天然多实例，所以项目用 Redis 锁；而 JVM 内的共享集合（SSE 注册表）单实例内部用 ConcurrentHashMap 就够——**两层工具各管一段，不互相替代**。

## 9. 常见坑速查

| # | 坑 | 说明 | 解法 |
|---|-----|------|------|
| 1 | `count++` 直接多线程跑 | 三步操作非原子，丢失更新 | `AtomicInteger` / `synchronized` |
| 2 | 状态开关不加 volatile | 线程读缓存旧值，停不下来 | `volatile`（只做标志位时够用） |
| 3 | 以为 volatile 保证原子性 | `volatile int count` 的 count++ 照样丢 | 原子类或 synchronized |
| 4 | DCL 忘了 volatile | 拿到半初始化对象（NPE/字段异常） | 设计模式 01 的标准写法 |
| 5 | 锁对象每次 new / 用字符串字面量 | 锁了个寂寞 / 全局死锁风险 | `private final Object lock` |
| 6 | HashMap 多线程 put | 数据覆盖/结构破坏 | `ConcurrentHashMap` |
| 7 | ConcurrentHashMap 复合操作拆两步 | get 判空再 put 有竞态 | `putIfAbsent` / `computeIfAbsent` |
| 8 | 遍历 ArrayList 时被别的线程修改 | `ConcurrentModificationException` | `CopyOnWriteArrayList` |
| 9 | ThreadLocal 不 remove | 线程池复用 → 脏数据 + 泄漏 | finally remove |
| 10 | CountDownLatch.countDown 不在 finally | 子线程异常 → await 永远等 | finally 里 countDown |

## 12. 面试速答

```text
Q：volatile 和 synchronized 的区别？
A：volatile 保证可见性+有序性，不保证原子性，无阻塞；synchronized 三者全保证，但会阻塞。
   标志位用 volatile，复合操作用 synchronized/原子类。

Q：count++ 为什么不安全？怎么解决？
A：三步（读改写）非原子。解法：AtomicInteger（CAS 自旋）/ synchronized / LongAdder（高并发计数首选）。

Q：ConcurrentHashMap 为什么线程安全？和 Hashtable 差在哪？
A：1.8 用 CAS + synchronized 锁单个桶（细粒度）；Hashtable 锁整张表（粗粒度全串行）。

Q：本地锁和分布式锁怎么选？
A：先看部署形态——单实例 synchronized/原子类够用；多实例（K8s 多 Pod）必须 Redis/DB 锁。
   本项目：JVM 内共享集合用 ConcurrentHashMap，跨实例任务互斥用 Redis SET NX EX。

Q：ThreadLocal 是什么？有什么风险？
A：线程私有副本（事务连接/登录上下文/traceId 靠它传递）；风险 = 线程池复用导致脏数据与内存泄漏，
   必须 finally remove。
```

## 13. 一句话总结

```text
并发三大问题：可见性（volatile）、原子性（synchronized/原子类）、有序性（volatile 禁重排）；
count++ 是三步操作——本地用 AtomicInteger，跨进程用 Redis INCR；
组合操作必须原子：ConcurrentHashMap 的 putIfAbsent/computeIfAbsent ↔ Redis 的 SET NX；
ThreadLocal = 线程私有口袋（事务/上下文的传递机制），用完 remove；
本地锁管 JVM 内，Redis 锁管跨实例——先看部署形态再选工具。
```
