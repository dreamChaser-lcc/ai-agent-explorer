## 1. 泛型：容器的"标签"

```java
List<TaskSummaryResponse> listTasks()
//  ↑ 容器类型    ↑ 标签：这个列表里装的是 TaskSummaryResponse
```

**前端类比**：`Array<TaskSummaryResponse>` / `Promise<TaskDetailResponse>`——同款心智。

**价值三连**：编译期检查（装错当场报）/ 不用强转 / 签名即文档。

**嵌套例子**：`List<String> plannedSteps`——"装 String 的列表"（record 里装 List）。

**预告**：Java 泛型有"擦除"（`<T>` 只活在编译期——和 TS 泛型一样是编译期概念）。

---

## 2. 集合三兄弟 + "List 是接口"

| 集合 | 是什么 | 项目现身 |
|------|--------|---------|
| **List** ★ | 有序、可重复 | `List<TaskSummaryResponse>`、`List<ResearchStepEntity>`、`List<String>` |
| **Map** | 键值对 | `Map<String, Object> payload`（TaskEventService） |
| **Set** | 不重复 | 少见 |

★ **`List` 是接口**——`ArrayList` / `LinkedList` 是"两副面孔"——**J2"面向接口"知识在集合世界 100% 渗透**。

---

## 3. ArrayList vs LinkedList（实战结论）

| 操作 | ArrayList（动态数组） | LinkedList（双向链表） |
|------|---------------------|----------------------|
| `get(i)` | **O(1)** ★ | O(n) |
| 头部/中间插删 | O(n)（全员挪位） | O(1)（**需已定位**） |
| 遍历 | 快（缓存友好） | 较慢（指针跳转） |

**实战**：**几乎只用 ArrayList**（缓存 + "找位置成本" + 队列场景被 `ArrayDeque` 取代）。
**项目实测**：backend 全项目 **0 处 `new ArrayList` / 0 处 `new LinkedList`**——见下节。

## 4. 不可变工厂：`List.of` / `.toList()`（项目风格）

```java
List.of("search", "fetch", "report")     // 一次性小清单（9+ 处在用）
steps.stream().map(...).toList()          // 流水线产出（满屏）
```

**"第三选择"**：现代 Java 的"不可变优先"——需要后续增删的"工作台"才轮到 `ArrayList`。

**小坑**：`List.of` / `toList()` 返回**不可变清单**——`add` 会抛 `UnsupportedOperationException`；想改就 `new ArrayList<>(list)` 包一层。

**ArrayList 扩容小知识**：默认 10 起步、1.5 倍扩容；批量添加可 `new ArrayList<>(10000)` 预估容量。

## 5. Optional：写在类型上的"可能没有"

| 姿势 | 代码 | 语义 |
|------|------|------|
| **必须有** | `.orElseThrow(() -> new TaskNotFoundException(id))` | 不存在 = 错误（404） |
| **可以有** | `.orElse(null)` | 还没有 = 合法状态 |
| **桥** | `List.stream().findFirst()` | 把"列表可能空"翻译成 Optional |
| 兜底 | `.orElse(默认值)` | 有就用、没有用默认 |
| 顺手 | `.ifPresent(...)` / `.map(...)` | 有就处理 / 有就转换 |

**分界线**：**"不存在"（错误→异常）vs "还没有"（合法缺席→null）**——任务详情页里：任务必须存在（抛），计划可以还没生成（null，下游 mapper 温柔接住）。

**为什么不用 null 直说**：签名不吭声、null 无声传递、全靠自觉——Optional 是"类型层的强制表态"（不 `orElse` 拿不到值）。

## 6. Optional vs JS 的 `?.`（同一母题、不同形态）

```java
// 现代 Java：
Optional.ofNullable(task)
        .map(ResearchTaskEntity::getLatestPlan)
        .map(ResearchPlanEntity::getPlanSummary)
        .orElse("暂无计划");
```
```javascript
// JS：
const summary = task?.latestPlan?.planSummary ?? "暂无计划";
```

- `?.` = **运算符**；Optional = **容器 + 方法链**（`map().map().orElse()` ≈ `?.?.??` 的"Java 拼写法"）；
- **Java 没有 `?.` 语法**——null 安全靠"防线组合"（if / `Objects.requireNonNull` / Optional / `@Nullable`+IDE / ……或去写 Kotlin）；
- 小知识：`Optional.of` 遇 null **当场炸**；`ofNullable` 才允许"空盒子"；`?.` 也是 ES2020 才进 JS 的（旧 JS 靠 `&&` 流——**每种语言都在解同一个"缺席"母题**）。

## 7. "看不见的 Optional"：类型藏在返回值里

```java
researchTaskRepository.findById(taskId)   // 返回 Optional<ResearchTaskEntity>（Spring Data 签名）
...stream().findFirst()                    // 返回 Optional<ResearchPlanEntity>（Stream 终结操作）
```

**没写"Optional"≠没用 Optional**——它是**方法返回的东西**，只是没存变量（即用即点）。

**查类型三招**：① IDE 悬停/Ctrl+点读签名 ② 打 `.` 看候选方法（出现 `orElse*` = 上一步是 Optional）③ 顺继承链看（`ResearchTaskRepository` 是**空接口**——`extends JpaRepository<实体, 主键>`——方法全继承自父接口，实现由 Spring Data **运行时动态生成**）。

**泛型新用法**：`JpaRepository<ResearchTaskEntity, UUID>` 的 `<...>` = 给框架的"配置参数"（"我管什么实体、主键什么类型"）。

## 8. Stream 流水线（本课主角）

```java
return researchTaskRepository.findAll().stream()   // ① JPA：查库 → List（唯一属于 JPA 的调用）
        .sorted(Comparator.comparing(...).reversed())  // ② JDK Stream：排序（倒序）
        .filter(task -> task.getTitle().contains("测试"))  // ③ 筛选（谓词 true 留 false 走）
        .map(taskResponseMapper::toTaskSummary)    // ④ 映射（Entity → Response）
        .toList();                                 // ⑤ 收拢成 List
```

**认门（产权归属）**：**只有第 ① 步是 JPA（Spring Data）的**——②~⑤ 全是 **JDK 的 Stream API**（任何 List 可用、换掉 JPA 链照用——前端对照：`arr.filter().map().sort()`）。

**`::` 方法引用**：`taskResponseMapper::toTaskSummary` = `task -> taskResponseMapper.toTaskSummary(task)` 的简写（J1 lambda 的进阶形态）。

**前端对照表**：

| JS 数组链 | Java Stream 链 |
|-----------|----------------|
| `arr.sort(...)` | `.stream().sorted(...)` |
| `arr.filter(fn)` | `.filter(predicate)` |
| `arr.map(fn)` | `.map(mapper)` |
| `arr.slice(0, 2)` | `.limit(2)` |
| 本身就是数组 | 需 `.stream()` 打开、`.toList()` 收拢 |

## 9. ★ 顺序即语义（动手实测：8 → 3 → 2 → 1）

**实验设定**：库里 8 条任务（4 条乱码对照组 + 4 条正常：`测试任务-A/B/C` + `正式任务-D`，**D 最新**）。

| 步骤 | 代码形态 | 预期 | 实测 |
|------|---------|------|------|
| 基线 | 原版 | 8 条 | （库里 8 条，H2 Console 证实） |
| +filter | `.filter(测试)` | 3 条 | ✅ **3 条**（C、B、A） |
| +limit（先筛后截） | `.filter(测试).limit(2)` | 2 条 | ✅ **2 条**（C、B） |
| ★ 换序（先截后筛） | `.limit(2).filter(测试)` | **1 条** | （推演：正式D 占名额后又被筛掉 → 只剩 C） |

```text
顺序 A（先筛后截）：8 →筛"测试"→ 【C,B,A】 →截前2→ 【C,B】= 2 条
顺序 B（先截后筛）：8 →截前2→ 【正式D, C】 →筛"测试"→ 【C】= 1 条
                                            ↑ "不达标者"在"截"那步吃掉了名额！
```

**法则**：**流水线按书写顺序逐个执行——顺序不同，语义不同，结果不同**（前端同理：`arr.filter().slice(0,2)` ≠ `arr.slice(0,2).filter()`）。

## 10. 分层：Entity / Response / Mapper（"翻译官"）

```java
public record TaskDetailResponse(..., List<String> plannedSteps, ...) { }
//                                  ↑ 数据库表里【没有】这个字段——是 mapper 从 steps 加工出来的
```

**为什么 Entity 不直接返回前端**：

| 理由 | 说明 |
|------|------|
| **契约** | Response 是"对前端的承诺"——改它要慎重（**加字段向后兼容 / 删改字段=契约破坏**） |
| **解耦** | 数据库加字段，前端无感（Response 不加就不暴露）；前端要字段，可能不用动库（mapper 加工） |
| **安全** | Entity 可能带不该见光的字段 |
| **形状差异** | Entity 是"数据库的形状"；Response 是"页面的形状"——`plannedSteps` 就是"算出来的" |

**金句**：**Entity = 数据库的形状；Response = 对前端的承诺；mapper = 翻译官（决定什么该出去）。**

## 补充：思考题与答案（课堂问答收录）

**题 1（业务语义题）**——同一个 `getTaskDetail` 里：为什么"任务查不到 → 抛异常"，而"计划查不到 → 给 null"？

**答**：分界线是一句话——**"不存在（错误）" vs "还没有（合法缺席）"**：

| | 任务查不到 | 计划查不到 |
|---|---|---|
| 语义 | **不存在**——"你要看的这个东西没有"——**错误** | **还没有**——任务可能刚创建、计划尚未生成——**合法状态** |
| 处理 | `.orElseThrow(...)` | `.orElse(null)` |
| 下游 | 全局处理器 → **404 结构化错误响应**（"明确地说没有"） | mapper 温柔接住（`latestPlan != null ? ... : null`）→ **200 正常响应** |

**为什么任务不能也给 null**：若给 null，详情页"静悄悄地空"——**前端无法区分"任务不存在"和"页面坏了"**——**错误必须有人明确表达**。

**题 2（分层设计题）**——为什么不把 `ResearchTaskEntity` 直接返回前端？

**答**：四个维度：

1. **契约**：Response 是"对前端的承诺"——加字段向后兼容（安全）；删/改字段=契约破坏（要协商）。Entity 是"数据库的形状"，随意改不该绑架前端；
2. **解耦**：数据库加字段 → 前端无感（Response 不加就不暴露）；前端要新字段 → 可能不用动库（mapper 加工）；
3. **安全**：Entity 可能含不该见光的字段（如密码哈希）；
4. **形状差异**（最锋利）：**Response 里可以装"数据库里没有的东西"**——如 `List<String> plannedSteps` 是 mapper 从 steps 集合**算出来**的（`steps.stream().map(ResearchStepEntity::getTitle).toList()`）——"页面的形状"本来就≠"表的样子"。

**金句**：**Entity = 数据库的形状；Response = 对前端的承诺；mapper = 翻译官（决定什么该出去）。**

## 15. 进阶：类型擦除——运行时泛型去哪了（2026-10-27 补，面试级）

### 15.1 一个实验证明擦除存在

```java
List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
System.out.println(a.getClass() == b.getClass());   // true！

// 运行时只有一个 ArrayList——List<String> 和 List<Integer> 是同一坨字节码
// 泛型只活在【编译期】（编译器用它做类型检查），编译完就丢
```

### 15.2 擦除规则（背两条）

```text
无界 <T>            → 擦成 Object
<T extends Xxx>     → 擦成【第一个上界】Xxx（多个上界取最左）
```

### 15.3 擦除的三个后果（面试高频三连）

```text
① 不能 new T() / new T[10]        → 运行时根本不知道 T 是谁
② 不能 instanceof List<String>    → 编译器直接报错（运行时没这信息）
③ 静态方法不能用类的泛型参数      → static 与实例无关，T 属于实例
```

### 15.4 工程上怎么绕（项目就在用）

```java
// 传 Class<T> 当"类型令牌"——Spring Data 就是这么知道实体类型的
public <T> T find(Class<T> type, String sql) { ... }

JpaRepository<ResearchTaskEntity, UUID>   // 泛型在接口上声明，
                                          // 框架反射读的是【方法签名里的类型信息】
                                          //（签名会保留泛型，叫 Signature 属性）

// 泛型数组：Array.newInstance(type, n)
T[] arr = (T[]) Array.newInstance(clazz, size);
```

## 16. 进阶：通配符与 PECS（面试必考）

### 16.1 为什么需要通配符

```text
动物饲养员能喂猫也能喂狗 → 你以为 List<Cat> 能传给喂(List<Animal>)？
不能！List<Cat> 【不是】List<Animal> 的子类。

为什么这么设计？看数组的反面教材：
Object[] objs = new String[10];      // 数组是协变的（编译过）
objs[0] = 123;                        // 💥 ArrayStoreException（运行时才炸）
集合放弃协变（编译期就拦住），改用通配符表达灵活性
```

### 16.2 PECS 口诀（Producer Extends, Consumer Super）

```java
// <? extends T> = 生产者：从它【读】数据（它产 T 给你）
void feed(List<? extends Animal> animals) {
    Animal a = animals.get(0);     // ✅ 读出来的至少是 Animal
    animals.add(new Cat());        // ❌ 不能写（不知道确切类型）
}

// <? super T> = 消费者：往它【写】数据（它消费 T）
void collect(List<? super Cat> box) {
    box.add(new Cat());            // ✅ 写 Cat 一定安全（盒子里装的就是 Cat 或其父类）
    Cat c = box.get(0);            // ❌ 读出来只能当 Object
}
```

**JDK 原版应用**（面试可引用）：

```java
static <T> void copy(List<? super T> dest, List<? extends T> src)
//                  ↑ 消费者（往里写）        ↑ 生产者（从里读）
```

### 16.3 项目里的通配符

```java
// Comparator 链式排序——thenComparing 的签名就是 PECS 实践
Comparator.comparing(Task::getStatus)
          .thenComparing(Task::getCreatedAt)
// Comparator<Task> 在中途会以 Comparator<? super Task> 出现
```

## 17. 面试级问答（2026-10-27）

**Q1：`List<String>` 能赋给 `List<Object>` 吗？**

```text
不能（编译错）。协变会像数组那样埋 ArrayStoreException 的雷。
要灵活性用通配符：List<String> 可以赋给 List<?>（只读）
```

**Q2：泛型擦除后，框架怎么拿到类型（如 Spring Data 的 Repository）？**

```text
运行时实例上的泛型确实没了，但【类/方法签名】里的泛型信息保留在字节码
（Signature 属性）——框架用反射读签名，不是读实例。
所以 Spring Data 能从 JpaRepository<TaskEntity, UUID> 的接口定义里拿到类型。
```

**Q3：`<?>` 和 `<? extends Object>` 有区别吗？**

```text
语义上等价（都只能读成 Object、不能写）。
习惯用 <?> 表达"任意类型"，<? extends Object> 几乎只出现在泛型边界推导里。
```

### 一句话

```text
泛型 = 编译期的类型检查（运行时擦掉）
擦除三不能：new T / instanceof 泛型 / 静态用 T
通配符口诀：读 extends 写 super（PECS）
框架拿类型靠【签名反射】不靠实例
```

## 18. 进阶：HashMap 全家桶（面试第一考点，2026-10-27 补）

> 学员点名："集合没讲清楚，HashMap 什么之类的经常有面试考题"——本节一次讲透。

### 18.1 底层结构（JDK 8）

```text
table[]（数组，容量恒为 2 的幂）
   │
   ├── 桶 0：null                          ← 空
   ├── 桶 1：Node(k1,v1) → Node(k2,v2)     ← 链表（hash 撞车排队）
   ├── 桶 2：TreeNode（红黑树）             ← 链表太长（≥8）变身，查找 O(log n)
   └── ...
```

```java
// 一个 Node 就是链表节点（也是树节点的爹）
class Node<K, V> {
    final int hash;      // 缓存的 hash（final——hash 变了就找不到这个桶了！）
    final K key;
    V value;
    Node<K, V> next;
}
```

### 18.2 put 一个键值对的完整流程（六步）

```text
① hash(key) = key.hashCode() 高 16 位 异或 低 16 位     ← 扰动函数
② 定位桶：index = (n - 1) & hash                        ← n 是容量
③ 桶空 → 直接放
④ 桶不空 → 逐个 equals：
     · 相同 key → 覆盖 value，返回旧值
     · 都不同 → 尾插到链表末尾（JDK8；JDK7 是头插——并发扩容会成环死循环）
⑤ 链表长度 ≥ 8 且数组容量 ≥ 64 → 链表转红黑树
⑥ size > 容量 × 0.75 → 扩容两倍 + 全员 rehash 分桶
```

### 18.3 灵魂五连问（面试必背，每问一个设计权衡）

| 问 | 答（一句话） | 背后的权衡 |
|---|---|---|
| **为什么容量是 2 的幂？** | `(n-1) & hash` 等价于 `hash % n` 但位运算快；且 n-1 是全 1 掩码，散得均匀 | 速度 + 均匀分布 |
| **为什么负载因子 0.75？** | 太小浪费空间（频繁扩容），太大碰撞多（链表变长）——0.75 是数学上的折中 | 空间 vs 时间 |
| **为什么链表长 8 才树化？** | 理想 hash 下链表长度服从泊松分布，撞到 8 的概率约亿分之六——到了 8 说明 hash 质量有问题，值得用树兜底 | 树节点内存是链表 2 倍，不能轻易用 |
| **为什么树化还要数组 ≥ 64？** | 数组还小时，碰撞多是因为容量不够——**先扩容**比树化更治本 | 扩容 vs 树化的成本比较 |
| **hash 要高 16 位异或？** | 定位只用了低位（n-1 掩码在高容量前只有低几位有效）——把高位信息掺进来减少碰撞 | 让 hashCode 的全部比特参与定位 |

### 18.4 equals/hashCode 契约（HashMap 的地基）

**三条契约**（违反任何一条，Map 直接行为错乱）：

```text
① equals 相等 → hashCode 必须相等
② hashCode 相等 → equals 可以不等（撞桶是允许的）
③ hashCode 不相等 → equals 必须不等（推论）
```

**经典事故：可变对象当 key**

```java
List<String> key = new ArrayList<>(List.of("a"));
map.put(key, "v1");        // hash 基于当前内容
key.add("b");              // 内容变了 → hashCode 变了
map.get(key);              // null！按新 hash 找不到旧桶
// 对象还在 Map 里（内存泄漏），但你永远取不出来了
```

**项目的免疫设计**：

```text
· 23 个 record 全部不可变 → hashCode 天生稳定（J1 补充：自动生成 equals/hashCode）
· Entity 千万别拿去当 Map 的 key：字段可变（updatedAt 每次更新都变）
  → 项目里 Map 的 key 都是 UUID/枚举/String（不可变类型）——纪律正确
```

### 18.5 三大 Map 对比与线程安全

| | HashMap | Hashtable | ConcurrentHashMap |
|---|---|---|---|
| 线程安全 | ❌ | ✅（全表一把锁，性能烂，**已废弃**） | ✅ |
| null key/value | ✅（null key 落 0 号桶） | ❌ | ❌ |
| 锁粒度 | — | 整张表 | **JDK8：桶级**（CAS 放空桶 + synchronized 锁桶头） |
| 演进 | — | 上古 | JDK7 分段锁（16 段）→ JDK8 桶级 CAS（更细） |

**项目对照**（实测 3 处 ConcurrentHashMap）：

```java
// TaskProgressStreamService —— SSE 进度推送
private final Map<UUID, SseEmitter> emitters = new ConcurrentHashMap<>();
// 为什么必须并发安全：HTTP 连接线程注册 emitter，异步任务线程完成时移除——
// 两类线程同时摸这张 Map（J8 的"共享+可变+多线程"三条件齐了）
```

### 18.6 fail-fast：`ConcurrentModificationException`

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
for (String s : list) {
    if ("b".equals(s)) list.remove(s);   // 💥 下一次迭代时炸
}
// 机制：迭代器创建时记住 modCount；结构被改（remove/add 使 modCount++）
//       迭代器一发现对不上，立刻抛——"宁可炸也不 silently 错"
```

**三种正确姿势**：

```java
list.removeIf("b"::equals);                    // ① 条件删除（底层用迭代器的 remove）

for (Iterator<String> it = list.iterator(); it.hasNext();) {
    if ("b".equals(it.next())) it.remove();   // ② 迭代器自己的 remove（同步 modCount）
}

List<String> cow = new CopyOnWriteArrayList<>(list);  // ③ 写时复制
for (String s : cow) { cow.remove(s); }       // 安全：迭代的是旧快照
```

**项目对照**：4 处 `CopyOnWriteArrayList`（SSE 场景——读多写少、遍历时允许并发改）。

### 18.7 其他高频快问快答

| 问 | 答 |
|---|---|
| ArrayList 怎么扩容？ | 1.5 倍（`oldCap + (oldCap >> 1)`）；HashMap 是 2 倍——都为摊平成本 |
| HashSet 底层？ | 就是 HashMap——元素当 key，value 是一个共享的哑对象 `PRESENT` |
| LinkedHashMap 特殊在哪？ | 链表维护插入序（或访问序）——项目 11 处用它保 DTO 字段序 |
| TreeMap 特殊在哪？ | 红黑树按 comparator 排序，范围查询（headMap/tailMap）O(log n) |
| HashMap 遍历顺序？ | 无序（按桶）——要顺序用 LinkedHashMap |

### 18.8 面试速查追加

```text
开口模板："HashMap 我分三层讲——存取流程、扩容策略、线程安全演进……"

一句话：
HashMap = 数组挂链表（长了变红黑树）+ 2 幂容量位运算定位 + 0.75 负载因子 2 倍扩容
灵魂五问全部是"权衡"：2幂（速度）、0.75（折中）、8 树化（泊松）、64（先扩容）、扰动（均匀）
契约三条：等则同码、同码可不等、hashCode 稳定性靠不可变 key（record 天然达标）

```
