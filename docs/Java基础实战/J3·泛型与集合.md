## 1. 泛型：容器的"标签"

```java
List<TaskSummaryResponse> listTasks()
//  ↑ 容器类型    ↑ 标签：这个列表里装的是 TaskSummaryResponse
```

**前端类比**：`Array<TaskSummaryResponse>` / `Promise<TaskDetailResponse>`——同款心智。

**价值三连**：编译期检查（装错当场报）/ 不用强转 / 签名即文档。

**嵌套例子**：`List<String> plannedSteps`——"装 String 的列表"（record 里装 List）。

**预告**：Java 泛型有"擦除"（`<T>` 只活在编译期——和 TS 泛型一样是编译期概念）。

---

## 2. 集合三兄弟 + "List 是接口"

| 集合 | 是什么 | 项目现身 |
|------|--------|---------|
| **List** ★ | 有序、可重复 | `List<TaskSummaryResponse>`、`List<ResearchStepEntity>`、`List<String>` |
| **Map** | 键值对 | `Map<String, Object> payload`（TaskEventService） |
| **Set** | 不重复 | 少见 |

★ **`List` 是接口**——`ArrayList` / `LinkedList` 是"两副面孔"——**J2"面向接口"知识在集合世界 100% 渗透**。

---

## 3. ArrayList vs LinkedList（实战结论）

| 操作 | ArrayList（动态数组） | LinkedList（双向链表） |
|------|---------------------|----------------------|
| `get(i)` | **O(1)** ★ | O(n) |
| 头部/中间插删 | O(n)（全员挪位） | O(1)（**需已定位**） |
| 遍历 | 快（缓存友好） | 较慢（指针跳转） |

**实战**：**几乎只用 ArrayList**（缓存 + "找位置成本" + 队列场景被 `ArrayDeque` 取代）。
**项目实测**：backend 全项目 **0 处 `new ArrayList` / 0 处 `new LinkedList`**——见下节。

---

## 4. 不可变工厂：`List.of` / `.toList()`（项目风格）

```java
List.of("search", "fetch", "report")     // 一次性小清单（9+ 处在用）
steps.stream().map(...).toList()          // 流水线产出（满屏）
```

**"第三选择"**：现代 Java 的"不可变优先"——需要后续增删的"工作台"才轮到 `ArrayList`。

**小坑**：`List.of` / `toList()` 返回**不可变清单**——`add` 会抛 `UnsupportedOperationException`；想改就 `new ArrayList<>(list)` 包一层。

**ArrayList 扩容小知识**：默认 10 起步、1.5 倍扩容；批量添加可 `new ArrayList<>(10000)` 预估容量。

## 5. Optional：写在类型上的"可能没有"

| 姿势 | 代码 | 语义 |
|------|------|------|
| **必须有** | `.orElseThrow(() -> new TaskNotFoundException(id))` | 不存在 = 错误（404） |
| **可以有** | `.orElse(null)` | 还没有 = 合法状态 |
| **桥** | `List.stream().findFirst()` | 把"列表可能空"翻译成 Optional |
| 兜底 | `.orElse(默认值)` | 有就用、没有用默认 |
| 顺手 | `.ifPresent(...)` / `.map(...)` | 有就处理 / 有就转换 |

**分界线**：**"不存在"（错误→异常）vs "还没有"（合法缺席→null）**——任务详情页里：任务必须存在（抛），计划可以还没生成（null，下游 mapper 温柔接住）。

**为什么不用 null 直说**：签名不吭声、null 无声传递、全靠自觉——Optional 是"类型层的强制表态"（不 `orElse` 拿不到值）。

## 6. Optional vs JS 的 `?.`（同一母题、不同形态）

```java
// 现代 Java：
Optional.ofNullable(task)
        .map(ResearchTaskEntity::getLatestPlan)
        .map(ResearchPlanEntity::getPlanSummary)
        .orElse("暂无计划");
```
```javascript
// JS：
const summary = task?.latestPlan?.planSummary ?? "暂无计划";
```

- `?.` = **运算符**；Optional = **容器 + 方法链**（`map().map().orElse()` ≈ `?.?.??` 的"Java 拼写法"）；
- **Java 没有 `?.` 语法**——null 安全靠"防线组合"（if / `Objects.requireNonNull` / Optional / `@Nullable`+IDE / ……或去写 Kotlin）；
- 小知识：`Optional.of` 遇 null **当场炸**；`ofNullable` 才允许"空盒子"；`?.` 也是 ES2020 才进 JS 的（旧 JS 靠 `&&` 流——**每种语言都在解同一个"缺席"母题**）。

## 7. "看不见的 Optional"：类型藏在返回值里

```java
researchTaskRepository.findById(taskId)   // 返回 Optional<ResearchTaskEntity>（Spring Data 签名）
...stream().findFirst()                    // 返回 Optional<ResearchPlanEntity>（Stream 终结操作）
```

**没写"Optional"≠没用 Optional**——它是**方法返回的东西**，只是没存变量（即用即点）。

**查类型三招**：① IDE 悬停/Ctrl+点读签名 ② 打 `.` 看候选方法（出现 `orElse*` = 上一步是 Optional）③ 顺继承链看（`ResearchTaskRepository` 是**空接口**——`extends JpaRepository<实体, 主键>`——方法全继承自父接口，实现由 Spring Data **运行时动态生成**）。

**泛型新用法**：`JpaRepository<ResearchTaskEntity, UUID>` 的 `<...>` = 给框架的"配置参数"（"我管什么实体、主键什么类型"）。

## 8. Stream 流水线（本课主角）

```java
return researchTaskRepository.findAll().stream()   // ① JPA：查库 → List（唯一属于 JPA 的调用）
        .sorted(Comparator.comparing(...).reversed())  // ② JDK Stream：排序（倒序）
        .filter(task -> task.getTitle().contains("测试"))  // ③ 筛选（谓词 true 留 false 走）
        .map(taskResponseMapper::toTaskSummary)    // ④ 映射（Entity → Response）
        .toList();                                 // ⑤ 收拢成 List
```

**认门（产权归属）**：**只有第 ① 步是 JPA（Spring Data）的**——②~⑤ 全是 **JDK 的 Stream API**（任何 List 可用、换掉 JPA 链照用——前端对照：`arr.filter().map().sort()`）。

**`::` 方法引用**：`taskResponseMapper::toTaskSummary` = `task -> taskResponseMapper.toTaskSummary(task)` 的简写（J1 lambda 的进阶形态）。

**前端对照表**：

| JS 数组链 | Java Stream 链 |
|-----------|----------------|
| `arr.sort(...)` | `.stream().sorted(...)` |
| `arr.filter(fn)` | `.filter(predicate)` |
| `arr.map(fn)` | `.map(mapper)` |
| `arr.slice(0, 2)` | `.limit(2)` |
| 本身就是数组 | 需 `.stream()` 打开、`.toList()` 收拢 |

## 9. ★ 顺序即语义（动手实测：8 → 3 → 2 → 1）

**实验设定**：库里 8 条任务（4 条乱码对照组 + 4 条正常：`测试任务-A/B/C` + `正式任务-D`，**D 最新**）。

| 步骤 | 代码形态 | 预期 | 实测 |
|------|---------|------|------|
| 基线 | 原版 | 8 条 | （库里 8 条，H2 Console 证实） |
| +filter | `.filter(测试)` | 3 条 | ✅ **3 条**（C、B、A） |
| +limit（先筛后截） | `.filter(测试).limit(2)` | 2 条 | ✅ **2 条**（C、B） |
| ★ 换序（先截后筛） | `.limit(2).filter(测试)` | **1 条** | （推演：正式D 占名额后又被筛掉 → 只剩 C） |

```text
顺序 A（先筛后截）：8 →筛"测试"→ 【C,B,A】 →截前2→ 【C,B】= 2 条
顺序 B（先截后筛）：8 →截前2→ 【正式D, C】 →筛"测试"→ 【C】= 1 条
                                            ↑ "不达标者"在"截"那步吃掉了名额！
```

**法则**：**流水线按书写顺序逐个执行——顺序不同，语义不同，结果不同**（前端同理：`arr.filter().slice(0,2)` ≠ `arr.slice(0,2).filter()`）。

## 10. 分层：Entity / Response / Mapper（"翻译官"）

```java
public record TaskDetailResponse(..., List<String> plannedSteps, ...) { }
//                                  ↑ 数据库表里【没有】这个字段——是 mapper 从 steps 加工出来的
```

**为什么 Entity 不直接返回前端**：

| 理由 | 说明 |
|------|------|
| **契约** | Response 是"对前端的承诺"——改它要慎重（**加字段向后兼容 / 删改字段=契约破坏**） |
| **解耦** | 数据库加字段，前端无感（Response 不加就不暴露）；前端要字段，可能不用动库（mapper 加工） |
| **安全** | Entity 可能带不该见光的字段 |
| **形状差异** | Entity 是"数据库的形状"；Response 是"页面的形状"——`plannedSteps` 就是"算出来的" |

**金句**：**Entity = 数据库的形状；Response = 对前端的承诺；mapper = 翻译官（决定什么该出去）。**

## 补充：思考题与答案（课堂问答收录）

**题 1（业务语义题）**——同一个 `getTaskDetail` 里：为什么"任务查不到 → 抛异常"，而"计划查不到 → 给 null"？

**答**：分界线是一句话——**"不存在（错误）" vs "还没有（合法缺席）"**：

| | 任务查不到 | 计划查不到 |
|---|---|---|
| 语义 | **不存在**——"你要看的这个东西没有"——**错误** | **还没有**——任务可能刚创建、计划尚未生成——**合法状态** |
| 处理 | `.orElseThrow(...)` | `.orElse(null)` |
| 下游 | 全局处理器 → **404 结构化错误响应**（"明确地说没有"） | mapper 温柔接住（`latestPlan != null ? ... : null`）→ **200 正常响应** |

**为什么任务不能也给 null**：若给 null，详情页"静悄悄地空"——**前端无法区分"任务不存在"和"页面坏了"**——**错误必须有人明确表达**。

**题 2（分层设计题）**——为什么不把 `ResearchTaskEntity` 直接返回前端？

**答**：四个维度：

1. **契约**：Response 是"对前端的承诺"——加字段向后兼容（安全）；删/改字段=契约破坏（要协商）。Entity 是"数据库的形状"，随意改不该绑架前端；
2. **解耦**：数据库加字段 → 前端无感（Response 不加就不暴露）；前端要新字段 → 可能不用动库（mapper 加工）；
3. **安全**：Entity 可能含不该见光的字段（如密码哈希）；
4. **形状差异**（最锋利）：**Response 里可以装"数据库里没有的东西"**——如 `List<String> plannedSteps` 是 mapper 从 steps 集合**算出来**的（`steps.stream().map(ResearchStepEntity::getTitle).toList()`）——"页面的形状"本来就≠"表的样子"。

**金句**：**Entity = 数据库的形状；Response = 对前端的承诺；mapper = 翻译官（决定什么该出去）。**

## 附：本课一句话总结

1. **泛型 = 容器的标签**（编译期检查 + 不用强转）；
2. **`List` 是接口**——ArrayList 是默认之选，`List.of`/`toList` 是不可变优先；
3. **Optional = 写在类型上的"可能没有"**——`orElseThrow` 表错误、`orElse(null)` 表合法缺席；
4. **Stream 链按顺序执行——顺序即语义**（8→3→2→1 实测）；
5. **Entity→Response 经"翻译官"**——契约、解耦、安全、形状；
6. **显示层会骗人**——用最原始的通道校准（H2 / curl / .Count）。
