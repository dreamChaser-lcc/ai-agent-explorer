## 1. 术语拆解："有界命令下发线程池"

```text
有界命令下发线程池
  └─ 拆开读：有界（bounded）+ 命令下发（做什么用的）+ 线程池（是什么）
```

**"有界（bounded）"说的是容量被硬性封顶**——线程数封顶、排队任务封顶，满了就立刻拒绝（而不是无限堆积）。这是一个**刻意设计的背压机制**，防止消息洪峰把服务打爆。

> **背压（backpressure）**：当生产速度快于消费速度时，把"压力"反馈给生产端（拒绝/等待），让上游降速——而不是下游无限吸收直到崩溃。前端类比：**Exponential Backoff 重试 + 429 Too Many Requests**——服务端明确告诉你"我满了，稍后再来"，而不是默默把请求吞了。

## 2. "有界"体现在哪两个数字上

```java
private static final int CORE_THREADS = 8;
private static final int MAX_THREADS = 8;
private static final int QUEUE_CAPACITY = 200;

this.executor = new ThreadPoolExecutor(
        CORE_THREADS, MAX_THREADS, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(QUEUE_CAPACITY),      // ← 定长队列！
        ...,
        new ThreadPoolExecutor.AbortPolicy());          // ← 满了直接拒绝
```

| 维度 | 配置 | 意义 |
|------|------|------|
| 线程数有界 | core = max = 8 | 无论来多少命令，干活的人最多 8 个 |
| 队列有界 | `ArrayBlockingQueue(200)` | 最多排队 200 个，第 201 个直接拒绝 |
| 拒绝策略 | `AbortPolicy`（抛异常） | 让调用方**立刻知道"满了"**，而不是默默吞掉 |

**三个数字相加的含义**：这个池最多同时承载 **8 + 200 = 208** 个任务，再多一个都进不来。

> 回忆 J8 §3：`ThreadPoolExecutor` 的执行顺序是 core → queue → max → reject——因为 core=max=8，所以实际顺序是"8 个线程忙 → 排 200 → 再来就拒绝"。队列定长是触发"拒绝"的前提。

## 3. 为什么必须有界——Executors 两大反面教材

JDK 的 `Executors` 快捷工厂就是"无界"的反面典型：

```java
// ❌ 坑 1：newFixedThreadPool —— 队列是无界的 LinkedBlockingQueue
//    来多少任务排多少 → 内存无限增长 → OOM
Executors.newFixedThreadPool(10);

// ❌ 坑 2：newCachedThreadPool —— 线程数无界（上限 Integer.MAX_VALUE）
//    任务突发 → 疯狂创建线程 → 线程爆炸/系统卡死
Executors.newCachedThreadPool();
```

《阿里巴巴 Java 开发手册》**强制禁止**用 Executors 创建线程池，就是这两个原因。案例项目手写 `new ThreadPoolExecutor(...)` 并显式指定**定长队列 + 拒绝策略**，正是规范要求的标准写法。

**如果这里用无界队列会怎样**（案例项目的推演）：某企业批量发 1 万条人工回复 → 1 万个下发任务全部堆进队列 → 每个任务持有引用 → JVM 堆被撑爆 → realtime 整个进程 OOM，**所有客户端连接全部断开**。有界后：最多堆积 200 个，其余走"拒绝 + 稍后重试"。

## 4. 池满之后：拒绝 ≠ 丢失（设计的精髓）

```java
public boolean tryExecute(Runnable task) {
    try {
        executor.execute(task);
        return true;
    } catch (RejectedExecutionException e) {
        return false;      // 池满：返回 false，不抛给上层
    }
}
```

```java
// 调用方（CommandPump）的处理：
boolean accepted = dispatcher.tryExecute(() -> { ... });
if (!accepted) {
    log.warn("Dispatch deferred (BUSY) ... retryAfterMs={}", dispatcher.retryAfterMs());
}
```

**关键在最后一环：拒绝 ≠ 丢失。**

```text
任务被拒绝 → 只是这次"提醒"没处理
           → 命令还在 Redis ZSET 队列里躺着（没有丢！）
           → 2 秒后兜底轮询扫到 → 重新下发
```

```java
/** 池满后建议的重试间隔（ms），与 CommandPump 2s 兜底轮询对齐 */
public static final long RETRY_AFTER_MS = 2_000L;
```

**这笔账算得很清楚**：

```text
拒绝的成本 = 延迟 2 秒
无界堆积的成本 = OOM 全挂（所有客户端断连）
```

> **推拉结合架构**（拒绝能兜底的前提）：命令本体在 Redis ZSET 队列里，"敲门"（Pub-Sub 通知）只是**提醒**——推（实时性好）+ 拉（2s 轮询兜底，保底不丢）。**拒绝只是丢一次提醒，拉的兜底永远能捞回来**。没有这个"本体在别处"的设计，拒绝就是真丢失。

## 5. 拒绝策略的选择逻辑：绑定"调用方是谁"

J8 记过四种策略的**行为**，本篇补**选择逻辑**——核心是问一句：**"拒绝异常抛给谁？那个线程能不能处理？"**

| 策略 | 行为 | 在这里的问题 |
|------|------|--------------|
| **AbortPolicy（选用）** | 抛异常 → tryExecute 捕获返回 false | ✅ 调用方立刻知情，自行决策 |
| CallerRunsPolicy | 谁提交谁自己执行 | ❌ **致命**：提交者是兜底轮询线程/Pub-Sub 订阅线程——让它们执行阻塞操作，正好违反"订阅线程/轮询线程绝不做阻塞操作"的铁律（订阅断了 = 收不到新命令 = 雪崩） |
| DiscardPolicy | 静默丢弃 | ❌ 丢了还不留日志，排查灾难 |
| DiscardOldestPolicy | 丢掉队列里最老的 | ❌ 破坏命令顺序（FIFO 保序是业务要求） |

案例注释里专门点明了这一条：

```java
 * ...的下一次敲门/轮询重试，不阻塞、不 CallerRuns（防止把阻塞任务回灌调用线程）。
```

> **CallerRunsPolicy 的通用误用**：它"表面安全"（任务不会丢），但在两个场景下是毒药——①调用线程是**不能阻塞的关键线程**（事件循环/订阅线程/心跳线程）；②任务执行时间很长（调用线程被拖死）。**它只适合"调用方是廉价线程 + 任务很快"的场景**。

## 6. 背压哲学：一个模式贯穿三层

同一个设计哲学，贯穿案例项目的三个层：

| 层 | 有界的东西 | 满了之后 | 兜底 |
|-----|-----------|---------|------|
| CommandDispatcher | 线程池 8 + 队列 200 | 返回 false（BUSY） | 2s 兜底轮询 |
| WsMessageSender | 每 Channel 待发帧 256 | 返回 false，丢帧 | 心跳/session_sync 补 |
| wsBizExecutor（鉴权/守卫线程池） | 队列 200 | 拒绝 → 鉴权 503 / 守卫 BUSY | 客户端重试握手 |

**统一哲学**：

```text
每一层都给自己划定"我最多承担多少"（有界）
超出的部分明确拒绝（Abort/返回 false）、明确记日志（BUSY warn）、明确留给下一层兜底（轮询/心跳/客户端重试）
—— 绝不无限吸收，绝不静默丢弃
```

> **前端类比**：这三个层 ≈ 前端的"请求队列上限 + 429 快速失败 + 指数退避重试"——网关限流（429）+ 客户端退避重试 + 本地 pending 上限，是同一个模式。

## 7. 为什么 8 个线程就够（容量估算方法）

这个数字不是拍脑袋，依据是**负载特征分析**：

1. **单条任务是 I/O 等待型**：ZPOPMIN 取命令 + SET NX 闸门 + 写帧，每个耗时几毫秒；
2. **并发上限天然受限**：inflight 闸门保证每个实例同一命令同时只有 1 条在途——假设在线客户端 500 个，理论并发上限 500，但同一时刻实际在下发的远少于这个数；
3. **任务太重会自己被闸门挡住**：客户端执行慢 → 闸门 300s 超时强制放行 → 不会无限占着。

**如果开 100 个线程**：多出来的线程只是排队等 inflight 闸门——**真正的并发瓶颈是闸门，不是线程数**，开再多也快不起来，反而增加上下文切换开销。**8 个够用且好运维**。

> **容量估算心法**：先找"真正的瓶颈在哪"（这里是下游闸门），线程数对齐瓶颈即可；无界加线程只会换来上下文切换开销。这与"数据库连接池不是越大越好"是同一个道理。

## 8. 与我们项目的对照：Kafka 背压 vs Redis 敲门

案例项目与我们场景⑥ 解决**同一个问题**（异步任务洪峰），架构不同：

| 维度 | agent-realtime（案例） | 我们场景⑥ |
|------|----------------------|-----------|
| 任务队列 | Redis ZSET（持久化 + 轮询） | **Kafka topic** |
| 触发方式 | 敲门（Pub-Sub 推）+ 2s 轮询（拉兜底） | Kafka 主动推送 |
| 背压方式 | **线程池有界 → 拒绝 → 命令留在 ZSET → 轮询重下发** | **消费能力有限 → 消息积压在 Kafka（LAG 增长）→ 消费端慢慢消化** |
| 拒绝/积压的代价 | 延迟 2s | 积压延迟（LAG 可监控告警） |
| 丢失风险 | 无（ZSET 持久化） | 无（Kafka 持久化 + at-least-once） |

**同一个哲学**：**任务本体在持久化队列里（丢不了）→ 执行端声明自己的容量（有界）→ 超出部分明确拒绝/积压（不吸收）→ 兜底机制保证最终执行（轮询/重试/重平衡）**。区别只是队列载体（Redis ZSET vs Kafka）——选型的分界线：需要延迟排序/复杂捞取用 ZSET，需要高吞吐/消费组扩展用 Kafka。

## 9. 常见坑速查

| # | 坑 | 说明 | 解法 |
|---|-----|------|------|
| 1 | 无界队列 | newFixedThreadPool / new LinkedBlockingQueue() → OOM | ArrayBlockingQueue 显式定长 |
| 2 | 线程数无界 | newCachedThreadPool → 线程爆炸 | 显式 core/max |
| 3 | CallerRunsPolicy 误用 | 阻塞回灌关键线程（订阅/轮询/事件循环） | 换 Abort + 调用方决策 |
| 4 | 拒绝后没有兜底 | 任务真丢了 | 拒绝 ≠ 丢失的前提：本体在持久化队列 + 轮询/重试兜底 |
| 5 | 吞掉 RejectedExecutionException | catch 后不打日志 | 记 warn（BUSY）+ 返回明确信号 |
| 6 | 队列容量拍脑袋 | 200 哪来的？ | 按内存预算反推（每任务大小 × 容量 < 堆预算的可分配份额） |
| 7 | 线程数越多越快 | 瓶颈在下游闸门/DB 时无效 | 先找真瓶颈，线程数对齐瓶颈 |
| 8 | 拒绝策略破坏顺序 | DiscardOldest 丢最老任务 | FIFO 是业务要求时禁用 |

## 11. 动手实验

1. **无界队列 OOM 复演**：newFixedThreadPool(10) 提交 100 万个持引用任务（`-Xmx64m`）→ 观察堆增长/OOM；

## 12. 面试速答

```text
Q：为什么不建议用 Executors 创建线程池？
A：newFixedThreadPool 队列无界（OOM 风险）、newCachedThreadPool 线程数无界（爆炸风险）——
   阿里规约强制手写 ThreadPoolExecutor 并显式指定定长队列 + 拒绝策略。

Q：四种拒绝策略怎么选？
A：先问"拒绝异常抛给谁、那个线程能不能处理"：关键线程（订阅/轮询/事件循环）绝不
   CallerRuns；有兜底重试机制 → Abort 让调用方决策；无兜底且任务可丢 → Discard（但要打日志）；
   保序业务禁用 DiscardOldest。

Q：线程池满了任务会丢吗？
A：取决于架构——如果任务本体在持久化队列（Redis/Kafka/DB），拒绝只是"延迟处理"
   （拒绝→兜底轮询/重试捞回）；如果任务只存在于提交瞬间，拒绝=真丢失。
   所以"有界 + 拒绝"必须配"本体持久化 + 兜底重试"才完整。

Q：线程数设多少合适？
A：先找真瓶颈（CPU 密集 ≈ 核数；I/O 等待型 = 核数 × (1 + 等待/计算)，且受下游并发上限约束）；
   瓶颈在下游时线程再多也快不起来，反而增加上下文切换。
```

## 13. 审计实战：本项目 LlmCallGuard 的整改实录（2026-11-20）

> 按本篇的"审计自己项目"实验，对 [`LlmCallGuard`](../../backend/src/main/java/com/aiexplorer/researchagent/infrastructure/llm/LlmCallGuard.java)（[网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/backend/src/main/java/com/aiexplorer/researchagent/infrastructure/llm/LlmCallGuard.java)）做了整改——**J13 坑 2 在本项目里的活教材，已修复**。`mvn compile` 通过。

### 13.1 发现了什么

```java
// ❌ 整改前（LlmCallGuard:43）
this.callExecutor = Executors.newCachedThreadPool(runnable -> { ... });
```

`newCachedThreadPool` = **坑 2 的活实例**：`core=0 / max=Integer.MAX_VALUE / SynchronousQueue`——**线程数无界**，并发洪峰时线程跟着暴涨。

### 13.2 为什么改（三条理由）

| # | 理由 | 出处 |
|---|------|------|
| 1 | **规约**：《阿里巴巴 Java 开发手册》强制禁止 Executors 快捷工厂——它隐藏了 core/max/queue 三个关键参数 | §3 |
| 2 | **无界风险**：并发 LLM 调用洪峰 → 线程数失控（当时的缓解因素：入口受控（Kafka 串行+状态守卫）、单线程生命周期短（timeout+60s 回收）、daemon——所以没炸，但风险是"未知"而非"有界"） | §3 坑 2 |
| 3 | **背压哲学**：容量应显式声明（"我最多承担多少"），而不是隐含在工厂里 | §6 |

### 13.3 改成了什么

```java
// ❌ 整改前
this.callExecutor = Executors.newCachedThreadPool(runnable -> {
    Thread workerThread = new Thread(runnable, "llm-call-worker");
    workerThread.setDaemon(true);
    return workerThread;
});

// ✅ 整改后：显式 ThreadPoolExecutor
private static final int MAX_CONCURRENT_CALLS = 64;      // ★ 给线程数画天花板

this.callExecutor = new ThreadPoolExecutor(
        0, MAX_CONCURRENT_CALLS, 60L, TimeUnit.SECONDS,  // core=0 按需创建 / max=64 天花板 / 60s 回收
        new SynchronousQueue<>(),                        // ★ 保留：不排队，保超时语义
        runnable -> { ...daemon... },                    // 保留：命名 + daemon
        new ThreadPoolExecutor.AbortPolicy());           // ★ 新增：超 64 并发快速失败
```

### 13.4 三个关键设计决策

| 决策 | 为什么 |
|------|--------|
| **保留 `SynchronousQueue`（不排队）** | 排队会让 `future.get(timeout)` 的超时语义失真（排队时间混进超时）——cached 池的这个特征是**刻意选择**，保留 |
| **新增 `max=64` 天花板** | 并发上限估算：LLM 并发受消费入口控制（量级几十），64 = 留足余量的硬顶——风险从"未知"变"有界" |
| **新增 `AbortPolicy`** | 超 64 并发 → 抛 `RejectedExecutionException` → 被 `call()` 的 `catch (Exception)` 接住 → 记失败原因 → 重试/降级——**治理层正好接得住拒绝**（这就是"Abort + 有兜底的调用方"的配对，§5 的选择逻辑） |

### 13.5 好处（四条）

1. **线程数有界**：风险从"未知"变成"≤ 64"（最坏情况可控）；
2. **拒绝可观测**：超限走 AbortPolicy 抛异常 → 治理层记 warn 日志（而不是无声暴涨）；
3. **合规**：满足《阿里巴巴 Java 开发手册》强制条款；
4. **超时语义零变化**：SynchronousQueue 保留，行为对调用方完全兼容（编译通过，接口未变）。

> **审计方法论回顾**：`grep Executors\. → 读上下文（为什么用它/风险量化）→ 修复（显式化 + 画天花板）→ 编译验证 → 沉淀`——这套流程适用于任何"学了规范 → 审计项目 → 整改"的闭环。

## 14. 一句话总结

```text
"有界" = 线程数（8）和队列（200）都被硬性封顶，满了立刻拒绝而不是无限堆积；
它是"有界 + 快速拒绝（Abort）+ 调用方决策（返回 false）+ 兜底重试（2s 轮询）"背压哲学的实例：
命令本体在持久化队列里丢不了——拒绝只是延迟 2 秒，
用确定性的短暂延迟，换掉不确定的 OOM 风险——这是长连接服务应对消息洪峰的标准姿势。
```
