## 0. 教材原文（先通读一遍）

**抛的人**（13 行）：

```java
public class TaskNotFoundException extends RuntimeException {
    public TaskNotFoundException(UUID taskId) {
        super("Research task not found: " + taskId);

}
```

**接的人**（节选）：

```java
public class ApiExceptionHandler {

```

**回信的格式**：`ApiError`（record——J1 写的"60 行"）。

## 1. 异常是什么？——"错误被打包成了对象"

```java
throw new TaskNotFoundException(taskId);
//    ↑ 错误对象携带三样东西：类型（什么错）/ 消息（细节）/ 堆栈（从哪炸的）
```

**两条道设计**：正常结果走 `return`、错误走 `throw`——**互不混杂**（对比 C 时代"错误码挤在返回值里"）。

**前端对照**：`throw new Error("...")`——同款"打包往上扔"（JS 更宽松：能扔任何值；Java 严格：只能扔 `Throwable` 子类）。

---

## 2. 异常家族树

```text
Throwable
├── Error          —— 不可救药（OutOfMemoryError……"别接，接了也白接"）
└── Exception
    ├── 【受检 Checked】IOException / SQLException……（编译器强制处理）
    └── RuntimeException（非受检 Unchecked）
           └── TaskNotFoundException（业务异常）
```

**"是不是异常"由族谱决定**——异常就是普通类，"受检/非受检"只看**继承线**：
- `extends Exception`（且非 RuntimeException 后代）→ **受检**
- `extends RuntimeException` → **非受检**

---

## 3. ★ 受检 vs 非受检：一条黄金判据

> **"调用者能做的动作，是否因错误类型而异、且值得被编译器提醒？"**

| 异常 | 直接调用者能干嘛 | 判定 |
|------|-----------------|------|
| `IOException`（文件读不到） | **能**——换路径 / 重试 / 降级 | **受检**（逼他表态有价值）|
| `TaskNotFoundException` | **啥也干不了**——只有最外层"值班室"能翻译成 404 | **非受检**（放它安静冒泡）|

**改成受检的"多米诺推演"**：编译器当场翻脸 → catch（Service 里无事可做 → 包装重抛=绕圈）或 throws（传染到 Controller 及更上层）→ **"异常污染"**（全链被迫声明，哪怕不关心）——**这就是选 `RuntimeException` 的全部原因**。

---

## 4. `extends RuntimeException` = "身份认领"

- **一认祖，自动获得**：能被 throw / 带堆栈 / 带 message / 能被 catch——**全是继承来的能力**（所以 13 行就够）；
- **JS 对照**：`class MyError extends Error {}`——**同款"认祖归宗"**（不继承 Error，`throw` 出去连堆栈都没有）。

---

## 5. 受检的用法补遗（本轮追问）

**"就地 catch、不往上 throws"——行！** 编译器只要求**二选一**（catch 或 throws）。但 **catch 之后干什么** 才是关键：

```java
} catch (IOException e) {
    return "默认配置";                                   // ① 真有意义的处理（降级/兜底）✓
    // throw new IllegalStateException("读取失败", e);   // ② 包装重抛（翻译成非受检）✓
    // e.printStackTrace();                             // ③ 吞掉 = 反模式 ⚠️
}
```

**判据**：catch 块里**有没有真正有意义的事**——没有就别 catch（"受检被嫌弃"的根源：逼人 catch 但无事可做 → 大量"假处理"）。

**项目现状**：**全非受检**（自定义异常仅 `TaskNotFoundException`）；**现代趋势**：JDK 新 API 少受检、Spring 处处"翻译"成非受检（JPA → `DataAccessException`）、"受检异常是设计失误吗"是社区 20 年公案。

---

## 6. 异常的信息设计——"错误也是数据"

```java
super("Research task not found: " + taskId);   // message 带关键上下文（id）——给人排障用
```

好 message：不啰嗦 + 带 id/参数——最终流向：日志（内部）与 `ApiError`（外部）。

---

## 7. 值班室：`@RestControllerAdvice`（Javadoc 即提纲）

> *"应用启动时被 Spring 扫描并注册；请求处理中抛出的异常'冒泡'到 DispatcherServlet 时，按类型查表派发到这里。没有任何业务代码显式调用——框架通过反射回调的（'值班室'模式）。"*

**三个关键词**：**注册**（启动装配——J2）→ **冒泡**（异常层层上飞）→ **查表派发**（拿类型查 handler 表 → 反射回调）。

**★ 它又是"钩子"**（J2 家族成员）：`@ExceptionHandler` = "声明式挂钩"，异常发生时框架替你回调。

**前端对照**：Express 错误中间件 / React `ErrorBoundary` / Vue `app.config.errorHandler`——"集中式错误处理"同款。

---

## 8. 翻译表：五种 handler

| 抛出的异常 | → HTTP | 错误码 | 备注 |
|---|---|---|---|
| `TaskNotFoundException` | **404** | `TASK_NOT_FOUND` | 业务异常（J3 的 `orElseThrow` 抛的）|
| `MethodArgumentNotValidException` | **400** | `VALIDATION_ERROR` | **带 fields 明细**（哪个字段/为什么）|
| `HttpMessageNotReadableException` | 400 | `MALFORMED_REQUEST` | JSON 坏 / **枚举值非法** |
| `IllegalStateException` | 400 | `INVALID_STATE` | JDK 自带异常也有专属翻法 |
| `Exception`（兜底） | **500** | `INTERNAL_ERROR` | 最后一道网 |

**每一份响应都是 `ApiError`**——"错误响应统一形状"（J1 的 record 在此使命达成）。

---

## 9. 匹配优先级："最具体优先"

同匹配多个 handler 时（TaskNotFound **同时**匹配"精确 handler"和"Exception 兜底"）——**继承树就近者赢** → 走 404（否则全被兜底吞成 500）。

**前端同款母题**：`instanceof` 梯子 / 路由匹配（`/tasks/:id` 赢 `/tasks/*`）/ CSS 优先级。

## 10. 兜底三讲究

```java
@ExceptionHandler(Exception.class)
@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
public ApiError handleUnexpected(Exception exception, HttpServletRequest request) {
    log.error("未处理异常: {} {}", request.getMethod(), request.getRequestURI(), exception);  // ① 日志留痕（内部：全尸）
    return ApiError.of("INTERNAL_ERROR", "服务器内部错误", request.getRequestURI());            // ② 响应脱敏（外部：人话）
}
// ③ 覆盖一切：新异常类型没专属 handler 时，它接住
```

**"内外有别"的三层理由**：**安全泄露**（堆栈=免费侦察情报：框架版本/表名/路径）/ **受众错配**（堆栈给开发（日志的活）；响应给前端（人话+机器码））/ **信息流向**（内部可查、外部无感）。

**彩蛋**：Spring Boot 的 `server.error.include-stacktrace` **默认 `never`**——行业教训的结晶。

## 11. ⚠️ 异常会不会"挂掉整个服务"？——不会

| 层 | 机制 |
|----|------|
| **① 线程隔离** | 每请求一个 Tomcat 工作线程（`nio-8080-exec-N`）——异常最多冒到"这一个线程的顶层" |
| **② 框架兜底** | DispatcherServlet 的"响应生成"外圈有 try-catch 外套 + 我们的兜底 handler——**异常到不了线程顶层就被翻译** |
| **结论** | **单请求失败、服务照跑、其他接口无感知** ✓ |

**灾难分级**（什么才会真挂）：

| 情况 | 后果 |
|------|------|
| 普通 Exception 家族 | ✗ 不会（本主题）|
| **Error 家族**（OOM……） | ⚠️ 可能拖垮进程（"家族树的另一支"）|
| **线程池耗尽** | ⚠️ "假死"（资源问题，非异常问题）|
| **★ 异步线程** | ⚠️ **"例外世界"**——请求线程有框架兜，**自开的异步线程抛异常=无人兜 → 静默失败**（J8 并发课展开）|

## 12. 实战实验记录（2026-10-04，"值班室"实地参观）

**命令约定**：`curl.exe -s -i`（状态码 + 响应体一起看）+ JSON 文件法（`Set-Content -Encoding ASCII`——避开转义与 BOM）。

| # | 实验 | 实测结果 | 判定 |
|---|------|---------|------|
| 1 | `GET /api/tasks/0000...`（不存在） | **404** + `{"code":"TASK_NOT_FOUND","message":"Research task not found: 00000000-…","path":"…","retryable":false}` | ✅ 全中 |
| 2 | POST 空 title | **400** + `{"code":"VALIDATION_ERROR","fields":[{"field":"title","reason":"title 不能为空"}]}` | ✅ 全中 |
| 3 | POST 坏 JSON（缺逗号） | **400** + `MALFORMED_REQUEST` | ✅ |
| 3b | POST 枚举 `TURBO` | **400** + `MALFORMED_REQUEST`（同一位 handler）| ✅ |

**彩蛋**：响应体里的 `"retryable":false` 与 `"timestamp"`——**J1 亲手往 `ApiError` 里加的字段**，此刻正在真实错误响应里"值班"（**J1 → J4 闭环**）。

## 附：本课一句话总结

1. **异常 = 错误的对象化**（类型 + 消息 + 堆栈；"两条道"设计）；
2. **受检/非受检由继承决定**——判据："**调用者能做的动作是否因错误而异**"；
3. **业务异常选非受检**——不被"处理义务"传染，安静冒泡到值班室；
4. **值班室 = 钩子家族成员**——注册 → 冒泡 → 查表派发（最具体优先）；
5. **兜底"内外有别"**——日志留痕、响应脱敏；
6. **异常不挂服务**——线程隔离 + 框架兜底（唯有 Error 家族与异步线程例外）。
