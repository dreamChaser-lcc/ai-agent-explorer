## 1. 异常是什么？——"错误被打包成了对象"

```java
throw new TaskNotFoundException(taskId);
//    ↑ 错误对象携带三样东西：类型（什么错）/ 消息（细节）/ 堆栈（从哪炸的）
```

**两条道设计**：正常结果走 `return`、错误走 `throw`——**互不混杂**（对比 C 时代"错误码挤在返回值里"）。

**前端对照**：`throw new Error("...")`——同款"打包往上扔"（JS 更宽松：能扔任何值；Java 严格：只能扔 `Throwable` 子类）。

---

## 2. 异常家族树

```text
Throwable
├── Error          —— 不可救药（OutOfMemoryError……"别接，接了也白接"）
└── Exception
    ├── 【受检 Checked】IOException / SQLException……（编译器强制处理）
    └── RuntimeException（非受检 Unchecked）
           └── TaskNotFoundException（业务异常）
```

**"是不是异常"由族谱决定**——异常就是普通类，"受检/非受检"只看**继承线**：
- `extends Exception`（且非 RuntimeException 后代）→ **受检**
- `extends RuntimeException` → **非受检**

---

## 3. ★ 受检 vs 非受检：一条黄金判据

> **"调用者能做的动作，是否因错误类型而异、且值得被编译器提醒？"**

| 异常 | 直接调用者能干嘛 | 判定 |
|------|-----------------|------|
| `IOException`（文件读不到） | **能**——换路径 / 重试 / 降级 | **受检**（逼他表态有价值）|
| `TaskNotFoundException` | **啥也干不了**——只有最外层"值班室"能翻译成 404 | **非受检**（放它安静冒泡）|

**改成受检的"多米诺推演"**：编译器当场翻脸 → catch（Service 里无事可做 → 包装重抛=绕圈）或 throws（传染到 Controller 及更上层）→ **"异常污染"**（全链被迫声明，哪怕不关心）——**这就是选 `RuntimeException` 的全部原因**。

---

## 4. `extends RuntimeException` = "身份认领"

- **一认祖，自动获得**：能被 throw / 带堆栈 / 带 message / 能被 catch——**全是继承来的能力**（所以 13 行就够）；
- **JS 对照**：`class MyError extends Error {}`——**同款"认祖归宗"**（不继承 Error，`throw` 出去连堆栈都没有）。

---

## 5. 受检的用法补遗（本轮追问）

**"就地 catch、不往上 throws"——行！** 编译器只要求**二选一**（catch 或 throws）。但 **catch 之后干什么** 才是关键：

```java
} catch (IOException e) {
    return "默认配置";                                   // ① 真有意义的处理（降级/兜底）✓
    // throw new IllegalStateException("读取失败", e);   // ② 包装重抛（翻译成非受检）✓
    // e.printStackTrace();                             // ③ 吞掉 = 反模式 ⚠️
}
```

**判据**：catch 块里**有没有真正有意义的事**——没有就别 catch（"受检被嫌弃"的根源：逼人 catch 但无事可做 → 大量"假处理"）。

**项目现状**：**全非受检**（自定义异常仅 `TaskNotFoundException`）；**现代趋势**：JDK 新 API 少受检、Spring 处处"翻译"成非受检（JPA → `DataAccessException`）、"受检异常是设计失误吗"是社区 20 年公案。

## 6. 异常的信息设计——"错误也是数据"

```java
super("Research task not found: " + taskId);   // message 带关键上下文（id）——给人排障用
```

好 message：不啰嗦 + 带 id/参数——最终流向：日志（内部）与 `ApiError`（外部）。

## 7. 值班室：`@RestControllerAdvice`（Javadoc 即提纲）

> *"应用启动时被 Spring 扫描并注册；请求处理中抛出的异常'冒泡'到 DispatcherServlet 时，按类型查表派发到这里。没有任何业务代码显式调用——框架通过反射回调的（'值班室'模式）。"*

**三个关键词**：**注册**（启动装配——J2）→ **冒泡**（异常层层上飞）→ **查表派发**（拿类型查 handler 表 → 反射回调）。

**★ 它又是"钩子"**（J2 家族成员）：`@ExceptionHandler` = "声明式挂钩"，异常发生时框架替你回调。

**前端对照**：Express 错误中间件 / React `ErrorBoundary` / Vue `app.config.errorHandler`——"集中式错误处理"同款。

## 8. 翻译表：五种 handler

| 抛出的异常 | → HTTP | 错误码 | 备注 |
|---|---|---|---|
| `TaskNotFoundException` | **404** | `TASK_NOT_FOUND` | 业务异常（J3 的 `orElseThrow` 抛的）|
| `MethodArgumentNotValidException` | **400** | `VALIDATION_ERROR` | **带 fields 明细**（哪个字段/为什么）|
| `HttpMessageNotReadableException` | 400 | `MALFORMED_REQUEST` | JSON 坏 / **枚举值非法** |
| `IllegalStateException` | 400 | `INVALID_STATE` | JDK 自带异常也有专属翻法 |
| `Exception`（兜底） | **500** | `INTERNAL_ERROR` | 最后一道网 |

**每一份响应都是 `ApiError`**——"错误响应统一形状"（J1 的 record 在此使命达成）。

---

## 9. 匹配优先级："最具体优先"

同匹配多个 handler 时（TaskNotFound **同时**匹配"精确 handler"和"Exception 兜底"）——**继承树就近者赢** → 走 404（否则全被兜底吞成 500）。

**前端同款母题**：`instanceof` 梯子 / 路由匹配（`/tasks/:id` 赢 `/tasks/*`）/ CSS 优先级。

## 10. 兜底三讲究

```java
@ExceptionHandler(Exception.class)
@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
public ApiError handleUnexpected(Exception exception, HttpServletRequest request) {
    log.error("未处理异常: {} {}", request.getMethod(), request.getRequestURI(), exception);  // ① 日志留痕（内部：全尸）
    return ApiError.of("INTERNAL_ERROR", "服务器内部错误", request.getRequestURI());            // ② 响应脱敏（外部：人话）
}
// ③ 覆盖一切：新异常类型没专属 handler 时，它接住
```

**"内外有别"的三层理由**：**安全泄露**（堆栈=免费侦察情报：框架版本/表名/路径）/ **受众错配**（堆栈给开发（日志的活）；响应给前端（人话+机器码））/ **信息流向**（内部可查、外部无感）。

**彩蛋**：Spring Boot 的 `server.error.include-stacktrace` **默认 `never`**——行业教训的结晶。

## 11. ⚠️ 异常会不会"挂掉整个服务"？——不会

| 层 | 机制 |
|----|------|
| **① 线程隔离** | 每请求一个 Tomcat 工作线程（`nio-8080-exec-N`）——异常最多冒到"这一个线程的顶层" |
| **② 框架兜底** | DispatcherServlet 的"响应生成"外圈有 try-catch 外套 + 我们的兜底 handler——**异常到不了线程顶层就被翻译** |
| **结论** | **单请求失败、服务照跑、其他接口无感知** ✓ |

**灾难分级**（什么才会真挂）：

| 情况 | 后果 |
|------|------|
| 普通 Exception 家族 | ✗ 不会（本主题）|
| **Error 家族**（OOM……） | ⚠️ 可能拖垮进程（"家族树的另一支"）|
| **线程池耗尽** | ⚠️ "假死"（资源问题，非异常问题）|
| **★ 异步线程** | ⚠️ **"例外世界"**——请求线程有框架兜，**自开的异步线程抛异常=无人兜 → 静默失败**（J8 并发课展开）|

## 补充：思考题与答案（课堂问答收录）

**题 1（想象题）**——假如把 `TaskNotFoundException` 改成 `extends Exception`（受检），会引发什么连锁反应？

**答**：**多米诺骨牌推演**：

1. **编译器当场翻脸**：`.orElseThrow(() -> new TaskNotFoundException(taskId))` 处报 `Unhandled exception`——受检异常必须"表态"（catch 或 throws）；
2. **二选一都难受**：
   - **catch**：Service 层对"任务不存在"**什么都干不了**（它的职责就是查库）——只能 `throw new RuntimeException(e)` 包装重抛——**绕一圈又变回非受检**；
   - **throws**：把处理义务甩给调用者 → **Controller 也得 `throws`** → 再往上……**一路传染**；
3. **"异常污染"全景**：全链路被迫声明 `throws TaskNotFoundException`——哪怕它们根本不关心、也处理不了。而且 `throws` 是**方法契约**的一部分——改一处、动全链。

**★ 黄金判据**：**"直接调用者真的能对这个错误做点什么"——才配得上受检**。`IOException`（换路径/重试=有得做）→ 受检值得；`TaskNotFoundException`（全世界只有"值班室"能翻 404 一个动作）→ **非受检**（安静冒泡直达）。

**题 2（设计题）**——兜底 handler 为什么"日志打全、响应只说一句"？

**答**：**"内外有别"——把细节给该看的人**。三个层次：

| # | 若把堆栈塞进响应 | 后果 |
|---|---|---|
| 1 | **安全泄露**（最致命） | 堆栈=**免费侦察情报**：框架与版本（挑对应漏洞）、表名（库结构暴露）、包名/路径（内部结构暴露） |
| 2 | **受众错配** | 前端用户看不懂 `NullPointerException`——**技术细节是给开发/运维的（那是日志的读者）**；响应只需要"机器码 + 人话" |
| 3 | **信息流向错** | 正确姿势：`log.error(..., exception)`（内部：全尸+堆栈，SLF4J 末参=堆栈惯例）；响应只说 `"服务器内部错误"`（外部：零细节）——**日志留痕 + 响应脱敏：内部可查、外部无感** |

**彩蛋**：Spring Boot 的 `server.error.include-stacktrace` **默认 `never`**——行业事故换来的默认值。

**共同母题**：**题 1 = 把"处理义务"给"能处理的人"；题 2 = 把"细节信息"给"该看的人"——都是"分工"。**

## 补充：Spring 异常翻译——用本课三条规则看懂 @Repository（2026-10-27 课堂问答）

> 学员提问："结合异常体系复习 @Repository 的异常转换，还是不太理解"
>
> 本节只用本课已学的三条规则解释，不需要任何新知识。

### 锚点：本课三条规则

```text
规则①（§1）：异常就是普通对象——能 new、能 throw、能被 catch
规则②（§2 家族树）：catch (A e) 只能接住【A 或 A 的子类】——按继承树匹配
规则③（§7/§9）：全局处理器按"最具体优先"接异常
```

### 两棵树的问题（为什么业务层接不住数据库异常）

```text
Hibernate 家族树：                      Spring 家族树：
RuntimeException                       RuntimeException
  └── HibernateException                 └── DataAccessException
        └── ConstraintViolationException       └── DataIntegrityViolationException
                                                       ↑ 全局处理器只想接这棵
两棵树【没有任何继承关系】
→ catch (DataIntegrityViolationException) 永远匹配不上 Hibernate 抛的对象
→ 落到 Exception 兜底 → 500
```

### "翻译"的代码本质（去魔法）

```java
// @Repository 让 Spring 给 DAO 包一层代理，代理的代码逻辑（伪代码）：
public void save(TaskEntity task) {
    try {
        真正的save(task);                          // 你写的 DAO
    } catch (RuntimeException e) {                 // 规则①：异常能被 catch
        if (e instanceof HibernateException) {
            // ★ "翻译"就这一行：new 一个 Spring 家族的新异常，旧的塞进 cause
            throw new DataIntegrityViolationException(e.getMessage(), e);
        }
        throw e;                                   // 翻不了的，原样抛
    }
}
```

| 规则 | 在这里的体现 |
|---|---|
| ① 异常是对象 | `new DataIntegrityViolationException(...)` 就是 new 个普通对象再 throw |
| ② catch 按继承树 | 代理先接 Hibernate 树的（同树）；新抛的换到了 Spring 树 |
| ③ 最具体优先 | 处理器接住 `DataIntegrityViolationException` → 400/409 而非 500 |

### 场景⑨ 的 409 套同一个模子

```text
乐观锁冲突：Hibernate 抛 StaleObjectStateException（Hibernate 树）
  ↓ @Repository 代理翻译
new ObjectOptimisticLockingFailureException（Spring 树）
  ↓ 最具体优先
@ExceptionHandler(OptimisticLockingFailureException.class) → 409
```

实测：`ApiExceptionHandler` catch 的全是 Spring 树；Hibernate 的 `StaleObjectState` 全项目 0 处——**上层永远只跟 Spring 树打交道，Hibernate 树在 DAO 边界就被换掉了**。

### @Repository 注解本身一行逻辑都没有

```text
J7 §八："注解不加功能，功能来自读标签的人"
读 @Repository 标签的是 PersistenceExceptionTranslationPostProcessor：
  启动时扫描到标了 @Repository 的 bean → 生成上面那个"带 try-catch 翻译"的代理类
想亲眼看到：打印 dao.getClass() → 类名带 $$SpringCGLIB$$（代理类，运行时生成）
```

### 困惑对号入座

| 困惑 | 答案 |
|---|---|
| "翻译是什么意思" | catch 旧对象 → new 新对象 → 抛出去（规则①） |
| "谁做的翻译" | Spring 启动时生成的代理类（@Repository 是信号） |
| "代理类在哪" | 运行时动态生成，`dao.getClass()` 类名带 `$$SpringCGLIB$$` |
| "为什么 catch 不住" | 规则②：两棵继承树不搭界 |

### 追问：@Repository 要和 @ExceptionHandler 一起结合使用吗？

**不是"配对搭档"，是"流水线上下游"**——各自独立有用，组合起来才完整：

```text
数据库错误
  → 【@Repository：翻译官】数据库方言 → Spring 统一异常
  → 【@ExceptionHandler：前台接待】Spring 统一异常 → HTTP 语义（409/400）
```

**四种组合效果**（数据库异常场景）：

| @Repository | @ExceptionHandler | 结果 |
|---|---|---|
| ✅ | ✅ | **409**（语义正确，场景⑨） |
| ✅ | ❌ | 翻译了但没人处理 → 500 |
| ❌ | ✅ | 具体类型接不住 → 落 Exception 兜底 → 500（语义错） |
| ❌ | ❌ | 500 |

**两个纠正**：

1. `@ExceptionHandler` 不是为数据库异常而生的——它 11 个 handler 里只有 2 个和数据库有关，
   其余处理参数校验/业务异常（价值独立存在）
2. `@Repository` 的价值也独立存在——统一异常体系让 Service 层能
   `catch DataAccessException` 做补偿，与有没有 Handler 无关

### 实战实验：四端点对照（2026-10-27 实测）

**实验设计**：两个 DAO 代码逐字相同（执行 `SELECT * FROM table_that_does_not_exist_xyz` 必然失败的 SQL），
唯一差异是注解——`TranslatedDao` 标 `@Repository`，`UntranslatedDao` 标 `@Component`。

**实测结果**：

| 端点 | 含义 | 实测结果 |
|---|---|---|
| ① `GET /api/demo/translate/repo/class` | 有 @Repository，Controller catch 看类名 | **`org.springframework.dao.InvalidDataAccessResourceUsageException`**（Spring 树 ✅ 被翻译）<br>cause 链：`[Spring的, Hibernate的SQLGrammarException, H2的JdbcSQLSyntaxErrorException]` |
| ② `GET /api/demo/translate/plain/class` | 无 @Repository，同样 catch | **`org.hibernate.exception.SQLGrammarException`**（Hibernate 树 ❌ 未翻译）<br>cause 链：`[Hibernate的, H2的]` |
| ③ `GET /api/demo/translate/repo/http` | 有 @Repository，不 catch 走全局处理器 | **HTTP 400** + `{"code":"DATA_ACCESS_ERROR","message":"数据访问失败：Table ... not found"}` |
| ④ `GET /api/demo/translate/plain/http` | 无 @Repository，不 catch | **HTTP 500**（落 `Exception` 兜底） |

**①② 对比就是"翻译"的肉眼证据**：

```text
同一个错误（表不存在）：
  有 @Repository → 抛出的对象属于 Spring 家族（org.springframework.dao.*）
  无 @Repository → 抛出的对象属于 Hibernate 家族（org.hibernate.exception.*）
  —— 两个对象【都是新的 RuntimeException 子类实例】，但继承树不同
```

**③④ 对比就是"接不接得住"的证据**：

```text
handler：@ExceptionHandler(DataAccessException.class)   ← catch 的是 Spring DAO 树的根
  ③ 异常在 Spring 树上（是根的子类）→ J4 规则②匹配成功 → 400
  ④ 异常在 Hibernate 树上（与根无继承关系）→ 匹配失败 → Exception 兜底 → 500
```

**③④ 的继承链分析（规则②逐层看）**：

```text
③ 的异常（被翻译后）：
  InvalidDataAccessResourceUsageException
    extends ... extends DataAccessException
    → 是根类的【子类】 → handler 匹配成功 → 400

④ 的异常（未翻译）：
  SQLGrammarException
    extends HibernateException
      extends RuntimeException
    → 与 DataAccessException【没有任何继承关系】→ 匹配失败 → 500
```

**一句话总结这组实验**：

```text
两个测试共享同一个 handler，结果 400 vs 500——
唯一的变量就是那个 @Repository。
```

**两个附加知识点**：

1. **翻译的具体类型由"翻译表"决定，不是固定映射**：

```text
JPA 路径（@Repository + EntityManager）
  → InvalidDataAccessResourceUsageException
JdbcTemplate 路径
  → BadSqlGrammarException（在 org.springframework.jdbc 包，不在 dao 包）
```

   家族对了，具体类看翻译表——**本次实验我自己就踩了两次坑**：
   一开始把 handler 写成 `BadSqlGrammarException`（编译才发现它根本不在
   `org.springframework.dao` 包）；实测又发现 JPA 路径产出的类型根本不是它。
   两次都是"翻译表"知识缺失的学费。

2. **catch 根类 `DataAccessException` 不会抢走 409 handler**——J4 §9"最具体优先"：
   `OptimisticLockingFailureException`/`DataIntegrityViolationException` 的
   子类 handler 仍然优先命中。**catch 根类 = 兜住整棵树但不影响更精确的分流**
   （这本身就是规则②③的活用法）。

### 现在你能给别人讲的完整链路

```text
一条 SQL 出错
  ↓ JDBC 层：H2 抛 JdbcSQLSyntaxErrorException（驱动家族）
  ↓ Hibernate 层：包成 SQLGrammarException（Hibernate 家族）
  ↓ 【@Repository 的翻译代理】：new 一个 InvalidDataAccessResourceUsageException
  │   （Spring 家族），旧的塞进 cause —— 翻译完成
  ↓ Controller 冒泡
  ↓ 全局处理器：@ExceptionHandler(DataAccessException.class)
  │   规则②：是根的子类 → 接住
  ↓ HTTP 400 + "数据访问失败：Table not found"

没有 @Repository：第 ③ 步不存在 → handler 匹配失败 → 500
```

### 追问：DAO 只声明了 @Repository，我怎么知道该 @ExceptionHandler 哪个类？

**诚实回答：推不出来——翻译是运行时行为，写码时无法精确预知（教的人也会猜错）。**

#### 企业里确定它的四个方法

**方法 1：实测打印（最直接）**

```java
try { dao.xxx(); } catch (Exception e) {
    log.error("实际类型：{}", e.getClass().getName());   // 看控制台抄下来
}
// 或：故意不写 handler → 看兜底 Exception handler 的日志里打的类型
// 本课演示端点 /api/demo/translate/repo/class 的 exceptionClass 字段就是干这个的
```

**方法 2：分层策略，不追求精确预知（企业主流）**

```java
// 第一层：明确业务语义 → 精确 handler
@ExceptionHandler(OptimisticLockingFailureException.class)   // 并发 → 409
@ExceptionHandler(DataIntegrityViolationException.class)     // 唯一键 → 409

// 第二层：数据库异常兜底 → catch 根类【不需要知道具体子类】
@ExceptionHandler(DataAccessException.class)                 // → 400

// 第三层：完全未知 → 兜底
@ExceptionHandler(Exception.class)                           // → 500
```

根类 handler 靠规则②接住整棵树——**根本不需要预知具体类型**（本课最终方案）。

**方法 3：查 Spring Javadoc 类树**

```text
org.springframework.dao.DataAccessException → All Known Subclasses
IDEA：类名上 Ctrl+H（Type Hierarchy）
```

**方法 4：经验速查表**

| 数据库错误 | JPA 路径常见翻译结果 |
|---|---|
| 唯一键冲突 | DuplicateKeyException / DataIntegrityViolationException |
| 语法错/表不存在 | InvalidDataAccessResourceUsageException |
| 乐观锁冲突 | ObjectOptimisticLockingFailureException |
| 死锁/拿不到锁 | CannotAcquireLockException |
| 连不上库 | DataAccessResourceFailureException |
| 期望 1 行得 0 行 | EmptyResultDataAccessException |

⚠️ JPA 路径与 JdbcTemplate 路径的映射可能不同（本课实测即证据）。

#### 心智模型纠正

```text
隐含假设："写码前应该精确知道是哪个类"
实际：     "翻译是运行时行为，用【分层策略】而非【精确预知】"

标准工作流：
  ① 先写根类 DataAccessException 兜底（保证数据库错误不 500）
  ② 需要特定语义（如 409 重试）→ 实测打印类型 → 加精确 handler
  ③ 精确 handler 自动优先（最具体优先），根类只接剩下的
```

#### 本课实战就是活教材

```text
我猜：表不存在 → BadSqlGrammarException → 写了 handler
  踩坑①：编译失败——它在 org.springframework.jdbc 包不在 dao 包
  踩坑②：实测发现 JPA 路径产出的是 InvalidDataAccessResourceUsageException
  最终：放弃精确匹配 → 根类 DataAccessException → 一次搞定
连"教的人"都要靠实测纠正——这就是真实开发节奏：猜 → 实测 → 根类兜底
```

### 再追问：先不加具体 handler，让它 500 看日志，可以吗？

**方向对一半——漏了"根类兜底"这一层（三层不是两层）。**

```text
两层（漏了中间层）：不加具体 → 500 → 看日志 → 加 or 不加（继续 500）
三层（正确）：
  ① 精确 handler（业务语义，如 409 请重试）
  ② ★ 根类 DataAccessException 兜底（400）← 起步第一天就该写
  ③ Exception 兜底（500）
```

**为什么不能放任 500**：

```text
500 语义 = "服务器内部错误" → 前端以为系统坏、运维告警、可能触发紧急排查
但数据库异常往往是"请求侧问题"（重复提交 / 违反约束 / 语法错）
例：用户重复提交 → 409"任务已存在"（停止重试）远好于 500"系统繁忙"（再点几次）
```

**修正后的标准节奏**：

```text
起步：写根类 DataAccessException（400）+ Exception 兜底（500）
     → 所有数据库错误至少 400，不吓人
迭代：需要精确语义 → 实测类型 → 加精确 handler（自动优先于根类）
"不加具体的" = 走根类 400 + 通用提示 —— 可接受
```

**日志坑（实测验证）**：

```text
@ExceptionHandler 接住后，Spring 不再打默认 ERROR 日志！
兜底 handler 必须自己 log——本项目有（ApiExceptionHandler 154 行）：
  log.error("未处理异常: {} {}", method, uri, exception);
       → 异常对象当参数 → 完整堆栈（含具体类型）进日志
很多项目踩过：兜底忘 log → 生产排障时日志空白
```

### 学员实录：注释掉 handler 看堆栈，反推该 catch 谁（2026-10-27）

学员自己做了实验：把 `DataAccessException` handler 注释掉 → 访问
`/api/demo/translate/repo/http` → 拿到 500 堆栈 → 问"从这段日志怎么知道该
`@ExceptionHandler` 哪个类？"——**答案就在日志里，三步读法**：

#### 读日志三步法

```text
第①步：第一行就是最精确的答案（直接抄）
  org.springframework.dao.InvalidDataAccessResourceUsageException
  → @ExceptionHandler(InvalidDataAccessResourceUsageException.class) 必然拦住

第②步：看包名往上找根类（更聪明）
  org.springframework.dao.* = Spring DAO 家族
  家族根 = DataAccessException
  → 用根类 = 规则②接住整棵树（DuplicateKey/死锁/连接失败一并兜住）

第③步：IDEA 上 Ctrl+H（Type Hierarchy）确认继承
  InvalidDataAccessResourceUsageException
    extends NonTransientDataAccessException
      extends DataAccessException   ← 根
```

**选择**：要特定语义（409）抄精确类名；只兜底（400）用根类。

#### 该 500 堆栈同时是"翻译现场"的完整录像（理论 → 实证对照）

| 本课理论 | 堆栈里的真实类 |
|---|---|
| "@Repository 让 Spring 生成翻译代理" | `PersistenceExceptionTranslationInterceptor.invoke` |
| "代理包住你的 DAO" | `TranslatedDao$$SpringCGLIB$$0.executeBadSql` |
| "翻译器查表换异常" | `HibernateJpaDialect.convertHibernateAccessException` |
| "翻译产出 Spring 家族" | 第一行 `org.springframework.dao.*` |

```text
堆栈从下往上读 = 翻译链从外到内：
  Controller → 代理类($$SpringCGLIB$$) → CGLIB 拦截 →
  PersistenceExceptionTranslationInterceptor（try 包住）→
  真实方法抛 Hibernate 异常 → DataAccessUtils.translateIfNecessary →
  HibernateJpaDialect.convertHibernateAccessException（查翻译表）→
  new 出 InvalidDataAccessResourceUsageException 抛出 → 冒泡 → 兜底 500
```

#### 完整排障流（学员已亲证）

```text
① 注释掉/不写具体 handler → 触发错误 → 落 500
② 兜底 handler 的 log.error 打出完整堆栈（前提：兜底有 log）
③ 读日志三步：第一行类名（精确）/ 包名找根（家族）/ Ctrl+H 确认
④ 写 handler → 重新触发 → 验证状态码变了
```

### 追问确认：受检/非受检的精确表述（2026-10-27）

学员表述："受检就是要加 catch 或者 throw，非受检就是不当场同步处理，让它向上自动抛"——
**90% 对，两处精修**：

#### 精修①：throw vs throws（两个关键字）

```java
throw new TaskNotFoundException(id);          // 语句：抛出一个异常对象
void readFile() throws IOException { ... }    // 声明：方法签名上"我可能抛，调用者表态"

受检异常的表态二选一：catch（就地处理） 或 throws（往上传，会传染调用者）
```

#### 精修②：非受检不是"不处理"，是"自愿处理"

```text
区别不在"能不能 catch"——两者都能 catch！
区别在【编译器逼不逼你】：

受检：  不 catch 也不 throws → 编译不过（强制表态）
非受检：catch 也行、不 catch 也行（自愿）→ 不 catch 才自动向上冒泡

本项目的活证据（catch 非受检异常）：
  @ExceptionHandler(Exception.class)        ← Exception 是非受检体系，照样 catch
  demo Controller 的 catch (Exception e)    ← 主动处理非受检
```

#### 对比表（记这张）

| | 受检 | 非受检 |
|---|---|---|
| 编译器 | **强制表态** | **不管** |
| 能不能 catch | ✅ | ✅（想处理随时可以） |
| 不处理的结果 | 不存在（编译不过） | **自动冒泡** |
| 继承自 | Exception（除 RuntimeException） | RuntimeException / Error |

#### 比喻：地铁安检 vs 商场

```text
受检 = 进地铁（必须过安检）：自己开包（catch）或安检员转交上级（throws）
非受检 = 进商场（没安检）：可自己注意安全（自愿 catch），
                          出事惊动保安逐级上报（不管 → 自动冒泡）
```

#### 一句话

```text
受检 = 编译器逼你表态（catch 或 throws）
非受检 = 随你（想管就管，不管就自动冒泡到值班室）
```

### 一句话

```text
异常转换 = catch 旧家族异常 → new 新家族异常 → 抛出去
零魔法，全部由本课规则①②③ 解释
@Repository 的唯一作用：让 Spring 生成那个"带翻译 try-catch"的代理类
```

相关：J7 §十六（同一主题的框架视角：翻译表/两类 DAO 的触发方式）。
