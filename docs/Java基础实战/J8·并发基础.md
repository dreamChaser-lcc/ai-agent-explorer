## 1. 动机：为什么需要"异步"——接单与干活分开

**问题**：研究任务要跑几分钟（规划 → 搜索 → 写报告）。同步处理的话，HTTP 请求要**挂几分钟**——浏览器/网关超时、用户对着转圈干等。

**解法**：**"接单"和"干活"分开**：

```text
前端 POST /api/tasks ──→ 后端【秒回】任务ID ──→ 前端拿 ID 去 /stream 看实时进度
                            ↓ 后台线程继续跑那几分钟
```

## 2. 线程 vs 线程池——为什么不能"一个请求雇一个工人"

**线程 = 干活的工人**（OS 级稀缺资源）。每次 `new Thread` 的三宗罪：

| # | 罪 | 后果 |
|---|---|------|
| 1 | 创建/销毁成本高 | 每单外卖都新雇一个厨师（招聘+培训+遣散） |
| 2 | 数量无上限 | 1000 个请求 → 1000 个线程 → 内存爆炸 + CPU 忙着切换 |
| 3 | 无管理 | 没有排队、没有复用、没有监控、没有名字 |

**线程池 = 固定编制的班组**：工人常驻复用、数量可控、活多了排队、**每个工人有名字**。

## 3. 线程池七参数（人话版 + 项目对照）

| 参数 | 人话 | 项目里的值 |
|------|------|-----------|
| `corePoolSize` | **常驻编制**（核心工人数） | `executionProperties.asyncThreadPoolSize()`（**从配置来**） |
| `maxPoolSize` | 旺季最多扩到几人 | 同上——**core = max**（固定班组） |
| `keepAliveTime` | 临时工闲置多久辞退 | 默认（core=max 时用不上） |
| `queueCapacity` | **任务等待区**（排队的活） | **100** |
| `threadNamePrefix` | 工人的**名字前缀** | ★ `"research-task-"` |
| 拒绝策略 | 工人满 + 队列满 → 怎么办 | 默认（抛异常） |

**提交流程**：活来了 → 核心工人有空？直接干 → 满了？进队列 → 队列满？扩编到 max → 还满？拒绝策略。

## 4. 教材链三站（配置 → 定义 → 使用）

### 4.1 配置怎么进来（`ExecutionProperties`）

```java
@ConfigurationProperties(prefix = "app.execution")
public record ExecutionProperties(
        String defaultMode,
        int asyncThreadPoolSize,
        boolean pauseAtStepBoundaryOnly) { }
```

**J7 + J1 双重会师**：`@ConfigurationProperties` 把 `app.execution` 下的 yml 配置**自动绑进 record 字段**（由 `PropertiesConfiguration` 的 `@EnableConfigurationProperties` 激活）。

### 4.2 线程池怎么造（`AsyncExecutionConfiguration`）

```java
@Configuration
public class AsyncExecutionConfiguration {
    @Bean(name = "researchTaskExecutor")                      // J7 的"手工注册法"
    public Executor researchTaskExecutor(ExecutionProperties executionProperties) {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setThreadNamePrefix("research-task-");       // 工人名牌
        executor.setCorePoolSize(executionProperties.asyncThreadPoolSize());
        executor.setMaxPoolSize(executionProperties.asyncThreadPoolSize());
        executor.setQueueCapacity(100);
        executor.initialize();
        return executor;                                      // 返回类型是接口！
    }
}
```

**三个看点**：① 返回值声明 `Executor` **接口**（J2 精神——使用者只管"能提交任务"）；② 池大小**从配置来**（不写死——部署可调）；③ `@Bean(name=...)` 给名字——**为什么重要，第三站揭晓**。

**★ 本段代码零业务逻辑**——它只是"搭台子"（装修车间、招工人、定编制），**不包含"要执行的活"**。

### 4.3 ★ 怎么用（`ResearchTaskOrchestrator`）

```java
private final Executor researchTaskExecutor;   // 声明接口类型（J2）

public ResearchTaskOrchestrator(..., @Qualifier("researchTaskExecutor") Executor researchTaskExecutor) {
```

**`@Qualifier("researchTaskExecutor")`**：容器里可能**不止一个** `Executor`（Spring 自己也有默认线程池）——**按名字点名**（不点名又撞上多个候选 → 启动报错，经典故障）。

```java
public void startExecution(UUID taskId) {
    ResearchTaskEntity task = loadTask(taskId);
    if (task.getExecutionMode() == ExecutionMode.ASYNC) {          // J6 的枚举！
        researchTaskExecutor.execute(() -> executeTask(taskId));   // ★ 扔给班组，立刻返回
        return;
    }
    executeTask(taskId);                                           // 同步：当场跑完才返回
}
```

**全课件眼——"同步/异步双轨"**：同一个 `executeTask(taskId)`（同一个演员）；ASYNC → 打包扔线程池（后台门出场）；SYNC → 当场跑（正门出场）。**J6 枚举 + J7 注解 + J2 接口 + J1 lambda 四课会师于这一个 if。**

## 5. `execute` 执行什么？——活不在池子里

`Executor` 接口**唯一方法**：

```java
public interface Executor {
    void execute(Runnable command);   // ← command = "要干的活"，作为【参数】传进来
}
```

| | 线程池（班组） | Runnable（任务包） |
|---|---|---|
| 存在时长 | **长期** | **一次性** |
| 知道什么 | 怎么调度、多少工人 | **要干什么**（写在 lambda 里） |
| 类比 | 快递公司（车辆/人员） | **你当场递的包裹**——公司不关心里面是什么 |

**★ "从哪看出执行什么"= 追代码三步**：

1. **找提交点**：`execute(() -> executeTask(taskId))`——活的名字就写在 lambda 里；
2. **点进方法**：IDE **Ctrl+点击** `executeTask`——**方法体 = 执行内容全文**；
3. **逐层深入**：`executeTask` 内又调 `researchToolRegistry.execute(...)` 等——继续追。

**`executeTask` 全貌（业务语言版）**：加载任务 → 检查该不该停（暂停/取消）→ 取全部步骤 → `for` 每个步骤（更新状态 → 建执行记录 → 推 SSE → ★调工具干活（搜索/抓取）→ 存资料来源 → 标记完成）→ 全部完成标记 COMPLETED。

## 6. 动手实操记录（`ThreadPoolLab`，2026-10-07）

**实验**：JDK 原生 `Executors.newFixedThreadPool(2)`（自定义 ThreadFactory 起名 `lab-worker-N`——**Spring 的 `ThreadPoolTaskExecutor` 是对 JDK 原生的友好包装**，原理同款）；5 个任务各 `sleep(2000)`。

**第一幕实测输出**：

```text
========== 第一幕：2 个工人 vs 5 个任务 ==========
   [21:02:22] 任务-1 开工 @ lab-worker-1
   [21:02:22] 任务-2 开工 @ lab-worker-2      ← 两个工人同时开工
   [21:02:24] 任务-2 完工 @ lab-worker-2（耗时 2029ms）
   [21:02:24] 任务-1 完工 @ lab-worker-1（耗时 2029ms）
   [21:02:24] 任务-3 开工 @ lab-worker-2      ← 排队约 2 秒后才轮到（谁先完工谁接单）
   [21:02:24] 任务-4 开工 @ lab-worker-1
   [21:02:26] 任务-3 完工 @ lab-worker-2（耗时 2005ms）
   [21:02:26] 任务-4 完工 @ lab-worker-1（耗时 2005ms）
   [21:02:26] 任务-5 开工 @ lab-worker-2
   [21:02:28] 任务-5 完工 @ lab-worker-2（耗时 2016ms）
>> 5 个任务总耗时：6070ms（约 3 批 × 2 秒——2 个工人流水线的账）
```

**判读要点**：

| 现象 | 证据 |
|------|------|
| **同时开工** | 任务-1/2 同一时刻（21:02:22）在 lab-worker-1/2 上 |
| **排队** | 任务-3/4 的开工时间戳 = 前两位完工后（约 2 秒后） |
| **复用** | 任务-3 被 **lab-worker-2** 接走（它先完工）、任务-4 被 lab-worker-1 接走——**同一批工人反复干活** |
| **总耗时对账** | 6070ms ≈ 3 批 × 2 秒（5 工人 → 2 秒；串行 → 10 秒） |

**第二幕实测输出**（两种提交方式）：

```text
========== 第二幕：this:: 直传 vs () -> 绑参 ==========
   [21:02:28] 零参任务在 lab-worker-solo 上执行      ← pool2.execute(ThreadPoolLab::zeroArgJob)
   [21:02:28] 零参任务在 lab-worker-solo 上执行      ← 再来一次（同一工人复用铁证）
   [21:02:28] 绑参任务 开工 @ lab-worker-solo        ← pool2.execute(() -> researchJob("绑参任务"))
   [21:02:30] 绑参任务 完工 @ lab-worker-solo（耗时 2003ms）
```

**彩蛋**：线程名 `lab-worker-N` 来自自定义 ThreadFactory——去掉它，默认名是 `pool-1-thread-1`（生产日志里难认）——**这就是项目 `"research-task-"` 前缀的用处**（排障时的"身份证"）。

## 7. 方法不是值：lambda / 方法引用 / 函数式接口

**问题**（源自课堂追问）：`execute` 能不能像 JS 一样"直接传方法名"？

**答**：Java 里**方法不是值**（只有对象能传递）——但给了两条"传函数"的路：

| 写法 | 是什么 | 条件 |
|------|--------|------|
| `() -> executeTask(taskId)` | **lambda**（把代码"冻"成对象） | ✅ 万能——尤其**需要绑参**时 |
| `this::cleanUp` | **方法引用**（直接提方法名） | ⚠️ **形状必须匹配**（零参无返回才能当 `Runnable`） |

```java
executor.execute(executeTask(taskId));        // ❌ 立刻执行 + void 不能传
executor.execute(this::executeTask);          // ❌ 形状不匹配（Task 方法要 1 个参数）
executor.execute(() -> executeTask(taskId));  // ✅ 箭头【现场绑参】——把有参方法适配成零参包裹
```

**★ JS 同构三行**（规律完全一致）：

```javascript
setTimeout(doSomething, 1000);                 // ✅ 零参直传引用 ≈ Java 方法引用
setTimeout(() => executeTask(taskId), 1000);   // ✅ 要绑参用箭头 ≈ Java lambda
setTimeout(executeTask(taskId), 1000);         // ❌ 立刻执行 —— 同款坑
```

**Java 8 之前的原貌**（理解 lambda 的来路）：

```java
executor.execute(new Runnable() {        // 手写匿名对象
    @Override
    public void run() { executeTask(taskId); }
});
executor.execute(() -> executeTask(taskId));   // Java 8+：编译器自动生成上面那一坨
```

**函数式接口家族**（只有一个抽象方法的接口）：

| 接口 | 形状 | 见过的地方 |
|------|------|-----------|
| `Runnable` | 零参、无返回 | 线程池 |
| `Supplier<T>` | 零参、返回 T | 惰性取值 |
| `Consumer<T>` | 一参、无返回 | `forEach` |
| `Function<T,R>` | 一参、返回 R | `.map(...)` |
| `Predicate<T>` | 一参、返回 boolean | `.filter(...)`（J5） |

## 8. `@Async` 对照——项目没用的"语法糖"

```java
@Async          // 贴标签 → Spring 造代理 → 调用时自动扔线程池（需 @EnableAsync）
public void executeTask(UUID taskId) { ... }
```

**原理还是 J7 那套**：贴标签 → 框架读 → 造代理戏服 → 把调用偷偷转发给线程池（操作全谱第 ③ 类）。

**项目为何选"手动 `execute(...)`"**：显式（看得见的提交）、好调试、少一层代理魔法。两种都认识，看团队口味。

## 9. 补充：思考题与答案（课堂问答收录）

**题 1（观察题）**——`execute(() -> executeTask(taskId))` 为什么必须用 `() ->` 包一层？去掉会怎样？

**答**：双层——

1. **编译层**：`executeTask(taskId)` 带括号 = **方法调用**（求值即执行）、类型是 `void`——`void` 不能当参数传给 `execute(Runnable)`，**编译错**；
2. **语义层**：`() -> executeTask(taskId)` = **把"要干的活"冻成 Runnable 对象**递过去（等班组拆包才执行）——**"把活干了"vs"把活的说明书递过去"**。

**前端同构坑**：React `onClick={handleClick}`（对——递函数）vs `onClick={handleClick()}`（错——渲染时立刻执行）。
**口诀：带括号 = 现在干；箭头包 = 装进包裹等会干。**

**题 2（架构题）**——ASYNC vs SYNC，HTTP 响应分别等多久？为什么默认 ASYNC + SSE？

**答**：

| 维度 | SYNC | ASYNC |
|------|------|-------|
| HTTP 响应 | **全程挂住**（几分钟） | **毫秒级秒回**（taskId） |
| 超时风险 | 高（浏览器/网关/LB 任一环超时） | 无 |
| 用户看到 | 转圈干等 | 秒开 + SSE 实时进度 |
| **任务与连接** | **绑死** | ★ **解耦** |

**三层理由**：① HTTP"一问一答"模型与长任务八字不合（行业解法 = 202 Accepted + 轮询/SSE）；② 用户体验（能看见它在动）；③ **任务状态存在数据库、独立于 HTTP 连接** → 才能**暂停/取消/查历史/断线重连**（PAUSED/CANCELLED 枚举 + StepExecutionEntity 时间线才有意义）。
**SYNC 仅"测试和简单场景"**（代码注释原话）。

**附加题**——`execute` 的参数能"直接传方法名"吗？

**答**：能——但叫**方法引用**（`::`）且**形状必须匹配**（零参无返回才能当 `Runnable`）；有参数时必须 lambda **绑参**。**JS 也一样分流**（直传引用 vs 箭头包），规律同构。
