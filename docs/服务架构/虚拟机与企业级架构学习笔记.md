# 虚拟机与企业级架构学习笔记

---

## 一、虚拟机有什么用？

虚拟机（VM）就是在一台物理机上模拟出多台独立的电脑，主要用途：

| 用途 | 说明 |
|------|------|
| **隔离环境** | 测试软件不影响主机系统 |
| **多系统运行** | 一台电脑同时跑 Windows、Linux、macOS |
| **开发测试** | 搭建与生产环境一致的测试环境 |
| **安全隔离** | 运行可疑软件、病毒样本不怕感染主机 |
| **快照恢复** | 搞坏了直接回滚到之前的状态 |
| **学习实验** | 练习 Linux、网络、集群搭建等 |

常用虚拟机软件：VMware Workstation、VirtualBox、Hyper-V（Windows 自带）

## 二、Windows 中能装 MySQL / Docker / K8s 吗？

### MySQL → 直接装，没问题

```
下载 MySQL Installer 安装即可
https://dev.mysql.com/downloads/installer/
```

Windows 原生支持 MySQL，装好就能用。

### Docker → 可以，但有限制

| 方式 | 说明 |
|------|------|
| **Docker Desktop for Windows** | 官方支持，推荐方式 |
| **WSL2 模式** | Docker Desktop 底层用 WSL2 运行 Linux 容器 |
| **Hyper-V 模式** | 需开启 Hyper-V 功能 |

**注意**：Windows 上的 Docker 实际是跑一个 Linux 虚拟机，容器里的环境是 Linux，不是 Windows。

### Kubernetes (K8s) → 可以，但比较重

| 方式 | 说明 |
|------|------|
| **Minikube** | 单节点 K8s 集群，适合本地学习 |
| **Docker Desktop 自带 K8s** | 勾选设置中的 "Enable Kubernetes" 即可 |
| **Kind** | 用 Docker 容器模拟 K8s 节点 |
| **K3s / K3d** | 轻量级方案 |

### 总结

| 软件 | Windows 直接装 | 说明 |
|------|:-:|------|
| MySQL | ✅ | 原生支持 |
| Docker | ✅ | 需 WSL2 或 Hyper-V，底层跑 Linux 虚拟机 |
| K8s | ✅ | 通过 Minikube / Docker Desktop / Kind 实现 |

## 三、学习后端企业级架构需要搭虚拟机吗？

### 你需要虚拟机吗？

不一定。取决于你的目标：

| 目标 | 方案 |
|------|------|
| 学习单个组件（Spring Boot + MySQL + Nginx） | Windows 本机直接装，够用 |
| 模拟微服务集群（多节点 K8s、Nacos 集群） | 需要虚拟机或多台机器 |
| 企业级生产环境模拟 | 虚拟机 + K8s 集群 |

### 两条路线对比

#### 路线一：Windows 本机直接装（推荐新手先用这个）

适合学 Spring Boot + MySQL + Nginx + Nacos 单机版：

```
MySQL      → 官网下载 Installer，下一步安装
Nginx      → 下载 Windows 版解压即用
Nacos      → 下载 zip 包，启动脚本直接运行
Spring Boot → IDEA 写代码，本地启动
```

**优点**：零门槛，1-2 小时全搭好
**缺点**：没有集群感，无法模拟多节点

#### 路线二：虚拟机 + K8s 集群（接近企业真实环境）

这是最终要走的路线。

### 虚拟机搭建步骤（以 VMware + CentOS 为例）

#### 第一步：装虚拟机软件

```
1. 下载 VMware Workstation Pro（个人免费）
2. 安装，一路下一步
```

#### 第二步：装 Linux 系统

```
1. 下载 CentOS 7/8 或 Ubuntu 22.04 的 ISO 镜像
2. VMware → 新建虚拟机 → 选择 ISO → 设置 2核4G 或 4核8G
3. 启动 → 按提示安装系统
4. 安装完配网络（桥接模式，能上网就行）
```

建议配置（本机 16G 内存的话）：

```
Master 节点：2核 4G  （跑 K8s 控制面 + Nacos）
Worker 节点：2核 4G  （跑业务服务）
本机 Windows：跑 MySQL、Nginx
```

#### 第三步：配基础环境

```bash
# 每台虚拟机都要做
# 关闭防火墙（学习环境）
systemctl stop firewalld && systemctl disable firewalld

# 配 hosts（让节点之间能互认）
vim /etc/hosts
# 加上所有节点的 IP 和主机名

# 安装 Docker
yum install -y docker-ce
systemctl start docker
```

#### 第四步：装 K8s 集群

```bash
# 方案A：kubeadm（官方工具）
# 每台机器执行
kubeadm init --pod-network-cidr=10.244.0.0/16   # Master 上
kubeadm join <master-ip>:6443 --token ...        # Worker 上

# 方案B：轻量替代（学习推荐）
# 直接用 Docker Desktop 自带 K8s，或用 Minikube / K3s
curl -sfL https://get.k3s.io | sh -   # 一条命令装 K3s
```

#### 第五步：部署服务到 K8s

```bash
# 通过 YAML 或 Helm 部署
kubectl apply -f nacos-deployment.yaml
kubectl apply -f mysql-deployment.yaml
kubectl apply -f springboot-app.yaml
```

### 偷懒方案（省掉虚拟机）

| 工具 | 说明 |
|------|------|
| **Docker Desktop + K8s** | 勾选设置里的 Enable K8s，直接本地有 K8s |
| **K3d** | 在 Docker 里模拟 K8s 集群，几分钟搞定 |
| **Minikube** | 单机 K8s，一条命令启动 |
| **云厂商免费额度** | 阿里云/腾讯云有免费试用，直接开几台 ECS 练手 |

### 推荐学习顺序

```
阶段1（本机 1-2天）：
  MySQL + Spring Boot + Nginx → 写个 CRUD 项目跑起来

阶段2（虚拟机 2-3天）：
  Docker 打包镜像 → Nacos 注册中心 → Spring Cloud 微服务

阶段3（K8s 集群 3-5天）：
  K8s 集群搭建 → Helm 部署微服务 → 服务发现/负载均衡/滚动更新
```

## 四、虚拟机里能装哪些软件？

虚拟机就是一台 Linux 电脑，上面能装任何 Linux 能装的东西：

| 软件 | 能装在虚拟机里吗 | 说明 |
|------|:-:|------|
| **MySQL** | ✅ | 就是在 Linux 上装个 MySQL，跟装在真机上一模一样 |
| **Docker** | ✅ | 虚拟机里装 Docker，然后再在 Docker 里跑容器 |
| **K8s** | ✅ | 虚拟机里装 K8s，一台做 Master，一台做 Worker |
| **Spring Cloud** | ✅ | 虚拟机里装 Java 环境，然后跑你的 Spring Boot 服务 |
| **Nacos** | ✅ | 虚拟机里装 Nacos，其他服务来注册发现 |
| **Nginx** | ✅ | 虚拟机里装 Nginx 做反向代理 |

### 企业实际架构

```
物理服务器（一台很贵的机器）
  └── 虚拟化层（VMware / KVM）
        ├── 虚拟机1：跑 Nacos、MySQL
        ├── 虚拟机2：跑 K8s Master + Nginx
        ├── 虚拟机3：跑 K8s Worker + Spring Cloud 服务A
        └── 虚拟机4：跑 K8s Worker + Spring Cloud 服务B
```

## 五、虚拟机能完全独立于 D 盘吗？

**能，完全可以。** 安装时指定就行：

```
VMware 软件本身    → 装 D:\VMware
虚拟机磁盘文件     → 存 D:\VirtualMachines\centos1
虚拟机磁盘文件     → 存 D:\VirtualMachines\centos2
```

唯一会占 C 盘的：VMware 的一个很小的配置文件（几MB），可以手动改路径。虚拟机的系统、软件、数据全在 D 盘，不增加 C 盘负担。

## 六、真正的企业级框架用虚拟机跑服务吗？

**是的，但现在已经进化了。** 企业环境的演变：

```
早期：物理机直接装服务
     一台服务器跑一个应用，浪费资源

现在：虚拟化 + 容器化
     物理机 → 虚拟化平台 → 虚拟机 → Docker 容器 → K8s 管理
```

| 层级 | 说明 |
|------|------|
| **物理服务器** | 公动机房里的真实机器 |
| **虚拟化层** | VMware / KVM 把物理机切成多台虚拟机 |
| **虚拟机** | 每台装 Linux 系统 |
| **Docker** | 虚拟机里再装 Docker，一个虚拟机跑几十个容器 |
| **K8s** | 管理这些容器的调度、扩缩容、负载均衡 |

企业里服务最终跑在虚拟机里，只是虚拟机里大多又套了 Docker + K8s。

## 七、跳板机是什么？

跳板机（也叫堡垒机）就是 **进入公司服务器的"大门"**。

```
你的电脑 ──→ 跳板机 ──→ 内部服务器
  （公网）    （唯一入口）   （内网，外网访问不了）
```

### 为什么要跳板机？

| 原因 | 说明 |
|------|------|
| **安全管控** | 所有人必须经过这一道门，能记录谁做了什么 |
| **隔离内网** | 开发/测试/生产服务器不暴露在外网 |
| **权限控制** | 不同的人给不同的权限，不是谁都能碰生产环境 |
| **审计追溯** | 出事了能查是谁执行了什么命令 |

### 跳板机上一般有什么？

```bash
# 你 SSH 连上跳板机后，看到的是一个 Linux 终端
# 上面装了各种运维工具：
kubectl get pods          # 查看 K8s 容器状态
docker ps                 # 查看 Docker 容器
mysql -u root -p          # 连数据库
vim /etc/nginx/nginx.conf # 改 Nginx 配置
```

### 跳板机典型流程

```
1. 用 SSH 连跳板机（有公网 IP）
2. 输入账号密码 + 可能要二次验证
3. 在跳板机上用 SSH 跳转到目标服务器
4. 在目标服务器上操作服务
```

## 八、Docker 是干嘛用的？

### 一句话

**Docker = 把你的程序和它需要的所有东西打包成一个"集装箱"，在哪都能跑。**

### 没有 Docker 时的痛点

```
开发者电脑上：Java 17 + MySQL 8.0 + Ubuntu → 跑得好好的
部署到服务器：Java 8 + MySQL 5.7 + CentOS → 挂了！

经典借口："我电脑上能跑的啊"
```

### 有了 Docker 之后

```
开发者把程序 + Java 17 + MySQL 8.0 + Ubuntu 全打包成一个镜像
服务器上直接运行这个镜像 → 跟开发者电脑上一模一样
```

### Docker 核心概念

| 概念 | 类比 | 说明 |
|------|------|------|
| **镜像（Image）** | 安装光盘 | 打包好的模板，包含程序+环境+配置 |
| **容器（Container）** | 跑起来的系统 | 镜像运行起来就是容器，一个镜像能跑多个容器 |
| **Dockerfile** | 安装说明书 | 告诉 Docker 怎么打包镜像 |
| **仓库（Registry）** | 应用商店 | 存放镜像的地方，如 Docker Hub、阿里云镜像仓库 |

### Docker 实际能干嘛

```bash
# 1. 一条命令启动 MySQL
docker run -d -p 3306:3306 -e MYSQL_ROOT_PASSWORD=123456 mysql:8.0

# 2. 一条命令启动 Nginx
docker run -d -p 80:80 nginx:latest

# 3. 一条命令启动 Redis
docker run -d -p 6379:6379 redis:7

# 4. 一条命令启动你的 Spring Boot 应用
docker run -d -p 8080:8080 my-springboot-app:1.0
```

### Docker 的好处

| 好处 | 说明 |
|------|------|
| **环境一致** | 开发、测试、生产环境完全一样 |
| **隔离** | MySQL 和 Nginx 各跑各的，互不影响 |
| **快速部署** | 秒级启动，不用装一堆依赖 |
| **易于扩展** | 流量大了？多开几个容器就行 |
| **方便迁移** | 换服务器？打包带走就行 |

## 九、K8s 是干嘛用的？

### 一句话

**K8s = 管理 Docker 容器的"调度中心"，告诉你哪个容器跑在哪台机器、挂了怎么重启、流量大了怎么加。**

### 为什么需要 K8s？

Docker 解决了打包和运行的问题，但当你有几十上百个容器时：

```
问题1：容器挂了谁来重启？
问题2：流量大了怎么自动扩容？
问题3：10台机器，容器该放哪台？
问题4：怎么让外界访问到容器里的服务？
问题5：新版本上线怎么不停机更新？
```

### K8s 核心概念

| 概念 | 类比 | 说明 |
|------|------|------|
| **Pod** | 一个包裹 | 最小部署单元，里面装一个或多个容器 |
| **Node** | 一台机器 | 物理机或虚拟机，Pod 跑在上面 |
| **Deployment** | 管家 | 告诉 K8s 要跑几个副本、用什么镜像 |
| **Service** | 门牌号 | 给 Pod 一个固定访问地址，Pod 重启也不变 |
| **Ingress** | 大门 | 外部流量从这里进来，转发到内部服务 |
| **Namespace** | 房间号 | 把不同项目的资源隔离开 |

### K8s 实际能干嘛

```bash
# 1. 部署你的 Spring Boot 应用（跑3个副本）
kubectl apply -f deployment.yaml

# 2. 扩容（3个变10个）
kubectl scale deployment my-app --replicas=10

# 3. 滚动更新（不停机升级）
kubectl set image deployment my-app my-app=my-app:2.0

# 4. 自动重启挂掉的容器（不用管，K8s 自动拉起来）
# 5. 负载均衡（外部请求自动分配到多个 Pod）
```

### K8s 集群架构

```
                    ┌─────────────────────────┐
                    │      Master 节点         │
                    │  ┌───────────────────┐  │
                    │  │  API Server       │  │  ← 所有操作的入口
                    │  │  Scheduler        │  │  ← 决定 Pod 放哪台机器
                    │  │  Controller       │  │  ← 保证实际状态=期望状态
                    │  │  etcd (数据库)    │  │  ← 存储集群状态
                    │  └───────────────────┘  │
                    └───────────┬─────────────┘
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
    ┌─────────▼──────┐ ┌───────▼────────┐ ┌──────▼───────┐
    │  Worker 节点1   │ │  Worker 节点2  │ │ Worker 节点3 │
    │  ┌────┐ ┌────┐ │ │ ┌────┐ ┌────┐  │ │ ┌────┐      │
    │  │Pod │ │Pod │ │ │ │Pod │ │Pod │  │ │ │Pod │      │
    │  └────┘ └────┘ │ │ └────┘ └────┘  │ │ └────┘      │
    └────────────────┘ └────────────────┘ └──────────────┘
```

### Docker 和 K8s 的关系

```
Docker：负责把程序打包成容器，让容器跑起来
K8s：  负责管理这些容器（调度、扩缩、重启、网络）
```

| | Docker | K8s |
|---|---|---|
| 类比 | 集装箱 | 港口调度系统 |
| 职责 | 制造和运行集装箱 | 管理集装箱放在哪、怎么调运 |
| 单独用 | ✅ 可以，小项目够用 | ❌ 不能，K8s 需要 Docker 提供容器 |

## 十、Spring Cloud 和 Docker/K8s 的关联

### Spring Cloud 是干嘛用的？

**Spring Cloud = 一套 Java 工具箱，专门解决微服务之间的"沟通"问题。**

### 核心组件

| 组件 | 作用 | 类比 |
|------|------|------|
| **Nacos** | 服务注册与发现 + 配置中心 | 电话簿 + 公告栏 |
| **Gateway** | API 网关，统一入口 | 公司前台 |
| **LoadBalancer** | 负载均衡 | 接线员分机 |
| **OpenFeign** | 服务之间调用 | 打电话给同事 |
| **Sentinel** | 限流、熔断、降级 | 保险丝 |
| **Seata** | 分布式事务 | 跨部门协调 |
| **Sleuth** | 链路追踪 | 快递单号 |

### 三者各管什么？

| 问题 | 谁来解决 |
|------|----------|
| 程序打包环境不一致 | **Docker** |
| 服务挂了自动重启 | **K8s** |
| 流量大了自动扩容 | **K8s** |
| 服务之间怎么互相找到对方 | **Spring Cloud (Nacos)** |
| 服务之间怎么调用 | **Spring Cloud (Feign)** |
| 某个服务挂了不拖垮整体 | **Spring Cloud (Sentinel)** |
| 统一入口、鉴权限流 | **Spring Cloud (Gateway)** |
| 分布式事务怎么保证一致性 | **Spring Cloud (Seata)** |

### 三者配合的完整架构

```
┌─────────────────────────────────────────────────────┐
│                    你写的业务代码                     │
│              Spring Boot + Spring Cloud              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐            │
│  │ 用户服务  │ │ 订单服务  │ │ 支付服务  │            │
│  │ +Nacos   │ │ +Nacos   │ │ +Nacos   │            │
│  │ +Feign   │ │ +Feign   │ │ +Feign   │            │
│  └──────────┘ └──────────┘ └──────────┘            │
└────────────────────────┬────────────────────────────┘
                         │ Dockerfile 打包
                         ▼
┌─────────────────────────────────────────────────────┐
│                   Docker 镜像                       │
│     user-service:1.0  order-service:1.0             │
└────────────────────────┬────────────────────────────┘
                         │ 部署到 K8s
                         ▼
┌─────────────────────────────────────────────────────┐
│                   K8s 集群                          │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐    │
│  │Nacos │ │用户  │ │订单  │ │支付  │ │Nginx │    │
│  │Pod   │ │Pod x3│ │Pod x3│ │Pod x3│ │Pod   │    │
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘    │
└─────────────────────────────────────────────────────┘
```

### 一句话总结

```
Spring Boot  →  写单个服务
Spring Cloud →  管服务之间的协作（发现、调用、熔断、事务）
Docker       →  把服务打包成标准容器
K8s          →  管容器的调度、扩缩、重启、网络
```

## 十一、Docker 镜像打包详解

### 镜像里到底打包了什么？

```
镜像 = 一个"压缩包"，里面全部打包好了：
  ├── Ubuntu 系统文件（精简版）
  ├── Java 17（已装好）
  ├── MySQL 8.0（已装好）
  ├── 你的程序代码
  ├── 配置文件
  └── 所有依赖

服务器上只需要装一样东西：Docker
然后运行镜像 → 里面什么都有，不用额外装任何东西
```

### 镜像的分层结构

```
┌─────────────────────────────────┐
│          你的应用代码             │  ← 最上层
│       myapp.jar + 配置文件       │
├─────────────────────────────────┤
│         依赖库 / 中间件           │  ← 比如 MySQL 8.0
├─────────────────────────────────┤
│         Java 17 运行环境         │  ← 已经装好
├─────────────────────────────────┤
│         Ubuntu 精简系统           │  ← 最底层（base image）
└─────────────────────────────────┘
```

### Dockerfile 示例

```dockerfile
# 第1层：告诉 Docker 用哪个系统底座
FROM ubuntu:22.04

# 第2层：在系统里装 Java 17
RUN apt-get update && apt-get install -y openjdk-17-jdk

# 第3层：设置 Java 环境变量
ENV JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
ENV PATH=$JAVA_HOME/bin:$PATH

# 第4层：把你的程序复制进去
COPY target/myapp.jar /app/myapp.jar

# 第5层：配置启动命令
ENTRYPOINT ["java", "-jar", "/app/myapp.jar"]
```

### 服务器运行时发生了什么？

```
服务器原始状态：
  ├── CentOS 7（系统）
  ├── 没有 Java
  ├── 没有 MySQL
  └── 只有一个 Docker

运行 myapp:1.0 之后：
  ├── CentOS 7（系统）
  ├── Docker
  └── 容器（里面自带 Ubuntu + Java 17 + 你的应用）

服务器本身不需要装 Java，容器里已经有了
```

### 镜像大小优化

| 方法 | 效果 |
|------|------|
| 用 Alpine 精简基础镜像（5MB vs Ubuntu 70MB） | 大幅缩小 |
| 多阶段构建：编译和运行分开 | 编译工具不进入最终镜像 |
| 只打包必要文件，数据用 Volume 挂载 | 避免镜像臃肿 |

```dockerfile
# 多阶段构建示例
# 第1阶段：编译（用完整的 Maven 镜像）
FROM maven:3.9-eclipse-temurin-17 AS builder
COPY src /app/src
COPY pom.xml /app/
RUN cd /app && mvn clean package -DskipTests

# 第2阶段：运行（只用精简的 JRE 镜像）
FROM eclipse-temurin:17-jre-alpine
COPY --from=builder /app/target/myapp.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

## 十二、宿主机是什么？

### 定义

**宿主机 = 运行 Docker 的那台电脑/服务器。**

```
你的 Windows 电脑 ──→ 装了 Docker ──→ 跑了容器
                     ↑
                  这台 Windows 电脑就是"宿主机"
```

### 图示

```
┌─────────────────────────────────────────┐
│  宿主机（你的 Windows 电脑）              │
│                                         │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐ │
│  │ 容器1    │  │ 容器2    │  │ 容器3    │ │
│  │ MySQL   │  │ Nginx   │  │ 你的App  │ │
│  └─────────┘  └─────────┘  └─────────┘ │
│                                         │
│  硬盘：D盘                              │
│  内存：16GB                             │
│  CPU：i7                               │
└─────────────────────────────────────────┘
```

| 概念 | 说明 |
|------|------|
| **宿主机** | 跑 Docker 的那台机器 |
| **容器** | 跑在宿主机里的"小电脑" |
| **宿主机硬盘** | 你的 D 盘 |
| **宿主机内存** | 容器共享使用 |

## 十三、数据持久化与挂载

### 核心问题：容器删了数据会丢吗？

**会！** 容器里的数据是临时的，容器删了就没了。

### 解决方案：Volume 挂载

```bash
# 正确做法：把容器内目录映射到宿主机目录
docker run -d \
  -v D:/data/mysql:/var/lib/mysql \    # 宿主机目录:容器内目录
  -v D:/data/logs:/app/logs \
  myapp:1.0
```

### 挂载原理

```
容器内路径（固定）          宿主机路径（你指定）
/var/lib/mysql    ←──映射──→  D:/data/mysql
/app/logs         ←──映射──→  D:/data/logs

MySQL 实际写数据时：
  写到 /var/lib/mysql（容器内）
  实际存储在 D:/data/mysql（宿主机硬盘）

容器被删 → 宿主机数据还在
新建容器 → 再挂载同一个目录 → 数据恢复
```

### 打包时 vs 运行时的区别

| 阶段 | 做什么 | 路径 |
|------|--------|------|
| **打包时（Dockerfile）** | 定义容器内部需要持久化的目录 | 只有容器内路径 |
| **运行时（docker run）** | 你指定宿主机用哪个目录 | 宿主机路径由你决定 |

```dockerfile
# 打包时：只定义容器内部路径
VOLUME /var/lib/mysql    # 告诉 Docker：这里需要挂载
VOLUME /app/logs
```

```bash
# 运行时：你自己决定宿主机路径
docker run -d \
  -v D:/mydata/mysql:/var/lib/mysql \     # 你指定的
  -v D:/mydata/logs:/app/logs \           # 你指定的
  myapp:1.0
```

### 同一个镜像，不同运行环境

```bash
# 在 Windows 上跑
docker run -d -v D:/data/mysql:/var/lib/mysql my-mysql:8.0

# 在 Linux 服务器上跑
docker run -d -v /home/data/mysql:/var/lib/mysql my-mysql:8.0

# 镜像完全一样，只是宿主机路径不同
```

## 十四、总结

| 问题 | 答案 |
|------|------|
| 虚拟机能放 D 盘吗 | ✅ 能，安装时指定路径就行 |
| 企业用虚拟机跑服务吗 | ✅ 用，虚拟机里再套 Docker + K8s |
| 跳板机是什么 | 公司服务器的唯一入口，负责安全管控和权限管理 |
| Docker 解决什么问题 | 环境一致性，打包程序+环境，哪都能跑 |
| K8s 解决什么问题 | 容器调度、扩缩、重启、负载均衡 |
| Spring Cloud 解决什么问题 | 微服务之间的发现、调用、熔断、事务 |
| 容器删了数据会丢吗 | 会，所以要用 Volume 挂载到宿主机 |
| 宿主机是什么 | 运行 Docker 的那台机器 |
| 挂载目录打包时定还是运行时定 | 运行时由你指定，打包时只定义容器内路径 |
| 新手推荐路线 | 先本机跑 Spring Boot + MySQL，再上虚拟机搭 K8s |
