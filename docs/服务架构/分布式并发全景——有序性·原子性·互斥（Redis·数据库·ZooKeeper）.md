## 1. 环境升级：从单机并发到分布式并发，问题怎么变

J11 的所有工具（volatile / synchronized / 原子类 / ConcurrentHashMap）都有一个共同前提：

```text
所有线程在【同一个 JVM】里，共享同一块内存。
```

一旦部署成 K8s 多实例（你项目就是），环境变化：

```text
实例 A（JVM 1）──┐
实例 B（JVM 2）──┼── 各自独立内存，互不可见；唯一的共同"见面地点"是外部系统：
实例 C（JVM 3）──┘      数据库 / Redis / ZooKeeper / Kafka
```

**结果**：J11 的工具全部失效或降级——

| J11 工具 | 多实例下失效原因 | 分布式替代 |
|---------|----------------|-----------|
| `volatile`（可见性） | 实例 B 的内存变化，实例 A 永远看不见（不同机器） | 把状态放**数据库/Redis**（外部可见） |
| `ConcurrentHashMap`（共享容器） | 每个实例各有一张自己的 Map，不共享 | 状态放数据库；或 Redis |
| `synchronized`（互斥） | 只锁本 JVM 的线程，拦不住别的实例 | **分布式锁**（Redis/ZK/DB） |
| `AtomicInteger`（原子） | 原子性只在单 JVM 内 | Redis `INCR` / 数据库 CAS |

> **前端类比**：浏览器里多个标签页共享 `localStorage`？——不共享！每个标签页独立。想跨标签页共享要用 `BroadcastChannel`/服务端。**"多实例 = 多个独立浏览器"**，这是前端工程师理解分布式最快的跳板。

**所以分布式并发的核心变化是：共享状态从"内存"搬到"外部存储"，而外部存储各自提供不同的协调能力——本篇就是讲这个工具箱。**

## 2. 三性在分布式下的重新定义

| 三性 | 单机含义（J11） | 分布式含义（本篇） |
|------|----------------|-------------------|
| **有序性** | 同一 JVM 内线程执行的先后 | **同一业务实体的多次操作，跨实例/跨时间保持顺序**（如：同一任务的"创建→执行→完成"不能乱序、消息不能乱序消费） |
| **原子性** | 一段代码不被线程切断 | **一组操作要么全部完成，要么全部不留痕迹**（跨多次写库/跨多个服务） |
| **互斥** | 多线程只有一个进临界区 | **多实例/多机器只有一个能执行某段逻辑/占用某资源** |

## 3. 互斥全景：四种分布式锁方案

### 3.1 方案一：数据库（最朴素，也是兜底）

**乐观锁（version 字段）**——场景② 已实战：

```sql
-- 多个实例同时想更新同一任务：version 不匹配的失败
UPDATE research_task
SET status = 'RUNNING', version = version + 1
WHERE id = ? AND version = ?;      -- 影响行数 = 1 才算抢到
```

**CAS 抢占（状态守卫）**——场景⑥ 的消费防线：

```sql
UPDATE research_task SET status = 'RUNNING'
WHERE id = ? AND status = 'QUEUED';  -- 只有 QUEUED 才能变 RUNNING
```

**唯一约束**——场景④ 幂等键：重复插入直接报错。

**悲观锁 `FOR UPDATE`**：行级锁，事务提交前别人读不了/改不了——⚠️ 长任务占连接（场景⑨ 驳回过）。

```text
优点：无新组件、强一致、与业务数据在同一事务里
缺点：性能差（走 DB）、锁范围是"行"不是"代码块"
定位：★ 兜底防线 + 数据层面的最后裁决者
```

### 3.2 方案二：Redis（性能首选）

```text
手写版（场景⑨⑩，教学）：SET NX EX + token + Lua 释放
      └─ 缺陷：锁过期 ≠ 业务完成；主从切换可能丢锁
Redisson（T7，生产）：看门狗自动续期 + 可重入 + 读写锁 + tryLock 带等待
      └─ 生产 99% 场景的选择
RedLock（Redlock 算法）：向 N 个独立 Redis 主节点同时抢锁，过半成功才算——
      └─ 争议大（分布式专家 Martin Kleppmann 与 antirez 的著名论战），一般不推荐
```

```text
优点：快（内存）、纯内存操作无 DB 压力、生态成熟（Redisson）
缺点：AP 倾向——主从异步复制，主挂了从升主，锁可能"消失"（极端情况两个客户端同时持锁）
定位：★ 性能首选，配合"数据库兜底防线"使用（锁失效也有 version/唯一约束挡着）
```

### 3.3 方案三：ZooKeeper / etcd（强一致）

见 §4 专节。

### 3.4 选型决策树

```text
需要互斥/防并发
│
├─ 数据层面的并发（更新同一行/防重复插入）
│    └─ 数据库乐观锁 / 唯一约束 / CAS 抢占      ← 无锁化，首选
│
├─ 计数/扣减类
│    └─ Redis 原子 INCR/DECR + Lua（09 篇扣库存）← 无锁化
│
└─ 真正的"代码块互斥"（一段逻辑只允许一个执行者）
     ├─ 锁逻辑简单 + 能容忍极小概率失效 → Redis SET NX 手写（教学/轻量）
     ├─ 生产环境 → ★ Redisson（看门狗）
     └─ 金融级强一致 → ZooKeeper / etcd
```

## 4. ★ ZooKeeper 专节：分布式协调服务是什么

> 用户点名要讲的工具。ZooKeeper（ZK）不是锁工具，是一个**通用的分布式协调服务**——锁只是它的应用之一。

### 4.1 ZK 是什么

Apache ZooKeeper：为分布式系统提供**协调服务**的中间件（Google Chubby 的开源实现）。它自己是一个集群（3~5 台），对外提供四种能力：

| 能力 | 干什么 | 类比 |
|------|--------|------|
| **配置管理** | 集群配置集中存放 + 变更通知 | Nacos 配置中心的老前辈 |
| **命名服务** | 给分布式资源起全局唯一的名字 | 全局注册表 |
| **分布式锁** | 多实例互斥（本节重点） | 场景⑨ Redis 锁的强一致版 |
| **集群管理/选主** | 谁活着、谁是主节点 | Kafka 老版本、Hadoop 都用它选主 |

### 4.2 数据模型：一棵"文件树"

```text
/                       ← 根
├── /app1/config        ← ZNode（节点）：像目录，但每个节点可以存数据（小，1MB 内）
├── /locks
│   └── /task-exec
│       ├── n_0000001   ← 实例A 抢锁创建的顺序节点
│       └── n_0000002   ← 实例B 创建的
└── /masters/app1       ← 实例C 注册"我是主节点"
```

**三种节点类型（做锁的关键）**：

| 类型 | 特性 | 用途 |
|------|------|------|
| 持久节点 | 客户端断开也还在 | 存配置 |
| **临时节点（EPHEMERAL）** | **客户端会话断开 → 节点自动删除** | ★ 锁的"活着证明"——进程崩了锁自动消失，无过期问题 |
| **顺序节点（SEQUENTIAL）** | 创建时自动追加全局递增序号（n_0001, n_0002…） | ★ 排队取号 |

### 4.3 Watch 机制：变更通知

客户端可以对节点注册**监听（watch）**——节点被删除/修改/子节点变化时，ZK 会**推送通知**给客户端。注意：watch 是**一次性**的（收到后要重新注册）。

### 4.4 用 ZK 做锁的完整流程（羊群效应与优化）

```text
① 各实例想抢锁：在 /locks/task-exec/ 下创建【临时顺序节点】
     /locks/task-exec/n_0000001（实例A）
     /locks/task-exec/n_0000002（实例B）
     /locks/task-exec/n_0000003（实例C）

② 每个实例检查：我是不是序号最小的那个？
     实例A：是 → ★ 拿到锁，执行业务
     实例B/C：不是 → 进入等待

③ B/C 不傻等（防"羊群效应"——全盯一个节点，释放时几百个客户端同时被惊动）：
     B watch 自己的【前一个节点】n_0000001；C watch n_0000002（各盯各的前驱）

④ 实例A 执行完 → 删除 n_0000001（或会话断开自动删）
     → B 收到 watch 通知 → 检查自己是最小 → 拿到锁
     → C 继续等 B

⑤ 实例B 崩溃 → 会话超时 → ZK 自动删它的节点 → C 收到通知 → 上位
     ★ 临时节点 = 无需 TTL、无需看门狗，ZK 会话机制天然解决"进程崩了锁不放"
```

### 4.5 ZK 锁 vs Redis 锁：CP 与 AP

| 维度 | ZooKeeper | Redis |
|------|-----------|-------|
| 一致性模型 | **CP**：写必须过半节点确认才返回——宁可不服务，也不出现不一致 | **AP 倾向**：主从异步复制，主挂从升，可能丢最后几条写 |
| 锁可靠性 | **高**：临时节点 + 会话，崩溃自动释放，不存在"锁过期业务没完" | 中：TTL 与业务时长难匹配（看门狗补救）；主从切换丢锁 |
| 性能 | 低（写要过半确认、watch 网络交互） | **高**（纯内存） |
| 可用性 | 集群过半挂 → **整个 ZK 不可用**（宁死不一致） | Redis 挂 → 单点/哨兵切换（短暂不可用后恢复） |
| 复杂度 | 需要 ZK 集群（3~5 台） | 复用现有 Redis |
| 锁公平性 | 天然公平（顺序节点排队） | 不公平（谁抢到算谁） |

**一句话**：**ZK 用"慢和死板"换"强一致与自动释放"；Redis 用"可能不一致"换"快"**——这就是 CAP 定理的取舍（一致性 vs 可用性，网络分区时只能选一个）。

### 4.6 etcd：K8s 世界里的 ZK

你不需要在 K8s 里再装 ZK——**K8s 自己的"协调大脑"就是 etcd**（Raft 协议，同为 CP）：

```text
K8s 所有资源（Pod/Service/ConfigMap）都存在 etcd 里；
apiserver 的 watch 机制 = ZK 的 watch；
节点心跳、选主 = ZK 的会话/临时节点思想。
```

Spring 侧如果不用 Nacos，可以用 `spring-cloud-starter-kubernetes-client` 直接吃 K8s 的协调能力——**这就是"用环境自带的协调服务，不重复造轮子"**。

### 4.7 什么时候真的需要 ZK

```text
✅ 已有 ZK 集群（Hadoop/Kafka 老版本生态）
✅ 强一致金融场景（资金、配额，锁失效代价 = 资损）
✅ 需要"会话级自动释放"且业务时长完全不可控
❌ 普通 Web 业务互斥 → Redisson 足够（99% 场景）
❌ K8s 环境 → etcd/Service 原生能力
```

## 5. 有序性全景：分布式下怎么给任务排队

| 方案 | 原理 | 优点 | 缺点 | 项目 |
|------|------|------|------|------|
| **Kafka 按 key 分区** | 相同 key → 同分区 → 分区内严格串行 | 有序 + 并行（不同 key 并行）、持久化、可重放 | 只保证分区内有序 | ✅ [`TaskExecutionProducer`](../../backend/src/main/java/com/aiexplorer/researchagent/application/service/TaskExecutionProducer.java)：`send(TOPIC, payload, payload)` key=taskId |
| **单线程执行器** | `Executors.newSingleThreadExecutor()` FIFO | 绝对有序、简单 | 吞吐 = 1 | 单实例内同资源串行 |
| **状态机 + 轮询** | 任务带 step 字段，按状态推进 | 可靠、可恢复 | 要自己实现 | 场景⑥ 断点续跑（step 状态） |
| **CompletableFuture 链** | `thenCompose`/`allOf` 编排 | 单机内灵活 | 只在本 JVM | 单实例内多步编排 |
| **数据库时间戳 + CAS** | 按 createdAt 排序处理，CAS 防并发 | 无 MQ 依赖 | 轮询有延迟 | 小规模任务表 |
| **ZSet 延迟队列** | score 存执行时间戳，捞到期任务 | 延迟任务（订单超时取消） | 要自己轮询 | Redis 08 §7.3 提及 |

**核心口诀**：**"同一实体的操作串行（按 key 排队），不同实体的操作并行（散分区）"**——这就是"既有序又并行"的标准解法。

## 6. 原子性全景：分布式事务与幂等

单机原子性 = `@Transactional`（一个数据库、一个事务）。**跨服务/跨存储时，一个事务包不住了**——这才是分布式原子性的难点。

### 6.1 第一原则：能不分布式事务就不分布式事务

**项目做法（场景⑥）**："轻消息原则"——

```text
消息里只带 taskId，任务数据在数据库里（"任务活在数据库里"）
→ 消费端读 DB 拿最新状态 → 不存在"消息与库不一致"问题
→ 跨服务原子性问题被"共享数据库 + 消息只当敲门砖"规避掉
```

> 能用"共享一个数据库 + 事务"解决的，不要拆成两个服务各自写库——**拆库才是分布式事务问题的起点**。

### 6.2 真的跨库了：方案阶梯

| 方案 | 原理 | 一致性 | 复杂度 | 适用 |
|------|------|--------|--------|------|
| **本地消息表** | 业务写库时同事务写"待发消息表"，后台任务扫表发 MQ，发完标记 | 最终一致 | 低 | ★ 最实用（不引新组件） |
| **事务消息**（RocketMQ） | 半消息 + 回查 | 最终一致 | 中（需 RocketMQ） | RocketMQ 生态 |
| **Saga** | 长事务拆成 N 步，每步配补偿动作；失败逆序补偿 | 最终一致 | 高（要写补偿） | 长流程（订机票+酒店） |
| **TCC** | Try（预留资源）-Confirm（确认）-Cancel（取消） | 较强 | 高（每个参与者三接口） | 资金类 |
| **2PC/XA** | 两阶段提交，所有参与者锁资源到统一提交点 | 强一致 | 中（协议重、阻塞） | 传统数据库集群，Web 场景少用 |

### 6.3 兜底：对账

最终一致的系统**必须有对账任务**：定时比对"业务事实"与"消息/缓存/下游数据"，发现不一致补偿或告警——**承认会不一致，但保证最终被发现**。

## 7. 消息队列在并发中的角色（含"数据库当队列"）

### 7.1 MQ = 分布式版的"线程池队列"

| 能力 | 单机（J8/J11） | 分布式 |
|------|---------------|--------|
| 任务缓冲 | 线程池的 BlockingQueue | **Kafka/RabbitMQ topic** |
| 任务分发 | 线程池多个 worker 抢 | **消费组多实例抢分区**（一分区同一组内只被一个消费者消费——**分区天然就是分布式锁**！） |
| 失败重试 | catch + 重放 | 重试主题/死信（场景⑥ DLT） |
| 有序 | 单线程池 | 分区有序（key=业务 id） |

> **Kafka 消费组 = 分布式锁的"消息化变体"**：一个分区同一时刻只被组内一个消费者消费——不需要锁，架构本身保证了互斥。**选择"分区数 = 实例数"就是天然的负载均衡互斥。**

### 7.2 "数据库当队列"（用户提到的"数据库异步"）

不引入 MQ 时，数据库表可以当任务队列：

```sql
-- 任务表：status=待处理，加索引
-- 抢任务（MySQL 8：SKIP LOCKED 跳过被锁行——多 worker 不互相阻塞）
SELECT * FROM task_queue
WHERE status = 'PENDING'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;      -- ★ 多实例抢任务的标准姿势
-- 抢到 → UPDATE status='PROCESSING' → 处理 → 标记 DONE/FAILED
```

| 维度 | 数据库队列 | Kafka/RabbitMQ |
|------|-----------|----------------|
| 依赖 | 无（已有 DB） | 需要中间件 |
| 吞吐 | 低（千级/秒） | 高（十万级/秒） |
| 可靠性 | 高（事务保证） | 高（持久化+副本） |
| 适用 | 任务量小、可靠性优先、不想引组件 | 大流量、解耦、广播 |

**项目对照**：场景⑩ 定时清理 = "定时任务 + 分布式锁 + 批量删除"；如果清理任务变多变重，下一步就是把"清理任务表"当队列（或上 MQ）——**演进路线：单机定时 → DB 队列 → MQ**。

## 8. 全景选型总表

| 需求 | 单机（J11） | 分布式首选 | 强一致场景 | 兜底 |
|------|------------|-----------|-----------|------|
| 互斥执行 | synchronized / ReentrantLock | **Redis SET NX / Redisson** | ZooKeeper / etcd | DB CAS 抢占 |
| 计数/扣减 | AtomicInteger | **Redis INCR/DECR + Lua** | DB 事务 | — |
| 防重复创建 | — | **DB 唯一约束 / 幂等键** | 同左 | — |
| 防状态覆盖 | volatile + CAS | **DB 乐观锁 version** | 同左 | — |
| 任务有序 | 单线程池 / 链式编排 | **Kafka key 分区** | 同左 | DB 时间戳轮询 |
| 多步写原子 | @Transactional | **单库事务优先**；跨库 → 本地消息表/Saga | 2PC | 对账 |
| 任务缓冲 | 线程池队列 | **Kafka / RabbitMQ** | — | DB 队列（SKIP LOCKED） |
| 状态/配置共享 | 内存 / volatile | **Redis / Nacos / ConfigMap** | ZK/etcd | — |

## 9. 防线家族：多层防御的架构思想

项目防线的完整地图（每一层独立成立，叠加防御）：

```text
第 1 层：架构规避（最好）
   单库事务 / 轻消息原则 / 分区有序 —— 用设计绕开分布式并发问题

第 2 层：无锁化
   DB 乐观锁（version）/ 唯一约束（幂等键）/ Redis 原子 INCR+Lua（扣库存）
   —— "原子操作 + 约束" 替代 "锁"

第 3 层：分布式锁
   Redis SET NX（手写）→ Redisson（生产）—— 真正需要串行时才上

第 4 层：幂等与审计
   状态守卫（消费前 CAS）/ 断点续跑 / REQUIRES_NEW 审计留痕
   —— 假设前面全部失效，业务仍然正确

第 5 层：监控与对账
   LAG 告警 / 审计日志 / 对账任务 —— 假设问题发生了，保证被发现
```

> **架构原则一句话**：锁是最后手段；**先幂等、先原子、先约束，锁只兜"必须串行执行"的底，监控保证一切问题最终被发现**。

## 10. 常见坑速查

| # | 坑 | 说明 | 解法 |
|---|-----|------|------|
| 1 | 锁过期 ≠ 业务完成 | TTL 5 分钟业务跑 6 分钟 → 双实例同时执行 | Redisson 看门狗；或业务完成前续期 |
| 2 | Redis 主从切换丢锁 | 主挂未同步 → 从升主 → 锁消失 → 双持锁 | 数据库兜底防线（version/唯一约束）；强一致上 ZK |
| 3 | ZK 会话超时误判 | GC 停顿/网络抖动 → 会话过期 → 临时节点被删 → 锁被别人抢 | 调会话超时 + 持锁期间自检 |
| 4 | 羊群效应 | ZK watch 同一节点，释放时惊动所有等待者 | watch 自己的**前驱**节点（§4.4） |
| 5 | 消息重复消费 | 重平衡/重试必然发生 | 幂等（状态守卫+唯一约束），别指望恰好一次 |
| 6 | 分区数改小导致乱序 | key 不变但分区减少 → 重新分配 → 短暂乱序 | 分区数规划好；乱序敏感场景用状态机纠偏 |
| 7 | 本地消息表忘记清理 | 发完不标记 → 重复发送 | 标记 + 定时清档 |
| 8 | FOR UPDATE 长事务占连接 | 悲观锁持锁期间连接不释放 | SKIP LOCKED / 短事务 / 改 Redis 锁 |
| 9 | 锁粒度太大 | 全局一把锁 → 全部串行 | 按 key 分锁（lock:task:exec:<uuid>） |
| 10 | 最终一致的中间态没处理 | 本地消息表有中间状态，前端误读 | 状态设计考虑"中间态"或用对账修正 |

## 12. 动手实验

1. **Redis 锁失效演示**：把场景⑨ 的锁 TTL 调成 5 秒、任务睡 10 秒 → 起两个实例 → 观察双持锁（日志两个实例都在跑）→ 理解"锁过期 ≠ 业务完成"；
2. **DB CAS 抢占实验**：两个事务同时 `UPDATE ... WHERE status='QUEUED'` → 一个影响行数 1、另一个 0 → 理解"数据库当锁"；
3. **ZK 体验**（可选）：`docker run -d --name zk -p 2181:2181 zookeeper` → `zkCli.sh` → `create -e -s /locks/n_ ""`（临时顺序节点）→ 观察序号自动递增 → 断开会话（Ctrl+C）→ 节点自动消失；
4. **SKIP LOCKED 实验**：两个终端同时对同一张任务表执行 `FOR UPDATE SKIP LOCKED` → 一个抢到、另一个跳过锁行拿下一行；
5. **对账思维**：写一个定时任务比对"消息表已发送"与"下游已处理"的数量差。

## 13. 面试速答

```text
Q：分布式锁有哪些实现？怎么选？
A：Redis（性能首选：手写 SET NX 或 Redisson 看门狗）/ ZooKeeper/etcd（强一致：临时顺序节点）/
   数据库（乐观锁/唯一约束兜底）。选型：性能优先选 Redis，强一致选 ZK，
   能用乐观锁/唯一约束无锁化就不上锁。

Q：Redis 锁为什么会失效？Redisson 怎么解决的？
A：TTL 与业务时长不匹配（过期后双持锁）+ 主从异步复制切换丢锁。
   Redisson 看门狗自动续期解决前者；后者靠"数据库兜底防线"或强一致协调服务。

Q：ZooKeeper 为什么能做锁？和 Redis 锁的本质区别？
A：临时顺序节点 + watch：会话断开节点自动删（崩溃自动释放）、顺序编号天然排队（公平）。
   本质区别是 CP vs AP——ZK 宁可不服务也不不一致；Redis 快但主从切换可能丢锁。

Q：消息队列怎么保证不重复消费？
A：at-least-once 是前提（必然可能重复），靠消费端幂等：状态守卫（DB CAS）+
   唯一约束 + 断点续跑——"恰好一次"是营销词，工程上是"至少一次 + 幂等"。

Q：什么是最终一致？
A：不强求同一时刻一致，但保证"经过一段时间 + 补偿/对账后达到一致"。
   实现：本地消息表 / 事务消息 / Saga 补偿；配套对账任务兜底。
```

## 14. 一句话总结

```text
单机并发靠内存工具（J11），分布式并发靠外部协调（数据库/Redis/ZK/MQ）；
互斥四方案：DB 兜底、Redis 性能、ZK 强一致、无锁化最优；
ZK = 分布式协调服务：临时节点（崩溃自动释放）+ 顺序节点（排队）+ watch（通知），CP 取舍；
有序性：同一实体按 key 排队（分区），不同实体并行；
原子性：单库事务优先，跨库用本地消息表/Saga，对账兜底；
锁是最后手段——先幂等、先原子、先约束，监控保证问题最终被发现。
```
