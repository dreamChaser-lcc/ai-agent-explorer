## 一、项目概览

### 1.1 这是什么

**micro-lab**：为学习微服务机制而建的迷你教学项目——不接数据库、代码极简，目标是"用最少的代码跑通微服务的全部核心机制"，跑通后再迁移到真实项目（ai-agent-explorer）。

### 1.2 服务清单与端口地图

| 服务 | 端口 | 角色 |
|------|------|------|
| user-service | 8081 | 用户域：提供用户信息查询（被调用方） |
| order-service | 8082 | 订单域：查询订单时聚合用户信息（调用方） |
| gateway | **9090** | 统一入口：路径路由（本机 8080 被占用，改用 9090） |
| nacos | 8848 / 9848(gRPC) | 注册中心 + 配置中心（跑在 K3s 里；NodePort 30048 / 31048） |
| sentinel-dashboard | 30058（NodePort） | ✅ 已部署：可视化控制台（流控/熔断规则）——2026-09-19，见 9.11 |

**两个必须记住的端口约定**：

1. **Nacos 2.x 的 gRPC 端口 = 主端口 + 1000**——通过 NodePort 访问时，两个映射必须成对（30048 → 8848，31048 → 9848），否则客户端注册时报 gRPC 连接失败；
2. 开发机 **8080 端口**被主项目 backend 占用——micro-lab 的网关使用 **9090**。

### 1.3 技术栈与版本（重点！）

| 组件 | 版本 |
|------|------|
| Java | 21 |
| Spring Boot | **3.2.4** |
| Spring Cloud | **2023.0.1** |
| Spring Cloud Alibaba | **2023.0.1.0** |
| Maven | 多模块（父工程统一管理版本） |

**⚠️ 三件套版本必须配套（Spring Cloud 第一坑）**：

- Spring Cloud / Alibaba 的代码是按"特定 Spring Boot 版本的内部结构"写的，大版本升级会大改内部结构（如 Boot 3.0 的 javax→jakarta），版本错配会导致**编译通过但启动报 `NoSuchMethodError`** 等底层错误；
- 官方适配矩阵（节选）：

| Spring Cloud | 适配 Spring Boot |
|--------------|-----------------|
| 2021.0.x | 2.6.x / 2.7.x |
| 2022.0.x | 3.0.x |
| **2023.0.x** | **3.2.x / 3.3.x** |
| 2024.0.x | 3.4.x |
| 2025.0.x | 3.5.x |

- Spring Cloud Alibaba 再叠一层适配：`2023.0.1.0 → Cloud 2023.0.1 → Boot 3.2.4`；
- **别用"三方各自最新版"**——发布有延迟（Boot → Cloud → Alibaba 逐层适配），最新组合经常不兼容；
- 正确姿势：父 pom 用 BOM（`dependencyManagement` import）统一锁死三件套版本，子模块不写版本号。

## 二、第 1 站：Nacos 部署到 K8s

### 2.1 为什么把 Nacos 放进 K8s

微服务需要注册中心 + 配置中心（Nacos 二合一）。之前 Nacos 跑在 node1 的 Docker 里（8848），微服务要进 K8s，注册中心也一并住进集群——服务之间通过 K8s Service 名（`nacos-svc:8848`）互访，不再依赖某台机器的固定 IP。

### 2.2 部署清单（~/k8s-lab/nacos.yaml）

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nacos
  labels:
    app: nacos
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nacos
  template:
    metadata:
      labels:
        app: nacos
    spec:
      containers:
        - name: nacos
          image: nacos/nacos-server:v2.3.2
          env:
            - name: MODE
              value: "standalone"        # 单机模式（学习环境）
            - name: JVM_XMS
              value: "256m"              # 限制 JVM 内存
            - name: JVM_XMX
              value: "512m"
          ports:
            - containerPort: 8848        # 控制台 + HTTP API
            - containerPort: 9848        # Nacos 2.x 的 gRPC 端口（=8848+1000，客户端通信必需）
---
apiVersion: v1
kind: Service
metadata:
  name: nacos-svc
spec:
  type: NodePort
  selector:
    app: nacos
  ports:
    - name: http
      port: 8848
      targetPort: 8848
      nodePort: 30048
    - name: grpc
      port: 9848
      targetPort: 9848
      nodePort: 31048               # ★ 必须是 30048+1000，否则客户端 gRPC 连不上
```

### 2.3 ⚠️ 核心坑：gRPC 端口必须保持"+1000"关系

- Nacos 2.x 客户端是"两条腿"通信：HTTP 主端口（8848）+ **gRPC 长连接（9848）**；
- 客户端计算 gRPC 端口的规则是**「配置端口 + 1000」**——我们配置 `server-addr=192.168.157.129:30048`，客户端就会去连 **31048**；
- 所以 Service 的 grpc nodePort 必须写 **31048**（最初误配成 30049，会导致 Windows 本地服务注册时 gRPC 超时）；
- **K8s 集群内部访问不受影响**：微服务连 `nacos-svc:8848` 时，gRPC 自动算 9848，而 Service 里两个端口都映射了，天然可达。

### 2.4 部署与验证命令

```bash
# node2 上部署
kubectl apply -f ~/k8s-lab/nacos.yaml

# 等待 Pod Running（首次要拉镜像）
kubectl get pods -w

# 验证 Service（应显示 30048/31048）
kubectl get svc nacos-svc

# 健康检查（返回 UP 即就绪）
curl -s http://192.168.157.129:30048/nacos/v1/console/health/readiness

# 浏览器访问控制台：http://192.168.157.129:30048/nacos （nacos / nacos）
```

> 命令知识点：`kubectl apply` 是**声明式**的——文件里写什么状态，集群就调成什么状态；重复执行输出 `unchanged`（没变化）/ `configured`（有更新）——这就是幂等。

## 三、第 2 站：工程骨架（Maven 多模块）

### 3.1 服务拆分设计

```
客户端 → gateway(9090) ──路由──→ order-service(8082) ──Feign──→ user-service(8081)
```

- **order 需要 user 的数据**——跨服务调用的天然演示点；
- 拆分原则：按业务能力拆（用户域 / 订单域）、高内聚低耦合、**不过度拆分**（2~3 个服务足够教学）；
- 数据用内存 Map（不接数据库），注意力集中在微服务机制。

### 3.4 服务代码（以 user-service 为例）

**启动类**：

```java
@SpringBootApplication
public class UserServiceApplication {

**模型（record）**：

```java

**接口**：

```java
@RestController
@RequestMapping("/users")
public class UserController {

    private static final Map<Long, UserProfile> USER_PROFILE_STORE = new ConcurrentHashMap<>();

    static {
        USER_PROFILE_STORE.put(1L, new UserProfile(1L, "张三", "13800000001", "黄金会员"));
        USER_PROFILE_STORE.put(2L, new UserProfile(2L, "李四", "13800000002", "普通会员"));

    @GetMapping("/{userId}")
    public UserProfile queryUserProfile(@PathVariable("userId") Long userId) {
        return USER_PROFILE_STORE.getOrDefault(userId,
                new UserProfile(userId, "未知用户", "00000000000", "游客"));
    }
}
```

```yaml

### 3.5 编译与运行命令（多模块要点）

```powershell
# 在 micro-lab 根目录：
mvn clean package -DskipTests           # 构建所有模块（验证工程编译健康 + 产出 jar）
mvn -pl user-service spring-boot:run    # 只启动指定模块
mvn -pl order-service spring-boot:run
```

**命令逐参数**：

| 命令/参数 | 含义 |
|-----------|------|
| `mvn clean package` | 清理旧产物 → 编译 → 打包（jar 落到各模块 target/） |
| `-DskipTests` | 跳过测试执行（学习期无测试；正式 CI 的最终构建不建议跳过） |
| `-pl <模块>` | `--projects`：多模块工程里"点名"只操作哪个模块 |
| `-am` | `--also-make`：把依赖的兄弟模块一起构建（以后抽公共模块时用） |
| `spring-boot:run` | 插件目标：**自动编译**后以 classpath 方式启动（开发模式，不打包） |

**package 产物长什么样**：`target/user-service-1.0.0-SNAPSHOT.jar`（Spring Boot 重打包后的可执行 "fat jar"，含全部依赖）+ `.jar.original`（重打包前的原始 jar）。

**开发循环**：改代码 → `Ctrl+C` → 重新 `mvn -pl xxx spring-boot:run`（run 自带编译，**不需要**每次手动 package；package 用于"验证工程"与"交付镜像"）。

## 四、第 3 站：服务注册与发现（Nacos Discovery）

### 4.1 原理

- **注册**：服务启动时把自己的「服务名 + IP + 端口」写入 Nacos 注册表；
- **发现**：调用方不写 IP，而是问 Nacos"叫 user-service 的服务现在有哪些实例"；
- 解决的核心问题：**IP 会变、实例会增减**（K8s 里 Pod 重建就换 IP）。

### 4.2 改动（两处）

**① pom 加依赖**（两个服务都加）：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

**② application.yml 加 Nacos 地址**：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 192.168.157.129:30048    # Nacos 的 NodePort（开发期从 Windows 访问）
```

> 注意：**不需要** `@EnableDiscoveryClient` 注解——Spring Cloud 2020 版之后全部自动装配（老教程里的注解已多余）。

### 4.3 验证

- 启动日志出现：`nacos registry, DEFAULT_GROUP user-service ... register finished`；
- Nacos 控制台 → 服务管理 → 服务列表：能看到 user-service / order-service 各 1 个实例。

## 五、第 4 站：服务间调用（OpenFeign）

### 5.1 原理

Feign 是**声明式 HTTP 客户端**：写一个接口 + 注解，Spring 启动时生成动态代理实现。调用发生时自动完成：
**服务名 → Nacos 查实例列表 → LoadBalancer 挑一台 → 拼 URL 发 HTTP → JSON 反序列化**。

### 5.2 改动（order-service 侧，共 5 处）

**① pom 加两个依赖**：

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-openfeign</artifactId>
</dependency>
<!-- 负载均衡器：Feign 挑选目标实例时依赖它（缺了会报 loadBalancing 相关错误） -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>
```

**② 启动类加注解**：

```java
@EnableFeignClients          // 开启 Feign 扫描：为 @FeignClient 接口生成动态代理
@SpringBootApplication
public class OrderServiceApplication { ... }
```

**③ Feign 客户端接口（核心，一个接口就是全部"代码"）**：

```java
@FeignClient(name = "user-service")          // ★ 写服务名，不是 IP！
public interface UserServiceClient {

    @GetMapping("/users/{userId}")           // 与服务提供方的接口路径对应
    UserProfileView queryUserProfile(@PathVariable("userId") Long userId);
}
```

**④ 视图 DTO**（各服务各自定义，不共享实体类）：

```java
public record UserProfileView(Long userId, String userName, String userPhone, String userLevel) {
}
```

**⑤ Controller 聚合调用**：

```java
@GetMapping("/{orderId}")
public OrderDetailView queryOrderInfo(@PathVariable("orderId") Long orderId) {
    OrderInfo orderInfo = ORDER_INFO_STORE.getOrDefault(orderId,
            new OrderInfo(orderId, "未知订单", 0L, 0L));

    // 跨服务调用：不写 IP，只写服务名
    UserProfileView userProfile = userServiceClient.queryUserProfile(orderInfo.userId());

    return new OrderDetailView(orderInfo.orderId(), orderInfo.orderTitle(),
            orderInfo.orderAmount(), userProfile);
}
```

### 5.3 验证

```powershell
curl.exe http://localhost:8082/orders/1001
# 期望：{"orderId":1001,...,"userProfile":{"userId":1,"userName":"张三",...}}
#       userProfile 来自 user-service 的跨服务调用
```

### 5.4 延伸实验（为熔断埋伏笔）

停掉 user-service 再调 order → **500 错误**：调用方被依赖方"拖下水"——这正是"服务依赖雪崩"的雏形。

## 六、第 5 站：配置中心（Nacos Config）

### 6.1 为什么需要

- 多实例：服务扩到 5 个实例，配置散在 5 台机器；
- 多环境：dev/test/prod 配置混杂；
- 动态性：改个参数不想发版重启。
- 配置中心：**集中存放 + 启动拉取 + 变更推送（热更新）**。

### 6.2 Nacos 配置模型三要素

| 要素 | 作用 | 本项目的值 |
|------|------|-----------|
| Data ID | 配置的"文件名"，全局唯一 | `user-service.yaml` |
| Group | 分组 | `DEFAULT_GROUP`（默认） |
| Namespace | 环境隔离（dev/prod） | `public`（默认） |

### 6.3 改动

**① pom 加依赖**：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>
```

**② application.yml**：

```yaml
spring:
  config:
    import:
      # 新方式接入配置中心（替代老版的 bootstrap.yml）
      # optional: 前缀 = Nacos 上没这份配置也照常启动（不加则启动失败）
      - optional:nacos:user-service.yaml
  cloud:
    nacos:
      config:
        server-addr: 192.168.157.129:30048
        file-extension: yaml      # Data ID 拼接规则：服务名 + .yaml
```

**③ 读取配置的接口（带动态刷新）**：

```java
@RefreshScope                     // ★ 动态刷新：配置变更后重建该 Bean，@Value 重新注入
@RestController
@RequestMapping("/users/config")
public class UserConfigController {

    @Value("${microlab.welcome-message:兜底默认值}")     // 冒号后 = 读不到时的默认值
    private String welcomeMessage;

    @GetMapping("/welcome")
    public String queryWelcomeMessage() {
        return welcomeMessage;
    }
}
```

### 6.4 操作与验证（动态刷新实验）

```bash
# ① Nacos 控制台创建配置：配置管理 → 配置列表 → "+"
#    Data ID: user-service.yaml    Group: DEFAULT_GROUP    格式: YAML
#    内容：
#      microlab:
#        welcome-message: 欢迎使用 micro-lab 用户服务（来自 Nacos 配置中心）

# ② 重启 user-service 后：
curl.exe http://localhost:8081/users/config/welcome
# → 返回 Nacos 配置的内容

# ③ 动态刷新（高潮）：控制台把文案改掉 → 发布 → 不重启服务 → 再次 curl
# → 立即返回新文案！
```

**背后机制**：Nacos 客户端**长轮询**监听配置变更（挂起请求最多 30 秒，变更立即响应）→ 发布 RefreshEvent → `@RefreshScope` 的 Bean 重建 → 新值生效。不加 `@RefreshScope` 则 `@Value` 不会更新（"改了配置没反应"的常见根因）。

## 七、第 6 站：网关（Spring Cloud Gateway）

### 7.1 与 K8s Ingress 的关系（别学乱）

```
客户端 → Ingress（K8s 层：域名 → Service，运维视角）      ← 已在《虚拟机DockerK8s复盘》学过
       → Gateway（应用层：路径/鉴权/限流 → 微服务，开发视角） ← 本站
       → 各微服务
```

- Ingress：集群大门，管"进来之后去哪个 Service"；
- Gateway：应用网关，管业务路由 + 横切关注点（认证、限流、日志、跨域）；
- 企业里常两层叠加使用。

### 7.3 路由配置（网关的灵魂）

```yaml
server:
  port: 9090        # 本机 8080 被占用，改用 9090

spring:
  application:
    name: gateway
  cloud:
    nacos:
      discovery:
        server-addr: 192.168.157.129:30048
    gateway:
      discovery:
        locator:
          enabled: false        # 关闭"按服务名自动路由"（教学用显式路由更清晰）
      routes:
        - id: user-service-route
          uri: lb://user-service           # lb = 从注册中心按服务名找实例 + 负载均衡
          predicates:
            - Path=/api/users/**           # 匹配条件（断言）
          filters:
            - StripPrefix=1                # 转发前去掉路径第 1 段
        - id: order-service-route
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1
```

**三大概念**：Route（路由）/ Predicate（匹配条件）/ Filter（过滤器）。

**StripPrefix 图示**：

```
客户端请求 http://localhost:9090/api/users/1
  → 匹配 Path=/api/users/**
  → StripPrefix=1 去掉 "/api"
  → 实际转发到 user-service: /users/1   ✓ 命中接口
（不加则转发 /api/users/1 → 服务端 404）
```

## 八、第 7 站：熔断降级（Sentinel）

### 8.1 三板斧（对应三个问题）

| 能力 | 回答的问题 | 手段 |
|------|-----------|------|
| 降级 | 调用失败了怎么办 | 返回兜底数据，异常不外抛（本站实现） |
| 熔断 | 失败太多了还试吗 | 失败率超阈值 → 跳闸 → 快速失败 |
| 限流 | 流量太大怎么办 | 超过 QPS/并发阈值直接拒绝 |

**熔断器三态**：`Closed 正常放行 → (失败率超阈值) → Open 跳闸（直接降级）→ (冷却后) → Half-Open 试探 → 成功回 Closed`。

### 8.2 改动（4 处）

**① pom 加依赖**（装在**调用方** order-service——熔断是调用方的自我保护）：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>
</dependency>
```

**② application.yml**：

```yaml
spring:
  cloud:
    sentinel:
      eager: true                  # 启动即初始化（默认懒加载：首次请求才初始化）
      transport:
        port: 8719
        # dashboard: 192.168.157.129:30058   # ✅ 控制台已部署（2026-09-19，见 9.11；实际经 set env 注入）

# ★ 关键开关：不开这个 @FeignClient 的 fallback 不生效
feign:
  sentinel:
    enabled: true
```

**③ Feign 接口指定兜底实现**：

```java
@FeignClient(name = "user-service", fallback = UserServiceClientFallback.class)
public interface UserServiceClient { ... }
```

**④ 兜底实现类**：

```java
@Component       // 必须注册为 Spring Bean，Feign 才能找到
public class UserServiceClientFallback implements UserServiceClient {

    @Override
    public UserProfileView queryUserProfile(Long userId) {
        return new UserProfileView(userId, "用户服务暂不可用", "-", "降级兜底");
    }
}
```

### 8.3 验证实验（对比才有冲击力）

```powershell

curl.exe http://localhost:9090/api/orders/1001        # → "张三"

# ② 停掉 user-service（Ctrl+C），再调

# → 200 + 兜底数据（userName="用户服务暂不可用"）——不再 500！

```

| 时间点 | 停掉 user-service 后调用 order |
|--------|------------------------------|
| 第 4 站（无兜底） | 500 错误（异常穿透） |
| 第 7 站（有 fallback） | 200 + 降级兜底（局部故障不扩散） |

### 8.4 规则 vs 兜底（进阶认知）

- 当前（**未配规则**）：每次请求仍真的尝试调用（要等连接失败），失败后走兜底；
- 配置**熔断规则**后：失败率超阈值 → 跳闸 → 后续请求**瞬间**返回兜底（连试都不试）——完整的"快速失败"；
- 配规则两种途径：**Sentinel Dashboard**（可视化，📌 待办）或代码（`DegradeRuleManager.loadRules(...)`）。

### 9.1 目标链路

```

[K8s 集群]

  nacos-svc (:8848/9848)       ← 已在集群里
```

### 9.2 四个技术要点

| # | 要点 | 说明 |
|---|------|------|
| 1 | **暴露策略** | 只有 gateway 开 NodePort 对外；user/order 用 ClusterIP 不对外（安全原则） |
| 2 | **Nacos 地址的环境差异** | 本地开发连 `192.168.157.129:30048`；进集群后连 `nacos-svc:8848`（K8s Service 名）——用 **Deployment 环境变量覆盖**（12-Factor 配置外置） |
| 3 | **镜像交付** | 三个镜像走"本地构建 → save → scp → ctr import"链路 |
| 4 | **部署前停本地服务** | 否则 Nacos 里同服务名会混着"Windows 实例"和"K8s 实例" |

> 顺带理解："微服务间调用"有两套寻址系统可共存——**Nacos（Spring Cloud 路线）**与 **K8s Service DNS（K8s 原生路线）**。本项目代码走 Nacos，K8s Service 主要给 gateway 对外用 + 作为内部固定入口。

### 9.3 Step 1：构建三个镜像（Windows）

**Dockerfile 内容**（三个服务各一份，单阶段"装运"模式）：

```dockerfile
# 前提：已在 micro-lab 根目录执行 mvn clean package -DskipTests（产出 jar）
# 构建命令（在 micro-lab 根目录）：docker build -t user-service:1.0.0 user-service
FROM docker.m.daocloud.io/library/eclipse-temurin:21-jre-alpine    # 直写加速源

```

**构建命令**：

```powershell
cd d:\project\lcc-github\ai-agent-explorer\micro-lab
mvn clean package -DskipTests

docker build -t user-service:1.0.0 user-service
docker build -t order-service:1.0.0 order-service

docker images | findstr "user-service order-service gateway"
```

**⚠️ 构建上下文知识点**：

- `docker build -t 名字:标签 <上下文路径>`：上下文目录会被打包发给构建引擎，**Dockerfile 里的 COPY 只能从上下文里取文件**；
- 在服务目录内执行时用 `.` 当上下文：`docker build -t gateway:1.0.0 .`；
- 常见报错：`path "xxx" not found`（上下文路径错了）、`COPY failed: file not found`（要拷的文件不在上下文里，比如忘了先 `mvn package`）。

**单阶段 vs 多阶段（两种构建路线对比）**：

| | 单阶段（micro-lab 用） | 多阶段（backend 用的） |
|---|---|---|
| 谁跑 `mvn package` | 开发机上**手动**跑（build 之前） | Dockerfile 第 1 阶段，**容器内自动** |
| 构建命令 | `mvn package` → `docker build`（两步） | `docker build`（一步） |
| 速度/环境 | 快；依赖开发机 JDK+Maven | 首次慢；不依赖开发机（CI 友好） |
| 隐蔽坑 | 忘了 package → **旧 jar 打进镜像**（"改了代码没生效"） | 无此问题 |

**⚠️ 实战坑（2026-09-17 首次部署踩中）：`no main manifest attribute, in /app/app.jar`**

现象：三个 Pod 全部 CrashLoopBackOff，容器日志仅一行 `no main manifest attribute, in /app/app.jar`。

根因链条（**自建父 POM 工程特有**）：

1. micro-lab 父 POM 没有继承 `spring-boot-starter-parent`（只在 dependencyManagement 里 import 了 BOM）——**import BOM ≠ 继承 parent**：前者管依赖版本，后者才管插件默认行为；
2. `repackage` 目标靠"继承 starter-parent"自动绑定；自建 parent 必须在 `pluginManagement` 里**显式声明 execution**，光写 `<version>` 不触发；
3. 于是 `mvn package` 只产出普通 jar（几十 KB、无依赖、无 Main-Class）→ 被 COPY 进镜像 → `java -jar` 报错；
4. 为何本地没暴露：`spring-boot:run` 以 classpath 方式启动、**不读 manifest**——坑只在交付镜像时爆发。（对照：backend 继承 starter-parent，从无此问题。）

修复（父 POM 的 pluginManagement 中显式声明）：

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <version>${spring-boot.version}</version>
    <executions>
        <execution>
            <id>repackage</id>
            <goals><goal>repackage</goal></goals>
        </execution>
    </executions>
</plugin>
```

**修复铁证**：重新 package 后 target/ 出现两个文件——`xxx.jar`（30~47MB 的 fat jar）+ **`xxx.jar.original`**（打回原形的普通 jar）。见到 `.jar.original` = repackage 生效。

**连带坑：修好 jar 后只 `rollout restart` 不够**——restart 只重建 Pod、**不重建镜像**，必须补全链路：`mvn package → docker build → docker save → scp → ctr import → rollout restart`。

**修复成功判据（对比观察）**：坏镜像的 Pod 起来后几秒内即 Error → CrashLoopBackOff（RESTARTS 速涨）；好镜像稳定 Running 且 **RESTARTS = 0**。

### 9.4 Step 2：导出镜像 + 传给两台节点

```powershell
# ① 导出为 tar
docker save user-service:1.0.0 -o user-service-1.0.0.tar
docker save order-service:1.0.0 -o order-service-1.0.0.tar
docker save gateway:1.0.0 -o gateway-1.0.0.tar
dir *.tar

# ② 分别传给两台节点（Pod 可能调度到任意一台，两边都要有镜像）
scp user-service-1.0.0.tar order-service-1.0.0.tar gateway-1.0.0.tar lcc@192.168.157.129:/tmp/
scp user-service-1.0.0.tar order-service-1.0.0.tar gateway-1.0.0.tar lcc@192.168.157.128:/tmp/
```

> **为什么两台都要传镜像？**（多节点集群的镜像常识，2026-09-17 用户提问引出）
>
> Deployment 里**没有指定"跑哪台"**——Pod 落点由 kube-scheduler 动态打分决定。以下场景都会触发"重新调度"，把 Pod 放到任意节点：
> ① Pod 重建（rollout restart / 滚动更新）；② **节点驱逐**（如磁盘压力——2026-09-17 早上 nacos 被驱逐重建就是实例）；③ 扩副本；④ 节点故障/维护。
> 若调度到的那台**没有镜像** → `ImagePullBackOff`（本地 tag 公网拉不到）。传两份的成本只是几百 MB 磁盘，换来"调度到任何节点都能活"。
>
> **另一个反直觉点：NodePort 与 Pod 位置完全无关。**
>
> "30090 端口"不是某台机器的私有端口，而是**集群级入口**——由每台节点上的 kube-proxy（K3s 内置组件）在**本机**写入转发规则（iptables DNAT）。三层寻址：
>
> ```
> 任意节点 IP:30090（NodePort，每台节点都接）
>    ↓ kube-proxy 规则
> Service ClusterIP（虚拟 IP，稳定不变）
>    ↓ 负载均衡挑一个 Ready 的 Pod
> Pod IP:10.42.x.x:9090（真实容器地址，重建就换）
> ```
>
> 所以从 128（node1）或 129（node2）访问 30090 **都通**——流量会被自动送回"当前有 Pod 的那台"（同机直达，或跨节点经 flannel 转发）；Pod 重建换节点，前端访问不受影响。
>
> 查看真实端点：`kubectl get endpoints gateway-svc`（显示当前 Pod IP）——对比记忆：**NodePort/ClusterIP 稳定不变，Pod IP 随重建而变**，这就是 Service 存在的意义。
>
> 彩蛋验证：`sudo ss -lntp | grep 30090`——iptables 模式下**看不到任何进程监听 30090**，但 curl 就是通：转发是内核 netfilter 层做的（规则劫持），不是应用程序在监听端口。
>
> （速查：Pod IP 第三段 = 节点子网号。`10.42.1.x` = node1、`10.42.0.x` = node2——看 IP 即知 Pod 在哪台，不用看 NODE 列。）
```

**⚠️ Service 三个端口的区别（`gateway-svc` 的 ports 段）**：

| 字段 | 值 | 在哪一层 | 谁在访问 |
|------|-----|---------|---------|
| `nodePort` | 30090 | 节点层（**每台机器都开放**） | 集群外部（浏览器 / Windows curl） |
| `port` | 9090 | Service 虚拟层（ClusterIP） | 集群内部的其他 Pod |
| `targetPort` | 9090 | 容器层（Pod 内） | kube-proxy 的最终转发目标 |

流量走法：`外部 → 任意节点:30090 →(kube-proxy)→ Service:9090 →(负载均衡)→ Pod IP:9090`。

- **`nodePort: 30090` 这个字段就是"30090 端口"的唯一定义处**（写死在 YAML 里；**不写则 K8s 从 30000~32767 自动分配**，每次重建可能变号）；
- 30090 数字来源：应用端口 9090 前加"3 万"的记法（NodePort 固定区间），好记且避让常用端口；
- 查看集群里的权威定义：`kubectl describe svc gateway-svc` / `kubectl get svc gateway-svc -o yaml`；
- `kubectl get svc` 输出列 `9090:30090/TCP` 读作 **"port:nodePort"**。

**环境变量名的由来（重要）**：Spring Boot 的 relaxed binding 规则——配置项 `spring.cloud.nacos.discovery.server-addr` 对应的环境变量是 `SPRING_CLOUD_NACOS_DISCOVERY_SERVER_ADDR`（`.` 和 `-` 都换成 `_`，全大写）。环境变量优先级高于 jar 内的 yml，所以能实现"同一镜像、不同环境连不同 Nacos"。

 "userProfile":{"userId":1,"userName":"张三","userPhone":"13800000001","userLevel":"黄金会员"}}
```

这个 JSON 就是 8 站成果的集合验证：

### 9.8 探针与零中断发布（tcpSocket 版，2026-09-19 实战完成）

**背景**：9.7 部署后遗留的问题——Pod `1/1 Running` ≠ 应用就绪（无探针时 K8s 只判"容器进程存活"）。滚动更新时，新 Pod 在"端口还没监听"的窗口期就被加进流量名单，出现 `connection refused`。

**方案（零成本）**：tcpSocket 探针——探针定义在 Deployment（Pod spec）里，**与镜像无关**，改 YAML + `kubectl apply` 即生效，无需重建镜像。

```yaml
          readinessProbe:              # 就绪探针：端口能连上才进流量名单（失败不重启，只摘流量）
            tcpSocket:
              port: 8081
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 6
          livenessProbe:               # 存活探针：连续失败才重启
            tcpSocket:
              port: 8081
            initialDelaySeconds: 40    # ★ 容忍时间必须 > 应用最长启动时间
            periodSeconds: 10
            failureThreshold: 5
```

**参数设计黄金法则**：

| 探针 | 容忍时间设计 | 要点 |
|------|-------------|------|
| readiness | ~35s 没就绪则持续重试 | 失败**不重启**（安全），宁可宽松；端口最终起来即自动 Ready |
| liveness | 40s 后开始查，连挂 5 次（~90s）才重启 | ⚠️ **必须大于应用最长启动时间**，否则"没起完就被杀 → CrashLoopBackOff" |

**对比实验（金标准）**——同一个操作跑两遍：

```bash
# 观测窗口（每 0.5s 一次，只打印状态码；000 = 连接失败）
while true; do curl -s -o /dev/null -w "%{http_code} " http://192.168.157.129:30090/api/orders/1001; sleep 0.5; done
# 另一个窗口触发滚动更新
kubectl rollout restart deployment/gateway
```

| 状态 | 观测输出 | 结论 |
|------|---------|------|
| 加探针前 | 一串 `000`（连接失败） | 新 Pod 未监听就被发流量 |
| **加探针后** | **全程 `200`** | **零中断滚动更新 ✅** |

**机制链**（为什么探针能消除中断）：

```
新 Pod 创建 → 容器 Running
  → [无探针] 立即 Ready → 进 Endpoints（应用还没监听端口！）→ 流量打空 → 000
  → [有探针] readiness 未过 → 留在 Endpoints 之外 → 流量全走老 Pod
       → 端口监听成功 → 探针通过 → 才进 Endpoints → 老 Pod 才开始退场 → 全程 200
```

观察特征：加探针后新 Pod 会经历 `0/1 Running → 1/1 Running`——这个"0/1 窗口"就是零中断的保险费。

### 9.9 actuator + httpGet 探针（路线 B，2026-09-19 实战完成）

**与 tcpSocket 版的本质区别**：tcpSocket 只知道"端口通不通"；httpGet 走 actuator health 端点，能读到应用内部的**状态语义**（HTTP 200=就绪、503=未就绪），端点还可聚合依赖健康（DB、注册中心等）——这才是企业标准的"健康检查"。

**改动一：依赖**（三个模块 pom.xml 各加）

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

**改动二：探针 + 开关**（Deployment YAML）

```yaml
env:
  - name: MANAGEMENT_ENDPOINT_HEALTH_PROBES_ENABLED   # relaxed binding：management.endpoint.health.probes.enabled
    value: "true"                                     # 打开 /actuator/health/{liveness,readiness} 子端点
# ...容器片段：
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8081
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8081
  initialDelaySeconds: 40
  periodSeconds: 10
  failureThreshold: 5
```

**三个端点的分工（actuator 手册）**：

| 端点 | 含义 | 适合用途 |
|------|------|---------|
| `/actuator/health` | 聚合健康（diskSpace / ping / livenessState / readinessState…） | 人工排查 / 监控 |
| `/actuator/health/liveness` | 应用自身是否还能活（**不含外部依赖**——外部挂了重启也没用） | livenessProbe |
| `/actuator/health/readiness` | 应用是否可接流量 | readinessProbe |

**验证（容器是 alpine 基础镜像：有 busybox wget，没 curl）**：

```bash
kubectl exec deploy/user-service -- wget -qO- http://localhost:8081/actuator/health
# {"status":"UP"}
```

**⚠️ 实战大坑（同日踩中）：同名旧 tar 冒充新镜像**

- 现象：apply 后 gateway 新 Pod 永远 `0/1`（探针 404 永不通过，liveness 反复重启）；而 user/order 正常就绪——**同一流程唯独一个服务异常 → 一定是"那个服务的某个环节"漏了**；
- 排查链：user/order 就绪（新镜像流程通）→ gateway 探针 404（跑的是无 actuator 的旧镜像）→ 两台 digest 一致但为旧值 → **`dir *.tar` 看时间戳：`gateway-1.0.0.tar` 还是两天前的旧文件**（当天的 `docker save` 没跑成/被漏过——多行粘贴丢命令的老毛病）；
- 修复：单点重做 `build → save（核对时间戳）→ scp → 两台 import（核对 digest）→ 删 Pod 重建`；
- **三道防线**：① `save` 后 `dir` 看文件时间；② `import` 后 `ctr images ls` 看 **digest 指纹变化**；③（进阶）用不可变 tag（如 `gateway:0919-1`）替代同名覆盖。

> 核心收获：**"文件名相同、内容旧"无法肉眼识别，只有指纹（时间戳 / digest）能识破**；排查时"单点异常 → 单点检查"是最省时的思路。

**📚 当日答疑记录（学习中的疑问，2026-09-19）**

**Q1：tcpSocket 和 httpGet 的"聪明"差在哪？**
> tcpSocket 测【网络层】：端口能连上吗（内核回答）；httpGet 问【应用层】：应用自己报告状态（必须应用代码回答，200=就绪 / 503=未就绪）。差距在异常时暴露：应用假死、依赖断连时端口仍在监听（tcpSocket 误报健康），而 actuator 如实报病。

**Q2："读应用内部状态"到底怎么看？**
> 默认 `show-details: never` 把明细藏了 → ① 打开开关（`MANAGEMENT_ENDPOINT_HEALTH_SHOW_DETAILS=always`）看 components（Nacos 连通性、磁盘、内部状态机全在）；② 抓"未就绪窗口"看 503（见实验二）。

**Q3：`deploy/user-service` 里的 `deploy/` 是固定格式吗？**
> 语法是 `<类型>/<名称>`：类型可写全称（deployment）或缩写（deploy）；`exec`/`logs` **必须写类型**（默认按 Pod 找，不写会报 "pods xxx not found"）；名称=YAML 的 `metadata.name`。
> `exec deploy/xxx` 会"下钻"到它的 Pod——⚠️ **多 Pod 时选哪个不保证**（排查时先 `kubectl get pods` 拿全名再 exec；这个坑当天就踩过：gateway 新老 Pod 并存时 exec 钻进了老 Pod，404 误导排查）。
> 缩写查询：`kubectl api-resources`；常用：deploy / po / svc / sts / cm / ds / ns / no / ing。

**Q4：三种探针是 `spring-boot-starter-actuator` 实现的吗？actuator 到底管什么？**
> **不是。** 三层分工要分清：
> ① **K8s（探针机制）**：readiness / liveness / startup 定义在 Pod spec 里，**由 kubelet 执行**——这是 K8s 自己的能力，与 Spring 无关；
> ② **应用（状态暴露）**：Spring Boot 的可用性机制在内部维护 `LivenessState` / `ReadinessState`，actuator 负责把它们**暴露成 HTTP 端点**（`/actuator/health/liveness`、`/actuator/health/readiness`）——这是"被检查的接口"；
> ③ **交集只在 httpGet 方式**：探针选 httpGet 时去问 actuator 的端点；选 tcpSocket / exec 时**完全不需要 actuator**（路线 A 就是纯 tcpSocket，零依赖）。
> 补充：`startupProbe` **没有** actuator 专用端点（Spring Boot 无 startupState），一般用 tcpSocket 或任意 http 端点。
>
> **actuator 的完整作用面**（不止探针）：① 健康检查（health，聚合各组件——今天看到的 `nacosDiscovery` / `discoveryComposite` / `refreshScope` 都是 Spring Cloud 侧注册进来的 HealthIndicator）；② 指标（`/actuator/metrics`：JVM / GC / 线程 / HTTP 统计，监控系统入口）；③ 运行时管理（`/actuator/loggers` 动态改日志级别等）。
> 注：它是 **Spring Boot** 的组件（groupId `org.springframework.boot`），不是 Spring Cloud 的——只是微服务项目里必配。

**Q5：探针是为了"服务调度"吗？K8s 是不是一开始只检测端口？**
> 两个心智偏差都要修：
> ① **探针不参与"调度"（scheduling）**——调度是 `kube-scheduler` 决定"Pod 放哪台节点"（依据资源、亲和性、污点），**与探针无关**。探针参与的是运行期三件事：**流量指挥**（Ready 才进 Endpoints）、**重启决策**（liveness 失败 → kubelet 重启）、**发布节奏**（Deployment 按就绪数控制滚动）。
> ② **出厂设置连端口都不看**——不配探针时 K8s 只判"进程 In/Exited"；"端口检测"（tcpSocket）已经是第一次主动升级。演进阶梯：**进程级（默认）→ 端口级（tcpSocket）→ 应用级（httpGet + 健康端点）→ 启动期保护（startupProbe）**。
> ③ 咬文嚼字："0 中断发布"靠 readiness（切换无感）；**"重启"本身是有中断的**（单副本重启期间不可用），liveness 的价值是"假死自愈"，想"重启无感"需要多副本。
> ④ 没有探针时，三大决策会退化成什么样？——见下方对照表。

**④ 对照表：有探针 vs 没探针（三大决策的差别）**

| 决策 | 没有探针（默认） | 有探针 |
|------|----------------|--------|
| **流量给谁** | 容器 Running = 立刻进 Endpoints | readiness 通过才进 |
| **何时重启** | 只有"进程退出"能触发 | 加上"假死"（liveness 失败） |
| **发布切换** | 新 Pod"进程一起来"就切，老 Pod 按 maxUnavailable 撤 | 新 Pod 真正就绪才切 |
| **典型故障画像** | 发布抖动 000；假死带病运行；崩了才补 | 发布平滑；假死自愈；故障实例被摘除 |
| **判断信号数** | **1 个**（进程存在性） | 2~3 个（+ 网络层 / + 应用层） |

> 一句话：**探针的终极价值 = 让 K8s 学会识别"进程活着但服务已死"这类软故障**。

### 9.10 零中断"完全体"：preStop + 优雅停机 + startupProbe（2026-09-19 实战完成）

**背景**：9.8/9.9 解决了"入口侧"（新 Pod 就绪才切流量），但"出口侧"还欠着——**老 Pod 退场瞬间，迟到的流量会打到正在关闭的容器上**（连接重置 / 502）。

**出口侧问题的时序（为什么需要两件套保护）**：

```text
① 触发删除 → Pod 变 Terminating，开始"从流量名单摘牌"
② 【魔鬼窗口】"摘牌"要向全集群传播（API Server → 各节点 kube-proxy 更新转发规则），
   有延迟（毫秒~数秒）——期间新流量还在往它打！
③ kubelet 开始终止容器：
   有 preStop → 先执行 preStop（容器活着、继续服务）
   无 preStop → 直接 SIGTERM
④ SIGTERM 后：
   默认 → 立即死（处理中的请求被掐断）
   graceful → 在途请求处理完再退
⑤ 超过 terminationGracePeriodSeconds（默认 30s）→ SIGKILL 强杀
```

**两件套的分工**：

| 机制 | 管哪一段 | 效果 |
|------|---------|------|
| `preStop: sleep 5` | ②之后、③之前 | "延迟死刑"：多活 5 秒继续服务，等摘牌传播完（无新流量进来，但能应酬"迟到的客人"） |
| `SERVER_SHUTDOWN=graceful` | ④ | "善后"：不再收新活，但把手头的活干完再退 |

**v4 配置（每个服务 4 处改动）**：

| 改动 | 内容 | 作用 |
|------|------|------|
| ✚ `startupProbe` | httpGet liveness 端点，`5s/5s/30`（容忍 155s 启动） | 启动期保护（通过前压制 liveness/readiness） |
| ✎ `livenessProbe` | 去掉 `initialDelaySeconds: 40`，改 `periodSeconds: 5` + `failureThreshold: 3` | 启动期交给 startup 扛后，liveness 解放为"敏感模式"（假死约 15s 被发现） |
| ✚ `lifecycle.preStop` | `exec: ["sh","-c","sleep 5"]` | 出口侧保险① |
| ✚ env `SERVER_SHUTDOWN=graceful` | 环境变量（配置外置，零镜像成本） | 出口侧保险② |

另加 Pod spec 级 `terminationGracePeriodSeconds: 30`：终止总预算 = preStop(5s) + 优雅停机窗口。

**三个"肉眼可见"的验证证据（均已通过）**：

1. **Terminating 停留约 5 秒**（preStop 生效的最直接表现）：
   ```bash
   kubectl get pods -w          # 窗口 1
   kubectl delete pod <名字>     # 窗口 2：观察 Terminating 稳定停留 ~5s 才消失（没配 preStop 时几乎瞬灭）
   ```
2. **优雅停机日志**（graceful 生效）：
   ```bash
   kubectl logs -f <Pod名>        # 窗口 1 先挂住日志
   kubectl delete pod <同一Pod名>  # 窗口 2
   # 日志收尾出现：
   #   "Commencing graceful shutdown. Waiting for active requests to complete"
   #   "Graceful shutdown complete"
   ```
3. **startupProbe 探测记录**：
   ```bash
   kubectl describe pod <新Pod> | grep -A 2 -i "startup"
   ```

**至此"零中断发布"的完整拼图**：

| 环节 | 机制 | 状态 |
|------|------|------|
| 入口侧 | readinessProbe（新 Pod 就绪才切流量） | ✅ 9.8 / 9.9 |
| 出口侧 | preStop + 优雅停机（在途请求善后） | ✅ 9.10 |
| 启动期 | startupProbe（慢启动保护） | ✅ 9.10 |
| 节奏器 | 滚动策略（maxSurge / maxUnavailable） | 默认值够用 |
| 保险绳 | 多副本（replicas ≥ 2 抗单点） | 可选待做 |

| 1 | 公共源镜像被拒 | daocloud 加速源 403（sentinel-dashboard 未在白名单） | 放弃公共源 → 自建镜像路线 |

**C. 图形化流控实战（入口限流）**

- 控制台给 order-service 的**入口资源**配流控：QPS = 2；
- 压测 20 并发 → **`200 × 2` + `429 × 18`**；
- 实时监控页：通过 QPS 2.0 / 拒绝 QPS 18.0；**下游 Feign 资源恰好通过 2**——"进来 2 个、下游只被调 2 次"，链路层次保护一目了然。

**D. 限流 vs 熔断（控制台两大规则体系）**

| | 流控规则（FlowRule） | 熔断规则（DegradeRule） |
|--|--------------------|----------------------|
| 关注点 | **入口的速度**（QPS / 并发线程数） | **依赖的健康度**（错误率 / 慢调用比例） |
| 触发后 | 直接拒绝（可配 fallback 降级） | 快速失败一段时间（熔断窗口） |
| 恢复 | 流量回落立即恢复 | 窗口结束后半开试探，成功才恢复 |
| 一句话 | "最多涌进来这么多" | "下游病了，先别去烦它" |

### 9.12 彩蛋实验：Feign 资源限流 × fallback 降级联动（2026-09-19 实战完成）

**设计**：把流控规则从"入口"挪到"出口"——加在对 user-service 的 **Feign 调用资源**（`GET:http://user-service/users/{userId}`）上，QPS=1。看"被限流的调用"能否被 fallback 优雅接住。

**实验数据**：

| 压测方式 | 输出 | 状态码 |
|---------|------|--------|
| 串行 12 次（sleep 0.3，约 3 req/s） | `张三 ×4` + `用户服务暂不可用 ×8`（"1 真 2 假"规律交替） | **全 200** |
| 30 并发 | 几乎全是兜底（仅零星「张三」） | **全 200** |

**数字对账（QPS=1 严格生效）**：串行每 ~0.32s 一发 → 12 次覆盖约 4 个统计秒 → 恰好放行 4 次；30 并发挤在 1~2 个统计秒内 → 只抢到 1~2 个额度，其余全拒（Sentinel 按"滚动秒窗口"统计）。

**机制链（为什么被限流却返回 200）**：

```text
feign.sentinel.enabled=true → Feign 调用被 Sentinel 代理
  └─ SphU.entry("GET:http://user-service/users/{userId}")
       └─ 超出 QPS=1 → 抛 BlockException
            └─ Feign 降级机制捕获 → 调 UserServiceClientFallback
                 └─ 返回兜底 UserProfileView("用户服务暂不可用", "-", "降级兜底")
                      └─ OrderController 无感知，照常组装 → 200
```

**入口限流 vs 出口限流（核心对照）**：

| | 入口限流（9.11-C 实验） | 出口限流（本实验） |
|--|----------------------|------------------|
| 规则位置 | 服务自身入口资源 | Feign 调用资源（对下游） |
| 被拦后 | 默认处理器 → **429**（客户端感知失败） | BlockException → **fallback → 200**（无感降级） |
| 保护对象 | 保护自己不被压垮 | 保护下游（user-service） |
| 类比 | "客人太多，门口限流" | "后厨忙不过来，先上前菜顶一下" |

**认知升华**：限流给用户的"体验"取决于两个设计——① 拦在链路的哪一层；② 被拦后有没有降级兜底。生产系统对下游高频调用普遍采用"**限流 + 兜底**"组合：依赖过载时主流程依然可用，用户体验只是"数据略有降级"而非"报错"。

## 十、踩坑与知识点速查

| # | 坑/知识点 | 要点 |
|---|-----------|------|
| 1 | 三件套版本必须配套 | Boot 3.2.4 + Cloud 2023.0.1 + Alibaba 2023.0.1.0；BOM 统一锁版本；别用"三方最新" |
| 2 | Nacos gRPC 端口 +1000 | NodePort 必须成对：30048 与 **31048** |
| 3 | `mvn -pl` / `-am` | 多模块点名器；-am 带上依赖模块 |
| 4 | `spring-boot:run` 自带编译 | 改代码 → Ctrl+C → 重跑即可，无需每次 package |
| 5 | 单阶段 vs 多阶段构建 | package 的位置不同（本地手动 vs 容器内自动）；单阶段忘了 package 会打旧 jar |
| 6 | 构建上下文 | `docker build <上下文>`；Dockerfile 的 COPY 只能从上下文里拿文件 |
| 7 | 端口冲突标准四连 | `netstat -ano \| findstr :端口` → `tasklist \| findstr PID` → `taskkill /PID x /F` → 或换端口 |
| 8 | `feign.sentinel.enabled=true` | 不开，Feign 的 fallback 不生效 |
| 9 | `@RefreshScope` | 不加，`@Value` 不随配置变更更新 |
| 10 | Gateway 不能引 web starter | WebFlux 与 MVC 冲突，启动报错 |
| 11 | 环境变量覆盖配置 | `SPRING_CLOUD_NACOS_DISCOVERY_SERVER_ADDR=nacos-svc:8848`（12-Factor） |
| 12 | 微服务 ≠ 能互相调用 | 核心是"独立部署 + 治理体系"；调用只是协作手段 |
| 13 | 只暴露网关 | 内部服务 ClusterIP，不对外（安全原则） |
| 14 | Nacos 与 K8s 的关系 | 服务发现两套机制可共存：Nacos（Spring Cloud 路线）与 Service DNS（K8s 原生） |
| 15 | jar 无 Main-Class（`no main manifest`） | 自建父 POM 必须显式配 repackage execution（**import BOM ≠ 继承 parent**）；铁证：target/ 出现 `.jar.original`；修好 jar 后仅 `rollout restart` 不够，须走完整镜像链路（详见 9.3 实战坑） |
| 16 | `rollout restart` 不重建镜像 | 它只重建 Pod；镜像不换，代码永远不生效 |
| 17 | Pod Running ≠ 应用就绪 | 未配 readinessProbe 时，容器进程活=标记 Ready，但应用可能仍在启动 → NodePort 转发被拒 |
| 18 | liveness 参数必须 > 启动时间 | 容忍时间小于应用冷启动时间 → 没起完就被杀 → CrashLoopBackOff；readiness 失败不重启（只摘流量），参数可从宽（见 9.8） |
| 19 | 同名旧 tar 冒充新镜像 | 漏跑 `docker save` → scp 传的是旧文件（文件名相同肉眼不可辨）→ 探针 404 永不就绪；识破：`dir` 看 tar 时间戳 / `ctr images ls` 看 digest 变化；预防：不可变 tag（见 9.9） |
| 20 | 假 jar（404 页冒充 .jar） | 下载物只有几百字节（HTML 404 页被存成 .jar）→ 容器报 `Invalid or corrupt jarfile`；铁律：制品必做三重校验——文件大小 / PK 魔数 / 压缩包完整性（见 9.11） |
| 21 | 多节点镜像漏更新（第二次） | 镜像只导入部分节点 → Pod 恰好调度到未更新节点 → 旧症状复现；用 `ctr images ls` 的 digest 逐节点核对（见 9.11；同类坑：#19） |
