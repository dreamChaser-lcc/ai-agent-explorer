## 1. 先读懂这张表：术语与角色

先把表里的"黑话"翻译成人话：

| 术语 | 人话 | 课程对应 |
|------|------|---------|
| `SET NX + TTL` | 不存在才设置 + 自带过期（原子抢占） | J11 §4 / Redis 08 §5 |
| `UUID`（作为 value） | 持锁凭证——释放时验明正身，防止误删别人的锁 | Redis 08 §5.2 |
| **inflight** | "正在执行中"的标记（in-flight = 在途） | 执行许可闸门 |
| **闸门（gate）** | 允不允许进入执行——SET 成功 = 闸门开 | 状态守卫的 Redis 版 |
| **幂等占位** | 先占一个"我正在处理"的坑，重复请求被挡在门外 | 场景④ 幂等键的 Redis 版 |
| **claim（认领）** | 从任务池里"认领"一条：CAS 改状态，改到就是我的 | 场景⑥ 状态守卫 / MySQL SKIP LOCKED |
| **租约（lease）** | 认领有时限——超时没完成视为 worker 挂了，任务回收重派 | 数据库版"看门狗" |
| `reclaimExpiredJobs` | 定时任务：把"认领超时"的任务状态改回 QUEUED（重新排队） | 死信/重投的 DB 版 |
| XXL-Job 调度中心 | 独立的定时任务调度平台：谁来触发、触发给哪个实例（路由策略） | 场景⑩ 定时清理的"平台版" |

| 角色 | 机制 |
|------|------|
| **互斥锁** | #1 KB 解析锁、#6 JVM synchronized |
| **执行许可闸门** | #2 inflight（防同一命令并发执行） |
| **幂等/防重复** | #3 幂等占位、#4 分片 claim |
| **任务认领（DB 队列）** | #5 background_job CAS + 租约 |
| **调度互斥** | #7 XXL-Job |

## 2. 七种机制的角色分类：一条任务生命周期里的七道关卡

这张表**不是七种重复的锁，而是一条任务从触发到完成的七个阶段的七道防线**：

```text
【触发】外部命令进来（tid/iid = 任务/实例标识）
   │
   ▼
【防重复投递】#3 幂等占位：SET NX ai-trigger:{tid}:{conv}:{rev}
   │   同一个命令（同 revision）只投递一次；失败撤销 DEL 允许重试
   ▼
【执行许可】#2 inflight 闸门：SET NX cmd:inflight:{tid}:{iid} = commandId
   │   同一实例的同一命令不允许并发执行；终态/超时/停机时 DEL
   ▼
【认领执行】#5 DB CAS：UPDATE background_job SET status='EXECUTING' WHERE status='QUEUED'
   │   多实例谁认领到谁执行；租约过期由 reclaimExpiredJobs 回收重派
   ▼
【子任务分片】#4 分片 claim：SET NX report:part:<n>
   │   报告按分片生成，每个分片一个 claim（重传去重）
   ▼
【资源互斥】#1 KB 解析领取锁：SET NX kb:parse:fetch:lock
   │   保护共享资源（KB = 知识库，解析领取不能并发）
   ▼
【进程内串行】#6 synchronized (state.lock)
   │   同一实例内，同一状态对象的线程串行
   ▼
【调度入口（反向看）】#7 XXL-Job：整条链路的"谁在什么时候触发这一切"
```

> **读这张表的正确姿势**：不要问"为什么有七种锁"——它们**互斥范围、生命周期、所属层全都不一样**：#7 管调度入口、#5 管任务认领、#2 管命令执行许可、#3 管投递去重、#4 管分片去重、#1 管共享资源、#6 管进程内线程。**按 key 粒度和生命周期分层，才是分布式协调的正确设计方式**（呼应分布式全景 §9 防线家族）。

## 3. 逐个拆解（原理 / 设计意图 / 坑与改进）

### 3.1 #1 KB 解析领取锁——最标准的教科书锁

```java
// 获取：SET kb:parse:fetch:lock <uuid> NX EX 10
// 释放：GET → 比对 uuid → 一致则 DEL
```

- **设计意图**：保护"KB（知识库）解析领取"这个共享资源不被并发领取（防止两份解析重复劳动/数据错乱）。
- **为什么 value 是 UUID**：释放时验明正身——自己加的锁自己删（防止误删别人的）。
- **TTL 10s**：说明临界区预期很短（领取动作本身快，后续执行是异步的）。

**⚠️ Review 发现（唯一的原理性隐患）**：

```text
释放用的 "GET 比对 UUID 后 DEL" 是【两步操作】，中间存在竞态：
  线程A：GET → 是我的 uuid ✓
  ——恰在此刻锁过期，实例B SET NX 抢到（新 uuid）——
  线程A：DEL → ★ 把 B 的锁删了！B 和 C 可能同时执行
正确做法：用 Lua 把"比对 + 删除"合成原子操作（我们 09 篇的 token+Lua，Redis 08 §5.2）：
  if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end
```

> "最接近教科书"这句评价要打折——**教科书（和 Redis 官方文档）的释放就是 Lua 原子版**。TTL 10s 偏短也要确认：领取动作若超 10 秒，锁过期 → 双领取（TTL 与业务时长的经典矛盾，见分布式全景 §10 坑 1）。

### 3.2 #2 inflight 闸门——"执行许可"而不是"资源锁"

```text
SET cmd:inflight:{tid}:{iid} = commandId  NX EX 300
语义："这个命令正在执行中"——闸门关上；终态/超时/停机 → DEL → 闸门开
```

- **设计意图**：同一命令（tid+iid 标识）**不允许并发执行两次**——注意它锁的不是"资源"，是"**正在进行的执行**"。这是一种"执行许可闸门"：`SET NX` 成功 = 允许执行；失败 = 已有在途执行，直接拒绝/返回"处理中"。
- **为什么 TTL 300s**：命令执行的预期上限。超时放行 = 兜底（执行者挂了也能自愈）。
- **与 #1 的区别**：#1 锁"资源"（防止并发领取知识库），#2 锁"命令"（防止同一命令重复执行）——**锁的 key 粒度与语义完全不同，所以是两个机制**。

**⚠️ 注意点**：
1. "停机时 DEL"依赖优雅停机——`kill -9` / OOM 时删不掉，只能等 TTL 300s（可接受的兜底延迟）；
2. 业务超 300 秒 → 闸门超时放行 → 可能双执行——确认命令执行时间上限 < 300s，或加续期。

#### ★ inflight 详解：航空术语 → "在途标记"（2026-11-20 补）

**in-flight 是航空术语**——"在途/飞行中"（如 in-flight meal 飞行餐）。分布式系统借它指：**"已经受理、但还没完成"的请求或任务**——不在队列里排队，也还没出结果，正处于"在途"状态。

**inflight 标记的本质 = 一块"此事正在被处理"的公示牌**：

```text
某个命令 (tid, iid) 被受理
   → SET cmd:inflight:{tid}:{iid} = commandId  NX EX 300
      ↑ 在 Redis 挂公示牌："这件事我正在办"（value=commandId 记录是谁在办）
   → 执行中……
   → 出结果（终态）→ DEL 公示牌
   → 异常（崩溃/kill -9）没来得及 DEL → TTL 300s 后公示牌自动消失
```

**你其实天天在写 inflight 闸门——前端的防重复提交**：

```js
// 前端单机版 inflight 闸门（JS 内存变量）
let inflight = false;

async function submit() {
  if (inflight) return;            // ★ 闸门关：已有在途执行，直接返回
  inflight = true;                 // ★ 挂公示牌（= SET NX）
  try {
    await doSubmit();              // 执行
  } finally {
    inflight = false;              // ★ 终态摘牌（= DEL）
  }
}
```

**分布式版只改一件事：把变量从 JS 内存搬到 Redis**——多实例下 A 实例的内存变量 B 看不见，必须用共享存储公示：

| 前端写法 | 分布式写法 |
|---|---|
| `if (inflight) return` | `SET NX` 失败 → 返回"处理中" |
| `inflight = true` | `SET cmd:inflight:{tid}:{iid} = commandId NX EX 300` |
| `finally { inflight = false }` | 终态/停机时 `DEL` |
| （无兜底——页面关了变量就没了） | `TTL 300s`（崩溃/kill -9 自动摘牌） |

**三个易混概念：inflight ≠ 锁 ≠ 幂等**

| 概念 | 生命周期 | 回答的问题 | 冲突时的表现 |
|------|---------|-----------|--------------|
| **inflight 标记** | 执行期间（瞬态） | "这件事**正在**被谁处理？" | 后来的触发被**拒绝**（返回"处理中"） |
| **锁** | 临界区期间（瞬态） | "谁能进入这段代码？" | 抢不到**跳过或等待** |
| **幂等记录** | 永久/长期（持久） | "这件事**已经**做过吗？" | 重复请求被**静默忽略** |

三者协作时序：查幂等记录（做过→返回旧结果）→ 查 inflight（在途→返回"处理中"）→ 挂标记+抢锁 → 执行 → 写幂等记录 → 摘标记。**inflight 管"正在"、幂等管"已经"、锁管"互斥进入"**——这就是清单里 #3 和 #2 是两个独立机制的原因。

**生态里其他你会遇到 inflight 的地方**：

| 场景 | 含义 |
|------|------|
| Kafka：`max.in.flight.requests.per.connection=5` | 同一连接上"已发出未确认"的请求上限——在途超 5 个就等确认 |
| 网关/服务器监控：`inflight_requests` | 正在处理未返回响应的请求数——过高 = 过载，限流/背压依据 |
| HTTP 客户端 pending 计数 | axios 拦截器统计的 loading 数量 |

> **一句话**：inflight = 在途标记——声明"这个命令正在被处理"，让多实例环境下的重复触发者自动退出；生命周期 = `SET NX` 挂牌到终态 `DEL`（TTL 兜底防崩溃）。前端的"按钮 loading 防重复提交"就是它的单机版。

### 3.3 #3 幂等占位——投递去重

```text
SET ai-trigger:{tid}:{conv}:{rev} NX EX 600
语义：同一个 (任务, 会话, 版本) 的 AI 触发只投递一次；失败撤销 DEL 允许重试
```

- **设计意图**：防重复投递（比如前端重复点击、MQ 重复投递、定时重扫）。
- **rev（revision）的设计很聪明**：把"版本号"编进 key——**同一逻辑的重新触发天然是新 key**（rev+1），不用删旧占位就能重试。
- **"失败撤销 DEL"的语义**：只有确认投递失败才撤销占位——比"一律撤销"更严谨（成功路径不撤销，靠 TTL 过期自然清理，防止投递成功后又收到重复请求）。

### 3.4 #4 分片 claim——重传去重

```text
SET report:part:<n> NX EX
语义：报告的第 n 个分片由我生成——其他重传的同类请求 claim 失败即跳过
```

分片（part）是"把大任务切成小块并行"的产物——每个分片用独立 claim 去重。异常时释放（防泄漏 = 防止 claim 死锁占用）。

### 3.5 #5 任务认领——数据库 CAS + 租约（最值得细看的机制）

```sql
-- 认领：CAS 语义（乐观锁思想的队列版）
UPDATE background_job
SET status = 'EXECUTING', owner = ?, lease_until = NOW() + 租约时长
WHERE id = ? AND status = 'QUEUED';       -- 影响行数 = 1 → 认领成功

-- 回收：定时任务把"租约过期"的任务重新排队
UPDATE background_job SET status = 'QUEUED'
WHERE status = 'EXECUTING' AND lease_until < NOW();
```

- **设计意图**：多实例从任务表认领任务——**"数据库当队列 + DB CAS 当锁"**（分布式全景 §7.2 的"DB 队列 SKIP LOCKED"同族方案）。
- **租约（lease）**：认领不是永久的——超时没完成视为 worker 死了，`reclaimExpiredJobs` 把任务回收重派。**这就是"数据库版看门狗"**：Redisson 靠后台续期，DB 版靠回收扫描——语义相同，实现不同（DB 版简单但精度低、有延迟）。
- **为什么用 DB 而不是 Redis**：任务状态需要与业务数据同事务（认领+业务在同一 DB 事务里更强一致），且任务量在 DB 承受范围内。

### 3.6 #6 JVM 内存锁——最内层的串行

`synchronized (state.lock)`：**同一实例内**，同一状态对象的多线程操作串行。跨实例无效（J11 §8）——所以它前面必须套分布式机制；反过来说，**分布式机制解决不了"实例内多线程"的串行**，#6 补上最内层。七道关卡从外到内，一层都不能少。

### 3.7 #7 XXL-Job 调度互斥——入口层的"要不要触发"

XXL-Job 是分布式任务调度平台（调度中心 + 执行器）：

- **派发路由策略**：轮询/随机/一致性哈希/分片广播——决定"这次调度派给哪个实例"；
- **阻塞策略**：单机串行（同任务上一次没跑完，本次排队）/ 丢弃后续 / 覆盖——决定"上一次还没跑完，这次触发怎么办"；
- **故障转移**：路由目标挂了自动换一个实例。

**与我们场景⑩ 的对照**：场景⑩ 用的是"Spring @Scheduled + Redis 分布式锁"（自研调度互斥）——XXL-Job 把这件事**平台化**：调度中心统一管理触发时间/路由/阻塞/重试/告警，业务代码只写执行逻辑。**触发越多、任务越多，平台化越值钱；任务少时自研方案更轻**。

## 4. 这个项目做对了什么（设计亮点）

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **按生命周期分层，而不是一把大锁** | 七种机制对应七个阶段——粒度从"调度入口"到"进程内线程"，每层只解决自己的问题 |
| 2 | **语义分流** | 锁（#1）/ 闸门（#2）/ 占位（#3）/ 认领（#5）四种语义用四种机制——**失败处理方式各不相同**（呼应 11 篇"按语义封装"） |
| 3 | **TTL 全部显式** | 没有一个不带过期时间的 key——防死锁意识到位 |
| 4 | **租约回收（#5）** | 数据库版看门狗——认领超时自动重派，自愈能力强 |
| 5 | **key 结构化** | `cmd:inflight:{tid}:{iid}`、`ai-trigger:{tid}:{conv}:{rev}`——冒号分层 + 业务标识入 key（Redis 08 §6 同款规范） |
| 6 | **调度与执行分离**（#7） | 触发归 XXL-Job 平台，执行归业务——职责清晰 |

## 5. Review 建议：如果是我来改

| # | 位置 | 问题 | 建议 |
|---|------|------|------|
| 1 | **#1 释放锁** | GET 比对后 DEL 两步非原子 → 可能删别人的锁 | 改 Lua 原子释放（09 篇写法）；或直接换 Redisson（T7） |
| 2 | **#1 TTL 10s** | 领取动作超 10s → 双领取 | 确认临界区耗时上限；不足就加长或加续期 |
| 3 | **#2 停机 DEL** | 依赖优雅停机；kill -9 / OOM 删不掉 | 已有 TTL 300s 兜底 ✓；确认命令执行上限 < 300s |
| 4 | **#3 失败撤销** | 撤销 DEL 失败 → 占位阻塞重试最长 600s | 可接受（低频）；介意则撤销也用 Lua 或缩短 TTL |
| 5 | **机制收口** | 七种机制散落各处 → key/参数容易漂移 | 常量收口（我们项目的 `RedisConstant` 模式，Redis 08 §6） |
| 6 | **观测** | 七道关卡缺统一观测 | 每道关卡打点：抢锁成功率/闸门拒绝数/租约回收数——这是排障的眼睛 |

## 7. 面试速答

```text
Q：一个分布式系统里要几把锁？
A：不是几把，是【按生命周期分层】：调度入口（调度平台/定时）、任务认领（DB CAS+租约）、
   执行许可（inflight 闸门）、投递去重（幂等占位）、资源互斥（SET NX+Lua）、
   进程内串行（synchronized）——每层 key 粒度和语义都不同。

Q：释放锁为什么必须用 Lua？
A：GET 比对 + DEL 是两步，中间锁可能过期被别人抢走 → 误删别人的锁。
   Lua 把"比对+删除"合成原子操作。

Q：租约（lease）和 TTL 有什么区别？
A：TTL 是【锁】的过期（防死锁）；租约是【任务认领】的过期（worker 挂了任务回收重派）。
   一个保护资源，一个保护任务队列——配合使用。

Q：XXL-Job 怎么保证同一任务不重复调度？
A：调度中心路由（一次只派一个实例）+ 执行器阻塞策略（单机串行/丢弃后续）+
   业务侧再加分布式锁兜底——三层配合。
```

## 8. 一句话总结

```text
七种机制 = 一条任务生命周期的七道关卡：调度(#7) → 幂等(#3) → 闸门(#2) → 认领(#5+租约) → 分片(#4) → 资源锁(#1) → 进程内(#6)；
不同阶段的互斥范围与语义不同，所以要不同的机制——这正是"按 key 粒度和生命周期分层设计"的教科书示范；
唯一要改的：#1 的 GET+DEL 释放改成 Lua 原子释放（09 篇写法）。
```
