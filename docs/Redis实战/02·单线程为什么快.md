# 02 · 单线程为什么快

> **状态**：⬜ 未学习 ｜ **下一课**：03·持久化 RDB/AOF

---

## 一、先纠正一个说法

```text
"Redis 是单线程" ——不精确。
【命令执行】是单线程（一条条排队）；网络 IO 与持久化早就是多线程/多进程了
（6.0 起 IO 读写也多线程化了——但执行命令仍单线程）
```

## 二、为什么单线程还这么快

```text
① 纯内存操作（纳秒级，瓶颈根本不在 CPU）
② IO 多路复用（epoll）：一个线程看住所有连接——谁就绪处理谁
   （前端对照：一个事件循环看住所有 IO——Node 事件循环同一母题）
③ 避免锁竞争：没有多线程切换/加锁开销
④ 单线程 = 单线程安全：命令天然原子（SETNX 才能当锁——场景⑨ 的前提！）
```

## 三、IO 多路复用图解

```text
传统阻塞模型：一个连接一个线程（1 万连接 1 万线程——爆）
IO 复用：
  [epoll] ← 监听所有 socket 的"就绪事件"
     ↓ 只把就绪的连接交给【唯一的命令线程】
  执行 SET/GET → 回写结果
  = "餐厅一个服务员看一排呼叫铃"（而不是每桌一个服务员）
```

## 四、什么时候单线程反而成为瓶颈

```text
① 单条命令太慢（KEYS * 扫百万 key——阻塞所有连接，禁用！）
   → 用 SCAN 分批（渐进式思想又一例）
② 读写 QPS 真到 10 万+ → 集群分片（07 课）
③ 大 value 序列化耗时 → 拆小/压缩
```

## 五、项目关联

```text
场景⑨ 分布式锁为什么敢用 SETNX？
→ 命令执行单线程 = SETNX 原子（判断+设置不会被打断）
→ 如果是多线程执行，check-then-set 就有竞态，锁就不可靠
（这是"单线程"给工程的最大红利）
```

## 面试速答

```text
Q：单线程为什么快？ A：内存+epoll+无锁竞争；瓶颈不在 CPU。
Q：KEYS 为什么危险？ A：全量扫描阻塞唯一线程 → 所有请求排队 → 用 SCAN。
```

## 一句话

```text
快 = 内存 + IO 多路复用 + 无锁；
单线程的最大红利 = 命令天然原子（场景⑨ 锁的前提）。
禁 KEYS 用 SCAN。
```
