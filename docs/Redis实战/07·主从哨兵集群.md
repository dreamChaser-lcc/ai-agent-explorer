## 三形态一张表

| 形态 | 解决什么 | 核心机制 | 缺点 |
|---|---|---|---|
| **主从复制** | 读扩容 + 数据副本 | 主写 → 异步复制到从 | 主挂了要【人肉】切 |
| **哨兵 Sentinel** | 主挂了自动切 | 哨兵投票选新主 | 写容量没扩（仍单主） |
| **集群 Cluster** | 写容量 + 海量数据 | 16384 槽分片 | 跨槽操作受限 |

## 演进逻辑（每一层补上一层的洞）

```text
① 只有单机 → 挂了全完
   ↓ 主从：从库是热备 + 读分摊
② 主挂要人工 → 哨兵：监控+投票+自动 failover
   （哨兵至少 3 个——奇数投票防脑裂；和 K8s 的多副本选主一个思想）
③ 单主写性能/内存到顶 → Cluster 分片：
   key → CRC16 mod 16384 → 定位槽 → 定位节点
   （哈希分片——数据结构 04 哈希思想的再就业）
```

## 哨兵工作三步（面试常问）

```text
① 主观下线：哨兵 A ping 主超时 → 标记"我觉得挂了"
② 客观下线：询问其他哨兵，过半同意 → 确认"真挂了"
③ 选主 failover：哨兵们投票 → 从库按"数据新 + 优先级"选新主 → 客户端切换
```

## 集群的槽与三大限制

```text
限制① key 跨槽：MSET k1..k3 若落不同槽会报错 → hash tag {user1} 强制同槽
限制② 多 key 事务只能在同槽
限制③ 客户端要"聪明"：先查槽位表，MOVED 重定向跟随
```

## 项目关联

```text
项目当前：单实例 Redis（开发够用）
生产畅想：锁的可靠性要求 → 至少哨兵（自动切）；
若缓存 + 锁混合 → 锁独立一个小集群（noeviction），缓存另一个（lru）
——"按用途分实例"比"一个大杂烩"更稳
```

## 面试速答

```text
Q：主从复制的异步性有什么风险？ A：主挂时未同步的写丢失（锁场景就是
   05 课的丢锁问题）→ Redlock/ fencing 的动机。
Q：为什么槽是 16384？ A：心跳包里要带槽位图，16384 个 bit = 2KB 刚好省带宽。
```

## 一句话

```text
主从（副本）→ 哨兵（自动切）→ 集群（分片扩写）——每层补上层的洞。
哨兵投票防脑裂；集群哈希分片；锁与缓存按用途分实例。
```
