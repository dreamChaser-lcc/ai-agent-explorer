## 0. 先摆正：四种角色解决的是四种不同问题

| 角色 | 一句话 | 核心命令 | 数据形态 | 本项目 |
|---|---|---|---|---|
| **存储型** | 存数据、加速读取 | `SET` / `GET` / `EXPIRE` | String 存 JSON | ✅ 场景⑦ 报告缓存 |
| **协调型** | 多进程「抢资源」 | `SET NX EX` | 一个「占用标记」 | ✅ 场景⑩ 分布式锁 |
| **广播型** | 进程间「喊话 / 传信」 | `PUBLISH` / `SUBSCRIBE` / `XADD` | 消息流 | 🚧 本篇 demo |
| **计算型** | 边存边算统计 | `INCR` / `ZINCRBY` / `PFADD` / `SETBIT` | 计数 / 排名 / 基数 / 位图 | 🚧 本篇 demo |

记忆口诀：**存、抢、喊、算**。

一个容易混淆的点：**分布式锁不属于存储型**。它确实用 `SET` 命令，但存的是一个「我占着」的标记，不是业务数据——本质是用存储能力实现**协调**，所以单列。

## 1. 广播型（一）：Pub/Sub——进程间「喊话」

### 1.1 模型

```text
        PUBLISH demo:broadcast:channel "hello"
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   订阅者 A       订阅者 B       订阅者 C     ← "当时在线"的全部订阅者
  （各收到一份）（各收到一份）（各收到一份）      互不影响，各自处理
```

关键点：**发布方不知道谁在听，订阅方不知道谁发的**——完全解耦，这就是「喊话」。

### 1.2 跑起来

应用启动时 `RedisBroadcastDemoConfig` 已订阅 `demo:broadcast:channel`（应用自己就是一个订阅者）。

```bash
# ① 发布一条消息
curl -X POST "http://localhost:8080/api/redis-playground/broadcast/publish?message=hello-pubsub"

# ② 查看本实例收到的消息
curl "http://localhost:8080/api/redis-playground/broadcast/received"
```

### 1.3 实测输出

发布返回：

```json
{
  "channel": "demo:broadcast:channel",
  "message": "hello-pubsub-1",
  "subscribers": "1",
  "tip": "已推送给 1 个在线订阅者，可调 GET /broadcast/received 查看本实例收到的内容"
}
```

`subscribers` 就是 **PUBLISH 命令的返回值**——Redis 告诉我们「这一瞬间有几个订阅者收到了」。**如果是 0，消息会被直接丢弃**，没有任何补偿。

接收返回：

```json
{
  "channel": "demo:broadcast:channel",
  "count": "1",
  "messages": ["[16:07:53] hello-pubsub-1"]
}
```

### 1.4 ★ Pub/Sub 的四个致命特性

| 特性 | 含义 | 后果 |
|---|---|---|
| **不持久化** | 广播完就从内存消失，Redis 里不留任何痕迹 | 事后无法补读，也没有「历史消息」这回事 |
| **订阅者离线即丢失** | 只在「发布那一刻在线」的订阅者能收到 | 应用重启期间的命令全部错过 |
| **没有 ACK** | 订阅者收到与否、处理成功与否，发布方无从得知 | 没有重试、没有投递保证 |
| **没有消费组** | 所有订阅者都收到**全量**消息，没人分摊 | 想「一条消息只被一个实例处理」做不到 |

> **一句话**：Pub/Sub 是**实时广播**，不是**消息队列**。它适合「此刻在线的人需要知道这件事」（比如配置热更新通知、在线用户刷新），不适合任何「不能丢」的场景。

### 1.5 什么时候能用 / 不能用

| 能用 ✅ | 不能用 ❌ |
|---|---|
| 缓存失效通知（丢一次也没关系，下次查询自然回源） | 订单创建、支付回调 |
| 配置热更新广播 | 任务派发（必须执行的任务） |
| 在线用户/节点的状态广播 | 任何需要「事后补读」的场景 |

## 2. 广播型（二）：Streams——进程间「信箱」

### 2.1 为什么有了 Pub/Sub 还要 Streams

| 能力 | Pub/Sub | Streams |
|---|---|---|
| 消息持久化 | ❌ | ✅（存在流里，可回放） |
| 离线补读 | ❌ | ✅（按 ID 读历史） |
| 消费组（一条消息只被一个消费者处理） | ❌ | ✅ |
| ACK / 待处理列表（PENDING） | ❌ | ✅ |
| 消息堆积能力 | ❌（无缓冲） | ✅（受内存/上限约束） |
| 实现复杂度 | 极简 | 中等 |

**类比**：
- Pub/Sub = **大喇叭广播**：当时在场的人听到，不在场的永远错过
- Streams = **邮箱**：信投进去存着，谁来取都行，取过还能标记「已处理」

### 2.2 跑起来

```bash
# ① 追加两条消息（XADD）
curl -X POST "http://localhost:8080/api/redis-playground/broadcast/stream/send?message=任务A完成"
curl -X POST "http://localhost:8080/api/redis-playground/broadcast/stream/send?message=任务B完成"

# ② 读取流里最新的 N 条
curl "http://localhost:8080/api/redis-playground/broadcast/stream/latest?count=5"
```

### 2.3 实测输出

写入返回（注意 `recordId` 的格式 `时间戳-序号`）：

```json
{"stream":"demo:stream:events","recordId":"1794816474472-0","message":"任务A完成","tip":"消息已持久化，随时可以用 GET /broadcast/stream/latest 补读"}
```

读取返回：

```json
{
  "stream": "demo:stream:events",
  "totalInStream": "2",
  "latest": [
    "1794816474472-0  {message=任务A完成, source=playground}",
    "1794816474485-0  {message=任务B完成, source=playground}"
  ]
}
```

**ID 是可以按区间查询的**：`XRANGE stream 1794816474472-0 +` 就能从指定位置往后读——这就是「离线补读」的实现基础。

### 2.4 Stream 的数据结构：一条只追加的日志

Stream 本质是 **append-only log（只追加日志）**，不是「集合」也不是「队列」：

```text
XADD demo:stream:events * message "任务A完成"
     ↓
[ 1794816474472-0 ] { message: "任务A完成", source: "playground" }
[ 1794816474485-0 ] { message: "任务B完成", source: "playground" }
[ 1794816475001-0 ] { message: "任务C完成", source: "playground" }
        ↑
   消息 ID = <毫秒时间戳>-<同毫秒内序号>
```

三个关键点：

| 特性 | 说明 |
|---|---|
| **ID 由 Redis 生成**（用 `*`） | 单调递增，天然有序；也可以手动指定（如从别的系统导入） |
| **每条消息是 field-value 对** | 类似一个扁平的 Hash，不是任意 JSON 字符串 |
| **底层用 Rax 树索引** | 按 ID 范围查找是 `O(log N)`；`XRANGE` / `XREVRANGE` 极快 |

> **为什么 ID 长这样**：`1794816474472` 是毫秒时间戳（约等于 2026-11-16 16:07），`-0` 是同一毫秒内的第 0 条。所以单看 ID 就知道消息的产生时间，也天然支持「按时间区间查询」。

### 2.5 基础命令全家

```bash
# 写入（* 让 Redis 生成 ID；MAXLEN ~ 1000 表示只保留最近约 1000 条）
XADD demo:stream:events * message "任务A完成" source playground
XADD demo:stream:events MAXLEN ~ 1000 * message "任务B完成"

# 长度
XLEN demo:stream:events

# 按 ID 区间读（- 表示最小，+ 表示最大）
XRANGE demo:stream:events - +              # 全量正序
XRANGE demo:stream:events - + COUNT 10     # 只看前 10 条
XRANGE demo:stream:events 1794816474472-0 + # 从指定 ID 往后读（离线补读的基础）
XREVRANGE demo:stream:events + - COUNT 5    # 最新的 5 条（倒序）

# 删除与裁剪
XDEL demo:stream:events 1794816474472-0     # 删单条（只标记删除，内存不一定立刻回收）
XTRIM demo:stream:events MAXLEN ~ 1000      # 批量裁剪，控制内存上限

# 查看元信息（长度、首尾 ID、消费组数量等）
XINFO STREAM demo:stream:events
```

**两条运维红线**：

1. **必须设置长度上限**（`MAXLEN ~ N` 或定期 `XTRIM`）——Stream 不会自动过期，不裁剪会一直长下去，最终把 Redis 内存吃满。
2. `XDEL` 只删逻辑条目，不释放 Rax 树节点；想真正回收内存要靠 `XTRIM`。

### 2.6 消费组：Streams 真正的杀手锏

这是 Pub/Sub 完全没有、也是 Streams 区别于「简单日志」的核心能力。

```text
                     demo:stream:events（一条流）
                              │
             ┌────────────────┴────────────────┐
             ▼                                 ▼
      消费组 group-A                    消费组 group-B
   （last-delivered-id 独立）        （last-delivered-id 独立）
       ┌─────┴─────┐                        │
       ▼           ▼                        ▼
   消费者 A1    消费者 A2               消费者 B1
   （分摊消息） （分摊消息）          （独立读全量）
```

**四个概念**：

| 概念 | 含义 |
|---|---|
| **消费组（group）** | 一组消费者的逻辑集合，有一份**独立的读取进度**（`last-delivered-id`） |
| **消费者（consumer）** | 组内的具体实例，一条消息只会投给组内**一个**消费者 |
| **PEL（Pending Entries List）** | 已投递但**未 ACK** 的消息清单 |
| **ACK** | 消费者处理完发确认，消息移出 PEL |

**完整流程命令**：

```bash
# 1. 建组（$ = 从"当前最新"开始；0 = 从头开始补读全量）
XGROUP CREATE demo:stream:events group-a $
XGROUP CREATE demo:stream:events group-b 0

# 2. 消费者读取（> 表示"给我这个组还没投递过的新消息"）
XREADGROUP GROUP group-a consumer-1 COUNT 10 BLOCK 2000 STREAMS demo:stream:events >

# 3. 处理完确认（消息移出 PEL）
XACK demo:stream:events group-a 1794816474472-0

# 4. 查看未确认的消息（谁拿了、拿了多久没确认）
XPENDING demo:stream:events group-a

# 5. 故障转移：把"卡住太久"的消息转给别的消费者（Redis 6.2+ 有 XAUTOCLAIM 批量版）
XCLAIM demo:stream:events group-a consumer-2 60000 1794816474472-0
```

**这套机制带来「至少一次（at-least-once）」语义**：

```text
消费者拿到消息 → 处理中崩溃 → 消息仍在 PEL → 其他消费者 XCLAIM 接手 → 重新处理
```

代价是**可能重复处理**（所以消费逻辑要幂等）。这也是所有「至少一次」消息系统的共同要求。

> ⚠️ **版本差异**：`XREADGROUP` / `XPENDING` / `XACK` 在 Redis 5.0 就有；`XAUTOCLAIM` 需要 6.2+。本机 Windows 版 Redis 是 **5.0.14**（微软移植版，2021 年停更），Docker 里的是 **7.x**——两边能用的命令集合不同，写代码前先确认版本。

### 2.7 Spring Data Redis 里怎么写（命令 ↔ API 对照）

前面都是 redis-cli 命令，实际项目里用的是 Spring Data Redis 的 `StreamOperations`。先看对照表：

**基础读写**（不涉及消费组，`demo` 里的两个端点就只用了这组）

| Redis 命令 | Spring Data Redis | 用途 |
|---|---|---|
| `XADD` | `opsForStream().add(StreamRecords.newRecord().ofMap(map).withStreamKey(key))` → `RecordId` | 往流尾**追加一条消息**——写入的唯一入口，返回的 `RecordId` 就是这条消息的「门牌号」 |
| `XLEN` | `opsForStream().size(key)` | 流里**当前有多少条**消息，用来观测积压、判断是否需要裁剪 |
| `XRANGE` | `opsForStream().range(key, Range.unbounded())` | **按 ID 区间正序读**：从某条之后补读、按时间段回溯（离线补读的基础） |
| `XREVRANGE` | `opsForStream().reverseRange(key, Range.unbounded(), Limit.limit().count(n))` | **倒序读最新 N 条**，回答「最近发生了什么」 |
| `XDEL` | `opsForStream().delete(key, recordId)` | 删除指定消息——只是**逻辑标记**，内存不立刻回收（想回收用 `XTRIM`） |
| `XTRIM` | `opsForStream().trim(key, count)` / `trim(key, count, true)`（`true` = 近似裁剪，更快） | **裁剪流长度**，防止无限增长吃满内存（必做的运维动作） |
| `XINFO` | 无专用 API，需 `execute((RedisCallback<Object>) conn -> ...)` | 查看流的**元信息**：长度、首尾消息 ID、有几个消费组 |

**消费组**（回答「谁消费到哪了、有没有漏」）

| Redis 命令 | Spring Data Redis | 用途 |
|---|---|---|
| `XGROUP CREATE` | `opsForStream().createGroup(key, group)` 或 `createGroup(key, ReadOffset.from("0"), group)` | **创建消费组**并声明消费起点：`$` = 从最新开始，`0` = 从头补读全量 |
| `XREADGROUP`（拉） | `opsForStream().read(Consumer.from(group, consumer), StreamReadOptions..., StreamOffset.create(...))` | **组内拉取尚未投递给本组的新消息**（`>` 语义），同步阻塞读，占调用线程 |
| `XREADGROUP`（异步推） | `StreamMessageListenerContainer` + `StreamListener` | **后台线程持续消费**——生产常用形态，不占用 HTTP 请求线程 |
| `XACK` | `opsForStream().acknowledge(key, group, recordId)` | **确认已处理**，把消息移出 PEL（不确认就会被视为"未完成"，可被重投） |
| `XPENDING` | `opsForStream().pending(key, group)` / `pending(key, Consumer.from(...), range, count)` | 查看**积压与未确认**的消息：谁拿了、拿了多久没确认（排障第一命令） |
| `XCLAIM` | `opsForStream().claim(key, group, consumer, minIdleTime, recordId)` | 把**卡住太久**的消息转移给另一个消费者——消费端崩溃后的故障转移手段 |

> 一句话串起来：**`XADD` 写 → 消费组 `XREADGROUP` 取 → 业务处理 → `XACK` 确认**；中间的 `XPENDING` / `XCLAIM` 是"出问题时的补救"，`XTRIM` 是"日常保养"。

#### 本 demo 实际用的写法（同步、无消费组）

```java
// 写入（XADD）
RecordId recordId = redisTemplate.opsForStream().add(
        StreamRecords.newRecord()
                .ofMap(Map.of("message", message, "source", "playground"))
                .withStreamKey(STREAM_KEY));

// 读取全部（XRANGE - +）
List<MapRecord<String, Object, Object>> records =
        redisTemplate.opsForStream().range(STREAM_KEY, Range.unbounded());
```

#### 消费组的完整写法

```java
// ① 建组：从最新开始（$）；注释：组已存在会抛 BUSYGROUP，生产要先判断
redisTemplate.opsForStream().createGroup(STREAM_KEY, "group-a");

// ② 同步拉取（XREADGROUP）：拿组内未投递的新消息，最多 10 条，最多阻塞 2 秒
List<MapRecord<String, Object, Object>> batch = redisTemplate.opsForStream().read(
        Consumer.from("group-a", "consumer-1"),
        StreamReadOptions.empty().count(10).block(Duration.ofSeconds(2)),
        StreamOffset.create(STREAM_KEY, ReadOffset.lastConsumed()));   // lastConsumed() == ">"

// ③ 处理完确认（XACK）——不确认消息会一直留在 PEL
redisTemplate.opsForStream().acknowledge(STREAM_KEY, "group-a", recordId);

// ④ 查看积压（XPENDING）
PendingMessagesSummary summary = redisTemplate.opsForStream().pending(STREAM_KEY, "group-a");

// ⑤ 故障转移（XCLAIM）：把闲置超过 1 分钟的消息转给另一个消费者
redisTemplate.opsForStream().claim(STREAM_KEY, "group-a", "consumer-2",
        Duration.ofMinutes(1), recordId);
```

#### 异步消费者（更接近生产写法）

同步 `read(...)` 会**占住调用线程**，通常只用于定时轮询。生产里多用监听器容器，由后台线程推消息：

```java
@Bean
public StreamMessageListenerContainer<String, MapRecord<String, Object, Object>>
        streamListenerContainer(RedisConnectionFactory connectionFactory,
                                StringRedisTemplate redisTemplate) {

    var options = StreamMessageListenerContainer.StreamMessageListenerContainerOptions.builder()
            .pollTimeout(Duration.ofSeconds(2))     // 内部 XREADGROUP BLOCK 的超时
            .build();

    var container = StreamMessageListenerContainer.create(connectionFactory, options);

    container.receive(
            Consumer.from("group-a", "consumer-1"),
            StreamOffset.create(STREAM_KEY, ReadOffset.lastConsumed()),
            (StreamListener<String, MapRecord<String, Object, Object>>) record -> {
                try {
                    // 业务处理
                    handle(record.getValue());
                    // 成功才 ACK
                    redisTemplate.opsForStream().acknowledge(STREAM_KEY, "group-a", record.getId());
                } catch (Exception e) {
                    // 失败不 ACK → 消息留在 PEL → 可被 XCLAIM 重投（至少一次语义）
                    log.warn("处理失败，等待重投: {}", record.getId(), e);
                }
            });

    container.start();
    return container;
}
```

> 和 §1 里的 Pub/Sub 订阅容器一样，这也是一种**容器级 Bean**：启动即建立阻塞读循环，关闭时停止。区别是它带**消费进度**与 **ACK**，所以能扛住应用重启。

#### 六个必踩的坑

| 坑 | 现象 | 解决 |
|---|---|---|
| **消费组必须先创建** | `XREADGROUP` 报 `NOGROUP No such key ... or consumer group` | 应用启动时 `createGroup`（捕获 `BUSYGROUP` 当成功） |
| 把 `ReadOffset.from("0")` 当默认 | 应用重启后把历史消息全部重放一遍 | 新消息用 `ReadOffset.lastConsumed()`（`>`） |
| 处理完忘了 `acknowledge` | `XPENDING` 持续增长，内存不释放 | 成功分支必须 ACK，失败分支故意不 ACK |
| 在 HTTP 请求线程里 `block()` | 请求线程被挂住，并发一高就排队 | 用监听器容器或单独线程池 |
| 以为泛型是 `<String, String>` | 编译报类型不匹配 | `StringRedisTemplate` 的流操作泛型是 `<Object, Object>`，取值用 `String.valueOf()` |
| 同组多实例用同一个 consumer 名 | 消息被"自己抢自己"，负载不均 | 每实例用唯一名（如主机名/Pod 名） |

### 2.8 ★ 重启会丢吗？——分四种情况

这是实际项目里最重要的问题。答案是**取决于「重启的是什么」**：

| 重启对象 | Stream 数据 | 原因 |
|---|---|---|
| **Spring 应用重启** | ✅ **完全不丢** | 数据在 Redis 里，应用只是客户端；重启后 `XRANGE` 照样能读到 |
| **Redis 容器 restart**（`docker restart`） | ✅ 保留（可能有少量丢失） | 容器文件系统还在，从 `dump.rdb` 恢复 |
| **Redis 容器删除重建**（`docker compose down`） | ❌ **全丢** | 本项目 compose 里 **redis 没挂数据卷**，容器一删 RDB 文件跟着没了 |
| **Redis 进程崩溃**（未正常退出） | ⚠️ 存活到最近一次 RDB 快照 | AOF 关闭时，两次快照之间的写入会丢 |

**本机的真实配置（实测）**：

```text
Windows 版 Redis 5.0.14.1
  save       = 900 1 300 10 60 10000   ← RDB 快照规则（满足任一条件就落盘）
  appendonly = no                       ← AOF 关闭
  dir        = D:\softwares\Redis       ← dump.rdb 存放位置
  aof_enabled: 0
```

含义：

- 应用重启 → Stream 完好（这就是本篇 demo 里 `/broadcast/stream/latest` 重启后仍能读到历史的原因）
- Redis 重启 → 从 `dump.rdb` 恢复；**最后一次快照之后的写入会丢**
- 由于 AOF 关闭，**无法做到「每秒级持久化」**，最坏情况可能丢失几分钟到十几分钟的数据

**要做到「尽量不丢」，三档方案**：

| 目标 | 配置 |
|---|---|
| 丢数据可接受（缓存/事件通知） | 现状即可（RDB） |
| 最多丢 1 秒 | `appendonly yes` + `appendfsync everysec`（Redis 7 默认 AOF 也是 no，需显式开） |
| 绝不丢 + 高吞吐 | 换 Kafka/RocketMQ，Redis 只做缓存 |

**Docker 环境的补充**：`backend/docker/docker-compose.yml` 里的 redis 服务目前**没有挂数据卷**，所以 `docker compose down`（而非 `restart`）会清空所有 Stream 数据。要保留的话给 redis 加卷：

```yaml
  redis:
    volumes:
      - redis-data:/data      # 配合 command: redis-server --appendonly yes 更稳
```

### 2.9 与 Pub/Sub、Kafka 的三角对比

| 维度 | Pub/Sub | Streams | Kafka |
|---|---|---|---|
| 持久化 | ❌ | ✅（RDB/AOF） | ✅（磁盘，可配保留期） |
| 离线补读 | ❌ | ✅（按 ID） | ✅（offset） |
| 消费组 | ❌ | ✅ | ✅ |
| 消息确认 / 重投 | ❌ | ✅（PEL + XACK + XCLAIM） | ✅（offset commit） |
| 并行消费单位 | 无 | 消费组内多消费者（单流有序） | **partition**（可水平扩展） |
| 吞吐量 | 十万级/秒 | 十万级/秒（单节点） | **百万级/秒** |
| 部署复杂度 | 零 | 零（已有 Redis） | 高（集群 + ZK/KRaft） |
| 适用规模 | 实时通知 | 中小量事件流 | 企业级消息平台 |

一句话选型：**「不能丢、量不大、已有 Redis」→ Streams；「大流量、要分区扩容」→ Kafka。**

### 2.10 典型场景

- **轻量消息队列**：任务派发、异步事件（替代 Kafka 的场景，但吞吐和持久化保证弱很多）
- **事件溯源**：把所有领域事件按顺序记录下来，可回放
- **审计流水**：需要「可追溯、可回放」的操作日志

> ⚠️ 别把 Streams 当 Kafka 用：它没有分区（partition）、没有跨节点副本，单机内存受限。真要大吞吐、强持久，仍应上 Kafka/RocketMQ。

## 3. 计算型：四种「边存边算」

计算型的共同点：**数据的价值在「算出来的数字」上，而不是「存下来的原始内容」**。Redis 直接在存储侧完成计算，省掉「取出 → 计算 → 写回」的往返。

### 3.1 INCR 计数器

```bash
curl "http://localhost:8080/api/redis-playground/calc/pageview?page=home"
# 连调三次 → views: 1 → 2 → 3
```

**为什么不用 `GET` 再 `SET`**：

```text
❌  GET views → 10
    另一个请求 GET views → 10（也拿到 10）
    两者都 +1 后 SET 11 → 实际应该是 12（丢失更新）

✅  INCR views    ← 一条命令，原子自增
```

这正是 [09 篇](09·原子操作实战——验证码限流与Lua.md)讲的「原子性只到命令粒度」的正面用法。

**典型场景**：页面访问量、点赞数、库存扣减（配合 `DECR`）、未读数。

### 3.2 ZSet 排行榜

```bash
curl "http://localhost:8080/api/redis-playground/calc/hotkeyword?keyword=redis"
# 连调三次 redis、两次 java、一次 kafka → top5: ["redis : 4","java : 2","kafka : 1"]
```

`ZINCRBY` 累加分数、`ZREVRANGE ... WITHSCORES` 取 Top N。**底层是跳表（skiplist）**，插入和按分值范围查询都是 `O(log N)`。

> 注意：最后一次查询自己也 +1（`redis : 4` 是 3 次打榜 + 1 次查询），这是 demo 把「查询接口顺手算一次」的副作用，真实项目里查询与打榜通常分开。

**典型场景**：热搜榜、游戏排行、销量榜、延时队列（score 存时间戳）。

### 3.3 HyperLogLog 去重计数

```bash
curl "http://localhost:8080/api/redis-playground/calc/uv?userId=u1"   # estimatedUv: 1
curl "http://localhost:8080/api/redis-playground/calc/uv?userId=u2"   # estimatedUv: 2
curl "http://localhost:8080/api/redis-playground/calc/uv?userId=u3"   # estimatedUv: 3
curl "http://localhost:8080/api/redis-playground/calc/uv?userId=u1"   # estimatedUv: 3（重复不加）
```

**原理（一句话）**：HyperLogLog 不存元素本身，而是用哈希值前导零的最大长度来**估算**集合基数。

**关键账**：

| 方案 | 存 1 亿个 user_id 的内存 | 精度 |
|---|---|---|
| `Set`（存全部元素） | 约 1~2 GB | 精确 |
| **HyperLogLog** | **固定约 12 KB** | 误差约 **0.81%** |

差别是**五个数量级**。代价是「不能取出元素」（`PFADD` 只能加、`PFCOUNT` 只能问有多少个），也不能删除单个元素。

**典型场景**：日活 UV、独立 IP 数、搜索结果去重计数——凡是「只要一个大概的数字，不需要具体是谁」都适用。

### 3.4 Bitmap 位图

```bash
curl "http://localhost:8080/api/redis-playground/calc/checkin?userId=u100&dayOfWeek=1"  # checkedDays: 1
curl "http://localhost:8080/api/redis-playground/calc/checkin?userId=u100&dayOfWeek=3"  # checkedDays: 2
curl "http://localhost:8080/api/redis-playground/calc/checkin?userId=u100&dayOfWeek=5"  # checkedDays: 3
```

**原理**：String 的每个 bit 都可以独立寻址。`SETBIT key offset 1` 把第 offset 位设为 1，`BITCOUNT key` 数 1 的个数。

**关键账**：

| 需求 | 数据结构 | 内存 |
|---|---|---|
| 1 亿用户 × 每天签到（365 天） | `SET` 存用户 ID | 几十 GB |
| 同上 | **Bitmap**（每个用户 365 bit ≈ 46 字节） | **约 4.6 GB**；如果只是「某一天谁签到了」，1 亿 bit = **12.5 MB** |

**位运算还能做组合统计**：

- 连续签到：`BITOP AND` 求交集
- 「7 天内登录过」：`BITOP OR` 求并集
- 活跃用户留存：多天 Bitmap 做 AND

**典型场景**：签到、日活/月活、在线状态、去重标记（布隆过滤器也是位图的衍生）。

### 3.5 四种计算型横向对比

| 结构 | 能干的事 | 内存 | 精度 | 能取出元素吗 |
|---|---|---|---|---|
| String（`INCR`） | 单个计数 | 极小 | 精确 | 值本身就是结果 |
| ZSet | 排序 + 排名 + 范围查询 | 每元素约 50~100 字节 | 精确 | ✅ 能 |
| HyperLogLog | 只算「有多少个不同的」 | **固定 12 KB** | 估算 ±0.81% | ❌ 不能 |
| Bitmap | 布尔标记 + 位运算 | 按最大 offset 计，1 亿位 ≈ 12 MB | 精确 | 按位查 ✅ |

## 4. 选型决策表

```text
需求 → 选谁？

「要存一个对象，下次原样取出来」           → 存储型：String + JSON + TTL
「多个实例抢同一份资源」                   → 协调型：SET NX EX（或 Redisson）
「在线的人需要立刻知道，丢了也无所谓」      → Pub/Sub
「消息不能丢，要能补读 / 分摊消费」         → Streams（或直接上 Kafka）
「就是想知道有多少次 / 多少个」             → INCR
「想排名、想取 TopN」                      → ZSet
「只想要一个大概的独立访客数」              → HyperLogLog
「一堆是/否的状态，还想做位运算」           → Bitmap
```

## 6. 常见坑速查

| 坑 | 说明 | 正确做法 |
|---|---|---|
| 用 Pub/Sub 做任务派发 | 订阅者重启期间的消息全丢，且多实例会重复处理 | 用 Streams 消费组或 MQ |
| 以为 PUBLISH 成功就是「送到了」 | 返回值 0 时根本没人在听，消息已丢弃 | 检查 `subscribers`，或改用 Streams |
| 用 `Set` 统计 UV | 1 亿用户要 1~2 GB | HyperLogLog（12 KB） |
| 用 `KEYS` 找签到数据 | 全库扫描会阻塞 | 直接 `BITCOUNT` / `GETBIT` 按 key 查 |
| Bitmap 的 offset 乱用 | offset 决定内存上限（offset=1 亿就是 12MB） | offset 用「用户 ID 取模」或「天数」，别直接用超大的随机值 |
| 把计数器和缓存 key 混在一起 | 一是怕被误删，二是淘汰策略（LRU）会把统计值淘汰掉 | 统计类 key 单独前缀 + 不设 TTL 或单独 Redis 实例 |
| ZSet 存超大集合 | 元素多时内存和范围查询成本都上来 | 只保留 TopN（定期裁剪）或按天分 key |

---

## 7. 一句话总结

> **存储型存事实、协调型抢标记、广播型传消息、计算型算数字。**
> 广播型里 Pub/Sub 是「喊话」（在线的才听到），Streams 是「信箱」（存着，随时补读）；
> 计算型里 `INCR` 求次数、`ZSet` 求排名、`HyperLogLog` 求基数、`Bitmap` 求状态——**选对结构，内存能差五个数量级**。
