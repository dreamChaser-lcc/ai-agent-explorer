## 一、锁的进化四步（项目场景⑨ 的全景）

```text
① 裸 SETNX lock:task 1
   → 崩了没释放 = 死锁 ✗

② SET key value NX EX 30（原子：设 + 过期）
   → 解决死锁，但"删别人的锁"风险来了：
     A 超时 30s，第 31s 才干完 → DEL 删掉了 B 刚拿到的锁 ✗

③ value = 唯一标识（UUID.线程ID），删锁前【校验是不是自己的】
   → 但"GET 判断 + DEL"两步不原子（检查完就过期了呢）✗

④ Lua 脚本：判断 + 删除一气呵成（Redis 单线程 = 脚本原子执行）✓
   ——项目场景⑨ 走到的层级
```

## 二、场景⑨ 的真实链路对号

```text
executeTask(taskId)：
  SET research:lock:task:{id} token NX EX 30
  ├── 成功 → 执行 → finally：Lua 校验 token 删除锁
  └── 失败 → 跳过（消息会重投，下个消费者再试）——【宁可跳过不并发】
```

## 三、三个进阶问题（面试必追）

```text
Q1：锁过期但业务没跑完怎么办？
A：看门狗续期（Redisson 的 dog）：每 10s 检查还持有就延长——
   场景⑨ 若上 Redisson 就免费获得。

Q2：主从切换丢锁怎么办？
A：主写锁成功但还没同步到从 → 主宕机，从提升 → B 在"新主"上拿到锁
   → 两个 A/B 同时持锁！
   Redlock：向多个独立节点加锁，过半成功才算——争议大（有脑裂分歧），
   生产更多用" fencing token（带版本号的锁）"或改用 ZK/etcd。

Q3：Redis 锁 vs Zookeeper 锁？
A：Redis 性能高、实现简单但一致性弱（宕机窗口）；
   ZK 强一致（临时节点+会话失效自动释放）但吞吐低。
   项目选 Redis = 互联网主流取舍。
```

## 四、面试速答

```text
Q：Redis 分布式锁怎么保证原子？
A：加锁 SET NX EX 一条命令；解锁用 Lua（判断+删除原子）。
Q：为什么不用 synchronized？
A：只锁本 JVM——多实例部署锁不住另一台（J8 附二）。
```

## 一句话

```text
四步进化：SETNX → 加 EX → value 唯一标识 → Lua 原子删。
场景⑨ 就是第④级的工程实践；再往前是 Redisson 看门狗与 Redlock 之争。
```
