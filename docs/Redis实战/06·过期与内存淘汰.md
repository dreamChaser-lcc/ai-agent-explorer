# 06 · 过期删除与内存淘汰

> **状态**：⬜ 未学习 ｜ **下一课**：07·主从哨兵集群

---

## 一、两个不同的问题（最容易混）

```text
过期删除：key 到期了【怎么删】——定期+惰性
内存淘汰：内存满了【删谁】——8 种策略
先删过期的 → 不够 → 才轮到淘汰策略
```

## 二、过期删除：两招配合

```text
惰性删除：访问时发现过期才删（CPU 友好，但冷 key 占内存）
定期删除：默认每 100ms 随机抽 20 个带 TTL 的 key：
  过期比例 > 25% → 再抽一轮（循环兜底）
两者互补 = "顺手清 + 定时扫"——又是渐进式思想（数据结构 04 的 rehash 同源）
```

## 三、内存淘汰 8 策略（完整清单）

一共 8 种，是「**淘汰范围** × **淘汰依据**」的组合：

| 策略 | 淘汰范围 | 淘汰依据 | 一句话 |
|---|---|---|---|
| **`noeviction`**（默认） | — | 不淘汰 | 内存满了**写命令直接报错**，只允许读与删 |
| **`allkeys-lru`** | 全部 key | 最久**未使用** | 纯缓存首选，通用性最好 |
| **`allkeys-lfu`** | 全部 key | **使用次数最少** | 热点稳定的缓存，抗「缓存污染」 |
| `allkeys-random` | 全部 key | 随机 | 不在意淘汰谁，省 CPU |
| **`volatile-lru`** | 只含 TTL 的 key | 最久未使用 | 缓存 key 与持久 key 混放时 |
| **`volatile-lfu`** | 只含 TTL 的 key | 使用次数最少 | 同上，但需抗污染 |
| `volatile-random` | 只含 TTL 的 key | 随机 | 同上，但不在意 |
| `volatile-ttl` | 只含 TTL 的 key | **最快过期**的优先 | 缓存全带 TTL，且希望快过期的先走 |

> **LFU 是 Redis 4.0 才引入的**（老版本只有 LRU / random / ttl）——所以面试问"Redis 有哪些淘汰策略"，答 4 个和答 8 个，反映的是看的是哪年的文档。

### 3.1 LRU 与 LFU 的本质区别

| | LRU（Least Recently Used） | LFU（Least Frequently Used） |
|---|---|---|
| 关注点 | **上一次使用时是什么时候** | **一共被用了多少次** |
| 优点 | 实现简单、符合直觉、对新数据友好 | 保护长期热点，**抵抗缓存污染** |
| 缺点 | **偶发的大批量扫描会把热点挤掉** | 新 key 容易被老 key 压住（靠衰减机制补偿） |
| Redis 实现 | **近似 LRU**：每个 key 记「访问时钟」，淘汰时随机抽 `maxmemory-samples` 个（默认 5）挑最旧 | **8 bit 计数器**（0~255）+ 概率递增 + 按分钟衰减 |

#### 为什么需要 LFU：一句话讲清「缓存污染」

```text
场景：缓存了 100 万个热点商品，命中率 98%

凌晨跑了一个数据导出任务，全表扫描 200 万条冷数据
→ 这些冷数据都被"访问"了一遍（并可能写了缓存）
→ LRU 认为"它们是最近用过的" → 把热点商品挤了出去
→ 第二天早高峰，命中率跌到 20%，数据库被打穿

LRU 只看"最近"，不看"频率"——这是它最大的软肋。
换成 allkeys-lfu，那 200 万条冷数据哪怕刚被访问过，
因为累计次数低，仍然排在淘汰队列前面。
```

#### Redis 的 LFU 细节（面试爱问）

```text
计数器只有 8 位（0~255）→ 不是精确次数，到顶就不再涨
递增是【概率性】的 → 次数越多越难涨（避免一个 key 永远霸榜）
每 lfu-decay-time（默认 1 分钟）衰减一次 → 让"过去的爆款"慢慢失宠
可调：lfu-log-factor（默认 10，控制递增难度）、lfu-decay-time
```

### 3.2 `allkeys-*` 与 `volatile-*` 的分界线（两个坑）

```text
allkeys-*    → 从【所有 key】里挑
volatile-*   → 只从【设置了 TTL 的 key】里挑
```

**坑 1**：如果全库 key **都没设 TTL**，`volatile-lru` 就「无 key 可淘汰」→ 行为退化成 `noeviction`（写报错）。很多人配了 `volatile-lru` 以为万事大吉，内存照样爆。

**坑 2（本项目相关）**：分布式锁 `lock:task:exec:*` 是**带 TTL 的 key**。若同一实例配 `volatile-lru`，内存紧张时**锁可能被淘汰** → 并发保护失效，两个执行器同时跑同一个任务。所以：

> **存锁/计数器的实例必须 `noeviction`，或者拆到独立实例。**

### 3.3 Redis 的 LRU 是近似实现（考点）

```text
不是教科书 LRU（双向链表，全局精确）：
近似 LRU——每个 key 只记"最近访问时钟"，
淘汰时随机抽 maxmemory-samples 个（默认 5）挑最旧的
→ 省内存省 CPU（全局链表维护成本太高）
工程再一次印证：够好 > 完美
```

### 3.4 选型决策树

```text
① 这个 Redis 存了「不能丢」的东西吗？（锁 / 队列 / 计数器 / 会话）
   ├─ 是 → noeviction（配内存监控告警，靠扩容而不是淘汰）
   └─ 否 ↓

② 是不是纯缓存？（丢了能回源 DB）
   ├─ 是 ↓
   │   ├─ 访问分布平稳 → allkeys-lru        ← 最通用，闭眼选它
   │   ├─ 有明显热点 + 会被批量扫描污染 → allkeys-lfu
   │   └─ 完全无所谓谁走 → allkeys-random（省 CPU）
   │
   └─ 否（缓存 key 与持久 key 混存）↓

③ 混存场景
   ├─ 缓存带 TTL、持久不带 → volatile-lru / volatile-lfu   ← 用 TTL 区分两类 key
   ├─ 缓存带 TTL 且希望"快过期的先走" → volatile-ttl
   └─ 混存很重 → 别混，拆成两个实例（生产更常见）
```

### 3.5 本项目的对照表

| 项目里的 key | 性质 | 该用哪个策略 |
|---|---|---|
| `report::<taskId>`（场景⑦缓存，TTL 30 分钟） | 纯缓存，丢了回源 | `allkeys-lru` 也没问题 |
| `lock:task:exec:*`（场景⑨锁，TTL 5 分钟） | **绝不能丢** | 必须 `noeviction` |
| `demo:*`（教学演示） | 无所谓 | 随便 |
| Session（若将来引入 Spring Session） | 丢了用户掉登录 | `noeviction` 或独立实例 |

因为**锁和缓存现在共用一个 Redis**，最稳妥是：

```conf
maxmemory 512mb
maxmemory-policy noeviction     # 保护锁；缓存靠 TTL 自然过期（30 分钟）
```

生产里更常见的是**物理隔离**：一个实例存缓存（`allkeys-lru`），另一个存锁/计数（`noeviction`）。

### 3.6 三个相关参数

| 参数 | 默认 | 作用 |
|---|---|---|
| `maxmemory-samples` | 5 | 近似 LRU/LFU 的抽样数量，越大越接近真实算法（10 基本够用） |
| `lfu-log-factor` | 10 | LFU 计数器递增难度，越大越难涨 |
| `lfu-decay-time` | 1（分钟） | LFU 计数衰减周期，越小热点更替越快 |

## 四、★ 前置真相：`maxmemory` 默认是 0（不限内存）

这是理解"内存满了会怎样"的前提，很多人跳过了它：

```text
maxmemory          = 0            ← 默认值：不限制
maxmemory-policy   = noeviction   ← 默认值：不淘汰，写命令直接报错

两个默认值叠加 = 淘汰策略根本没有机会触发
内存一路涨到物理上限 → 操作系统 OOM Killer 杀掉 redis-server
→ 进程死亡 + 最后一次 RDB 之后的写入全部丢失
```

所以 **"内存满了会按策略淘汰"这句话，前提是你配了非 0 的 `maxmemory`**。不配的话不是"淘汰得不好"，而是"根本没在管"。

本机实测（Windows 服务版 Redis 5.0.14）：

```text
maxmemory        = 0
maxmemory-policy = noeviction
used_memory      = 1.00M（峰值 2.00M）
```

## 五、配置写在哪：三种来源，优先级从高到低

```text
① 启动命令行参数   redis-server --maxmemory 512mb --maxmemory-policy allkeys-lru
② 配置文件         redis.conf 里写 maxmemory 512mb
③ 编译内置默认值   maxmemory 0 / noeviction
```

**高优先级覆盖低优先级**：命令行参数最硬，其次是配置文件，最后是内置默认。

### 各环境的实际位置

| 环境 | 配置文件位置 | 改法 |
|---|---|---|
| **Windows 服务版**（本项目 dev） | `D:\softwares\Redis\redis.windows-service.conf`（服务注册时 `--service-run` 指定） | 改文件 → 管理员执行 `sc stop Redis` + `sc start Redis`。注意 `redis.windows.conf` 是命令行手动启动用的，**服务不读它** |
| **Docker（compose）** | 镜像默认不带 conf | 两种：① `command: ["redis-server", "--maxmemory", "512mb", "--maxmemory-policy", "allkeys-lru"]`；② 挂 `./redis.conf:/usr/local/etc/redis/redis.conf` + `command: ["redis-server", "/usr/local/etc/redis/redis.conf"]` |
| **K8s** | ConfigMap 挂载成 `redis.conf` | Deployment 里 `command: ["redis-server", "/etc/redis/redis.conf"]` + `volumeMounts` |
| **云托管**（阿里云 Tair / AWS ElastiCache） | 不提供 conf 文件 | 控制台「参数组 / 参数模板」里设 `maxmemory` 与 `maxmemory-policy`，重启实例生效 |

### 运行时临时改（验证用，重启失效）

```bash
CONFIG SET maxmemory 512mb
CONFIG SET maxmemory-policy allkeys-lru
CONFIG REWRITE     # 写回配置文件——仅当启动时指定过 conf 文件；无 conf 的容器会报错
```

## 六、企业里到底怎么配：配置文件为主，命令行参数为辅

| 维度 | 配置文件 | 启动命令行参数 |
|---|---|---|
| 可版本化 | ✅ 进 Git，能 diff、能回滚 | ❌ 散落在启动脚本/编排文件里 |
| 可审计 | ✅ 打开一个文件就是全部配置 | ❌ 分散多处，容易漏 |
| 条目数量 | ✅ 生产 conf 常 100+ 项 | ❌ 命令行塞不下（也不可读） |
| 变更管控 | ✅ 走 Code Review / GitOps | ⚠️ 改启动命令风险更高 |
| 适用场合 | **生产 / 预发** | 临时试验、快速验证 |

```text
生产/预发：redis.conf（Git 版本化）→ 挂载进容器或直接放主机 → 重启生效
临时试验：redis-server --maxmemory 100mb（或 docker run 追加参数）
小项目/compose：command 里写几项很常见（学习环境够用）
K8s：ConfigMap 存 redis.conf（独立更新与审计），而不是把参数塞进 command
云托管：参数组代替 conf 文件——本质仍是"集中式配置"，形态换成控制台/API
```


## 八、容量上限（"最大能存多少"）

```text
单 value：String 上限 512MB；集合类元素数上限 2^32-1（约 42.9 亿）
key 长度：理论 512MB，实践中建议 < 1KB（长 key 费内存又费带宽）
总容量：Redis 自己不限制（maxmemory=0）→ 由机器物理内存决定
经验值：单实例内存 ≤ 物理内存 60~70%（留 RDB fork 的写时复制空间）
        大 key 阈值：String > 10KB、集合 > 5000 元素 → 该拆了
        1 亿个 100 字节的 key ≈ 10~20GB（含 dict 与对象开销）
```

## 面试速答

```text
Q：过期 key 立刻消失吗？ A：不——惰性+定期两招，之间有窗口。
Q：内存满了怎么决定牺牲谁？ A：maxmemory-policy——纯缓存 allkeys-lru，
   关键数据 noeviction。
Q：内存满了就一定会淘汰吗？ A：不一定——maxmemory 默认 0 不限内存，
   没配它时淘汰策略不会触发，最终是 OS OOM Killer 杀进程。
Q：生产怎么配？ A：redis.conf 版本化管理后挂载，启动命令行参数只用于临时试验；
   K8s 用 ConfigMap，云托管用参数组。
Q：Redis 有哪些淘汰策略？ A：8 种 = noeviction + {allkeys,volatile}×{lru,lfu,random}
   + volatile-ttl；LFU 是 4.0 才加的。
Q：LRU 和 LFU 区别？ A：LRU 看"最近一次"，LFU 看"累计频率"；
   LFU 抗缓存污染（批量扫描不会把热点挤掉），代价是新 key 起步吃亏。
Q：volatile-lru 有什么坑？ A：只淘汰带 TTL 的 key——全库无 TTL 时等价 noeviction；
   而且带 TTL 的锁也可能被淘汰，存锁的实例必须 noeviction。
```

## 一句话

```text
过期删除（定期+惰性）管"到期"，内存淘汰（8 策略）管"满了"——两码事。
纯缓存 allkeys-lru；锁/计数器 noeviction。
Redis 的 LRU 是近似版——够用哲学。
★ maxmemory 不配（默认 0）= 根本没有保护，策略再对也不会触发，
  最终被操作系统 OOM Killer 杀掉——配置写在 redis.conf 里版本化管理。
```
