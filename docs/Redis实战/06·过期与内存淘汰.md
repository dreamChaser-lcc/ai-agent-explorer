# 06 · 过期删除与内存淘汰

> **状态**：⬜ 未学习 ｜ **下一课**：07·主从哨兵集群

---

## 一、两个不同的问题（最容易混）

```text
过期删除：key 到期了【怎么删】——定期+惰性
内存淘汰：内存满了【删谁】——8 种策略
先删过期的 → 不够 → 才轮到淘汰策略
```

## 二、过期删除：两招配合

```text
惰性删除：访问时发现过期才删（CPU 友好，但冷 key 占内存）
定期删除：默认每 100ms 随机抽 20 个带 TTL 的 key：
  过期比例 > 25% → 再抽一轮（循环兜底）
两者互补 = "顺手清 + 定时扫"——又是渐进式思想（数据结构 04 的 rehash 同源）
```

## 三、内存淘汰 8 策略（记 4 个主流）

| 策略 | 淘汰谁 | 场景 |
|---|---|---|
| **noeviction**（默认） | 不淘汰，写报错 | 缓存丢数据会伤的（如锁） |
| **allkeys-lru** | 全部 key 里最久未用 | **纯缓存场景首选** |
| volatile-lru | 只在带 TTL 的 key 里 LRU | 有"永久 key"混存时 |
| volatile-ttl | 快过期的先走 | 缓存自动续期的场景 |

```text
项目联想：如果把 Redis 当"任务详情缓存"→ allkeys-lru（丢了就回源 DB）
         如果存锁/计数器 → noeviction（被淘汰=锁失效=并发事故！）
```

## 四、LRU 的真实实现（考点）

```text
Redis 不是教科书 LRU（双向链表，全局精确）：
近似 LRU——每个 key 记"最近访问时钟"，淘汰时随机抽 N 个挑最旧的
→ 省内存省 CPU（全局链表维护成本太高）
工程再一次印证：够好 > 完美
```

## 面试速答

```text
Q：过期 key 立刻消失吗？ A：不——惰性+定期两招，之间有窗口。
Q：内存满了怎么决定牺牲谁？ A：maxmemory-policy——纯缓存 allkeys-lru，
   关键数据 noeviction。
```

## 一句话

```text
过期删除（定期+惰性）管"到期"，内存淘汰（8 策略）管"满了"——两码事。
纯缓存 allkeys-lru；锁/计数器 noeviction。
Redis 的 LRU 是近似版——够用哲学。
```
