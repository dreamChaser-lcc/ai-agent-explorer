## 零、先建立分层：这四样东西不是一回事

| 概念 | 属于哪一层 | 一句话定位 |
|---|---|---|
| **MQ（消息队列）** | 中间件**类别** | 系统间通过"队列"异步通信的统称 |
| **RabbitMQ** | 具体**产品**（业务队列流派） | 可靠投递的业务消息中间件 |
| **Kafka** | 具体**产品**（日志流流派） | 高吞吐、可重放的事件流平台 |
| **MQTT** | **协议**（不是产品） | 为物联网设计的轻量级发布/订阅协议 |

**关键**：RabbitMQ / Kafka 是"软件"，MQTT 是"通信协议"（就像 HTTP 是协议、Nginx 是实现 HTTP 的软件）。

## 一、MQ（消息队列）是什么

### 1.1 一句话与结构图

**MQ = 独立部署的"中转站"**，让系统之间不直接调用，而是"把话放进桶里，谁要谁取"。

```
生产者 Producer ──put──▶ [ Broker 消息队列 ] ◀──pull── 消费者 Consumer
```

| 角色 | 是什么 | 类比 |
|---|---|---|
| Producer 生产者 | 发消息的一方 | 寄信人 |
| Broker 服务器 | 存消息的中间件进程 | 邮局 |
| Queue / Topic | 存放消息的"桶/信道" | 邮箱/频道 |
| Consumer 消费者 | 取消息处理的一方 | 收件人 |

### 1.2 MQ 解决的四大价值

| 价值 | 解决的问题 | 例子 |
|---|---|---|
| **异步** | 主流程被慢操作拖住 | 注册不用等短信发完 |
| **解耦** | 加下游要改上游代码 | 支付后加新系统不用改支付服务 |
| **削峰填谷** | 瞬时洪峰压垮系统 | 秒杀请求先入队再慢慢处理 |
| **数据管道** | 海量数据写入顶不住 | 埋点日志高吞吐收集分发 |

**MQ 的本质**：**用"增加一个存储层"换掉"直接调用"**——把同步变异步、把耦合变订阅、把洪峰变排队。

### 1.3 消息系统两大流派（核心认知）

| | 流派 A：传统队列（RabbitMQ） | 流派 B：日志流（Kafka） |
|---|---|---|
| 推 / 拉 | Broker **推**给消费者 | 消费者自己**拉** |
| 谁记进度 | Broker（删了就是进度） | **消费者记 offset** |
| 消费完删吗 | 确认后**删除** | **保留 N 天**，可重读 |
| 适合 | 业务指令/任务 | 事件流/日志/大数据 |

### 1.4 投递语义（delivery semantics）

| 语义 | 含义 | 常见做法 |
|---|---|---|
| at-most-once | 最多一次，可能丢 | 先提交后处理（❌ 会丢消息） |
| at-least-once | 至少一次，可能重复 | **先处理再提交**（✅ 最常用，配幂等） |
| exactly-once | 精确一次 | 事务 + 去重，成本高 |

## 二、RabbitMQ 详解

### 2.1 定位

**"业务系统的可靠传话筒"**——消息是"指令/任务"，要保证送到、处理掉、失败能重试。

### 2.2 核心模型：多了一层 Exchange

```
生产者 Producer
    │ publish(exchange, routingKey, 消息体)
    ▼
Exchange 交换机（不存消息，只做路由判断）
    │ 按类型 + routingKey 投到 0~N 个 Queue
    ▼
Queue 队列（真正存消息）
    │ Broker 按轮询 push 给消费者
    ▼
Consumer（处理完回 ack，Broker 才删除）
```

**Exchange 三种类型**：

| 类型 | 路由规则 | 用途 |
|---|---|---|
| `fanout` | 广播给所有绑定队列 | 发布订阅 |
| `direct` | routingKey 精确匹配 | 点对点 |
| `topic` | routingKey 模糊匹配（`order.*.paid`） | 主题订阅 |

### 2.3 回答"订阅方怎么知道取哪条消息"

**消费者不用挑，是 Broker 派发的。**

**场景 1：一个队列多消费者（竞争消费，每条只给一人）**
```
Queue: [订单1][订单2][订单3][订单4]
消费者A ← 订单1（Broker 派发）
消费者B ← 订单2
消费者A ← 订单3
消费者B ← 订单4
```
Broker 轮询把队头消息 push 给空闲消费者，处理完 `ack` 才真正删除。

**场景 2：发布订阅（每个订阅者一份副本）**
```
Producer 发"用户下单"
    ▼ Exchange(fanout/topic)
    ├─▶ queue-积分 ──▶ 积分消费者（副本1，ack 后删）
    ├─▶ queue-短信 ──▶ 短信消费者（副本2，ack 后删）
    └─▶ queue-统计 ──▶ 统计消费者（副本3，ack 后删）
```
每个订阅者绑自己的 Queue，交换机复制一份投进各 Queue，各消费者互不影响。

### 2.4 一条消息的完整一生

```
t0 下单服务 publish("order.exchange", "order.created", {orderId:1})
t1 Exchange 按 routingKey 投到 order-queue
t2 Broker 把消息 push 给短信消费者
t3 消费者处理完 → ack
t4 Broker 删除该消息（使命完成）
   （若 t3 没 ack：消息留在队列，Broker 重新派发，直到成功）
```

### 2.5 RabbitMQ 适合的场景

- **异步解耦**：注册后发短信/送积分，主流程立刻返回
- **任务队列/削峰**：秒杀请求入队，worker 按能力消费（每条只处理一次）
- **延迟任务**：下单 30 分钟未支付自动关单（TTL + 死信队列，Kafka 做这个很别扭）
- **可靠业务事件**：订单支付 → 扣库存（要重试、要死信人工兜底）

**口诀**：凡"业务指令"——通知、任务、延迟、要重试死信——选 RabbitMQ。

## 三、Kafka 详解

### 3.1 定位

**"海量事件的传送带 + 可重放的数据底座"**——消息是"事实/数据"，要吞吐、要留存、要给多个下游各读各的。

### 3.2 核心概念

| 概念 | 说明 |
|---|---|
| **Topic** | 一类消息的集合（如 `user-click`） |
| **Partition** | Topic 拆成多个分区，可分布在不同机器 → 并行读写（吞吐的秘密） |
| **Offset** | 消息在分区里的递增编号（消息自带，存在 Broker 日志里） |
| **Append-only log** | 只往文件末尾追加，顺序写磁盘 → 极快（接近内存速度） |
| **Retention** | 消息保留 N 天（默认 7 天），**不因被消费而删** |
| **Consumer Group** | 消费组：组内每个消费者负责部分分区，组内分工并行 |
| **Broker / Replica** | 服务器节点；分区多副本，leader 挂了自动切换 |

### 3.3 两个"offset"必须分清（最容易晕）

| 名字 | 是什么 | 存在哪里 |
|---|---|---|
| **① 消息 offset** | 消息在分区里的**序号**（消息自带） | **Broker 磁盘**（分区日志 `.log` + 索引 `.index`） |
| **② 消费进度 offset** | 某消费组"读到第几条"（书签） | **Broker 内部 Topic `__consumer_offsets`** + 消费者内存 |

**① 是"书的页码"，② 是"你夹的书签"。**

### 3.4 ① 消息 offset 存在哪（物理存储）

```
Topic: order-events, Partition 0 → 目录 /kafka-logs/order-events-0/

00000000000000000000.log        ← 存消息本体（msg0~msg999）
00000000000000000000.index      ← 稀疏索引：offset → 物理位置（约每 4KB 一条）
00000000000000000000.timeindex  ← 时间索引：时间戳 → offset
00000000000000000999.log        ← 下一个 segment
```
- `.log` 只追加写，offset 是该分区内单调递增序号
- 查找：给定 offset → 二分查 `.index` → 定位 segment → 顺序扫描找到精确消息
- **消息和它的编号一起存在 Broker 磁盘上**，所以才能保留 7 天、支持重放

### 3.5 ② 消费进度 offset 存在哪

**存在 Kafka 自己维护的内部 Topic：`__consumer_offsets`（默认 50 个分区）**

它本质是一张 KV 表：

| Key | Value |
|---|---|
| `(group=库存组, topic=order-events, partition=0)` | `offset=5001, metadata` |
| `(group=库存组, topic=order-events, partition=1)` | `offset=4999` |
| `(group=数据分析组, topic=order-events, partition=0)` | `offset=1201` |

- **Key = 消费组 + 主题 + 分区**（三元组定位"谁的哪个分区读到哪"）
- 该 Topic 用 **compact 压缩策略**：同 Key 只保留最新值（旧进度会被清理）
- 历史：0.9 之前存 ZooKeeper，现代 Kafka 存 `__consumer_offsets`

### 3.6 完整流程时间线（offset 怎么流动）

```
【t0 启动】库存组 consumer-A 被分配到 Partition 0
   查 __consumer_offsets：(库存组, order-events, 0)
   ① 查到 → 从该 offset 继续
   ② 查不到（新组）→ 按 auto.offset.reset：
        earliest：从分区开头读（读历史全量）
        latest：从分区末尾读（只读新消息，默认）

【t1 拉取】发 pull 请求："我是库存组，P0，从 offset 5001 开始"
   Broker 用 .index/.log 定位 → 返回一批消息
   消费者内存 currentOffset 推进到 5501

【t2 处理】逐条处理业务（扣库存、写库...）

【t3 提交】处理成功后提交："库存组 P0 进度 = 5501"
   → 写入 __consumer_offsets（书签持久化）

【t4 崩溃】consumer-A 挂了 → rebalance → consumer-B 接管 P0
   → 读 __consumer_offsets：5501 → 从 5501 继续（不重头、不漏）

【t5 重放】发现昨天数据算错 → 把 offset 重置回 3000 → 重新消费
   （因为消息还在分区里没删！这是传统 MQ 做不到的）
```

### 3.7 提交时机决定语义（必懂的坑）

**自动提交（默认 5 秒一次）的问题**：
```
t0 自动提交 offset=100
t1 拉到 msg100~199，正在处理
t2 还没到下次提交 → 崩溃
t3 新消费者从 offset=100 继续 → msg100~199 被重复消费
→ at-least-once，消费者必须做幂等
```

**手动提交（推荐）**：
```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord record : records) {
        processRecord(record);      // ① 先处理业务
    }
    consumer.commitSync();          // ② 全部成功后才提交 offset
}
```

| 方式 | 语义 | 后果 |
|---|---|---|
| 先提交，后处理 | at-most-once | **丢消息**（❌ 禁止） |
| 先处理，再提交 | at-least-once | 可能重复（✅ 配幂等，最常用） |
| 事务 | exactly-once | 复杂、慢 |

**黄金法则：业务处理做幂等（用 orderId/msgId 去重），offset 处理完再提交。**

### 3.8 为什么 Kafka 不删消息（三个原因）

1. **多消费组需要各自重读**：3 个组读同一 Topic，各有各的 offset
2. **消费速率不同**：实时组跟得紧（offset 靠前），离线组慢（靠后），互不干扰
3. **可重放（replay）**：重置 offset 重跑历史数据（修 bug、补数据、重训练模型）

### 3.9 Kafka 为什么能百万 QPS

| 手段 | 说明 |
|---|---|
| 分区并行 | N 分区分布多台机器并行读写 |
| 顺序写磁盘 | append-only，顺序 IO 接近内存速度 |
| 批量 + 零拷贝 | 攒批发送、sendfile 减少拷贝 |
| 页缓存 | 近期数据直接读 OS 页缓存 |

### 3.10 Kafka 适合的场景

- **用户行为埋点/日志收集**（百万/秒，RabbitMQ 顶不住）
- **数据同步管道 CDC**（MySQL binlog → Kafka → ES/Redis/数仓）
- **事件溯源/审计日志**（全量事件留存 30 天，可回放排查）
- **实时流计算**（Kafka → Flink → 实时大屏/告警）

**口诀**：凡"数据/事件流"——埋点、日志、CDC、流计算、要重放——选 Kafka。

## 四、两流派正面对比

| 环节 | RabbitMQ（队列） | Kafka（日志流） |
|---|---|---|
| 消息放哪 | Exchange 路由到 Queue | 直接追加写 Partition（log） |
| 发给谁 | Broker 主动 **push** | 消费者自己 **pull** |
| 谁来挑消息 | **Broker 派发**（消费者被动收） | **消费者**凭 offset 自己拉 |
| 消费完 | ack → **删除** | **不删**，仅提交 offset |
| 一条消息几人读 | 队列内 1 人；订阅场景每人一份副本 | 组内 1 人；不同组可各读各的 |
| 失败重试 | 不 ack → 重回队列重投 | 不提交 offset → 下次重拉 |
| 能重放 | ❌ | ✅ |
| 吞吐 | 几万~十几万/秒 | 百万/秒 |
| 核心思想 | "把活派下去，干完就结案" | "把事件记下来，谁需要谁自己读" |

**RabbitMQ 用"删"表示读过；Kafka 用"记 offset"表示读过。**

## 五、应用层面：为什么需要 MQ（场景驱动）

### 5.1 四个真实痛点

**痛点 1：同步阻塞**（用户注册要等短信发完，用户干等 3 秒；短信服务挂了注册失败）
**痛点 2：强耦合**（支付后加一个下游就要改支付服务代码、重新发布核心服务）
**痛点 3：瞬时洪峰**（10 万人秒杀，系统只扛 2000/秒）
**痛点 4：海量写入**（每天 5 亿条埋点，直接写 MySQL 打爆）

### 5.2 改造前 vs 改造后

```
【改造前】用户注册
  → 写用户表(50ms) → 发短信(2s!) → 送积分(300ms) → 写营销(500ms)
  → 3 秒后返回；任一环节挂 → 注册失败

【改造后】
  → 写用户表(50ms) → 发消息 UserRegistered(5ms) → 立刻返回（55ms）
  后台各自消费：
    短信服务 ← 收消息 → 发短信
    积分服务 ← 收消息 → 送积分
    营销服务 ← 收消息 → 打标签
  加新系统？加个消费者即可，注册服务一行不改
```

### 5.3 真实公司里两者共存

```
业务请求 ──▶ 业务服务集群
              ├─▶【RabbitMQ】订单支付事件/短信通知/延迟关单/库存扣减
              └─▶【Kafka】用户点击埋点/日志收集/binlog同步/实时指标
```

## 六、Spring Cloud / K8s 与 MQ 的关系（分层澄清）

| 概念 | 层次 | 职责 |
|---|---|---|
| **Spring Cloud** | 应用代码层 | 微服务之间怎么发现、调用、容错（注册中心/网关/配置/熔断） |
| **MQ** | 中间件层 | 服务之间异步传消息（解耦/削峰） |
| **K8s** | 部署运维层 | 容器调度、自愈、伸缩、滚动发布 |

**Spring Cloud 与 K8s 职责重叠**：服务发现（Eureka vs K8s DNS）、网关（Gateway vs Ingress）、配置（Config vs ConfigMap）、伸缩（手写 vs HPA）。趋势是新项目用 K8s 原生能力接管一部分，或走 Service Mesh（Istio）把能力下沉到基础设施。

**一句话**：Spring Cloud 管"微服务怎么写"，K8s 管"微服务怎么跑"，MQ 管"服务之间怎么异步说话"。

## 七、MQTT 是什么（与 MQ 完全不同）

### 7.1 一句话定性

**MQTT = Message Queuing Telemetry Transport，一种轻量级发布/订阅消息协议**（OASIS 标准，ISO/IEC 20922）。

**它和 RabbitMQ/Kafka 不是一个维度的东西**：后者是"软件产品"，MQTT 是"协议"（类比：HTTP 是协议，Nginx 是实现 HTTP 的软件）。

### 7.2 为谁设计

为**物联网 IoT** 场景设计：低带宽、网络不稳定、设备算力/电量有限（传感器、车联网、智能家居、可穿戴设备）。

### 7.3 核心特点

| 特性 | 说明 |
|---|---|
| **极轻量** | 固定头最小 2 字节，省流量省电 |
| **发布/订阅** | 基于 Topic 层级（`home/livingroom/temp`），支持通配符 `+`/`#` |
| **长连接** | 设备与 Broker 保持 TCP 长连接，心跳保活 |
| **QoS 三级** | 0 最多一次 / 1 至少一次 / 2 恰好一次 |
| **保留消息 Retained** | Broker 保留每个 Topic 最新一条，新订阅者立刻拿到当前值 |
| **遗嘱消息 LWT** | 设备异常掉线，Broker 自动代发"遗嘱"（如"设备离线"） |
| **离线消息** | 设备离线期间的消息，恢复后补发（持久会话） |

### 7.4 MQTT Broker 有哪些

Mosquitto（轻量开源）、**EMQX**（国产，高并发）、HiveMQ、云厂商 IoT Core（AWS/Azure/阿里云 IoT）。

注意：**RabbitMQ 可以通过 `rabbitmq_mqtt` 插件充当 MQTT Broker**——但两者定位不同。

### 7.5 MQTT vs RabbitMQ vs Kafka（三方对比）

| 维度 | MQTT | RabbitMQ | Kafka |
|---|---|---|---|
| 本质 | **协议** | 产品（AMQP） | 产品（自定义协议） |
| 设计目标 | 省流量、弱网、海量设备长连接 | 可靠业务消息、灵活路由 | 超高吞吐、海量留存、可重放 |
| 通信模式 | 发布订阅，Broker 推 | Broker 推（push） | 消费者拉（pull） |
| 连接模型 | **百万级长连接设备** | 服务间连接 | 服务间连接 |
| 消息保留 | Retained（最新一条） | 消费即删 | 保留 N 天全部 |
| 吞吐 | 中等（胜在连接数） | 几万~十几万/秒 | 百万/秒 |
| 典型规模 | 百万设备连接 | 业务系统 | 数据管道 |
| 场景 | IoT、车联网、推送、智能家居 | 订单/通知/任务/延迟队列 | 埋点/日志/CDC/流计算 |

### 7.6 典型 IoT 架构（MQTT 与 Kafka 是搭档而非竞争）

```
百万设备（传感器/车机）
   │ MQTT 协议（长连接、省流量）
   ▼
EMQX / Mosquitto（MQTT Broker，规则引擎）
   │ 桥接/转发
   ▼
Kafka（海量数据管道）
   ├─▶ Flink 实时计算（实时监控告警）
   ├─▶ 数仓（离线分析）
   └─▶ Redis（设备最新状态缓存）
```

**分工**：MQTT 负责"设备 ↔ 云端"的接入（弱网、省电、长连接）；Kafka 负责"云端内部"的数据分发与分析。**它们是上下游搭档，不是替代关系。**

### 7.7 常见误解澄清

| 误解 | 真相 |
|---|---|
| "名字都带 MQ，是一回事" | ❌ MQTT 是协议，RabbitMQ/Kafka 是实现消息的产品 |
| "MQTT 可以替代 Kafka" | ❌ MQTT 解决设备接入，Kafka 解决数据管道，常配合使用 |
| "用了 RabbitMQ 就不能用 MQTT" | ❌ RabbitMQ 装 MQTT 插件即可同时支持 MQTT 协议接入 |

---

## 八、选型决策树

```
要传消息 / 传数据？
├─ 是"等业务结果"的调用？ → 直接 HTTP/RPC，不用 MQ
└─ 需要异步/解耦/削峰/数据流 → 用 MQ
     ├─ 设备接入（IoT/弱网/长连接）→ MQTT 协议 + EMQX/Mosquitto
     ├─ 业务指令（通知/任务/延迟/重试/死信）→ RabbitMQ 或 RocketMQ
     ├─ 海量事件流（埋点/日志/CDC/流计算/重放）→ Kafka
     └─ 量大 + 业务消息（电商订单）→ RocketMQ（兼顾两者）
```

## 九、什么时候不该用 MQ（反模式）

| 情况 | 原因 |
|---|---|
| 简单查数据要结果 | 直接 RPC，MQ 是异步的，不适合等结果 |
| 小项目/单体/两三个服务 | 直接调用最简单，MQ 是额外运维成本 |
| 要求强一致（转账立刻一致） | MQ 是最终一致 |
| 消息量极小（一天几百条） | 定时任务即可 |
| 团队没人维护中间件 | 中间件挂 = 全站故障 |

## 十、口诀速记

1. **MQTT 是协议，RabbitMQ/Kafka 是产品**——不是一回事
2. RabbitMQ = 快递员（可靠送达、签收回执、死信兜底）
3. Kafka = 高速公路 + 录像带（海量流过、留存 7 天、可倒带重放）
4. 消息 offset 存在 **Broker 分区日志**里；消费进度 offset 存在 **`__consumer_offsets`**
5. "先处理再提交 offset + 业务幂等"是 Kafka 黄金法则
6. RabbitMQ 用"删"表示读过；Kafka 用"记 offset"表示读过
7. 业务指令选 RabbitMQ；数据事件流选 Kafka；设备接入选 MQTT
8. IoT 场景：MQTT 负责接入 + Kafka 负责分析，上下游搭档
