## 〇、先搞懂"桶"——一个储物柜实例（2026-10-28 补）

> 学员问："结构图里的'桶'什么意思？"——**桶 = 数组的一个格子 = 一个储物柜**。

### 一句话先立住

```text
桶 = table[i]（数组的一个格子）
"桶 0 / 桶 1 / 桶 2" 就是 table[0] / table[1] / table[2]
叫"桶"不叫"格子"：一个格子可能装不止一个键值对（撞车的排队）——像水桶
```

### 完整实例：容量 8 的 HashMap 放三个水果

```java
HashMap<String, Integer> map = new HashMap<>();
map.put("苹果", 5);
map.put("香蕉", 3);
map.put("橙子", 8);
```

**每一步**（hashCode 是假设值，重点是流程）：

```text
put("苹果", 5)：
  ① 算指纹："苹果".hashCode() → 2481536（假设）
  ② 找柜子：2481536 & 7 = 0        ← & 7 就是"除以 8 取余"
  ③ 柜子 0 空着 → 放进去

put("香蕉", 3)：
  ① hashCode → 2481539   ② & 7 = 3   ③ 放进 3 号柜

put("橙子", 8)：
  ① hashCode → 2481552   ② & 7 = 0   ← ★ 和苹果撞车！都指向 0 号柜
  ③ 0 号柜已有苹果 → 排队挂上去（链表）
```

**三个 put 后，内存的真实样子**：

```text
桶0: [苹果=5] → [橙子=8]      ← 撞车的用 next 指针串成链表
桶1: null
桶2: null
桶3: [香蕉=3]
桶4~7: null
```

### get 是同一条路的回放

```java
map.get("橙子")
  ① hash("橙子") & 7 → 0 号柜        ← 与 put 时算出【同一个柜子】
  ② 遍历 0 号柜链表：
     [苹果=5] equals("橙子")？否 → 下一个
     [橙子=8] equals？是 → 返回 8 ✓
```

**O(1) 的秘密**：不遍历全部柜子，**一步算出柜号直接开柜**。

### 对照 J3 §18.1 的图逐行

| 图里的行 | 真实含义 | 什么时候出现 |
|---|---|---|
| `table[]（容量 2 的幂）` | 一排柜子 | new HashMap 时 |
| `桶 0: null` | 空柜子 | 没有 key 落进这个柜 |
| `桶 1: Node → Node` | 两个 key 撞车排队（链表） | 2+ 个 key 落同一柜 |
| `桶 2: TreeNode（红黑树）` | 排队 ≥8 变红黑树（柜内查找 O(n)→O(log n)） | 撞车极端严重 |

**三种状态 = 同一个柜子的拥挤升级路线**：空 → 链表（≤7）→ 红黑树（≥8），树化后不回退。

### Node 四字段逐个对号（苹果/橙子的 Node）

```java
class Node<K, V> {
    final int hash;    // 2481536（苹果的指纹）——final：指纹变了就找不到柜子
    final K key;       // "苹果"        ——final：key 不可变（否则同样失踪）
    V value;           // 5            ——可变：put 同 key 会覆盖这里
    Node<K, V> next;   // 指向橙子的 Node——撞车的下一个；最后一个是 null
}
```

### 为什么撞车必然发生（鸽笼原理）

```text
8 个柜子装第 9 个东西 → 必撞（数学无解）
即使 hash 再均匀：两个 key 的 hash & 7 完全可能相同
→ 碰撞不是 bug 是天性；链表/红黑树是"管理撞车"的手段（J3 §18.3）
```

### 本节一句话

```text
桶 = 数组格子 = 储物柜；key 算 hash → 定柜号 → 开柜找/放
撞车排队（链表）→ 太挤变树；Node 四字段：hash/key 不许变、value 可覆盖、next 串队
```

## 二、哈希冲突怎么解？（两大流派）

```text
链地址法（Separate Chaining）：
  桶里挂链表 → Java HashMap / Redis 字典
  优点：实现简单、删除容易、负载因子可超 1
  缺点：指针跳转对缓存不友好、最坏 O(n)

开放寻址法（Open Addressing）：
  撞了就探测下一个空位（线性探测/二次探测/双重散列）
  → Python dict / 布隆过滤器一族
  优点：数据连成片（缓存友好）、省指针内存
  缺点：删除麻烦（要打墓碑标记）、负载必须 < 0.75 否则性能崩
```

### 开放寻址实例演算（2026-10-28 学员追问补）

**本质对比**（撞车处理的两种哲学）：

```text
链地址：撞车了 → 【原地排队】（柜子里挂链表）
  柜3: [苹果] → [橙子] → [桃子]

开放寻址：撞车了 → 【换柜子】（往后找空位）
  柜3: [苹果]   柜4: [橙子]   柜5: [桃子]   ← 没有链表！平铺在数组里
```

**实例：容量 8，线性探测（撞了就 +1）**：

```java
put("苹果", 5);   // hash & 7 = 3
put("香蕉", 3);   // hash & 7 = 3   ← 撞车
put("橙子", 8);   // hash & 7 = 3   ← 又撞
```

```text
put 苹果：柜 3 空 → 放
  [ ][ ][ ][苹果][ ][ ][ ][ ]
put 香蕉：柜 3 占 → 探测柜 4 → 空 → 放
  [ ][ ][ ][苹果][香蕉][ ][ ][ ]
put 橙子：柜 3、4 占 → 探测柜 5 → 空 → 放
  [ ][ ][ ][苹果][香蕉][橙子][ ][ ]
```

**get 与 put 走同一条路**：

```text
get("橙子")：柜 3 苹果≠ → 柜 4 香蕉≠ → 柜 5 橙子 ✓
get("西瓜")（不存在）：柜 3≠ → 4≠ → 5≠ → 柜 6【空】→ 停：
  插入时一定放"第一个空位"，空位后面不可能再有 hash=3 的 → 判定不存在
```

**删除的坑——墓碑（tombstone）**：

```text
❌ 直接删香蕉（柜 4 置空）：
  get("橙子")：柜 3≠ → 柜 4【空】→ 判定"不存在" ✗（橙子在柜 5！查找链断了）

✅ 正确：删除处打 DELETED 墓碑标记：
  [ ][ ][ ][苹果][墓碑][橙子][ ][ ]
  get 时遇墓碑【跳过继续找】→ 柜 5 命中 ✓
代价：墓碑挡路积多 → 探测链变长 → 需定期全量 rehash 重建
```

**为什么负载必须低（聚集雪崩）**：

```text
连续被占的格子越长 → 新元素越容易落进"长队" → 队越滚越长（雪崩）
负载 0.5 平均探测 1.5 次；0.9 暴涨到十几次
三种探测缓解：线性（+1，最易聚集）/ 二次（+1,+4,+9 跳散）/ 双重散列（最均匀）
```

**两流派收口**：

| | 链地址（Java/Redis） | 开放寻址（Python） |
|---|---|---|
| 存储 | 节点带 next 指针（多耗内存） | 直接住桶（**省内存**） |
| 缓存 | 指针跳转（不友好） | 连成一片（**缓存友好**） |
| 删除 | 摘链（简单） | 墓碑+定期重建（麻烦） |
| 负载上限 | 可 >1 | <0.75 |

Python 选开放寻址的理由：对象开销本来大，省指针值钱；缓存友好对解释器性能关键。

**Java 的选择**：链地址法为主 + 链表太长（≥8）树化成红黑树（05/06 课的伏笔）。

## 三、扩容的"世界性难题"——rehash 停顿

```text
一次性 rehash：搬几百万 key 时服务卡顿几百毫秒（不可接受）
```

**Redis 的解法——渐进式 rehash**：

```text
① 扩容时不搬，保留新旧两张表
② 每次增删改查【顺手】搬一小撮（每次 1 桶）
③ + 后台定时任务搬剩余
④ 查询时先查旧表、没有再查新表

→ 把"一次大停顿"摊成"无数次小动作"
（与 GC 的分代/并发标记同一个思想：摊销大卡顿）
```

## 四、面试两问

```text
Q：哈希冲突的解决方案？
A：链地址（Java/Redis，桶挂链表）与开放寻址（Python，探测下一个空位）；
   前者删容易、后者缓存友好。Java 还加了"链长树化"兜底。

Q：Redis rehash 为什么不停顿？
A：渐进式——新旧双表并存，每次操作顺手搬一桶 + 后台任务收尾。
```

## 一句话

```text
哈希表 = O(1) 的代价是"碰撞 + rehash"
碰撞两流派：链地址（Java）/ 开放寻址（Python）
rehash 停顿的解 = 渐进式（Redis）——大动作摊成小动作
工程全景（put 六步/树化/并发）见 J3 §18
```
