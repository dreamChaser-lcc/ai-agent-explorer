## 一、先搞清楚动机：磁盘 IO 才是成本主角

```text
内存随机访问：       ~100 纳秒
SSD 随机读一页：     ~100 微秒    （慢 1000 倍）
机械盘随机读：       ~10 毫秒     （慢 10 万倍）

磁盘按【页】读写（InnoDB 一页 = 16 KB）
—— 读 1 字节和读 16 KB 耗时几乎一样（一趟的事）

结论：数据结构为磁盘设计时，唯一目标是
      ★ 让树变矮 —— 每下降一层 = 一次磁盘 IO
```

## 二、B 树：多路搜索树

```text
二叉树每个节点 1 个 key、2 个孩子
B 树（m 阶）：每个节点最多 m-1 个 key、m 个孩子

              [ 13 | 47 ]              ← 一个节点装 2 个 key、3 个分叉
             /     |     \
      [3|7]    [17|29|38]   [51|64]    ← 节点 = 一整页（16KB 装几百个 key）

为什么能装这么多：节点不放在内存，放在【一页磁盘】里
一页读进来 = 几百个 key 一起到手 → 在页内二分 → 下一层
```

**树高对比（100 万条数据）**：

```text
二叉平衡树：log₂(100万) ≈ 20 层 → 20 次 IO
B 树（每节点 500 叉）：log₅₀₀(100万) ≈ 3 层 → 3 次 IO
★ 这就是"多路"的全部意义：把树压扁到 3~4 层
```

**B 树的问题（B+ 树的改进点）**：数据分散在**所有**节点里（内部节点也存数据）：
- 内部节点存了数据 → 每页能放的 key 变少 → 扇出变小 → 树变高
- 范围查询要回溯中序遍历，跳跃着读页

## 三、★★ B+ 树：数据库索引的标准答案

**与 B 树的两大区别**（就这两条，记住就赢）：

```text
① 非叶子节点【只存 key 不存数据】→ 一页全是 key → 扇出巨大 → 树更矮
② 数据【全部在叶子层】，且叶子之间用链表串成有序双向链表
```

```text
B+ 树结构示意：

              [ 15 | 56 | 77 ]              ← 内部节点：纯路标（只有 key）
             /      |       |  \
        [3..15]→[15..56]→[56..77]→[77..]   ← 叶子层：数据 + 有序链表
          数据     数据      数据     数据
          ↔        ↔        ↔        ↔      ← 叶子横向串联
```

**为什么这两点决定了 B+ 树赢？**

```text
优点①（更矮）：
  非叶节点一页 16KB 全装 key（int 4B + 指针 6B ≈ 10B/key → 约 1600 叉）

优点②（范围查询神器）：
  SELECT * FROM t WHERE id BETWEEN 100 AND 500;
  → 定位到 100 → 沿叶子链表【顺序扫】到 500
  → 不用回到树上反复上下（B 树做范围查询像跳台阶，B+ 树像跑直线）
  ORDER BY / LIMIT 分页同理
```

## 四、聚簇索引与"回表"（MySQL 落点）

```text
InnoDB 的表 = 一棵以主键组织的 B+ 树（聚簇索引）
  叶子节点存的不是"指针"而是【整行数据】

二级索引（如 name 列）也是 B+ 树，但叶子里存的是 (name → 主键值)
  → 查 name 得到主键 → 再回主键树查整行 = 【回表】（二次查询）

为什么"少建索引 / 联合索引把最常用的列放左边"：
  每个索引 = 一棵独立的 B+ 树（写入要维护所有树 → 变慢）
  联合索引 (a,b,c) 的最左前缀 = B+ 树按 a 排序的本质
```

## 五、经典面试推导：三层 B+ 树存约 2000 万行

```text
假设：主键 bigint 8B + 页指针 6B = 14B；一页 16KB

非叶节点一页可放 key 数：16KB / 14B ≈ 1170 个（即扇出 1170）
叶子一页存行数据：假设每行 1KB → 16 行

总容量 = 1170 × 1170 × 16 ≈ 2190 万行

★ 结论：2000 万行的表，任何一次主键查询 = 恰好 3 次页 IO（根常驻内存则 2 次）
★ 反过来说：单表超过几千万建议分表——树要变 4 层了，每查询多一次 IO
```

## 六、B+ 树 vs Hash 索引

| | B+ 树 | Hash |
|---|---|---|
| 等值查询 | O(log n) 次页IO | **O(1)** |
| 范围/排序 | **顺序扫叶子链表** | ❌ 全表扫 |
| 最左前缀 | ✅ | ❌ |
| 使用 | **InnoDB 默认** | Memory 引擎 / 手动建 |

**面试一句话**："哈希等值快但废范围——业务 90% 是范围和排序，所以 InnoDB 选 B+ 树。"

---

## 一句话

```text
B 树 = 把树压扁（节点=一页，多路扇出）—— 为磁盘而生
B+ 树两大区别 = 非叶只存 key（更矮）+ 叶子链表（范围神器）
三层 ≈ 2000 万行 ≈ 3 次 IO——单表分表的阈值依据
InnoDB 的聚簇索引 = 主键 B+ 树的叶子直接存整行
```

### 配套代码实测：TreeLab benchmark（2026-10-30）

TreeLab.java（仓库 `example-java/` 目录，javac/java 直接跑）实现了 B 树 / B+ 树 / 红黑树 / 朴素 BST 四结构，
插入 10 万条 + 1 万次随机查询（一半命中一半未命中）的实测：

| 结构 | 平均比较次数 | 平均耗时 | 建库 10 万耗时 |
|---|---|---|---|
| 线性 ArrayList | 50,000 | 57,729 ns | — |
| **朴素 BST（递增插入）** | **75,276** | 188,367 ns | **14,619 ms** |
| 红黑树 | **23** | **218 ns** | **20 ms** |
| B 树（2-3） | 18 | 666 ns | 79 ms |
| B+ 树（2-3） | 22 | 1,368 ns | 112 ms |

**读数**：
- 朴素 BST 75,276 次比较 = 退化成链表的实证（理论 ≈ N/2×1.5）
- 红黑树 23 次 ≈ log₂(10万)≈17 的 2 倍上界内 ✓（06 课规则⑤的价值）
- B/B+ 树 18~22 次：多 key 扇出（08 课"树更矮"）
- 建库：朴素 BST 14.6 秒 vs 红黑 20 ms——**730 倍**（插入退化 O(n²) 的代价）
- 内存场景红黑树最快（218ns）；B+ 树的优势在磁盘页式存储（08 课 §4.1）

## 图说话速览：B 树的三个画面（2026-10-30 学员需求）

### 画面一：B 树节点 = 多 key 胖节点（keys 数组 + children 数组）

```text
4 节点（3 个 key、4 个孩子）：
     [ 10 | 20 | 30 ]           ← keys 数组（最多 3 个）
    /     |      |     \
  <10  10~20  20~30   >30      ← children 数组（最多 4 个 = keys+1）

10 个 key 的 2-3 B 树（比红黑树矮一半）：
        [4]                    ← 只有 3 层
      /     \
    [2]     [6,8]
   /  \    /  |  \
 [1] [3] [5] [7] [9,10]
```

### 画面二：B+ 树 = B 树 + 三处改造（并排图）

```text
B 树（数据散在所有层）        B+ 树（数据全在叶子 + 叶链）
        [4] ← 4 是数据          [4] ← 只是路标
      /     \                /     \
    [2]     [6,8]         [2]      [6,8]
   /  \    /  |  \       /  \     /  |  \
 [1] [3] [5] [7] [9,10] [1]→[2]→[3]→[5]→[6,7]→[8,9]
                            ↑ 全部数据在这一层，next 链串联

三处改造：① 数据下放（内部只留路标）② 叶链（范围扫不回树）
         ③ 分裂复制（9 同时出现在 [8,9] 叶子和上层路标）
```

### 画面三：插入分裂（插满就上提中间）

```text
[1,2,3] 插 4 → 叶满（3 key）→ 分裂：中间 2【上提】
        [2]
       /   \
     [1]   [3,4]        ← 一次分裂就完事

根也满 → 根分裂长新根（树高 +1）
★ B 树的高度只在"根分裂"时增加，所有叶子同层——自带平衡，零旋转
```

### 画面四：为什么数据库选 B+（三层 2000 万推导）

```text
一个节点 = 一页 16KB，key+指针 12 字节 → 扇出 ≈ 1170
高 1：1170 个 ／ 高 2：137 万 ／ 高 3：16 亿 ← 2000 万数据只要 3 层
查任意行：1 次内存（根常驻）+ 2 次磁盘 IO = 3 次
红黑树对比：100 万数据高 20 → 20 次磁盘 IO（≈200ms）
```

### 画面五：范围查询对比（B+ 杀手锏）

```text
查 [4,8]：
B+：定位 4 → 沿叶链 next 扫 [5][6,7][8] → 顺序读，不回树
B ：取 4 回上层取 5 再下来取 6 → 来回跳，每个结果一次树遍历
MySQL EXPLAIN 里 range 扫描快，根源就是这条叶链
```
