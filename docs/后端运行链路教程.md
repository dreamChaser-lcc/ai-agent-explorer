# 后端运行链路教程

这份文档按“创建任务 -> 确认计划 -> 执行步骤 -> 生成报告”的顺序，带你从代码视角看清楚后端到底是怎么跑起来的。

## 一、先记住这条主链路

一个研究任务从前端发起，到后端完成，大致会经过这条链路：

1. 前端调用创建任务接口
2. 后端创建任务主记录
3. 后端生成研究计划与步骤
4. 任务进入等待人工确认
5. 用户确认计划
6. 执行器按步骤推进任务
7. 工具产出来源资料与执行结果
8. 报告服务生成最终研究报告
9. SSE 持续把进度推回前端

如果只想抓核心文件，先盯住这几个：

- `backend/src/main/java/com/aiexplorer/researchagent/api/controller/ResearchTaskController.java`
- `backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchTaskCommandService.java`
- `backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchPlanningService.java`
- `backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchTaskControlService.java`
- `backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchTaskOrchestrator.java`
- `backend/src/main/java/com/aiexplorer/researchagent/application/service/TaskEventService.java`
- `backend/src/main/java/com/aiexplorer/researchagent/application/service/TaskProgressStreamService.java`
- `backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchReportAssemblyService.java`

## 二、创建任务

### 1. 接口入口

前端创建任务时，请求会进入：

- `POST /api/tasks`

对应控制器方法：

- `ResearchTaskController#createTask`

控制器本身很薄，主要只做请求接收和参数转发：

```java
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public TaskSummaryResponse createTask(@Valid @RequestBody CreateResearchTaskRequest request) {
    return researchTaskCommandService.createTask(request, "demo-user");
}
```

### 2. 写入任务主记录

真正的写操作在：

- `ResearchTaskCommandService#createTask`

这一步会创建 `ResearchTaskEntity`，并填这些关键字段：

- `taskNo`
- `title`
- `goal`
- `executionMode`
- `status = QUEUED`
- `currentStage = PLANNING`

也就是说，任务刚创建时，并不是立刻开始执行，而是先进入规划阶段。

### 3. 创建任务后立刻进入规划

`createTask` 里最关键的一句是：

```java
researchPlanningService.generateInitialPlan(savedTask.getId());
```

这句意味着：

- 创建任务并不会停在“只有一条任务记录”
- 后端会马上开始生成该任务的初始计划

## 三、生成计划并等待人工确认

入口在：

- `ResearchPlanningService#generateInitialPlan`

这个方法会做四类事情。

### 1. 生成研究计划

它会创建 `ResearchPlanEntity`，写入：

- 计划摘要 `planSummary`
- 计划目标 `planObjective`
- 计划状态 `GENERATED`
- 确认状态 `PENDING`
- 原始计划内容 `rawPlanPayload`

当前版本使用的是模板化规划，所以计划步骤不是实时 LLM 自由规划，而是先按固定 MVP 模板生成。

### 2. 生成步骤清单

接着调用：

- `createSteps`
- `buildStep`

当前固定的步骤链是：

1. `SEARCH`
2. `FETCH`
3. `SUMMARIZE`
4. `CITATION_EXTRACT`
5. `REPORT`

这里的设计重点是：

- 第 1 步默认置为 `READY`
- 后续步骤先置为 `PENDING`

这样执行器后面就能按顺序推进。

### 3. 生成人工确认记录

它还会创建 `HumanConfirmationEntity`，表示：

- 当前任务已经有一条待处理确认
- 需要用户批准后才能真正执行

### 4. 更新任务状态并推送事件

任务会被更新成：

- `status = WAITING_FOR_CONFIRMATION`
- `currentStage = PLANNING`
- `requiresConfirmation = true`

然后调用：

- `TaskEventService.recordSystemEvent(...)`
- `TaskProgressStreamService.publish(...)`

所以前端会立即感知到：

- 计划已生成
- 任务正在等待人工确认

## 四、确认计划

用户点击“确认计划”后，请求进入：

- `POST /api/tasks/{taskId}/confirm`

对应方法：

- `ResearchTaskController#confirmPlan`
- `ResearchTaskControlService#confirmPlan`

### 1. 先找出任务、计划、确认记录

`confirmPlan` 会先加载：

- 当前任务
- 最新版本研究计划
- 最新人工确认记录

这一步是在保证“当前任务确实存在，而且真的有待确认对象”。

### 2. 如果用户批准

会发生这些变化：

- `research_plan.status = CONFIRMED`
- `research_plan.confirmation_status = APPROVED`
- `human_confirmation.status = APPROVED`
- `research_task.status = RUNNING`
- `research_task.currentStage = EXECUTING`
- `research_task.requiresConfirmation = false`

然后调用：

- `researchTaskOrchestrator.startExecution(taskId)`

也就是说，**真正开始执行任务的开关，就在这里被打开**。

### 3. 如果用户拒绝

会发生这些变化：

- 计划状态变成 `REJECTED`
- 任务状态变成 `CANCELLED`
- 记录拒绝原因
- 广播任务取消事件

整个任务流在这里直接停住。

## 五、执行步骤

后端执行器是：

- `ResearchTaskOrchestrator`

### 1. startExecution：决定同步还是异步

首先看：

- `ResearchTaskOrchestrator#startExecution`

它只做一件关键判断：

- `ASYNC`：交给线程池后台执行
- `SYNC`：当前线程直接调用 `executeTask`

线程池来自：

- `AsyncExecutionConfiguration#researchTaskExecutor`

### 2. executeTask：真正的主循环

`executeTask` 是整个后端最关键的方法之一。

它的执行顺序大致是：

1. 加载任务
2. 判断任务当前是否应该停止
3. 如果任务第一次执行，补 `startedAt`
4. 读取按顺序排列的所有步骤
5. 遍历步骤
6. 对每个步骤执行：
   - 更新任务当前步骤与阶段
   - 创建 `step_execution`
   - 写开始事件
   - 调用对应工具
   - 保存步骤产物
   - 成功则推进下一步
   - 失败则将任务标记为失败
7. 所有步骤完成后，将任务标记为完成

### 3. updateTaskForStep：切换任务上下文

每开始一个步骤时，会先调用：

- `updateTaskForStep`

这一步会更新：

- `currentStepId`
- `status = RUNNING`
- `currentStage`

并通过 SSE 向前端推送：

- 当前正在执行哪个步骤

### 4. createRunningExecution：创建执行记录

每一步真正执行前，都会先写一条：

- `StepExecutionEntity`

状态先记为：

- `RUNNING`

这条记录的意义是：

- 不管执行成功还是失败，都有完整的步骤级运行痕迹

### 5. 工具执行

对于非 `REPORT` 步骤，编排器会调用：

- `ResearchToolRegistry#execute`

根据步骤类型分发到：

- `WebSearchResearchTool`
- `PageFetchResearchTool`
- `SummarizeResearchTool`
- `CitationExtractResearchTool`

当前这些工具实现还是 MVP/mock 风格，但编排关系已经是完整的。

### 6. 成功收敛

如果步骤执行成功，会调用：

- `completeExecution`

它会：

- 把 `step_execution` 改成 `SUCCESS`
- 保存输出结果
- 记录耗时
- 把当前步骤改成 `COMPLETED`
- 把下一步改成 `READY`
- 写完成事件
- 推送 SSE

### 7. 失败收敛

如果执行报错，会调用：

- `failExecution`

它会：

- 把 `step_execution` 改成 `FAILED`
- 记录错误信息
- 把步骤改成 `FAILED`
- 把任务改成 `FAILED`
- 记录事件并推送失败状态

这就是为什么你后面调试问题时，可以从任务状态、步骤状态、事件日志、执行记录四个角度一起排。

## 六、生成报告

当步骤执行到 `REPORT` 时，编排器不再走工具注册表，而是直接调用：

- `ResearchReportAssemblyService#buildReport`

这个方法会做这些事情：

1. 从 `source_document` 查出来源资料
2. 从 `step_execution` 里找出总结与引用提取结果
3. 组装：
   - `summary`
   - `keyFindings`
   - `finalRecommendation`
   - `reportMarkdown`
   - `reportJson`
4. 保存到 `research_report`

这意味着最终报告并不是凭空生成，而是建立在：

- 前面步骤的执行输出
- 前面步骤产生的来源资料

之上。

## 七、事件日志和 SSE 是怎么贯穿全链路的

### 1. 事件日志入口

统一入口：

- `TaskEventService`

它负责：

- 记录系统事件
- 记录用户事件
- 持久化到 `task_event_log`
- 同时调用 SSE 推送

### 2. SSE 连接管理

统一入口：

- `TaskProgressStreamService`

主要方法：

- `subscribe`
- `publish`

前端通过：

- `GET /api/tasks/{taskId}/stream`

建立 `EventSource` 连接后，后端就可以把任务进度实时推回前端。

所以你在前端看到的任务详情变化，不是反复轮询接口，而是后端主动广播。

## 八、查询为什么单独拆服务

项目里把查询操作拆成了独立服务：

- `ResearchTaskQueryService`
- `TaskActivityQueryService`
- `ResearchReportQueryService`

这样做的好处是：

- 控制器更薄
- 写操作和读操作分离
- 代码阅读时更容易区分“谁在改数据”“谁在查数据”

## 九、这条链路最值得你记住的理解

如果你想真正搞懂后端，不要把它看成“一个接口调一个工具”。

更准确的理解是：

- 这是一个**状态驱动的任务工作流系统**
- 任务不是一次请求瞬间完成，而是经历多个阶段
- 每个阶段都有表记录、事件、状态推进与前端反馈

一句话总结这条链路：

`创建任务 -> 生成计划 -> 等待确认 -> 逐步执行 -> 保存执行痕迹 -> 生成报告 -> SSE 推送前端`
