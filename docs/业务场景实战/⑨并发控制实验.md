## 一、审计：三个发现（先证明问题存在）

### 发现 1：并发确认——乐观锁挡住了 HTTP，但没挡住消息

**实验 A**（并发 2 个 confirm，ASYNC 任务）：

```text
HTTP:  OK(200) / ERR: 409 冲突          ← @Version 乐观锁生效

日志：
[MQ] 已发送任务执行消息 taskId=6994228f...    ← exec-2
[MQ] 已发送任务执行消息 taskId=6994228f...    ← exec-3（★ 两条消息）
binding parameter <- [PLAN_CONFIRMED]        ← 两条事件（一条随后回滚）
```

**结论**：数据库状态只有一个赢家，**但 Kafka 消息发了两条**——乐观锁保护"最终状态"，保护不了"提交前的副作用"。

### 发现 2：SYNC 模式下，同一任务的步骤被并发执行（真 bug）

**实验 B**（并发 2 个 confirm，SYNC 任务）：

```text
HTTP:  OK(200) / ERR: 500

日志（注意线程名）：
exec-8: 开始执行步骤：检索权威资料     ← 12:25:14.260
exec-9: 开始执行步骤：检索权威资料     ← 12:25:14.357（★ 97ms 后另一线程也执行了）
exec-8: ...（exec-8 继续跑完全部 5 步）
```

**两个线程同时执行同一任务的同一步骤**——LLM 调用两次、事件重复写入。

**为什么并发能进来**：JPA 的 `save()` **不立即发 SQL**（写延迟），两个线程都还没触发 UPDATE → 没有行锁阻塞 → 都走到 `startExecution()`。

### 发现 3：消费端有"分区串行"，但缺"执行级互斥"

- Kafka `key = taskId` → 同一任务进同一分区 → 分区内串行消费（场景⑥ 的设计）→ **挡住了大部分重复**；
- 但 **SYNC 直接调用**、**多实例 + 重投**、**未来多分区** 等场景没有保护。

---

## 二、根因：事务边界把"执行"包进去了

```text
@Transactional confirmPlan()
   ├─ ① 读状态（WAITING）        ← 两个线程都读到
   ├─ ② 改状态（RUNNING）
   ├─ ③ save()                  ← JPA 写延迟，此时还没发 UPDATE
   ├─ ④ startExecution()        ← ❌ 事务未提交就执行/发消息（副作用已产生）
   └─ ⑤ 提交                    ← 一个成功、一个 409/500
                                   ↑ ③④ 的副作用收不回来
```

**一句话**：**乐观锁保护"最终状态"，保护不了"提交前的副作用"**（消息发出、任务执行、外部调用）。

---

## 三、方案：四层防护

| 层 | 方案 | 治什么 | 本项目 |
|---|---|---|---|
| ① **事务边界修正** | `startExecution` 挪到 `afterCommit` | 事务失败却启动执行/发消息 | ✅ 实现 |
| ② **执行级互斥** | **Redis 锁**（`SET NX EX`） | 重复执行（重投/多实例/并发） | ✅ 实现 |
| ③ 状态机兜底 | `requireStatus` + `@Version` | 非法状态流转 | ✅ 已有 |
| ④ 消息一致性 | outbox 表 / 事务消息 | 消息与事务原子性 | ⬜ 只讲不实现 |

**为什么第①层最关键**：它让"事务失败的请求**根本不会**启动执行"——这是治本；Redis 锁是第二道防线（防漏网）。

## 四、实现

### 4.1 Redis 锁组件

[`DistributedTaskLock.java`](../../backend/src/main/java/com/aiexplorer/researchagent/infrastructure/lock/DistributedTaskLock.java) [网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/backend/src/main/java/com/aiexplorer/researchagent/infrastructure/lock/DistributedTaskLock.java)

```java
@Component
public class DistributedTaskLock {
    private static final String KEY_PREFIX = "lock:task:exec:";
    private static final Duration LOCK_TTL = Duration.ofMinutes(5);

    // 释放锁：value 与自己的 token 一致才删除（Lua 原子操作）
    private static final DefaultRedisScript<Long> UNLOCK_SCRIPT = new DefaultRedisScript<>(
        "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end",
        Long.class);

    public Optional<String> tryLock(UUID taskId) {
        String token = UUID.randomUUID().toString();
        Boolean ok = redisTemplate.opsForValue()
                .setIfAbsent(KEY_PREFIX + taskId, token, LOCK_TTL);   // ★ SET NX EX
        return Boolean.TRUE.equals(ok) ? Optional.of(token) : Optional.empty();
    }

    public void unlock(UUID taskId, String token) {
        redisTemplate.execute(UNLOCK_SCRIPT, List.of(KEY_PREFIX + taskId), token);
    }
}
```

**三个关键设计**：

| 设计 | 为什么 |
|---|---|
| `SET NX EX`（原子） | 避免"setnx 成功但还没设过期，进程挂了"→ 永久死锁 |
| **token 校验释放**（Lua） | 防"执行超时锁过期 → 别人拿到锁 → 自己把别人的锁删了" |
| TTL 5 分钟 | 覆盖一次完整执行；进程崩溃也能自动释放 |

### 4.2 执行入口加锁

[`ResearchTaskOrchestrator.executeTask`](../../backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchTaskOrchestrator.java) [网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchTaskOrchestrator.java)

```java
public void executeTask(UUID taskId) {
    Optional<String> lockToken = distributedTaskLock.tryLock(taskId);
    if (lockToken.isEmpty()) {
        return;   // 已有执行者，跳过（重复执行没有意义）
    }
    try {
        doExecuteTask(taskId);
    } finally {
        distributedTaskLock.unlock(taskId, lockToken.get());
    }
}
```

### 4.3 事务边界修正（afterCommit）

[`ResearchTaskControlService.confirmPlan`](../../backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchTaskControlService.java) [网页版](https://github.com/dreamChaser-lcc/ai-agent-explorer/blob/main/backend/src/main/java/com/aiexplorer/researchagent/application/service/ResearchTaskControlService.java)

```java
if (approved) {
    runAfterCommit(() -> researchTaskOrchestrator.startExecution(taskId));
}

private void runAfterCommit(Runnable action) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() { action.run(); }
        });
    } else {
        action.run();
    }
}
```

**效果**：**事务回滚 → afterCommit 不触发 → 不发消息、不执行**。

## 五、验证：三组实验（2026-10-23 全部实测）

### 5.1 实验 C：并发确认（修复后，SLOW 模式制造 25 秒窗口）

```text
HTTP:  OK(200) / ERR: 400

[锁] 获取成功 taskId=4087562b... token=75c268bd ttl=300s     ← 只有一次
[锁] 释放   taskId=4087562b... 结果=1                        ← 31 秒后释放

（没有任何 "[锁] 获取失败"）
```

**关键差异**：修复前（实验 B）两个线程**都执行**；修复后（实验 C）**只有一次执行**——而且第二个请求连"拿锁"的机会都没有，因为它的**事务提交失败 → afterCommit 不触发 → 根本没启动执行**。

### 5.2 实验 D：锁竞争分支（手动占位 Redis key）

```text
[redis-cli] SET lock:task:exec:<taskId> "manual-holder" EX 300   → OK

[MQ] 收到任务执行消息 taskId=64183203...                        ← 消息被消费
[锁] 获取失败：任务已有执行者，跳过本次执行 taskId=64183203...    ← ★ 拿不到锁
（无任何"开始执行步骤"日志）
```

**这验证了第二道防线**：消息重投、多实例、并发到达时，**拿不到锁就跳过**。

### 5.3 实验 E：执行中暂停

```text
14:44:16.640  开始执行步骤：搜索候选资料
14:44:20.418  任务已暂停 + TASK_PAUSED
（没有"抓取并清洗正文"——第 2 步没开始）
任务状态：PAUSED
```

**暂停靠"状态机 + 执行者轮询"**：执行循环每步 `loadTask` + `shouldStop`，看到 PAUSED 就在下一步停下。

## 六、DB 锁 vs Redis 锁：为什么选 Redis

| | DB 悲观锁（`SELECT FOR UPDATE`） | **Redis 锁（`SET NX EX`）** |
|---|---|---|
| 锁载体 | 数据库行 + 事务 | Redis key + TTL |
| **执行 25 秒的任务** | ❌ **长事务**：连接被占 25 秒、行锁不放 | ✅ 不占 DB 连接 |
| 死锁风险 | 靠事务超时 | ✅ TTL 自动过期 |
| 跨实例 | ✅ 天然 | ✅ 天然 |
| 额外依赖 | 无 | Redis |
| 适用 | **短事务**（毫秒~秒级） | **长耗时任务**（本场景） |

**长事务的代价（SP4 + SP9 已实测）**：

```text
SP9 实测：事务进行中 active=1、idle=9；结束后 active=0、idle=10
推论：10 个并发长事务 → 10 个连接全被占 → 第 11 个请求排队到超时
```

> **本课未实跑 DB 锁模式**：需要额外实现 `@Lock(PESSIMISTIC_WRITE)` 开关；"长事务占连接"的代价已在 SP9 用 LLM 案例实测，此处直接复用结论。

## 七、暂停/取消的并发（本课覆盖范围）

| 场景 | 防护手段 | 实测 |
|---|---|---|
| **并发确认** | afterCommit + Redis 锁 + 状态机 | ✅ 实验 C |
| **执行中暂停** | 状态机 + 执行循环轮询（每步 `loadTask` + `shouldStop`） | ✅ 实验 E |
| 并发暂停两次 | `@Version` 乐观锁（短事务，第二个 409） | 逻辑保证（与实验 A 同源） |
| **暂停 vs 执行竞争** | **暂停不加执行锁**（否则执行持锁期间用户无法暂停） | ✅ 实验 E 证明暂停能立即生效 |

**一个重要的设计判断**：**暂停/取消绝不加执行锁**。
如果暂停也要拿同一把锁 → 执行持锁 5 分钟 → 暂停请求阻塞等待 → **用户想停却停不下来**（甚至等到锁超时）。正确做法：**执行者主动轮询状态**，暂停只负责改状态。

## 九、思考题（自查 + 参考答案）

1. 为什么 `startExecution` 必须放在 `afterCommit` 里？<br>
   **参考答案**：事务可能回滚，但**消息发出、执行启动是不可撤销的副作用**。实验 A 就是证据：第二个请求 409 回滚了，但它的 Kafka 消息已经发出去了 → 任务会被执行两次。
2. Redis 锁为什么必须"token 校验 + Lua 删除"？<br>
   **参考答案**：执行可能超过 TTL（锁自动过期），此时别人可能拿到新锁；如果自己执行完直接 `DEL`，会**误删别人的锁**，导致互斥失效。所以删除前要比对 token（Lua 保证原子）。
3. 为什么暂停/取消**不加**执行锁？<br>
   **参考答案**：执行持锁 5 分钟，暂停要拿同一把锁 → 阻塞等待 → **用户停不下来**。正确做法是"执行者轮询状态"（每步 `loadTask` + `shouldStop`），暂停只改状态。
4. 什么场景该用 DB 悲观锁而不是 Redis 锁？<br>
   **参考答案**：**短事务**（毫秒~秒级）、强一致要求、不想引入 Redis 的场景。长耗时任务用 DB 锁会变长事务——占连接、锁行，并发一高就把连接池打满。

### 11.1 附讲：锁的四层全景与死锁（Q1 · 2026-10-23）

#### 一、锁分四层

| 层 | 代表 | 特点 |
|---|---|---|
| **JVM 进程内** | `synchronized` / `ReentrantLock` / `ReadWriteLock` / `StampedLock` / `Semaphore` / 原子类（CAS） | 多线程互斥；`ReentrantLock` 支持超时与中断（`synchronized` 不支持） |
| **数据库** | 悲观锁 `SELECT ... FOR UPDATE` / 乐观锁 `@Version` / 共享锁 / 间隙锁 | 单库多连接；长事务会拖垮连接池（SP9） |
| **分布式** | Redis `SET NX EX`（本课）/ Redisson 看门狗 / ZooKeeper 临时节点 / DB 唯一索引 | 多实例互斥；TTL 与 token 是安全基石 |
| **业务层"锁"** | 幂等键（场景④）/ 状态机（场景②）/ 消息分区串行（场景⑥） | 不是锁，但解决"重复处理"同一类问题 |

#### 二、死锁的四个必要条件（缺一不可）

| 条件 | 含义 |
|---|---|
| 互斥 | 资源一次只能一个持有者 |
| **持有并等待** | 拿着 A 等 B |
| 不可剥夺 | 不能强行抢占 |
| **循环等待** | A→B→A 成环 |

**实测证据**（2026-10-23，`jstack` 抓到的 JVM 死锁）：

```text
Found one Java-level deadlock:
"thread-A": waiting to lock <0x...d70>, which is held by "thread-B"
"thread-B": waiting to lock <0x...d60>, which is held by "thread-A"
```

两个线程分别持有对方要的锁 → 四个条件全中 → 永久等待。

#### 三、三种死锁现场与预防

| 类型 | 现象 | 检测 | 预防 |
|---|---|---|---|
| **JVM 死锁** | 线程永久阻塞 | `jstack <pid>` → "Found one Java-level deadlock" | **固定加锁顺序**；`tryLock(timeout)` |
| **数据库死锁** | `Deadlock found when trying to get lock` | 应用日志 / `SHOW ENGINE INNODB STATUS` | **按主键顺序更新**；短事务（长事务是温床） |
| **分布式锁死锁** | 锁永不释放 / 两个执行者 | 监控锁 key 的 TTL | `SET NX **EX**`（TTL 兜底）+ token 校验释放 + 看门狗续期 |

> **本课两个设计正对这两种分布式死锁**：`EX` 防"进程崩了锁不释放"，token 校验防"锁过期被抢后误删他人锁"。

#### 四、项目三处呼应

| 位置 | 关系 |
|---|---|
| 场景⑨ Redis 锁 | TTL 防死锁；token 防误删 |
| SP1 循环依赖 | **概念同源**：A 等 B、B 等 A——Spring 选择直接报错（不挂死） |
| SP4 长事务 | 持锁时间长 → 死锁概率↑ + 连接池耗尽（SP9） |

#### 五、选型表

| 场景 | 用什么 |
|---|---|
| JVM 内多线程共享变量 | `synchronized` / 原子类 / `ReentrantLock` |
| 单库、短事务、冲突少 | `@Version` 乐观锁 |
| 单库、强一致、短操作 | `SELECT ... FOR UPDATE` 悲观锁 |
| **多实例互斥（长任务）** | **Redis 锁**（本课） |
| 重复请求去重 | 幂等键（不是锁） |

### 11.2 附讲：分布式锁详解（Q2 · 2026-10-23）

#### 一、为什么单机锁不够

```text
单实例：线程1/2/3 → synchronized(lock)  ← JVM 内互斥，有效
多实例：Pod A 的 synchronized  ┐
        Pod B 的 synchronized  ┘ 两把锁【互不相识】→ 同时执行
```

`synchronized` 只锁"自己 JVM 内部的线程"，锁不住另一台机器上的进程。**分布式锁 = 跨进程的"共享文档编辑中"状态**。

#### 二、分布式锁的四条要求

| # | 要求 | 做不到的后果 |
|---|---|---|
| 1 | **互斥**：跨进程只有一个持有者 | 锁形同虚设 |
| 2 | **不死锁**：持有者崩溃能自动释放 | 一次崩溃 = 全局卡死 |
| 3 | **不误删**：只释放自己的锁 | 误删他人锁 |
| 4 | 可重入（可选） | 同一线程自我阻塞 |

#### 三、Redis 三步实现（每步的"为什么"）

**第 1 步：加锁 `SET key token NX EX 300`**

| 参数 | 作用 | 省了会怎样 |
|---|---|---|
| `NX` | 不存在才设置 | 覆盖别人的锁 |
| **`EX 300`** | 过期时间 | **TTL=-1，进程崩了永久死锁** |
| `token`（UUID） | 持有者凭证 | 无法判断锁是不是自己的 |

> **必须一条命令**：`SETNX` 成功 → 进程崩溃（还没 `EXPIRE`）→ 锁永不过期 → 死锁。`SET NX EX` 是原子的。

**第 2 步：解锁（Lua 比对 token 再删）**

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**为什么不能直接 `DEL`**：

```text
t=0    A 拿到锁（TTL=30s），干一件要 40 秒的活
t=30   锁过期（A 还在干）
t=31   B 拿到锁，开始干
t=40   A 干完，DEL → 删掉的是【B 的锁】！
t=41   C 也能拿到锁 → B、C 同时执行
```

> 用 Lua 是因为 `GET`（比对）+ `DEL` 必须**原子**，否则中间可能被插入。

**第 3 步：续期（看门狗，可选）**

| TTL 设短 | TTL 设长 |
|---|---|
| 业务没跑完锁就过期 | 持有者崩了别人干等 |

Redisson 后台线程每 1/3 TTL 续期一次；本课手写版未做，靠 **TTL 5 分钟 + 业务幂等**兜底。

#### 四、实测：三个风险量化（2026-10-23，redis-cli）

```text
SETNX demo:lock:wrong "holder"          → TTL = -1   （永不过期 → 死锁风险）
SET demo:lock:right "holder" NX EX 60   → TTL = 60   （自动释放）
（模拟 A 超时后 B 持锁、A 直接 DEL）      → TTL = -2   （B 的锁被误删）
```

#### 五、五个坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 1. `SETNX` + `EXPIRE` 两步 | 中间崩溃 → 死锁 | `SET NX EX` 一条命令 |
| 2. 直接 `DEL` 释放 | 误删他人锁 | Lua 比对 token |
| 3. TTL 到期业务没跑完 | 两个执行者 | 看门狗续期 / 业务幂等 |
| 4. **Redis 主从切换** | 主挂了锁没同步 → 锁丢了 | Redlock（多节点）/ **幂等兜底** |
| 5. 锁粒度过大 | 全部串行、性能崩塌 | key 带业务 ID（`lock:task:{id}`） |

> **第 4 条最关键**：Redis 是 AP 系统（主从异步复制），极端情况锁会丢——**分布式锁永远需要业务幂等兜底**。锁是性能优化，幂等才是正确性保证。

#### 六、三种实现对比

| | **Redis**（本课） | ZooKeeper | DB 唯一索引 |
|---|---|---|---|
| 性能 | **高** | 中 | 低 |
| 一致性 | AP（极端丢锁） | **CP（强一致）** | CP |
| 自动释放 | TTL | 会话断开 | 需手动清理 |
| 实现成本 | 低 | 中（Curator） | 低 |
| 适用 | 大多数业务 | 强一致（选主等） | 简单场景 |

#### 七、对应本课代码

```java
// 加锁：setIfAbsent(key, value, timeout) = SET key value NX EX timeout
String token = UUID.randomUUID().toString();
Boolean ok = redisTemplate.opsForValue()
        .setIfAbsent("lock:task:exec:" + taskId, token, Duration.ofMinutes(5));

// 解锁：Lua 比对 token
redisTemplate.execute(UNLOCK_SCRIPT, List.of(key), token);
```

**锁粒度**：key 带 `taskId` —— 不同任务互不影响。

#### 八、锁的边界（必须建立的认知）

```text
分布式锁防的是：同一时刻【并发】重复执行
防不了的是：执行完但结果没保存（重跑）—— 需要【幂等】

生产公式：锁（性能，防并发） + 幂等（正确性，防重复） = 双保险
```

### 11.3 附讲：死锁详解（Q3 · 2026-10-23）

#### 一、是什么

**生活类比**：窄巷两车相向，A 要 B 退、B 要 A 退，谁都不退 → 永久僵持。

```java
synchronized (LOCK_A) { synchronized (LOCK_B) { } }   // 线程 A：先 A 后 B
synchronized (LOCK_B) { synchronized (LOCK_A) { } }   // 线程 B：先 B 后 A
```

结果：A 持 A 等 B，B 持 B 等 A —— **永远等下去**。

#### 二、四个必要条件（缺一不可）

| # | 条件 | 通俗解释 | 破它 |
|---|---|---|---|
| 1 | 互斥 | 一个坑一个人 | 破不掉；改用无锁方案 |
| 2 | **持有并等待** | 占着坑等别人手里的纸 | 一次性申请 / 粒度小不嵌套 |
| 3 | **不可剥夺** | 不能强行拽下来 | **带超时（tryLock）** |
| 4 | **循环等待** | A 等 B、B 等 A | **固定加锁顺序** |

#### 三、三种现场

**① JVM 死锁**

- 现象：卡住、CPU 低、线程 BLOCKED
- 判断：`jstack <pid>` → `Found one Java-level deadlock`
- 实测输出：

```text
"thread-A": waiting to lock <0x...d70>, which is held by "thread-B"
"thread-B": waiting to lock <0x...d60>, which is held by "thread-A"
```

**② 数据库死锁**

```sql
-- 事务1：UPDATE id=1 → UPDATE id=2
-- 事务2：UPDATE id=2 → UPDATE id=1
```

- 现象：`Deadlock found when trying to get lock; try restarting transaction`
- 判断：应用日志 / `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK`
- **重要认知**：InnoDB **自动检测并回滚**一个——死锁是数据库的常态，应用要**捕获 + 重试**（幂等前提下）

**③ 分布式锁死锁**

| 情况 | 现象 | 判断 |
|---|---|---|
| 锁没 TTL + 进程崩 | 锁永不过期 | `TTL = -1` |
| 锁过期但业务没跑完 | 两个执行者 | 日志重复执行 |

#### 四、怎么判断（先分清三种"卡"）

| 现象 | CPU | 线程状态 | 结论 |
|---|---|---|---|
| **死锁** | 低 | BLOCKED / WAITING（永久） | 互相等锁 |
| 死循环 | 高 | RUNNABLE | 代码问题 |
| 慢 | 正常 | RUNNABLE / TIMED_WAITING | 只是慢 |

```text
应用卡住
  ├─ CPU 高？ → 死循环/GC（jstack 看 RUNNABLE）
  └─ CPU 低？ → jstack
        ├─ 有 "Found one Java-level deadlock" → JVM 死锁
        ├─ 大量 BLOCKED 但无环 → 单点锁竞争（不是死锁）
        └─ 日志 Deadlock → DB 死锁
```

#### 五、怎么避免（按性价比）

| # | 手段 | 破的条件 | 成本 |
|---|---|---|---|
| 1 | **固定加锁顺序**（都按 ID 小的先锁） | 循环等待 | 极低，首选 |
| 2 | **tryLock 超时** | 不可剥夺 | 低 |
| 3 | 粒度小、不嵌套、不持锁做慢操作 | 持有并等待 | 低 |
| 4 | 一次性申请所有锁 | 持有并等待 | 中 |
| 5 | 无锁方案（原子类/乐观锁/消息串行） | 互斥 | 需改造 |

**实测对比（同一逆序加锁场景）**：

```text
synchronized    → 永久卡死（jstack 报 deadlock）
tryLock(1s)     → thread-A 拿到两把锁执行；thread-B 第二把超时 → 放弃（不卡死）
```

#### 六、怎么解决（已经死锁）

| 场景 | 应急 | 根本修复 |
|---|---|---|
| JVM | jstack 定位 → 重启进程 | 固定顺序 / tryLock |
| 数据库 | InnoDB 自动回滚 → 应用捕获重试 | 按主键顺序更新 + 短事务 |
| 分布式 | `DEL <lockKey>` 手动解锁 | 加 TTL + token 校验 |

```java
try {
    doInTransaction();
} catch (DeadlockLoserDataAccessException e) {
    retryOnce();     // 前提：业务幂等
}
```

#### 七、项目映射

| 位置 | 风险 | 现状 |
|---|---|---|
| 场景⑨ Redis 锁 | 无 TTL → 永久卡死 | ✅ `EX` + token 校验 |
| 场景⑨ 执行锁 | 长任务持锁 | ✅ 拿不到就跳过（不阻塞等待） |
| SP4 长事务 | 持锁 6 秒（LLM 在事务里） | ⚠️ 已记录隐患 |
| SP1 循环依赖 | 构造期互相等待 | Spring 直接报错（**快速失败 = 防死锁设计**） |

### 11.4 附讲：TTL = Time To Live（Q4 · 2026-10-23）

**字面意思**：生存时间——一个东西还能活多久。

#### 一、在 Redis 里

```text
给 key 设 60 秒 TTL → 60 秒后 Redis 自动删除它
```

`TTL <key>` 的返回值（**记这三个数字**）：

| 返回值 | 含义 | 风险 |
|---|---|---|
| **> 0** | 剩余秒数 | 正常 |
| **-1** | key 存在，但**没设过期时间** | **危险**（锁永久卡死） |
| **-2** | key 不存在（已过期/被删） | 可能是误删 |

**实测（2026-10-23）**：

```text
SETNX demo:lock:wrong          → TTL = -1   （永不过期 → 进程崩了锁卡死）
SET demo:lock:right NX EX 60   → TTL = 60   （自动释放）
（直接 DEL）                    → TTL = -2   （key 已不存在）
```

#### 二、对锁的意义：崩溃兜底

```text
锁 = Redis key
TTL = 持有者崩溃后，锁【自动释放】的时间

无 TTL → 崩溃即死锁
有 TTL → 崩溃后 TTL 到期，锁自动消失
```

`SET NX EX 300` 里的 `EX 300` 就是 TTL = 300 秒。

#### 三、同一个概念的其他地方

| 场景 | TTL 指什么 |
|---|---|
| Redis key | key 多少秒后自动删除 |
| DNS | 解析结果缓存多久 |
| CDN / 浏览器缓存 | 缓存文件多久后回源 |
| JWT | token 多久失效 |
| Kafka | 消息保留多久（`retention.ms`） |
| 项目报告缓存（场景⑦） | 30 分钟后重新查库 |

#### 四、TTL 的两难

| TTL 短 | TTL 长 |
|---|---|
| 业务没跑完锁就过期 → 两人同时执行 | 持有者崩了，别人白等 |

**解法**：看门狗（Redisson 每 1/3 TTL 续期）或 **TTL + 业务幂等兜底**（本课做法）。

### 11.5 附讲：看门狗（Watchdog）= 锁的心跳续期（Q5 · 2026-10-23）

#### 一、是什么

**后台定时任务：周期性检查"持有者是否还活着"，活着就帮它延长锁的 TTL。**

#### 二、为什么需要（TTL 两难）

```text
业务 10 秒~10 分钟不确定

TTL=30s   → 业务跑 40s，锁提前过期 → 第二人进来 ❌
TTL=10min → 崩溃后别人白等 10 分钟 ❌
```

看门狗解：**TTL 设短 + 只要还在干活就续期**——正常执行不误过期，崩溃后最多等一个 TTL。

#### 三、机制（三步）

```text
① 加锁 → TTL=30s，启动后台任务
② 每 10s（TTL/3）检查：活着 → TTL 重置为 30s
③ 业务完成 unlock → 看门狗停止
```

**为什么是 TTL/3**：留 3 次机会，容错 2 次网络抖动。

#### 四、模拟实测（2026-10-23）

```text
[A] 加锁成功，TTL=5s
[看门狗] 续期成功 ×5          ← A 干活期间一直续
[B] 第 1~4 次尝试：全部失败    ← 锁一直被续着
[A] ★ 进程崩溃（看门狗停止）
[B] 第 5、6 次尝试：仍失败     ← 残留 TTL 未到期
[B] 第 7 次尝试：拿到锁！      ← TTL 到期自动释放
```

**价值**：不是让锁永不过期，而是**让锁跟着业务活，业务一死就快速释放**。

#### 五、边界（解决不了什么）

| 情况 | 看门狗 | 兜底 |
|---|---|---|
| 进程崩溃 | ❌ 跟着死 | TTL 自动释放 |
| 网络分区（续期失败） | ❌ | TTL 过期 → 幂等兜底 |
| Redis 主从切换（锁丢） | ❌ | Redlock / 幂等 |

> **看门狗降低"误过期概率"，不保证"永不误过期"——锁 + 幂等才是完整方案。**

#### 六、本项目为什么没用

```java
private static final Duration LOCK_TTL = Duration.ofMinutes(5);   // 固定 TTL，无看门狗
```

业务最长 ≈30 秒（5 步 × LLM 6 秒），5 分钟 = 10 倍余量；**业务时长可预估 → 固定 TTL 足够**。

| 业务时长 | 方案 |
|---|---|
| 可预估（秒~分钟） | 固定 TTL（本项目） |
| 不可预估 | 看门狗（Redisson） |
| 极端不确定 | 看门狗 + 幂等 + 细粒度锁 |

#### 七、前端类比

| 前端机制 | 对应 |
|---|---|
| WebSocket 心跳 ping/pong | 定期喊"我还活着" |
| OAuth refresh token | 快过期自动续期 |

**看门狗 = 锁的心跳包。**
