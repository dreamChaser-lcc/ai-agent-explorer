## 一、什么是 N+1

```text
需求：列表页显示"每个任务有多少步骤"

❌ 直觉写法：
   ① 查任务列表            → 1 条 SQL（返回 N 条任务）
   ② 循环每个任务查步骤数   → N 条 SQL
   合计：1 + N 条

✅ 正确写法：
   ① 一条 JOIN + GROUP BY  → 1 条 SQL
```

**为什么叫 N+1**：**1 条主查询 + N 条子查询**（N = 列表长度）。

**危害**（按页大小线性恶化）：

| 页大小 | SQL 条数 | 影响 |
|---|---|---|
| 5 | 6 | 几乎无感 |
| 20 | **21** | 明显变慢 |
| 100 | **101** | 数据库压力陡增 |
| 1000 | **1001** | 接口超时、连接池打满（SP9） |

**关键认知**：**单条 SQL 都很快，加起来才要命**——网络往返（RTT）叠加才是杀手。

## 二、怎么发现 N+1

### 2.1 SQL 日志计数法（最简单，本课用）

```text
调一次接口 → 数日志里出现几次 SQL
  与"返回条数 + 1"接近 → 就是 N+1
```

本课实测：

```text
size=5  → 返回 5 条，产生 SQL 6 条（1 + 5）  ← 完全吻合

```

## 三、JPA 懒加载为什么会产生 N+1

```java
@Entity
public class ResearchTaskEntity {
    @OneToMany(mappedBy = "task", fetch = FetchType.LAZY)   // ★ 默认就是 LAZY
    private List<ResearchStepEntity> steps;
}
```

```java
// 列表查询后遍历 steps → 每个任务触发一条 SQL
List<ResearchTaskEntity> tasks = taskRepository.findAll();
for (ResearchTaskEntity task : tasks) {
    task.getSteps().size();    // ← 每调一次 = 一条 SQL（懒加载代理才去查库）
}
```

**★★ 它底层到底发了什么 SQL（必须看懂这一步）**：

```text
① 列表查询（1 条）：
   SELECT t.id, t.title, t.status, ... FROM research_task t LIMIT 10

② 每次 task.getSteps().size() 触发（N 条，参数是各自的任务 id）：
   SELECT s.id, s.task_id, s.step_no, s.status, ... 
   FROM research_step s 
   WHERE s.task_id = ?

   → 10 个任务 = 10 条这样的 SQL，只有 WHERE 的参数不同
```

**这就是 N+1 的真面目**：JPA 不会"聪明地一次查完"，它**按需查、一次一个任务**。你在 Java 里看不到 SQL，但数据库实际收到的是 1 + 10 条。

**为什么 JPA 默认 LAZY**：如果默认 EAGER，**每次查任务都会连表查全部步骤**——单任务详情变慢，且可能查出巨大结果集。LAZY 是"按需"的取舍，代价就是**遍历时 N+1**。

**关键区分**：

| 写法 | 是否 N+1 |
|---|---|
| `task.getSteps().size()` 在循环里 | ✅ 是（每次触发 1 条） |
| 单个实体 `task.getSteps()` | ❌ 不是（只多 1 条） |
| `findAll()` 不访问 steps | ❌ 不是（懒加载没触发） |

## 四、项目的设计取舍：不用关联映射

**审计结论**：项目里**没有任何 `@OneToMany` / `@ManyToOne`**——实体之间只有 `taskId` 外键字段，查询靠**显式 SQL**。

| 反面（关联映射） | 本项目的做法 | 好处 |
|---|---|---|
| `task.getSteps()` 隐式触发查询 | `stepRepository.findByTaskIdOrderByStepNoAsc(taskId)` 显式调用 | **每条 SQL 都在眼皮底下**，容易发现 N+1 |
| 列表页容易踩懒加载 | 列表用 **MyBatis 手写分页 SQL**（1 条查询 + 1 条 count） | 排序分页下推到数据库，只带 N 条数据进内存 |
| 实体图复杂难控 | DTO 只取需要的字段 | 传输量小、无意外查询 |

**代价**：多表展示要手写 JOIN（但换来的是完全可控）。

**结论**：**"不用关联映射"本身就是一种防 N+1 的设计**——隐式查询是 N+1 的温床，显式查询让问题无处藏身。

## 六、四种优化手段

| # | 手段 | 适用 | 代价 |
|---|---|---|---|
| 1 | **JOIN + GROUP BY**（本课） | 列表页聚合统计 | 手写 SQL（本项目走 MyBatis/JdbcTemplate） |
| 2 | **批量 IN 查询**（两段式） | 列表要展示子表明细 | 2 条 SQL + 内存分组；IN 太长要分批 |
| 3 | **JPA `join fetch` / `@EntityGraph`** | 有 `@OneToMany` 关联时 | 只对 JPA 关联有效；分页 + fetch join 需注意 |
| 4 | **缓存** | 子数据变化少 | 一致性成本（场景⑦ 的 TTL） |

### 6.1 批量 IN 查询（两段式，最常用）

```java
// ① 查主表（1 条）
List<ResearchTaskEntity> tasks = taskRepository.findAll(pageable).getContent();
List<UUID> taskIds = tasks.stream().map(ResearchTaskEntity::getId).toList();

// ② 一次 IN 查全部子表（1 条），内存分组
Map<UUID, List<ResearchStepEntity>> stepsByTask = stepRepository.findByTaskIdIn(taskIds).stream()
        .collect(Collectors.groupingBy(ResearchStepEntity::getTaskId));

// ③ 组装（0 条 SQL）
```

**共 2 条 SQL**——与 N 无关。**注意**：`IN` 列表过长要分批（本课清理的 `batchSize` 是同一思路）。

**★ 上面两个 JPA 方法底层发的 SQL**：

```text
① findAll(pageable) →
   SELECT * FROM research_task ORDER BY created_at DESC LIMIT ? OFFSET ?

② findByTaskIdIn(taskIds) →（派生方法名直接翻译成 WHERE ... IN）
   SELECT * FROM research_step WHERE task_id IN (?, ?, ?, ...)
```

**派生查询的命名规则**：`findBy` + `字段` + `In` → `WHERE 字段 IN (...)`。看懂这条规则，你就能预判任何 `findByXxx` 会生成什么 SQL。

**如果不用 JPA，等价写法**：

```java
// JdbcTemplate 版（同样 2 条 SQL，SQL 完全由你掌控）
List<Map<String, Object>> tasks = jdbcTemplate.queryForList(
        "SELECT * FROM research_task ORDER BY created_at DESC LIMIT ? OFFSET ?", size, offset);

List<Map<String, Object>> steps = jdbcTemplate.queryForList(
        "SELECT * FROM research_step WHERE task_id IN (" + placeholders + ")", taskIds.toArray());
```

### 6.2 JPA 的两种写法

```java
// 写法 A：JPQL join fetch
@Query("select t from ResearchTaskEntity t join fetch t.steps where t.id = :id")
Optional<ResearchTaskEntity> findWithSteps(@Param("id") UUID id);

// 写法 B：@EntityGraph（声明式，更推荐）
@EntityGraph(attributePaths = "steps")
Optional<ResearchTaskEntity> findById(UUID id);
```

**★ 这两种写法底层生成的 SQL**：

```text
写法 A / B 都生成同一条（一次 JOIN，但行数放大）：
   SELECT t.id, t.title, ..., s.id, s.task_id, s.step_no, ...
   FROM research_task t
   LEFT JOIN research_step s ON s.task_id = t.id
   WHERE t.id = ?

行数：1 个任务 × N 个步骤 = N 行（不是 1 行！）
```

**这就是"一条 SQL"的代价**：数据库网络传输的行数变多了，而且**一对多分页时 Hibernate 无法在 SQL 层 LIMIT**（因为一个任务被拆成多行）——只能全部查进内存再切页。

**坑**：`join fetch` + 分页（`Pageable`）会**先查全部再内存分页**（Hibernate 警告 `HHH000104`）——一对多分页应改用"两段式"（6.1）。

### 6.3 同一需求的三种写法（SQL 视角优先）

| 需求 | 原生 SQL（原理） | JdbcTemplate | JPA |
|---|---|---|---|
| 列表 + 步骤数 | `SELECT t.id, COUNT(s.id) FROM research_task t LEFT JOIN research_step s ON s.task_id=t.id GROUP BY t.id` | `queryForList(sql)` ← **本课优化版** | 无直接对应，需 `@Query(nativeQuery = true)` |
| 列表 + 子表明细 | `SELECT * FROM research_step WHERE task_id IN (?,...)`（**2 条 SQL**） | `queryForList(sql, ids)` | `findByTaskIdIn(ids)`（生成同样的 IN） |
| 遍历关联数据 | `SELECT ... FROM research_step WHERE task_id = ?`（**N 条**） | 循环 queryForList（同样 N 条） | `task.getSteps()`（懒加载，N 条） |

**读法**：**先看 SQL 列**（理解数据库实际做什么），再看框架列（理解它替你封装了什么）。**JPA 不会减少 SQL 条数，它只是把 SQL 藏起来**——这正是学它必须先看 SQL 的原因。

## 八、思考题（自查 + 参考答案）

1. 列表页显示"每任务步骤数"，20 条数据最差写法产生多少条 SQL？<br>
   **参考答案**：**21 条**（1 条主查询 + 20 条子查询）——本课实测 `size=20 → 21 条`。页大小翻倍，SQL 条数也翻倍。
2. 为什么本项目没用 `@OneToMany`？<br>
   **参考答案**：**显式查询可控**——每条 SQL 都在代码里可见（容易发现 N+1、便于优化）、DTO 只取需要的字段、避免懒加载的隐式触发。代价是多表展示要手写 JOIN。**"不用关联映射"本身就是一种防 N+1 的设计**。
3. `join fetch` 和 `@EntityGraph` 有什么区别？<br>
   **参考答案**：都用来解决懒加载 N+1。`join fetch` 写在 JPQL 里（`select t from T t join fetch t.steps`）；`@EntityGraph` 写在 Repository 方法上（`@EntityGraph(attributePaths = "steps")`），更声明式、不动 JPQL。
4. 一对多关联 + 分页，为什么不能用 `join fetch`？<br>
   **参考答案**：一对多 JOIN 会**放大行数**（1 个任务 × 5 个步骤 = 5 行），Hibernate 无法在 SQL 层正确分页，只能**先把全部数据查进内存再分页**（警告 `HHH000104`）。正确做法：**两段式**——先分页查主表（1 条），再用 `IN` 查子表（1 条），内存分组。
5. 批量 `IN` 查询有什么隐患？<br>
   **参考答案**：`IN` 列表过长会导致 SQL 解析慢、可能触发数据库参数上限（如 Oracle 1000 个）。要**分批**（如 500 个一批）——与本课清理的 `batchSize` 同理。

### 10.1 N+1 到底是什么（Q1 · 2026-10-24）

#### 一、生活类比（先理解"趟数"）

```text
需求：统计公司 10 个部门各有多少人

❌ N+1：第 1 趟去 HR 拿名单（10 个部门）
        再跑 10 趟，每个部门单独问"你们多少人"
        共 11 趟

✅ 正确：1 趟，HR 一次给"部门-人数"对照表
```

**数据一样，跑腿次数差 11 倍。**

#### 二、对应代码

```java
// ❌ N+1：先查列表，再循环查详情
List<Dept> depts = deptDao.findAll();              // 第 1 趟（1 条 SQL）
for (Dept d : depts) {
    int count = empDao.countByDeptId(d.getId());   // 又跑 N 趟（N 条 SQL）
}

// ✅ 一条 SQL
SELECT d.name, COUNT(e.id) FROM dept d LEFT JOIN emp e ON e.dept_id = d.id GROUP BY d.id;
```

#### 三、实测：数据库实际收到的（2026-10-24 抓取）

调 `size=3` 时日志里的 SQL 参数：

```text
parameter (1:UUID) <- [f84bca74-...]     ← 第 1 条（任务 A 的步骤）
parameter (1:UUID) <- [35fa5483-...]     ← 第 2 条（任务 B 的步骤）
parameter (1:UUID) <- [57ba8980-...]     ← 第 3 条（任务 C 的步骤）
```

**三条 SQL 除 `WHERE task_id = ?` 的参数外，一字不差。**

#### 四、不是"写法错误"，是"用法低效"

| 检查项 | 结果 |
|---|---|
| 代码能跑吗 | ✅ 能，结果正确 |
| 会报错吗 | ❌ 不会 |
| 测试能过吗 | ✅ 能过 |
| 问题 | ⚠️ **慢 N 倍**（每条数据多一次数据库往返） |

**功能正常、测试全绿、上线才发现超时**——这是它最坑的地方。

#### 五、为什么最容易犯（两个直觉陷阱）

1. **"先查列表再循环查详情"看起来天经地义**——人类直觉是逐个问，数据库的强项是一次查一批；
2. **JPA 让你看不到 SQL**——`task.getSteps()` 像"读属性"，实际悄悄发了一条查询。**看不见的 SQL = 最贵的 SQL**。

#### 六、自查三信号（任一命中即 N+1）

| 信号 | 怎么看 |
|---|---|
| for 循环里调 Dao/Repository | 看代码 |
| 同一条 SQL 反复出现、只有参数不同 | 看日志 |
| 循环里访问 JPA 关联属性 | 看代码 |

#### 七、一句话

```text
N+1 = 1 次"查列表" + N 次"逐个查详情" = N+1 趟数据库往返
不是错误，是用法低效——能跑、结果对，只是慢
```
