## 一、审计：测试腐化的真相

```text
项目有 5 个测试文件，但 8 个月没人跑过：

编译阶段：4 个错误
   ResearchTaskControllerTest:75    thenReturn(TaskSummaryResponse) 找不到方法

   ResearchTaskOrchestratorTest:34  构造器参数不匹配
```

**腐化链路**（主代码改了 5 个场景，测试一个都没跟）：

| 场景 | 改动 | 测试后果 |

| ③ 分页 | `listTasks()` → `listTasks(page, size, status)`，返回 `PageResponse` | 编译错误 |
| ④ 幂等 | `createTask` 返回 `TaskSummaryResponse` → `CreateTaskOutcome` | 编译错误 |
| ⑥ Kafka | Orchestrator 构造器末位 `Executor` → `TaskExecutionProducer` | 编译错误 |
| ⑨ 并发 | Orchestrator 构造器再加 `DistributedTaskLock` | 编译错误 |
| ② 实体演进 | `ResearchTaskEntity` 加 `@Version` | schema.sql 缺列 → 运行时错误 |

## 二、测试金字塔（先建立全局观）

| 层 | 测什么 | 速度 | 是否启动 Spring | 项目现状 |
|---|---|---|---|---|
| **单元测试** | 纯逻辑（无 IO） | 毫秒 | ❌ | 少（`LlmCallGuard` 可补） |
| **Web 层**（MockMvc） | Controller：参数校验/返回结构/异常转换 | 秒 | 部分（只装配 MVC） | ✅ `ResearchTaskControllerTest` |

**比例原则**：单元多、集成少、E2E 最少（越往上越慢越脆）。

## 三、修历史欠账（逐个击破）

### 3.1 ControllerTest：两处签名变化

```java
// ❌ 旧：createTask 直接返回 TaskSummaryResponse
when(commandService.createTask(any(), eq("demo-user"))).thenReturn(response);

// ✅ 新：返回 CreateTaskOutcome（场景④ 引入"是否真新建"）
when(commandService.createTask(any(), eq("demo-user")))
        .thenReturn(new CreateTaskOutcome(response, true));
```

```java
// ❌ 旧：listTasks 无参，返回 List
when(queryService.listTasks()).thenReturn(List.of(response));
jsonPath("$[0].title")

// ✅ 新：分页三参数，返回 PageResponse
when(queryService.listTasks(anyInt(), anyInt(), any()))
        .thenReturn(new PageResponse<>(List.of(response), 0, 10, 1L, 1));
jsonPath("$.content[0].title")
jsonPath("$.totalElements").value(1)
```

**踩坑**：`isNull()` 匹配器对泛型 `TaskStatus` 参数没命中（mock 返回 null → 响应体空 → `json can not be null or empty`）。改用 `any()` 宽松匹配才通。

### 3.2 OrchestratorTest：构造器从 10 个参数变 11 个

```java
// ✅ 补齐场景⑥/⑨ 新增的两个依赖
return new ResearchTaskOrchestrator(
        taskRepository, ..., new ObjectMapper(),
        mock(TaskExecutionProducer.class),      // 场景⑥
        mock(DistributedTaskLock.class));       // 场景⑨
```

**ASYNC 的行为也变了**（从"线程池提交"变"发 Kafka 消息"）：

```java
// ❌ 旧：verify(executor).execute(any(Runnable.class));
// ✅ 新：
verify(producer).publish(taskId);
```

### 3.3 RepositoryPersistenceTest：schema 与实体脱节（标记 @Disabled）

```text
第一版错误：insert into research_task (... version ...) → 列不存在
根因：src/test/resources/schema.sql 写于 8 个月前，实体后来加了 @Version 列

尝试 1：schema.sql 补 version 列 → 其他表可能也缺（不可持续）
尝试 2：改 ddl-auto=create-drop → 被主配置 ddl-auto=validate 覆盖 → 缺表

最终：@Disabled + 原因注释（**测试腐化标本**，待专项修复）
```

**正确修复方向**（写进类注释）：测试专用 profile（H2 原生方言）或 Testcontainers。

## 四、三个教训（测试腐化的解药）

| # | 教训 | 具体 |
|---|---|---|
| 1 | **接口一变，测试就断** | 这是测试的**成本**，也是它的**价值**——它逼你确认"改动是否影响调用方" |
| 2 | **绕过测试 = 藏欠账** | `-Dmaven.test.skip=true` 用了 5 天，欠账从 2 个错误涨到 8 个 |
| 3 | **手写 schema 必然腐化** | 实体加了列，schema.sql 不知道；测试应让 Hibernate 自动建表或用 Testcontainers |

**正确的使用姿势**：

```text
开发中：    mvn test -Dtest=XxxTest          只跑相关测试（秒级）
提交前：    mvn test                         全量回归（分钟级）
紧急修复：  -Dmaven.test.skip=true           仅限"测试本身正在修"，且当日必须补回
```

## 五、三个测试模板（可直接抄）

### 模板 1：纯单元测试（不启动 Spring）

```java
class LlmCallGuardTest {

    @Test
    void shouldRetryThenSucceed() {
        LlmClient client = mock(LlmClient.class);
        when(client.chat(any()))
                .thenThrow(new RuntimeException("超时"))
                .thenReturn("OK");

        LlmCallGuard guard = new LlmCallGuard(client, 1, 2);

        Optional<String> result = guard.execute("prompt");

        assertThat(result).contains("OK");
        verify(client, times(2)).chat(any());   // 第 1 次失败 + 第 2 次成功
    }
}
```

**特点**：毫秒级、无 IO、最适合"重试/退避/边界条件"这类纯逻辑。

### 模板 2：MockMvc（Controller 层，只装配 MVC）

```java
@WebMvcTest(controllers = XxxController.class)
@Import(ApiExceptionHandler.class)          // 全局异常也要装配，否则测不到 400
class XxxControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private XxxService service;

    @Test
    void shouldReturn400WhenTitleBlank() throws Exception {
        mockMvc.perform(post("/api/xxx")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("{\"title\":\"\"}"))
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("$.code").value(400));
    }
}
```

**特点**：不连数据库、不启 Tomcat，但**能验证参数校验、统一返回体、异常转换**（场景① 的三件套）。

### 模板 3：集成测试（Repository + 真实 DB）

```java
@SpringBootTest
@ActiveProfiles("test")            // 或用 Testcontainers
class XxxRepositoryIntegrationTest {

    @Autowired
    private XxxRepository repository;

    @Test
    void shouldPersistAndQuery() { ... }
}
```

**特点**：慢但真实，适合"SQL 行为、事务、索引"这类**必须打到数据库**的验证。

## 八、思考题（自查 + 参考答案）

1. 为什么测试代码会"腐化"？<br>
   **参考答案**：主代码演进（改签名、加依赖、改返回类型）而测试没跟着改；更致命的是**没人跑**——`-Dmaven.test.skip=true` 让编译错误被隐藏，腐化在无人知晓时累积。
2. MockMvc 测试和 `@SpringBootTest` 有什么区别？<br>
   **参考答案**：`@WebMvcTest` 只装配 MVC 层（Controller + 全局异常 + 消息转换器），**不启动完整容器、不连数据库**，快（秒级）；`@SpringBootTest` 启动完整容器（连 DB/Redis/Kafka），慢但真实（能测事务、SQL、中间件交互）。
3. 测试该用"手写 schema.sql"还是"Hibernate 自动建表"？<br>
   **参考答案**：**测试用自动建表（或 Testcontainers）**——测试关心"行为正确"，结构随实体自动生成，永不过时；**生产用 Flyway/schema 显式管理**——生产关心"结构可控、可回滚"。两者职责不同。
4. 为什么 `-Dmaven.test.skip=true` 危险？<br>
   **参考答案**：它**连测试编译都跳过**——测试代码坏了（签名不匹配）也发现不了；`-DskipTests` 至少还能编译（能发现签名问题）。只在"测试本身正在修"时短期使用，**当日必须补回**。
5. 一个 Service 方法有 3 个分支（成功/参数错/下游失败），最少写几个测试？<br>
   **参考答案**：至少 3 个（每个分支一个）；再加边界（空值、超时）与并发（如果涉及）就够。**不要追求 100% 覆盖率，要覆盖"会出错的路径"**。

### 10.1 Mockito 的 `when(...).thenReturn(...)` 是什么意思（Q1 · 2026-10-24）

**不是循环**——`when` 是 `Mockito.when()` 静态方法，中文读作"**当……被调用时，就返回……**"。

#### 一、中文读法

```java
when(某个 mock 对象的某个方法调用)  .thenReturn(返回值)
──────────────┬──────────────────    ──────────┬────────
        "当这个调用发生"                    "就返回这个值"
```

本课第 81-82 行读作：

> "当 `researchTaskCommandService.createTask(任意请求, "demo-user")` 被调用时，返回 `new CreateTaskOutcome(response, true)`"

#### 二、执行时序（反直觉的三步）

```text
① 先执行 service.createTask(any(), eq("demo-user"))
   —— service 是 mock，方法体不执行，只向 Mockito 报备"有人调了这个方法，参数是 matcher"
② when(...) 捕获这次调用 → 建立"调用 → 返回值"映射
③ .thenReturn(result) 把返回值填进映射
```

#### 三、参数匹配器

| matcher | 含义 |
|---|---|
| `any(类型)` | 任意该类型参数 |
| `any()` | 任意值（含 null） |
| `eq("demo-user")` | 精确匹配 |

**铁律**：一个调用里 matcher 与原始值**不能混用**（否则 `InvalidUseOfMatchersException`）：

```java
when(service.createTask(any(), "demo-user"))            // ❌
when(service.createTask(any(), eq("demo-user")))        // ✅
```

#### 四、前端类比

| 前端 | Mockito |
|---|---|
| `vi.fn().mockReturnValue(x)`（Vitest） | `when(mock.method()).thenReturn(x)` |
| `jest.spyOn(obj,'m').mockReturnValue(x)` | 同上 |

#### 五、不打桩会怎样

`@MockBean` 的假对象**默认所有方法返回 null** → Controller 拿到 null → 响应体空 → 断言失败（本课修历史欠账时遇到的 `json can not be null or empty` 就是这个）。

#### 六、其他常用形式

```java
when(x).thenReturn(a).thenReturn(b);          // 连续两次不同返回
when(x).thenThrow(new RuntimeException());    // 抛异常
doNothing().when(mock).someVoidMethod();      // void 方法
verify(producer).publish(taskId);             // 验证调用（事后检查，非打桩）
```

#### 七、三个常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| matcher 混用 | `InvalidUseOfMatchersException` | 全部用 matcher |
| 打桩参数不匹配 | 返回 null，**不报错** | 用 `any()` 或核对参数 |
| 对真实对象用 when | 真的执行了方法 | 只能对 mock 打桩 |

### 10.2 为什么没做 E2E（Q2 · 2026-10-24）

#### 一、项目真实状态

| 层 | 现状 |
|---|---|
| 单元测试 | 少（可补 LlmCallGuard 等） |
| MockMvc | ✅ 4 个 |
| 集成测试 | ✅ 2 个（Store + DB） |
| **E2E** | ❌ 无自动化，12 个场景全靠 curl 手工验证 |

手工验证**能覆盖但不可重复、不可 CI、无断言**。

#### 二、为什么没做（三个真实原因）

| # | 原因 | 说明 |
|---|---|---|
| 1 | **依赖全部环境** | DB + Kafka + Redis + 应用全起，启动 30 秒+ |
| 2 | **外部依赖不可控** | 真实 LLM 4~9 秒、花钱、偶发失败 → 红灯不稳 |
| 3 | **测试金字塔** | E2E 应最少，先补单元/集成更划算 |

**E2E 的真实成本**：

```text
环境：Docker/DB/Kafka/Redis
数据：每次造数据 + 清理
外部：LLM 真调用（钱 + 时间 + 不稳定）
维护：接口改字段就挂
时间：分钟级（vs 单测毫秒级）
```

#### 三、三种实现方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. Testcontainers** | 真 PG + 真 Kafka + 真应用 | 最真实、可 CI | Docker 依赖、启动 30 秒+ |
| **B. MockMvc + H2（薄 E2E）** | 全链路但 Kafka/LLM 用 mock | 快、无需 Docker | Kafka 是假的 |
| **C. 脚本化冒烟** | PowerShell/curl 跑完整链路 | 零依赖、贴近真实 | 不可断言、不能 CI |

#### 四、务实路径

```text
短期：手工 curl 固化成 scripts/e2e-smoke.ps1（半自动化）
中期：核心链路用 Testcontainers（创建 → 确认 → 完成 → 报告存在）
长期：CI 里跑（单元 + 集成 + E2E 冒烟）
```

#### 五、什么时候必须做 E2E

- 支付/订单等**钱相关**的核心链路；
- **多服务协作**（微服务拆开后，单测覆盖不到跨服务契约）；
- 合规/审计要求"上线前必须全链路验证"。

**本项目是单服务 + 单体应用**，集成测试的覆盖性价比更高——这就是没优先做 E2E 的判断依据。

### 10.3 E2E 实现教学（Q3 · 2026-10-24）

#### 一、E2E 与集成测试的区别

```text
集成测试：测【一层】——Repository + 真实 DB
E2E：    测【一个业务闭环】——HTTP 入口 → DB/中间件 → HTTP 响应
```

判断标准：是否同时跨过 **Controller → Service → Repository → DB/MQ**。

#### 二、本项目的完整链路（六步）

```text
① POST /api/tasks                  创建任务 → 落库 + LLM 生成计划
② POST /api/tasks/{id}/confirm     确认 → 状态 RUNNING + 发 Kafka
③ Kafka 消费者                      executeTask：5 个步骤
④ GET /api/tasks/{id}              轮询直到 COMPLETED
⑤ GET /api/tasks/{id}/report       断言报告存在
⑥ GET /api/tasks/{id}/events       断言事件序列
```

**第 ③ 步是 E2E 的独有价值**——只有它能验证"HTTP 确认 → 消息 → 消费 → 状态回写"的异步闭环。

#### 三、方案 A：Testcontainers（真环境）

```java
@SpringBootTest(webEnvironment = RANDOM_PORT)     // 真起 Tomcat
@Testcontainers
class TaskLifecycleE2ETest {

    @Container
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @Container
    static KafkaContainer kafka =
            new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.6.0"));

    @DynamicPropertySource                              // 容器地址 → 应用配置
    static void props(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.kafka.bootstrap-servers", kafka::getBootstrapServers);
    }

    @Autowired
    TestRestTemplate rest;

    @Test
    void shouldCompleteTaskLifecycle() {
        // ① 创建
        var created = rest.postForEntity("/api/tasks",
                new CreateRequest("E2E", "端到端验证", "ASYNC"), TaskSummary.class);
        assertThat(created.getStatusCode()).isEqualTo(HttpStatus.CREATED);
        String taskId = created.getBody().id();

        // ② 确认
        rest.postForEntity("/api/tasks/" + taskId + "/confirm",
                Map.of("approved", true, "responseMessage", "OK"), Void.class);

        // ③ 轮询（核心）
        awaitStatus(taskId, "COMPLETED", Duration.ofSeconds(60));

        // ④ 断言报告
        var report = rest.getForObject("/api/tasks/" + taskId + "/report", Report.class);
        assertThat(report.summary()).isNotBlank();

        // ⑤ 断言事件序列
        var events = rest.getForObject("/api/tasks/" + taskId + "/events", List.class);
        assertThat(events).extracting("eventType")
                .contains("TASK_CREATED", "PLAN_CONFIRMED", "TASK_COMPLETED");
    }

    /** 轮询直到目标状态；超时或异常状态则失败。 */
    private void awaitStatus(String taskId, String expected, Duration timeout) {
        Instant deadline = Instant.now().plus(timeout);
        while (Instant.now().isBefore(deadline)) {
            var detail = rest.getForObject("/api/tasks/" + taskId, TaskDetail.class);
            if (expected.equals(detail.status())) {
                return;
            }
            if (Set.of("FAILED", "CANCELLED").contains(detail.status())) {
                fail("任务异常结束：" + detail.status());
            }
            sleep(1000);
        }
        fail("等待 " + expected + " 超时（" + timeout + "）");
    }
}
```

#### 四、方案 B：MockMvc + H2（薄 E2E，快但链路不全）

```java
@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")
class TaskFlowE2ETest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void shouldCompleteSyncTask() throws Exception {
        // SYNC 模式：confirm 时同步执行完，不依赖 Kafka
        String response = mockMvc.perform(post("/api/tasks")
                        .contentType(APPLICATION_JSON)

                .andExpect(status().isCreated())
```

#### 五、方案 C：脚本化冒烟（零代码）

```powershell
# scripts/e2e-smoke.ps1
param([string]$BaseUrl = "http://localhost:8080")

$task = Invoke-RestMethod "$BaseUrl/api/tasks" -Method Post `
    -ContentType "application/json" `
    -Body '{"title":"E2E","goal":"端到端","executionMode":"SYNC"}'
$id = $task.id

Invoke-RestMethod "$BaseUrl/api/tasks/$id/confirm" -Method Post `
    -ContentType "application/json" -Body '{"approved":true}'

$deadline = (Get-Date).AddSeconds(60)
do {
    Start-Sleep -Seconds 2
    $detail = Invoke-RestMethod "$BaseUrl/api/tasks/$id"
} while ($detail.status -notin @("COMPLETED", "FAILED", "CANCELLED") -and (Get-Date) -lt $deadline)

if ($detail.status -ne "COMPLETED") {
    Write-Error "E2E 失败：$($detail.status)"
    exit 1
}
Write-Host "✅ E2E 通过（taskId=$id）"
exit 0
```

#### 六、五个设计要点

| # | 要点 | 为什么 |
|---|---|---|
| 1 | **轮询代替固定 sleep** | 异步任务不知道何时完成；固定 sleep 要么太短要么太慢 |
| 2 | **必须设超时** | 不设超时，CI 永远挂着 |
| 3 | **断言业务结果** | 断言 COMPLETED + 报告存在，别断言"执行了几次 SQL" |
| 4 | **数据隔离** | 每次新 UUID；或每个用例前后清理 |
| 5 | **外部依赖可控** | LLM 用 `APP_LLM_SIMULATED=true`（否则花钱 + 偶发失败） |

#### 七、坑清单

| 坑 | 现象 | 解法 |
|---|---|---|
| 固定 `sleep(10)` | 机器慢就超时、快就浪费 | 轮询 + deadline |
| 共享测试数据 | 用例互相污染 | 每次新 UUID / 独立 schema |
| 断言太细 | 改日志格式就红灯 | 只断言业务可见结果 |
| 外部依赖 | LLM/Kafka 挂 → 测试挂 | 模拟模式 / Testcontainers |
| 不可重入 | 跑第二次失败 | 每次重建数据 |

#### 八、落地顺序（若以后要做）

```text
第 1 步（半天）：Testcontainers 骨架 + 1 个核心用例（创建→确认→完成）
第 2 步（半天）：抽 awaitStatus 工具类 + 启用模拟 LLM
第 3 步（半天）：接 GitHub Actions（docker-compose 起 PG/Kafka）
```

#### 九、为什么"不做"也合理

```text
✅ 单服务单体：集成测试已覆盖数据层
✅ 手工 curl 覆盖了每课验证
✅ E2E 边际收益低（12 个场景没因缺 E2E 漏过 bug）
❌ 拆微服务后（跨服务契约测不到）E2E 才变刚需
```
