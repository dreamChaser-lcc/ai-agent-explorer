# ④ 幂等提交（重复提交不重复创建）

> **日期**：2026-10-09　**教材**：`ResearchTaskCommandService`、`ResearchTaskMapper.java/.xml`、`schema-dev.sql`
> **前置**：场景②（状态机 + 乐观锁——同为"并发防线"家族）｜**后续**：场景⑤（AOP 审计日志）

## 1. 开课动机

**真实的用户操作**：网络卡了一下——用户对着"创建任务"按钮**点了两下**（或请求超时后客户端自动重试）：

```text
没有防线时：
  第 1 次 POST ──→ 创建任务 A ✓
  第 2 次 POST ──→ 又创建任务 B ✗（用户只想建一个！）
```

**HTTP POST 天生不幂等**——同一请求打两次，就有两条数据。"重复提交"的三个真实来源：

1. **用户双击**（浏览器可没义务帮你防重）；
2. **客户端重试**（超时后自动重发——它不知道第一次成没成）；
3. **网关/中间层重试**（某些基础设施也会）。

**幂等的定义（一句话）**：**同一操作执行一次与执行多次，效果完全一致**。
"查列表"天然幂等（打 10 次和 1 次结果一样）；"创建"天然不幂等——所以需要**人为设计**。

## 2. 现状审计（证据）

读当时的 `ResearchTaskCommandService.createTask`（场景④ 前）：

```java
public TaskSummaryResponse createTask(CreateResearchTaskRequest request, String createdBy) {
    ResearchTaskEntity task = new ResearchTaskEntity();   // 裸创建
    ...
    researchTaskRepository.save(task);                    // 每次调用都 INSERT 一条
    ...
}
```

三处证据：

1. **服务层无任何"查重"逻辑**——来一次建一次；
2. **请求体无"业务标识"**——服务端收到两次请求，无法区分"重复"还是"两件事"；
3. **数据库 `research_task` 无相关唯一约束**——最后一道防线也是空的。

**结论**：同一请求打两次 = 两条任务（可复现）。

## 3. 设计抉择：幂等键 + 快路径重放 + 唯一索引兜底

### 3.1 幂等键（Idempotency Key）——机制的地基

**让客户端为"逻辑上的一次操作"生成一个唯一串**，随请求携带：

```json
{ "title": "...", "goal": "...", "executionMode": "ASYNC", "idempotencyKey": "客户端生成的唯一串" }
```

**关键约束：必须客户端生成**。

- 客户端重试 → 带**同一个**键 → 服务端认得出"这是同一件事" ✓
- 服务端生成 → 每次请求都是新键 → 永远不认识 → 幂等为零 ✗

**不传键 = 不参与幂等**——服务端不替客户端猜"这两个请求是不是一件事"（用户真心要建两个同名任务也是合法的）。

### 3.2 三种方案对比

| 方案 | 做法 | 缺陷 |
|------|------|------|
| A. 只查一下（check-then-act） | 收到请求先 `SELECT` 有没有同键任务 | ★ **并发窗口**：两个同键请求同时查、同时"没有"→ 同时创建（J8 学的"竞态"） |
| B. 只靠唯一约束 | 键上加唯一索引，撞了报错 | 体验差：**常态的重试也被当成"错误"**（其实只想要回结果） |
| **C. 快路径 + 索引兜底（选定 ✓）** | 先查（命中→重放）；真插入时靠唯一索引仲裁并发 | —— |

### 3.3 选定的完整流程（本场景核心）

```text
请求（带键）
   │
   ├─ ① 快路径：findByIdempotencyKey(键)
   │      命中 → 返回首次任务（200 重放）——【根本不去存】
   │
   └─ ② 创建路径：setIdempotencyKey(键) → saveAndFlush
          正常 → 201（新建）
          并发撞唯一索引 → DataIntegrityViolationException → 409"请重试"
                          （重试即回到 ①，拿到首次结果）
```

**两道防线分工**：

| 防线 | 执行者 | 性质 | 覆盖场景 |
|------|--------|------|---------|
| 快路径 | 应用代码（SELECT 先查） | 主动回避 | 常态（99% 的重试） |
| 唯一索引 | 数据库（INSERT 被拒） | 被动拦截 | 并发窗口那一瞬 |

**状态码即信号**：201（首次创建）/ 200（重放）/ 409（并发兜底"请重试"）。

## 4. ★ 知识课：三个设计细节

### 4.1 为什么用 `saveAndFlush` 而不是 `save`

```text
save         → INSERT 可能拖到【事务提交时】才发——冲突在方法外爆，接不住
saveAndFlush → INSERT 【立刻】发——唯一索引冲突【当场】抛出 → 值班室 409 优雅兜底
```

### 4.2 为什么需要 `normalizeIdempotencyKey`（空串炸弹）

```java
private String normalizeIdempotencyKey(String key) {
    if (key == null || key.isBlank()) return null;   // 空白 → 一律归为"没带"
    return key.trim();                               // 防 " key " 空格差异
}
```

- **空串炸弹**：前端表单没填时常传 `""`——若不归一化，`""` 会写进唯一索引 → **全库只能有一条空串记录** → 第二个"没填键"的请求撞墙（明明都该各自创建）；
- **空格隐身**：`"idem-001 "` 与 `"idem-001"` 不 trim 就是两把键——幂等悄悄失效。

### 4.3 唯一索引允许多个 NULL（设计前提）

```sql
CREATE UNIQUE INDEX uq_research_task_idempotency_key ON research_task (idempotency_key);
```

——SQL 标准：**NULL 不等于 NULL**（多个 NULL 互不冲突）——所以"不带键的请求"天然不受约束影响。

## 6. 验证记录（2026-10-09，全绿）

### 6.1 核心对照（干净复验——同一个文件连发两次）

| 发次 | 状态码 | 返回 id | 判读 |
|------|--------|---------|------|
| 第 1 发 | **201** | `be0da398-…`（TASK-A78EFFB2） | 首次创建 |
| 第 2 发 | **200** | ★ **同一个 id** `be0da398-…` | 幂等重放——没有第二条！ |

**两个细节彩蛋**：

1. 第 2 发返回的 `updatedAt`（30.854088）比第 1 发响应里的（30.8413485）**更新**——说明重放是**真去数据库现查的**（读到第一发事务提交后的最新版）；
2. 重放**只读**——数据一个字节没被改动。

### 6.2 破案：历史残骸的"忠实重放"

补打早前那发 `req1.json`（键 `idem-demo-001`）→ **200 + 命中 `b6664e85`（title=`"??????"`）**——说明那次"半成功"的请求**当时确实带了键**；服务端**忠实地把那条残骸重放**了（哪怕首次记录是坏的——**重放不挑内容**）。

### 6.3 其余各幕

| 幕 | 结果 |
|----|------|
| 换键（idem-demo-002） | **201** + "幂等测试任务2" ✓ |
| 不带键 | **201** + "无键任务" ✓（普通请求照常） |
| 列表检查 | **无重复任务** ✓ |

### 6.4 ★ 验证路上的意外课：PowerShell 三层坑（实战教训）

| 层 | 现象 | 根因 | 解法 |
|----|------|------|------|
| 1 | `curl: (3) URL rejected` | `\"` 是 cmd 转义，PowerShell 不认 → 参数拆碎 | **单引号包 JSON** |
| 2 | 仍 400（`fields:[]` 空） | **中文编码**：PS 把中文按 GBK 字节传给 curl → 服务端按 UTF-8 解析失败 | **文件法**：UTF-8 无 BOM 写文件 + `-d @文件` |

**副产品：`"??????"` 化石**——某次"半成功"请求的 GBK 字节被嚼成问号**静默入库**（比 400 更阴险的坏法：当场拒收你能立刻发现，脏数据潜行可能几个月后才被翻出来）。

**排障心法**：接口联调时，"看起来是业务问题"的 400，先排除**传输层**（编码/转义）——`fields:[]` 空 = 整包读不了（传输问题）；`fields` 非空 = 字段校验（业务问题）。

## 7. ★ 固化：幂等提交规范（本场景产出）

**客户端（调用方）**：

1. 为"逻辑上的一次操作"生成唯一键（UUID 等）——★ 重试时**携带同一个键**；
2. 键的粒度 = "这件事"，不是"这次请求"。

**服务端**：

1. 幂等键以可选字段接收；**不传 = 不参与幂等**（判断权在调用方）；
2. **快路径**：先查（走唯一索引）——命中即重放（200 + 首次结果，不做任何写入）；
3. **创建路径**：`saveAndFlush` 让唯一约束**当场仲裁**——冲突 → 409"请重试"（重试即重放）；
4. 入库前 `normalize`（空白 → null、trim）；
5. 状态码：**201 新建 / 200 重放 / 409 并发兜底**。

**数据库**：

1. 幂等键列 + **唯一索引**（并发最终仲裁者）；
2. 列可空（多个 NULL 不冲突——兼容"不带键"的调用方）。

## 9. 补充：思考题与答案（课堂问答收录，2026-10-09）

### 问 1（观察题）：裸请求（不带幂等键）为什么照常创建？

**答**：因为"是否重复"的**判断权在调用方**——服务端没有能力（也不应该）替客户端猜"这两个请求是不是同一件事"。带键 = "我声明这是同一件事，请帮我防重"；不传 = "每次都是一件新事"（用户真心要建两个同名任务也合法）。所以不带键的请求走**普通路径**（照常 201），只有带键的才进入幂等判定。

### 问 2（设计题）：为什么"快路径 + 唯一索引"两层都要（不直接用一个）？

**答**：

- **只有快路径** → 挡住 99% 的常态重试，但**并发窗口**（两个请求同时查、同时"没有"）漏网（check-then-act 的经典缺陷）；
- **只有唯一索引** → 可靠，但**常态重试也走"撞墙报错"路线**——体验差（明明只想要回结果，却收到错误）；
- **两层合体** → 快路径管"体验"（命中就重放，什么都不发生），唯一索引管"可靠"（并发漏网的由数据库物理仲裁）——**进门查名单 + 门口物理锁**。

### 问 3（追问收录）：`request.idempotencyKey()` 这个方法从哪来？

**答**：**record 的自动访问器**（J1：字段叫什么、访问器就叫什么——不是 `getXxx`）。验证法：打开 `CreateResearchTaskRequest.java` **找不到方法体**却能用——编译器自动生成。同轮另一位主角 `normalizeIdempotencyKey` 则是**本类手写的私有方法**（编辑器里能 Ctrl+点击跳到实现）——**"找得到出处的是手写，找不到的是自动生成"**。

### 问 4（概念校准）：幂等就是"已存在则显示已存在"吗？

**答**：**不是报错，是"无感重放"**——已存在时返回**首次创建的那个任务**（200 OK + 同一个 id），对客户端来说"重试 = 首发"，它甚至不需要知道第一次是否成功过。**最好的幂等让调用方无感**。409"请重试"只出现在并发撞唯一索引的兜底场景（非常态）。
