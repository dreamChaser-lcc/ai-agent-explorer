# ⑥ 异步执行升级——线程池 → Kafka

> **日期**：2026-10-11　**教材**：`TaskExecutionProducer`、`TaskExecutionConsumer`、`KafkaTopicConfiguration`、`ResearchTaskOrchestrator`
> **前置**：J8（线程池）、J7（注解）、场景②（状态机守卫）、场景④（幂等）｜**延伸**：G1（Kafka 进集群——StatefulSet/PVC，按需衔接）

## 1. 开课动机——线程池的三个"天花板"

J8 的线程池（`researchTaskExecutor`）队列**在进程内**，导致三个极限：

| # | 局限 | 场景 |
|---|------|------|
| 1 | **进程内 → 重启即蒸发** | 发版/崩溃 → 还在排队的任务全丢 |
| 2 | **不可跨进程 → 无法"加工人"** | 想加专职执行机？做不到（下单台和工厂焊死在一栋楼） |
| 3 | **容量有限 → 满了就拒** | 队列 100——高峰第 101 个任务直接拒绝 |

**核心思想**：**"下单"与"干活"彻底解耦**——提交任务 = 把订单挂到前台（发消息、秒回）；执行 = 工厂按自己节奏取单。
**前端锚点**：Kafka = **跨机器的 EventEmitter + 两样赠品**（① 消息持久化不阅后即焚；② 消费进度（书签）可管理）。

## 3. ★ 知识课一：Kafka 核心概念

### 3.1 五件套

| 概念 | 人话 | 类比 |
|------|------|------|
| Producer | 发消息的人 | `emit` 方 |
| Consumer | 收消息的人 | `on` 方 |
| Topic | 一个频道（按业务分类） | 电台频道 |
| Partition | 频道里的**多条车道**（并行度） | 高速车道（同 key 进同车道 → 局部有序） |
| Offset | 消息在车道上的序列号 | 书签（读到第几条） |

**Consumer Group**：一组同事分摊同一个 Topic（组内一条消息只被一人消费）。

### 3.2 两个颠覆直觉的点

1. **消息不是阅后即焚**——存磁盘保留（默认 7 天）——**可重放**（新消费者从头读一遍——排查/重构利器）；
2. **投递语义是"至少一次"（at-least-once）**——同一条消息可能被消费两次（"处理完"与"提交书签"之间的缝隙）——★ 呼应场景④：**HTTP 重试用幂等键防重；MQ 重投用什么防重？→ 状态守卫（思考题 2）**。

### 3.3 线程池 vs Kafka

| 维度 | 线程池 | Kafka |
|------|--------|-------|
| 位置 | 进程内 | 独立中间件（跨进程） |
| 重启 | 队列丢失 | 消息持久在磁盘 |
| 容量 | 100 条 | 海量堆积（磁盘容量） |
| 消费者可以是谁 | 只能本进程线程 | **任何进程/服务**（可独立扩容） |
| 失败重试 | 代码手写 | 书签不回滚/重投（至少一次） |

### 3.4 Spring Kafka 两个关键词（★ 注解第 4 次现身）

```java
kafkaTemplate.send("research-task-execution", taskId.toString());   // 生产
@KafkaListener(topics = "research-task-execution")                  // 消费——"申请书+外包工"（@Transactional/@AuditLog 同族）
```

## 4. 设计抉择

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 消息格式 | ★ **轻消息：只发 taskId** | "任务活在数据库里，消息只是敲门砖"（场景④ 思想续集）——消费时读最新状态 |
| 消费执行方式 | 监听线程**直接**跑 `executeTask` | 正确姿势：处理完才提交 offset；换线程池会破坏投递语义 |
| 长任务问题 | yml 调大 `max.poll.interval.ms`（1 小时） | 默认 5 分钟会误判"消费者死亡"→重平衡→重复消费 |
| 原线程池 | **保留 bean，退出主链路**（"退居二线"） | 不破坏既有结构；未来可作消费者内部并行等用途 |
| Topic 定义 | `@Bean NewTopic`（3 分区） | 主题定义随代码走、可版本化 |

## 6. 验证记录（2026-10-11，全绿）

### 6.1 链路铁证（describe 仪表盘）

```text
操作：创建（201）→ pause（204）→ resume（204，★ 触发发消息）
      → describe：
        PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
        0          1               1               0     ← ★ 消息落 P0（key=taskId 哈希）且已消费完
        1 / 2      -               0               -     ← 空车道
```

**结论**：发出去 ✓ 落进分区 ✓ 被消费 ✓ 书签提交 ✓——**describe 不会撒谎**（日志显示几条都不影响这个铁证）。

### 6.2 重放实验（书签 1 → 0 亲眼可见）

```text
停应用（组 inactive——★ 不停应用 reset 会报 "group is Stable"——门槛的教科书现场）
→ reset --to-earliest：NEW-OFFSET 三分区全 0
→ describe：CURRENT-OFFSET 1 → 0、LAG=1、no active members（三处对照，书签被打回）
```

### 6.3 ★★ 幂等活体演示（最强证据）

```text
同一任务的消息被消费【3 次】：
  首轮（14:53:50）：真执行（任务终态 COMPLETED）
  重放二轮（15:04:14.659 → .669）：10 毫秒——守卫秒拦
  重放三轮（15:19:10.620 → .630）：10 毫秒——守卫再拦
★ 任务记录的 updatedAt 停在 14:53:50.977——三次重放【没碰一个字节】= "零副作用"硬核证明
```

**10 毫秒的解剖**：`收到 → loadTask → shouldStop= true（终态）→ return`——"重放了一遍，业务效果为零"——**思考题 2 的"重投 + 守卫 + 幂等"三件套全部活体验证**。

### 6.4 意外观察（诚实记录，待查证）

任务终态是 **COMPLETED**（预期 FAILED），且首轮执行**极快完成**（updatedAt 与 resume 同刻、没有跑分钟级研究流程）——**疑似**"无待执行步骤 → 直接标记完成"类快捷路径——属 `executeTask` 的既有行为（非 Kafka 改造引入），**待回头翻代码确认**。不影响本课三条结论。

## 7. ★ 固化规范（本场景产出）

1. **任务消息化**：异步执行 = 发消息（轻消息只带 id）；消费端读 DB 拿最新状态；
2. **幂等消费**：消息可重投——靠"状态守卫 + 断点续跑 + 唯一约束"三层防线（效果幂等）；
3. **长任务护航**：`max.poll.interval.ms` 必须调大（默认 5 分钟 → 重平衡 → 重复消费）；
4. **监控**：`LAG`（积压）是消费者健康第一指标——生产要做告警；
5. **回退操作手册**：① 旁路查看（新组 console-consumer——安全）；② 重置重放（`--reset-offsets`——**必须先停应用**）；③ 预防"书签过期变新组"（调大 `offsets.retention.minutes`）。

## 9. ★ 补充：思考题与答案 + offset 五连问补课（2026-10-11）

### 思考题 1（对比题）：线程池队列 vs Kafka Topic 的三个本质区别？

**答**：① **边界**——进程内内存结构 vs 楼外独立中间件（跨机器）；② **重启后**——内存蒸发 vs 磁盘持久（可续读/可重放）；③ ★ **"谁来干活"的选择面**——只能本进程线程 vs 任何进程/服务（解耦与独立扩容的根源）。

### 思考题 2（设计题）：at-least-once（可能重复）为什么不怕？

**答**：三层底气——① **状态守卫**（`executeTask` 开头 `shouldStop`——终态/暂停/取消 → 空操作；本课 6.3 的三次消费即实证）；② **同 Partition 串行消费**（同条消息不会被两个消费者同时处理——重复只来自"提交前崩溃"的串行重放）；③ **升华**——"**消息队列给的是'至少一次'，'恰好一次'要业务自己挣**"（at-least-once + 幂等 = 事实 exactly-once）。**金句：MQ 重投 + 状态守卫 + 幂等思想 = 三件套结伴出现**。

### 追问 1：offset 在代码里怎么看不到？它是什么？

**答**：offset 由**客户端内部**（KafkaConsumer）管理——应用代码是"乘客层"（乘客睡觉、司机记里程）。原理：**分区内**消息的递增序号 + 消费者组的**书签**（一组 `<分区, offset>`）；书签存在**服务端**（`__consumer_offsets` 内部主题——Kafka 用自己的消息机制存消费进度——自举式设计）；**组间隔离**（每组一份书签——所以"重放"可行）。**"偏移"的本义 = 书签相对车道起点的偏移量**。

### 追问 2：什么时候"移动书签"？重复从哪来？

**答**：两代策略——① 原生客户端默认 `enable.auto.commit=true`（每 5 秒）→ "至多一次"（**可能丢**——处理一半就提交了）；② ★ **Spring Kafka 容器默认**（`enable.auto.commit=false` + `AckMode.BATCH`）→ "**处理完才提交**" → 崩在提交前 → 重读 → **至少一次**（可能重，不丢）。**价值观：宁重勿丢**（丢=任务永久消失；重=守卫兜底）。**重复的全部来源 = "处理完"与"提交书签"之间的那条微缝**。

### 追问 3：怎么排查丢/重？怎么回退？

**答**：**排查三层观测窗**——① 生产层（`[MQ] 已发送` 日志 + LOG-END-OFFSET）；② 消费层（**LAG**——积压=LOG-END−CURRENT；长期 0 且业务没执行=疑似跳过）；③ ★ **业务层对账**（Kafka 消息数 vs `[MQ] 收到` 日志数 vs 业务数据——丢=A>B、重=B>A）。**回退三姿势**——① 旁路查看（console-consumer 新组 `--from-beginning`——**只看不干**）；② 重置原组（`--reset-offsets`——**必须先停应用**（否则报 "group is Stable"——本课实测现场）；档位：earliest/latest/offset/shift-by/datetime）；③ 新组并行（审计/重算）。
**根原理**：Kafka 把"**消息生命周期**"与"**消费进度**"解耦（消息留磁盘、书签可改写）——传统 MQ "读走即焚"两者焊死——**这就是"可重放"的根**。

### 追问 4：代码层 `seek()` 用在什么场景？

**答**：**不是排查工具，是业务逻辑的一部分**（设计时写进去的）：① 失败重试原形（`seek` 回当前条——"卡住等外部恢复"）；② ★ 跳过"毒药消息"（坏消息卡死车道——如本项目 `UUID.fromString` 收到坏 id 的隐患）；③ 程序化"时间旅行"（`ConsumerSeekAware`——"每次启动从某时间点读起"——如每日对账）；④ `auto-offset-reset` 的主动版。**分工**：**看**（describe/LAG）→ 排查；**改**（reset）→ 运维恢复；**改**（seek）→ 业务内建。

### 追问 5：事故后重启会重复订阅，怎么保证幂等？

**答**：① **先校准**——**正常重启不重复**（从服务端书签续读）；重复的三个口子：**(a)** 提交前崩溃（小范围）；**(b)** ★ **书签过期**（`offsets.retention.minutes` 默认 7 天——停机太久→变"新组"→按 earliest **从头全量重放**——"事故停机很久"的真实风险，**对策：调大该配置**）；**(c)** 人为重置。② ★ **"不要重复操作"物理上做不到——能做到的是"重复了也无害"（效果幂等）**。③ **三板斧**：状态守卫（已有）/ 断点续跑（已有设计——精度见 `executeTask`）/ 唯一约束（写副作用兜底）；④ 升级选项：**messageId 去重表**（严格消费幂等的正规军——未来按需）。

### 追问 6（面试专题）："MQ 怎么保证不丢不重"——标准答法

> 高频面试题。先记住**答题框架**（别直接扎进细节）：**可靠性先拆"三段接力"，"不重"先讲"真相"。**

#### 一、开场拆题（话术）

> "MQ 的可靠性要拆成三段接力来看：**消息发出去不丢（生产端）、存下来不丢（Broker）、被处理不丢（消费端）**；'不重'则要先讲一个真相——**分布式里没有'恰好一次投递'**，靠的是**投递语义 + 业务幂等**。"

#### 二、三段接力（"不丢"的完整工具清单）

| 段 | 目标 | 手段 | 注意 |
|----|------|------|------|
| **① 生产端** | 发出去的一定存下 | **`acks=all`**（所有 ISR 副本确认——Kafka 3.0+ 客户端默认，生产建议**显式**配置）+ **`retries`**（网络抖动自动重发）+ ★ **幂等生产者**（`enable.idempotence=true`——PID+序列号，防"重试导致重复"且保序） | 只重试可能致重 → 所以配幂等 |
| **② Broker 端** | 存下的不会丢 | **副本**（`replication.factor ≥ 3`）+ **ISR**（跟得上的副本集合）+ **`min.insync.replicas ≥ 2`**（配合 acks=all 才写入成功）+ **`unclean.leader.election.enable=false`**（宁可不可用、不选"脏副本"当 leader） | 我们开发环境 replicas=1（单节点）——生产必须 ≥3 |
| **③ 消费端** | 存下的一定被处理 | ★ **"处理完才提交"**——关自动提交（`enable.auto.commit=false`）或交给容器管理（Spring Kafka 的 `AckMode`——**本项目用的默认**：处理完一批才提交书签）；更精细 = 手动 ack | 这就把"丢"换成了"可能重"——**宁重勿丢** |
| **④ 端到端兜底** | 把"万一"也补上 | 发送失败**落库+定时补偿**（本地消息表/事务消息）；**LAG 监控告警**；retention（默认 7 天）**给重放补偿留了窗口** | 生产工程的常规项 |

#### 三、"不重"——投递层做不到，业务自己挣

**先讲真相**（加分项）：

> "Kafka 只提供两种投递语义：**至多一次（可能丢）** 和 **至少一次（可能重）**——'恰好一次投递'在分布式里是神话（两将军问题）。Kafka 选的是**至少一次**——因为**丢了就真没了，重复可以靠业务无害化**——叫'**宁重勿丢**'。"

**重复的三个来源 + 各自解法**：

| 来源 | 解法 |
|------|------|
| 生产者重试导致重复 | ★ **幂等生产者**（Kafka 内部去重——`enable.idempotence=true`） |
| 消费者"处理完未提交书签"就崩 → 重读 | ★ **业务幂等**（见下） |
| rebalance / 人为重置 offset | 同上 + 慎用重置 |

**消费端幂等三件套（"不重"的正菜）**：

```text
① 状态守卫     —— 处理前先看业务状态："该干才干"（本项目 executeTask 的 shouldStop）
② 幂等键去重表 —— 每条消息带唯一 id（messageId），处理前查去重表（DB/Redis SETNX）
③ 唯一约束兜底 —— 写副作用处放唯一索引（撞了=已处理过）
= 三件套合体：重复消息"来了，但效果为零"
```

**★ 金句（背下来）**：

> "**消息队列负责'至少一次'——'恰好一次'是业务自己挣的**：at-least-once + **幂等消费** = 事实上的 exactly-once 效果。"

#### 四、★ 杀手锏：把项目实例讲出来（比背参数值钱得多）

> "我们项目实测过：任务消息被**消费了 3 次**（真执行 1 次 + 人为重置 offset 重放 2 次）——靠 `executeTask` 开头的**状态守卫**，重放的两轮各 **10 毫秒**就被拦下（读库→看状态终态→直接返回）——而且任务记录的 `updatedAt` **纹丝不动**：不止没跑步骤，连一个字段都没被碰过。**这就是'重复消费可以发生，重复操作发生不了'**。"

**再把运维视角补一句**（第三个加分点）：

> "可观测和可恢复也是'不丢'的一部分：用 **LAG（积压量）** 做消费健康监控和告警；真出事需要重放时，用 `--reset-offsets` 重置书签（**必须先停消费者**）；还要注意 `offsets.retention.minutes`（默认 7 天）——消费组离线超期会**书签过期变'新组'**，按 earliest 从头全量重放。"

#### 五、30 秒速答版（面试场上背这段）

> "拆成三段看：**生产端** `acks=all` + 重试 + 幂等生产者，保证发出去的一定存下；**Broker 端**多副本 ISR + `min.insync.replicas`，保证存下的不丢；**消费端**'处理完才提交'，保证存下的会被处理。至于'不重'——**分布式没有恰好一次投递**，Kafka 给的是至少一次（宁重勿丢）；真正的'不重'是业务层挣的：**状态守卫 + 幂等键 + 唯一约束**，把重复变无害。我们项目同一条消息消费了三次，业务效果只有一次。"
