> **课程**：业务场景实战 · 第 10 课（2026-10-23）
> **目标**：让数据"能删得掉"——过期任务连同子表清理、旧事件与审计按保留期回收
> **带出的知识**：`@Scheduled` 三种调度模式、批量删除 vs JPA 逐条删、表名白名单（SQL 注入）、定时任务的多实例互斥

## 一、审计：数据只增不减（实测）

```text
GET /api/admin/cleanup/stats（清理前）
{
  "research_task":    36,
  "task_event_log":   209,     ← 事件的增长速度是任务的 6 倍
  "step_execution":   36,
  "source_document":  48,
  "audit_log":        45
}
```

**问题**：项目从第 1 课跑到现在，**没有任何删除逻辑**——每跑一次任务，5 张表都会新增行。真实生产里，这意味着一两年后表变成千万级：查询变慢、备份变贵、索引失效。

**为什么数据会膨胀**：

| 表 | 增长来源 |
|---|---|
| `research_task` | 每次创建任务 +1 |
| `task_event_log` | **每步执行写多条事件**（任务状态、步骤开始/完成、确认…） |
| `step_execution` | 每步一条执行记录 |
| `source_document` | 每次搜索/抓取插入多条来源 |
| `audit_log` | 每次 `@AuditLog` 方法调用一条 |

## 二、设计：保留策略按"数据价值"分层

| 表 | 保留期 | 理由 |
|---|---|---|
| `research_task` + 7 张子表 | **30 天**（仅终态任务） | 业务数据，过期没价值；运行中的绝不碰 |
| `task_event_log` | **60 天** | 排障需要更长的历史轨迹 |
| `audit_log` | **90 天** | 合规要求通常 90 天+ |

**三条硬约束**：

1. **只删终态**（`COMPLETED` / `CANCELLED` / `FAILED`）——运行中的任务被删 = 数据事故；
2. **先子后父**——避免子表留下孤儿行；
3. **分批删**（默认 200/批）——一次删太多会长时间持锁，阻塞线上写入。

## 三、实现

### 3.1 `@Scheduled` 三种模式（为什么选 fixedDelay）

| 写法 | 含义 | 风险 |
|---|---|---|
| `fixedRate` | 按固定频率触发（不管上次跑完没） | 任务执行超过间隔 → **堆积** |
| **`fixedDelay`** | 上次**跑完**后再等间隔 | ✅ 不会堆积（本课采用） |
| `cron` | 按日历表达式（如每天 2 点） | 适合"定点"业务，不适合"兜底清理" |

```java
@Scheduled(
    initialDelayString = "${app.cleanup.initial-delay-ms:60000}",
    fixedDelayString   = "${app.cleanup.interval-ms:3600000}")
public void scheduledCleanup() { ... }
```

### 3.2 为什么用 `JdbcTemplate` 而不是 JPA

| | JPA `deleteBy...` | **JdbcTemplate 批量 DELETE** |
|---|---|---|
| 执行方式 | 先查实体，再逐条 DELETE | **一条 SQL 删一批** |
| 1 万行 | 1 万条 SQL + 实体加载 | 若干条批量 SQL |
| 内存 | 全量实体进内存 | 只传 ID 数组 |

**清理是"按条件批量删除"**——这正是 SQL 的主场，JPA 的实体模型反而是负担。

### 3.3 表名白名单（SQL 注入防线）

```java
// 表名无法参数化（? 只能替换值），只能字符串拼接 → 必须白名单
private static final List<String> CHILD_TABLES = List.of(
    "step_execution", "research_step", "source_document",
    "research_plan", "research_report", "human_confirmation", "task_event_log");

public int countOf(String table) {
    if (!"research_task".equals(table) && !CHILD_TABLES.contains(table)) {
        throw new IllegalArgumentException("非法表名：" + table);
    }
    ...
}
```

### 3.4 多实例互斥（复用场景⑨ 的锁）

```java
@Scheduled(...)
public void scheduledCleanup() {
    Optional<String> token = lock.tryLock("cleanup");   // ★ 只有一个实例能拿到
    if (token.isEmpty()) {
        log.info("[清理] 跳过：另一个实例正在清理");
        return;
    }
    try { cleanupService.cleanupOnce(); }
    finally { lock.unlock("cleanup", token.get()); }
}
```

**为什么必须加锁**：三个 Pod 各跑一次 → 三次并发删除 → 死锁/锁等待/重复统计。**定时任务天然是"多实例重复执行"的重灾区**。

### 3.5 开关与阈值全部可配

```yaml
app:
  cleanup:
    enabled: true
    task-retention-days: 30
    event-retention-days: 60
    audit-retention-days: 90
    batch-size: 200
    interval-ms: 3600000
    initial-delay-ms: 60000
```

## 五、六个坑

| # | 坑 | 后果 | 做法 |
|---|---|---|---|
| 1 | 一次删太多（不分批） | 长事务、锁表、阻塞线上写入 | 分批（200/批） |
| 2 | 只删主表不删子表 | 孤儿数据（96 行/3 任务） | 先子后父，固定顺序 |
| 3 | 多实例都跑定时任务 | 重复删除、锁等待 | 分布式锁（场景⑨ 复用） |
| 4 | 删了运行中的任务 | 数据事故（消息/锁仍引用） | 只删终态 |
| 5 | 表名直接拼接 | SQL 注入 | 白名单常量 |
| 6 | 定时任务异常被调度器吞掉 | 一直失败没人知道 | try-catch + ERROR 日志 |

## 七、思考题（自查 + 参考答案）

1. 为什么用 `fixedDelay` 而不是 `fixedRate`？<br>
   **参考答案**：`fixedRate` 按固定频率触发、**不管上次是否跑完**——执行时间超过间隔就会堆积；`fixedDelay` 是"上次跑完后再等间隔"，天然不堆积。清理耗时不确定，必须 `fixedDelay`。
2. 为什么清理用 `JdbcTemplate` 而不是 JPA 的 `deleteBy...`？<br>
   **参考答案**：JPA 派生删除会**先查实体再逐条 DELETE**（1 万行 = 1 万条 SQL + 全量实体进内存）；`JdbcTemplate` 一条 `DELETE ... WHERE id IN (...)` 删一批，效率高几个数量级，且不用加载实体。
3. 为什么表名不能参数化？<br>
   **参考答案**：JDBC 的 `?` **只能替换值、不能替换标识符**（表名/列名）。表名只能拼接 → **必须白名单校验**，否则就是 SQL 注入。
4. 三个实例部署，定时任务会发生什么？<br>
   **参考答案**：**每个实例都会触发**——三次并发清理（重复删除、锁等待、统计翻倍）。需分布式锁（本课复用场景⑨）或外部调度平台（XXL-JOB / K8s CronJob）。
5. 为什么只删终态任务？<br>
   **参考答案**：运行中的任务可能仍有 Kafka 消息在消费、Redis 锁被持有、SSE 连接在推送——删掉会造成"执行到一半数据消失"。终态才没有后续动作。
6. 清理任务本身要不要加事务？<br>
   **参考答案**：**要**——一批删除要么全成要么全回滚，避免"主表删了、子表没删干净"。但批次不能大（长事务），所以是"**小事务 + 多批**"。

### 9.1 定时任务完整链路（Q1 · 2026-10-23）

#### 一、前端 vs 后端（本质区别）

| 维度 | 前端 `setTimeout`/`setInterval` | 后端 `@Scheduled` |
|---|---|---|
| 驱动者 | 浏览器**事件循环**（单线程） | `ScheduledThreadPoolExecutor`（线程池） |
| 执行线程 | 主线程/Worker | **独立调度线程**（`scheduling-1`） |
| 阻塞影响 | 卡住页面 | 阻塞**其他定时任务**（默认 1 线程） |
| 生命周期 | 页面关闭即消失 | 跟随**应用进程** |
| 多实例 | 不存在 | **每个实例都跑**（需分布式锁） |
| 异常 | 中断本次执行 | **被调度器吞掉**（必须 try-catch） |

#### 二、六步链路（配实测日志）

```text
① @EnableScheduling → 注册 ScheduledAnnotationBeanPostProcessor
② 它扫描所有 bean → 找 @Scheduled → 解析 initialDelay/fixedDelay
③ 注册到 TaskScheduler（默认 1 线程）
④ initialDelay 到期 → scheduling-1 线程反射调用方法
⑤ 方法体：拿锁 → 清理 → 释放锁
⑥ fixedDelay 计算下次（本次完成 + 间隔）→ 重新入队
```

**实测对账**（2026-10-23 自动触发两次）：

```text
15:56:02 应用启动
15:57:02 [锁] 获取成功 key=cleanup        ← 启动 + 60 秒（initialDelay）
15:57:02 [清理] 完成：0 行，耗时 1 ms
15:57:02 [锁] 释放
16:57:02 [锁] 获取成功 key=cleanup        ← 上次 + 1 小时（fixedDelay）
16:57:02 [清理] 完成：0 行，耗时 2 ms
```

**线程名是铁证**：手动调接口是 `[nio-8080-exec-4]`（Tomcat 线程），定时执行是 `[scheduling-1]`（调度线程）——**两条完全不同的执行路径**。

#### 三、底层怎么定时（不是轮询）

```text
ScheduledThreadPoolExecutor：
  最小堆（DelayedWorkQueue）按时间排序
  工作线程：take() 取堆顶 → parkNanos 睡到时间点 → 执行 → 重新入队
```

**零轮询开销**——"睡到下一个时间点"，与前端 timer 队列思路一致。

#### 四、代码逐段对应

```java
@Configuration
@EnableScheduling                          // ① 打开调度总开关
@EnableConfigurationProperties(CleanupProperties.class)
public class CleanupConfiguration { }

@Component
public class RetentionCleanupJob {

    @Scheduled(
        initialDelayString = "${app.cleanup.initial-delay-ms:60000}",   // ② 启动后 60 秒第一次
        fixedDelayString   = "${app.cleanup.interval-ms:3600000}")      // ③ 每次跑完再等 1 小时
    public void scheduledCleanup() {
        Optional<String> token = lock.tryLock("cleanup");    // ④ 多实例互斥
        if (token.isEmpty()) {
            log.info("[清理] 跳过：另一个实例正在清理");
            return;
        }
        try {
            cleanupService.cleanupOnce();                    // ⑤ 真正清理（自己事务）
        } catch (Exception exception) {
            log.error("[清理] 执行失败：{}", exception.getMessage(), exception);   // ⑥ 异常必须自己接住
        } finally {
            lock.unlock("cleanup", token.get());             // ⑦ 无论成败都释放锁
        }
    }
}
```

#### 五、三个坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 默认 poolSize=1 | 一个任务跑久 → 其他全部排队 | `spring.task.scheduling.pool.size=5` |
| 异常直接抛出 | 被调度器吞掉，业务无感知 | try-catch + ERROR 日志 |
| 多实例重复跑 | 三次并发清理 | 分布式锁 / XXL-JOB / K8s CronJob |

#### 六、fixedDelay vs cron

| | fixedDelay | cron |
|---|---|---|
| 语义 | 上次跑完 N 毫秒后再跑 | 定点（每天 2:00） |
| 时钟校准影响 | 不受 | 可能漏/重 |
| 适用 | **兜底清理、轮询** | 日报、对账 |

### 9.2 附讲：JdbcTemplate = 数据库的 axios（Q2 · 2026-10-23）

#### 一、是什么、在哪

| 项 | 内容 |
|---|---|
| 定义 | Spring 对 JDBC 的**薄封装**：你写 SQL，它管连接/异常/映射 |
| 类 | `org.springframework.jdbc.core.JdbcTemplate` |
| jar | `~/.m2/repository/org/springframework/spring-jdbc/6.2.17/spring-jdbc-6.2.17.jar` |
| 自动配置 | `JdbcTemplateAutoConfiguration`（有 DataSource 就自动注册 bean） |

#### 二、解决什么问题

原生 JDBC 查一个字段要 15 行（拿连接 / 绑参 / 映射 / catch / 三层 close），JdbcTemplate 一行：

```java
String name = jdbcTemplate.queryForObject("SELECT name FROM users WHERE id = ?", String.class, 1L);
```

它替你做了：**获取连接、关闭资源、异常转换（SQLException → DataAccessException）、参数绑定、结果映射**。

#### 三、"Template" = 模板方法模式（与 SP8 同源）

```java
// JdbcTemplate 内部（简化）
Connection con = dataSource.getConnection();   // 固定
try { return action.doInConnection(con); }     // 可变（你填 SQL）
finally { con.close(); }                       // 固定
```

**固定步骤父类写死、可变步骤你填**——和 `OncePerRequestFilter.doFilter` 调 `doFilterInternal` 同一个模式。

#### 四、五个常用 API

| API | 用途 | 项目实例 |
|---|---|---|
| `update(sql, args...)` | INSERT/UPDATE/DELETE，返回影响行数 | `DELETE FROM task_event_log WHERE ...` |
| `queryForObject(sql, 类型, args...)` | 查单个值 | `SELECT COUNT(*) FROM research_task` |
| `queryForList(sql, 类型, args...)` | 查单列多行 | `SELECT id FROM research_task WHERE ...` |
| `query(sql, RowMapper, args...)` | 多行 → 对象映射 | 复杂查询时用 |
| `batchUpdate(sql, List<Object[]>)` | 批量执行（性能最好） | 批量 INSERT |

#### 五、与 JPA / MyBatis 的关系（可共存）

```text
   JdbcTemplate      JPA（ORM）      MyBatis（SQL 映射）
         └──────────────┼──────────────────┘
                        ↓
              DataSource（HikariCP）
                        ↓
                   数据库
```

**共享同一套连接与事务**：在 `@Transactional` 内用 JdbcTemplate 自动加入同一事务。

#### 六、三个注意点

| # | 注意点 | 说明 |
|---|---|---|
| 1 | SQL 注入 | `?` 只能替换值；表名/列名/ORDER BY 必须白名单 |
| 2 | 大结果集 | `queryForList` 全量进内存；百万行要分页或 `RowCallbackHandler` |
| 3 | 事务 | 必须在 `@Transactional` 内才共享事务 |

#### 七、前端类比

| 前端 | 后端 |
|---|---|
| `fetch()` + 手写解析与错误处理 | 原生 JDBC |
| **axios**（自动 JSON/错误/拦截） | **JdbcTemplate** |

### 9.3 附讲：JdbcTemplate / MyBatis / JPA 的选型（Q3 · 2026-10-23）

**结论：三者能力等价，选型看"项目主力与团队习惯"。**

#### 一、MyBatis 写法示例

```xml
<delete id="deleteByTaskIds">
    DELETE FROM ${tableName} WHERE task_id IN
    <foreach collection="taskIds" item="id" open="(" separator="," close=")">
        #{id}
    </foreach>
</delete>
```

| 写法 | 含义 | 安全性 |
|---|---|---|
| `#{id}` | 预编译占位符 | ✅ 安全 |
| `${tableName}` | 字符串直接拼接 | ❌ 注入风险 → **必须白名单** |

#### 二、三者对比（批量清理场景）

| 维度 | JdbcTemplate（本课） | MyBatis | JPA `@Modifying` |
|---|---|---|---|
| 动态 IN | 手拼 `?,?,?` | `<foreach>` 自动生成 | 派生方法 / `in :ids` |
| 7 张表批量删 | **一个循环** | 7 个 `<delete>` 或通用 `${table}` | 7 个 Repository 方法 |
| SQL 可读性 | 代码拼串 | **XML 最清晰（DBA 可审）** | 方法名推导 |
| 批量性能 | 一条 SQL | 一条 SQL | 先查实体再逐条（最差） |
| 与项目风格 | 边缘工具 | 与场景⑥ MyBatis 双实现一致 | 与主业务 JPA 一致 |

#### 三、为什么本场景选 JdbcTemplate

1. **7 张表 × 动态表名**：一个 `for (String table : CHILD_TABLES)` 循环解决；MyBatis 要写 7 个 delete 或用 `${table}`（同样白名单）；
2. **运维性质，不需要领域模型**：SQL 直给最直观；
3. 不想为一个定时任务引入 Mapper XML。

#### 四、换 MyBatis 更合适的场景

| 情况 | 建议 |
|---|---|
| 项目主力是 MyBatis | ✅ 风格统一 |
| SQL 复杂（多表 join / 条件组合） | ✅ XML 可读性更好 |
| 需要 DBA 审核 | ✅ SQL 一目了然 |
| 就是按 ID 批量删几张表 | ✅ JdbcTemplate 更省事 |

### 9.4 附讲：写操作都要加事务吗？（Q4 · 2026-10-23）

**结论：不是"要不要加"，而是"边界划在哪"。**

#### 一、单条语句不需要显式事务

```text
数据库默认 auto-commit = true
  → 每条 INSERT/UPDATE/DELETE 自带隐式事务（要么成要么不成）
```

```java
jdbcTemplate.update("DELETE FROM task_event_log WHERE id = ?", id);   // 单条，天然原子
```

#### 二、必须加事务的三个场景

| 场景 | 例子 | 不加的后果 |
|---|---|---|
| 多条写要一起成败 | 转账：扣款 + 加款 | 扣成功、加失败 → 钱消失 |
| 先查后改（check-then-act） | 查余额 → 判断 → 扣 | 并发下两人都判断"够" |
| 批量循环写 | 循环插 100 条明细 | 第 50 条失败 → 前 49 条残缺 |

**判断口诀**：

```text
第 2 条语句失败时，第 1 条的结果要不要撤销？
  要 → 必须事务
  不要 → 不用
```

#### 三、不该加事务的场景

| 场景 | 原因 |
|---|---|
| 单条语句 | auto-commit 已保证，加事务白占连接 |
| **事务里有慢调用**（LLM/HTTP/MQ） | 长事务：连接被占（SP9）、锁持有、并发崩塌 |
| 纯查询（单次 SELECT） | 不需要原子性 |
| 大批量删除/导入 | 长事务 + 日志膨胀 → **分小批、每批一事务**（本课做法） |

#### 四、事务的真实成本

```text
借连接（SP9：事务期间 active+1）→ 别人借不到
行锁/表锁持有 → 并发下降
undo/redo 日志增长
提交前数据不可见
```

**事务越短越好、粒度越准越好，不是越多越好。**

#### 五、项目正反对照

| 方法 | 事务 | 判定 |
|---|---|---|
| `confirmPlan`（多表更新） | ✅ | 必须原子 |
| `RetentionCleanupService.cleanupOnce` | ✅（**小事务+分批**） | 一批全成或全回滚 |
| `executeTask`（跑 30 秒） | ❌ 整段不加（每步单独事务） | 否则超长事务 |
| `age` 端点（单条 UPDATE） | ❌ | 单条天然原子 |
| `generateInitialPlan`（含 LLM） | ⚠️ 加了，是隐患 | 长事务（SP4 已记录） |

#### 六、两个细节（展开版）

**① 只读事务并不是多余**

```java
@Transactional(readOnly = true)
public List<Task> listTasks() { ... }
```

- Hibernate 会跳过 **dirty checking**（不再比对实体是否有改动）→ 性能提升；
- 某些数据库/中间件可以据此把查询路由到**从库**；
- 适合"多次查询需要一致视图"的场景。

**② 事务边界放 Service，不放 Controller**

```text
Controller：参数校验 + 编排（不该有事务）
Service   ：一个业务用例 = 一个事务边界 ✅
```

#### 七、项目里最值得记的两个例子

```java
// ✅ 该加的：confirmPlan —— 改任务 + 计划 + 确认 + 写事件，四张表必须一起成败
// ❌ 不该加的：executeTask —— 整个任务跑 30 秒，绝不能整段一个事务
//              （它故意每步开小事务，长任务不占死连接）
```

#### 八、反面教材（项目里已有的隐患）

```java
@Transactional
public void generateInitialPlan(...) {
    建计划 → 调 LLM（6 秒！）→ 落步骤
    //        ↑ 这 6 秒里连接一直被占着（SP4 已记录）
}
```

**这就是"事务加错位置"的典型**：有原子性需求，但边界里塞了网络调用。

#### 九、一句话总结

```text
单条语句 → 不用事务（数据库已保证）
多条语句要一起成败 → 必须事务
事务里别做慢操作 → 越短越好
批量操作 → 分小批，每批一个事务
```
