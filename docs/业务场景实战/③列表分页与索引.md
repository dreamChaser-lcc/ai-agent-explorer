## 1. 开课动机

`listTasks()` 改造前 = **`findAll()` 全量查询 + Java 内存排序 + 全量返回**——8 条时飞快，8 万条时**三层同时恶化**：

| 层 | 恶化 | 关联 |
|----|------|------|
| 数据库 | 全表扫 8 万行、索引用不上 | SQL/索引（本课） |
| JVM | 8 万对象同住堆 + O(n log n) 排序 | ★ J9 的 `-Xmx` 墙角 → OOM 路径 |
| 网络/前端 | 几十 MB JSON——解析假死 | 序列化 |

**一个 `LIMIT 20` 全解决**——把"筛选、排序、分页"**全部下推到数据库**。

## 3. 设计抉择：A（干净换分页壳）✓

列表接口返回结构从"裸数组"升级为"分页壳"（`PageResponse`）——**破坏性变更**——用户拍板 **A 方案（干净地换）**：

- **判断第一步**："谁在调用？"——本项目无真实外部调用方 → 破坏面≈0；
- **A 的理由**：单一形态 / **早期是改形状的最佳时机** / `Page` 结构是行业标准形状；
- **何时该选 B（兼容叠）**：真实多下游（已发布 App）、公共 API——"**兼容是有成本的，该花在不得不兼容的地方**"。

## 4. ★ SQL 第一课（findPage 逐行）

```sql
SELECT id, task_no, title, ..., created_at, updated_at   -- ① 列全写（不用 *：稳定/可读/少搬数据）
FROM research_task                                        -- ② 从哪张表
<where>                                                   -- ③ 动态 SQL：
    <if test="status != null">                            --    status 传了才拼条件
        status = #{status}                                --    #{} 预编译参数（防 SQL 注入）
    </if>                                                 --    （${} 是字符串拼接——危险，禁用）
</where>
ORDER BY created_at DESC                                  -- ④ 排序（最新在前）
LIMIT #{size} OFFSET #{offset}                            -- ⑤ 分页：取 N 条、跳过 M 条
```

**关键知识点**：

| 点 | 说明 |
|----|------|
| `#{}` vs `${}` | `#{}` = 预编译占位符（生成 `?`，安全）；`${}` = 直接拼接（注入风险，参数一律禁用） |
| `<where>+<if>` | 动态 SQL——一条 XML 支持"全部/按状态筛"两种查询；`<where>` 智能处理空条件 |
| `OFFSET` 公式 | `offset = page × size`（第 0 页→0、第 1 页→20、第 2 页→40……） |
| `COUNT(*)` 配套 | 条件必须与列表查询**严格一致**，否则"总数"和"本页"对不上 |
| `totalPages` 算法 | `(total + size - 1) / size`（向上取整，服务层算） |
| 索引 | `created_at`（排序）+ `status`（筛选）——索引 ≈ 书的目录；**代价**：写入时要维护 |

## 7. ★ 固化：分页接口规范（本场景产出）

1. **请求参数**：`page`（从 0 起，默认 0）；`size`（默认 20，**服务端夹取 1~100**）；筛选参数可选；
2. **响应壳**：`PageResponse{content, page, size, totalElements, totalPages}`——全局统一；
3. **防御规则**：页码负值按 0；size 超上限夹取（**永远不信任客户端参数**）；
4. **SQL 侧**：`#{}` 预编译强制；动态条件用 `<where>+<if>`；列表与计数 SQL 条件严格一致；
5. **`EXPLAIN` 自查**（自习清单）：H2 Console（`/h2-console`）里拍片——`EXPLAIN SELECT ... ORDER BY created_at DESC LIMIT 3`——看计划里有没有 `/* PUBLIC.IDX_RESEARCH_TASK_CREATED_AT */`（有=走索引）；**A/B 实验**：`DROP INDEX ...` 后再拍（退化成全表扫）→ `CREATE INDEX` 恢复。

## 8. 复盘与关联地图

**复盘**：

1. **"全量"到"分页"的本质**：把"筛选/排序/分页"**三层下推**到数据库——**搬运量与数据规模脱钩**（永远只搬一页）；
2. **动态 SQL 是 MyBatis 的招牌菜**：`<where>+<if>` 一条 XML 适配多条件组合；
3. **`#{}` 与 `${}` 的分界线是安全线**（注入漏洞的常见入口）；
4. **索引是"读的加速器、写的税"**——按高频查询建，不按列全建；
5. ★ **用户路线校准**：数据层主线固定为 MyBatis 手写 SQL——本场景是"SQL 从 0 到 1"的第一课。

**关联课程**：

| 课/场景 | 关联点 |
|---------|--------|
| J3/J5 | `stream().sorted().map().toList()` 曾是"内存版分页排序"——本场景给了"数据库版"的对照 |
| J8 | MyBatis 日志（`==> Preparing`）再次现身——这次是**自己写的 SQL** |
| J9 | 三重恶化里的"JVM 层"= 堆上限的直接应用 |
| 场景① | 非法参数 400 的 handler 串联（零新增代码） |
| 场景④（预告） | 幂等的另一半：POST 创建防重复提交 |

**自习练习**：① 把 `ORDER BY created_at DESC` 改成 `ASC`（看列表反转）；② 照 `<if>` 模子加 `execution_mode` 筛选；③ H2 Console 完成 EXPLAIN A/B 拍片。

## 9. 补充：框架机制四连问（课堂问答收录，2026-10-09）

> 由本场景的 MyBatis 代码引出的四个"框架原理"追问——从"Mapper 怎么绑上的"一路问到"bean 的一生"。

### 问 1：Mapper 接口怎么和 XML 绑上的？没有一处引用啊！

**答**：靠**两个名字**对上 + 两处登记：

| 绑定点 | 约定 |
|--------|------|
| XML 的 `namespace` | = 接口的**全限定名** |
| `<select id="...">` | = 接口的**方法名** |
| yml 的 `mapper-locations` | 告诉 MyBatis 去哪找 XML（`classpath:mapper/*.xml`） |
| 接口上的 `@Mapper` | 告诉 Spring"这是 Mapper，特殊处理" |

- **绑定时机 = 启动时**：扫描 `@Mapper` 接口 → 反射读全限定名 → 找同名 XML → `id` 与方法一一对上 → ★ **为接口生成 JDK 动态代理对象** → 注册进容器；
- **运行时**：调用 `findPage(...)` = 代理拦截 → 按方法名找 SQL → 参数填 `#{}` → 执行 → 结果映射返回；
- **名字对不上时的报错**：`Invalid bound statement (not found)`（一秒钟定罪）；
- ★ **模式识别**：这是"**框架约定**"的又一实例（用户的第二次独立发现——第一次是 J2 的 DemoRunner"没人调用却执行"）。

### 问 2：构造器里的 `ResearchTaskMapper` 参数，也是给 bean 吗？

**答**：**是构造器注入**（Spring 按类型装配）——★ 但注入进去的**不是手写实现，是 MyBatis 启动时生成的代理对象**。
**彩蛋——"代理开会"现场**：这个构造器里四个依赖是**代理**（三个 JPA Repository = Spring Data 代理、一个 MyBatis Mapper = MyBatis 代理），只有 `TaskResponseMapper`（普通 @Component 类）是真实对象。
**验证法**：打印 `researchTaskMapper.getClass().getName()` → **`$Proxy`**（JDK 动态代理的"出品标记"）——与 J2 见过的 CGLIB 标记 `$$SpringCGLIB$$0` 构成"**双代理体系**"：

| 代理工厂 | 手段 | 标记 | 用在 |
|---------|------|------|------|
| JDK 动态代理 | 基于**接口** | `$Proxy` | 有接口处（Mapper / Repository） |
| CGLIB | 基于**继承** | `$$SpringCGLIB$$0` | 无接口的类 |

### 问 3：有哪些是"bean 的注解"？（bean 全景地图）

**按三个角色分组**：

**① 生产端（bean 从哪来——四路来源）**

| 来源 | 注解 | 要点 |
|------|------|------|
| 自报家门 | `@Component` 家族：`@Component` / `@Service` / `@Repository`（★异常翻译）/ `@Controller` / `@RestController`（=@Controller+@ResponseBody）/ `@Configuration` / `@RestControllerAdvice` | **语义不同、装配相同** |
| 代报名 | `@Bean`（贴 @Configuration 类的方法上） | 方法返回值 = bean；**用于第三方类/复杂构造** |
| 自动配置 | `@SpringBootApplication` 内含 `@EnableAutoConfiguration` | ★ **容器里大部分 bean 的真实来源**（HikariCP/DispatcherServlet/MyBatis 工厂……都是它送的） |
| 高级导入 | `@Import` | 认识名字即可 |

**② 管控端**：`@Profile` / `@ConditionalOnProperty`（条件装配——J2 三步裁判）；`@Primary`（多候选优先）；`@Qualifier`（按名点选）；`@Lazy`。

**③ 消费端（注入）**：★ **构造器注入**（项目全程在用——**单构造器免注解**）＞ `@Autowired` 字段注入（项目不用：final 用不了/依赖隐形/难测试）；`@Resource` 认识即可。

**项目实例对照**：`@RestController`→ResearchTaskController / `@Repository`→双 Store / `@Component`→DemoRunner / `@Configuration`→AsyncExecutionConfiguration / `@Bean`→researchTaskExecutor / `@ConditionalOnProperty`→双 Store / `@Profile`→DemoRunner / `@Qualifier`→Orchestrator 构造器 / `@ConfigurationProperties`→ExecutionProperties / `@Mapper`→ResearchTaskMapper。

**两种"bean 车祸"**：`NoSuchBeanDefinitionException`（找不到 → 查生产端）；`NoUniqueBeanDefinitionException`（多个候选 → @Qualifier/@Primary 治）。

### 问 4：bean 是不是 Spring 帮你实例化初始化、直接可以从构造函数中使用？

**答**：对 90%——补两处精确化：

**bean 的一生（人话版六步）**：

```text
① 扫描发现（登记）→ ② ★ 先备料再造人（深度优先造依赖链：A依赖B→先造B）→
③ 实例化（new，构造器执行）→ ④ 依赖装配 → ⑤ 初始化（@PostConstruct 等钩子——J2 的钩子家族）→ ⑥ 上岗（被注入给需要者）
```

**精确化 ①：这套待遇只给"被管理的类"**——只有 bean 的构造器有注入服务；`new` 出来的对象 = 普通对象，没人管。

**精确化 ②：构造器里"只接收，别干活"**——依赖虽已就绪，但惯例只做赋值，理由：① 自己的 `@PostConstruct` 还没跑；② 防循环依赖；③ 好测试。**"开始干活"的第一站 = `@PostConstruct`**。

**精确化 ③（顺带）：默认单例**——一个类只造一个对象，所有注入点拿到**同一个实例**（"复用"——与 J8 线程池的班组复用异曲同工）。

> **一句话收**：**bean = 容器替你造、替你装、替你初始化、并全程复用的对象**；你在构造器里"报需求"，它把造好的递到你手上——前提是"你也在名册上（是 bean）"，且"收货时别拆箱就干活"。
