> **一句话**：LLM 是不可控的第三方——会慢、会限流、会崩。本场景给它装上"**限时 + 再来一次 + 兜底**"三道保险，并且让"失败"可观测、可回溯。

## 一、动机：为什么"下游调用"要单独治理

场景⑦ 治的是"**自己的缓存**不可靠"，本场景治的是"**别人的服务**不可靠"——差别在于：缓存你能重启，LLM 你只能求它快点。

LLM 调用的四个现实问题：

| 问题 | 现实表现 | 不治理的后果 |
|---|---|---|
| **慢** | 首字几秒、复杂提示 30 秒+ | 请求线程被拖死，并发一高整个服务雪崩 |
| **限流** | 429 Too Many Requests | 重试风暴 → 被平台限得更狠 |
| **不稳定** | 5xx / 连接中断 | 用户"点一下创建任务就报错" |
| **返回不可控** | 不说 JSON 只说人话、夹带 markdown | 解析炸掉，业务中断 |

治理三件套（本场景的全部内容）：

```text
超时   → 给"等待"设上限：超过 N 秒就当它失败（不能无限等）
重试   → 吸收短暂抖动：失败再来，但要退避、要限次数
降级   → 保业务可用：全都失败时给一个"够用的兜底"，而不是让用户看到错误
```

## 三、设计：双实现 + 治理层 + 降级兜底

```text
ResearchPlanningService（业务方：我要一份研究计划）
        ↓
LlmPlanGenerator（业务层：拼提示词 → 调治理层 → 解析 JSON → 失败降级）
        ↓
LlmCallGuard（治理层：超时 + 指数退避重试 + 降级判定）
        ↓
LlmClient（接口）
   ├── OpenAiCompatibleLlmClient  真实调用（UA / 代理 / 超时）
   └── SimulatedLlmClient         可控模拟（NORMAL / SLOW / ERROR）
```

四个设计决策（每个都有明确理由）：

| 决策 | 理由 |
|---|---|
| **双实现（真实 + 模拟）** | 真实下游不会配合你"慢 5 秒"或"返回 500"，异常路径必须用可控下游验证（场景⑦"直改库"实验的同款思路） |
| **真实客户端默认用 LangChain4j，手写 HttpClient 保留为备选** | LangChain4j 1.17.2 的 `customHeaders(...)` 能注入中转站要求的 UA（见第八节）；手写版保留给"需要代码层代理隔离"的场景，`app.llm.client-impl` 切换 |
| **降级 = 复用原有模板计划** | 原模板不删，改当"LLM 挂了的保底路径"——**可用性优先**：任务照常能创建，只是质量退化 |
| **降级必须留痕** | `plannerModel=template-fallback` + 事件 `LLM_DEGRADED` + `rawPlanPayload.degraded=true`——事后能查"哪次是降级的、为什么" |

### 关键代码：治理层的三层

```java
// ① 业务级超时：主线程最多等 3 秒，等不到就抛 TimeoutException 进重试
CompletableFuture<String> future = CompletableFuture.supplyAsync(
        () -> llmClient.complete(promptText), callExecutor);
return future.get(timeoutSeconds, TimeUnit.SECONDS);

// ② 指数退避：100ms → 200ms → 400ms……避免"下游刚抖动就被连打三下"
sleepQuietly(BASE_BACKOFF_MILLISECONDS << attemptIndex);

// ③ 全部失败 → 降级（不抛异常，业务层拿到 degraded 结果自行兜底）
return LlmCallResult.degraded(lastFailureReason, attemptCount, elapsed);
```

### 关键代码：解析的防御性！

LLM 说"只输出 JSON"，但它经常：包一层 ```` ```json ````、多一段解释、步骤序号跳号、type 写成小写。所以解析层做了四件事：

```java
String cleanedJson = stripCodeFence(contentText);            // ① 去 markdown 围栏
if (!stepsNode.isArray() || stepsNode.isEmpty()) return null; // ② 结构不对 → 交降级
if (!ALLOWED_STEP_TYPES.contains(stepType)) stepType = "REPORT"; // ③ 类型白名单兜底
normalizedSteps.add(new StepDraft(index + 1, ...));          // ④ 序号强制连续
```

## 六、★ 深挖一：中转站接入排障实录（本次最贵的经验）

**背景**：中转站 `agentrouter.org` + 模型 `deepseek-v4-flash` + 一个"看起来没问题"的 key，接了三轮全是 401。

### 三层 401，三个不同的病因

| 轮次 | 错误 | 病因 |
|---|---|---|
| 1 | `unauthorized client detected, contact support` | **网关做客户端指纹检测**：默认 UA（curl / Java）被判为"未授权客户端" |
| 2 | `未提供令牌` | UA 过关了，但令牌头没被识别（当时用的是 `x-api-key`，网关只认 `Authorization: Bearer`） |
| 3 | `无效的令牌` | **其实是我的环境变量没跨命令保留**（每条 exec 都是新 shell，`$env:OPENAI_API_KEY` 变空）→ 发出去的是**空 Bearer** |

### 最终可用配置（实测）

```text
base-url:   https://agentrouter.org/v1     ← 官方文档确认（OpenAI 兼容要带 /v1）
auth:       Authorization: Bearer <key>    ← 不是 x-api-key
UA:         claude-cli/2.0.0 (external, cli)   ← ★ 必须，否则第 1 轮 401
model:      deepseek-v4-flash              ← 可用；claude-opus-5 在该分组"无可用渠道"(503)
网络:        本机代理 127.0.0.1:7897        ← 直连 status=000，必须走代理
```

### 四条排障方法论（比结论更值钱）

1. **看响应头和错误体，不要只看状态码**：`X-Oneapi-Request-Id` 说明是 New-API 网关；三种错误的措辞差异直接指向三个不同层（指纹 → 认证头 → 令牌）；
2. **一次只改一个变量**：UA、认证头、模型名分开试，不要一把全换——否则不知道是哪个生效；
3. **验证环境变量是否真的生效**：`echo $env:OPENAI_API_KEY.Length`（我就是靠 `key_len=0` 抓出自己的坑）；
4. **不同协议要分开试**：OpenAI 兼容（`/v1/chat/completions`）、Anthropic 兼容（`/v1/messages`）、Codex 的 responses API——文档写了哪条就用哪条，别混。

> ⚠️ **安全**：key 只从环境变量注入（`${OPENAI_API_KEY:}`），**绝不写进 yml 提交**；测试用的 key 用完去平台重置。

## 七、★ 深挖二：三件套的工程语义

### ① 超时：为什么要"业务级 + HTTP 级"双保险

- `HttpRequest.timeout(...)` 管的是**单次 HTTP 往返**；
- `CompletableFuture.get(timeout)` 管的是**整个下游交互**（含连接、等待、重试前的退避）。

只设 HTTP 超时不够：连接卡住时可能根本不触发请求超时。只设业务超时也不够：HTTP 层不设上限，线程会堆积在套接字读上。**两层都要有**。

### ② 重试：三个"不能"

- **不能无限重试**：重试是"放大流量"，下游已经限流（429）时再猛打只会更糟；
- **不能立即重试**：指数退避（100→200→400ms）给下游喘息空间，也避免"抖动瞬间三连击"；
- **不能重试"注定失败"的错误**：4xx（参数错、鉴权错、模型名错）重试一百次也没用。**当前实现是简化版**（超时/5xx 一律重试），真实生产应识别状态码：
  ```text
  可重试：超时、连接失败、429（限流，需读 Retry-After）、500/502/503/504
  不可重试：400（参数）、401/403（鉴权）、404（模型/接口不存在）、422
  ```
- **重试的前提是幂等**：本场景的 LLM 补全只是"读"，天然幂等；若重试的是"创建订单"，就会重复下单——所以场景④ 的幂等键在这里是"重试的安全带"。

### ③ 降级：为什么兜底要"保留业务能力"

降级不是"返回 500 错误"，而是"**用低质量但可用的方案顶上**"：

- 用户点"创建任务" → LLM 挂了 → 仍然生成一份**模板计划** → 任务进入"等待确认" → 用户能继续操作；
- 如果直接抛错，用户得到的是"服务不可用"——**同一个故障，用户体验完全不同**。

降级必须留痕（三处）：`plannerModel` 记来源、`LLM_DEGRADED` 事件记原因、`rawPlanPayload.degraded` 记状态——否则"降级"会变成"静默的质量损失"，没人知道计划质量为什么变差了。

## 八、★ 深挖三：LangChain4j vs 手写 HttpClient（最终选了 LangChain4j）

### 8.1 最初的误判

第一版我判断"starter 自动装配无法设置 UA"，于是手写了 HttpClient。结果：**pom 里引的 LangChain4j 成了死依赖**（零 import、starter 也没装配出 bean）——被学员当场指出。

### 8.2 框架其实能做到（javap 查证）

用 `javap` 查 `OpenAiChatModel$OpenAiChatModelBuilder` 的方法清单，两个关键能力都在：

```text
customHeaders(Map<String, String>)        ← ★ 直接注入 User-Agent
maxRetries(Integer)                       ← ★ 必须设 0（见下）
timeout(Duration) / baseUrl / apiKey / modelName / maxTokens ...
```

于是实现切换成：

```java
OpenAiChatModel.builder()
    .baseUrl(...).apiKey(...).modelName(...).temperature(...).maxTokens(1200)
    .timeout(Duration.ofSeconds(timeout))
    .maxRetries(0)                                            // ★ 关掉框架重试
    .customHeaders(Map.of("User-Agent", userAgent))            // ★ 过网关
    .build();
```

**`maxRetries(0)` 是重点**：框架默认自带重试（2~3 次），如果不管，就会和 `LlmCallGuard` 的重试**叠乘**——框架 3 次 × 治理层 3 次 = 最多 9 次调用，把已经限流的下游打得更惨。**多层重试必须收敛到一层**。

### 8.3 新坑：代理的作用域（全局代理杀死了 Nacos）

用 `-Dhttps.proxyHost` 给 JVM 全局代理后，**应用直接启动失败**：

```text
[Nacos] Fail to connect server, after trying 13 times ... 192.168.157.129:30048
Process terminated with exit code: 1
```

原因：全局代理把**内网 Nacos 地址（`192.168.*`）也代理了**。修正方案两种：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 全局代理 + 排除内网**（实测可用） | `JAVA_TOOL_OPTIONS` 设代理 + `-Dhttp.nonProxyHosts=localhost\|127.*\|192.168.*` | 简单；但代理作用于整个 JVM |
| **B. 代码层代理（作用域隔离）** | `SpringRestClientBuilder.restClientBuilder(RestClient.builder().requestFactory(new JdkClientHttpRequestFactory(httpClientWithProxy)))` | 更干净；但**实测在 LangChain4j 里没生效**（请求仍然超时，说明我们注入的 RestClient.Builder 未被采用） |

**当前结论**：LangChain4j 实现**依赖方案 A**（JVM 参数 + 排除内网）；手写实现（`client-impl=http`）走**方案 B**（代码层代理，已验证生效）。这也是保留两个实现的实际理由。

> 教学点：**"代理"不是一个开关，而是一个作用域问题**——代理范围划大了会误伤内网服务，划小了外网请求出不去。生产环境通常由运维层（容器环境变量 `HTTP_PROXY` / `NO_PROXY`）统一管理。

#### 为什么"代理 LLM"会把 Nacos 拖下水？（2026-10-19 学员追问）

**LangChain4j 和 Nacos 毫无关系**，问题在于 `-Dhttp.proxyHost` 的层级：

```text
-Dhttp.proxyHost=127.0.0.1     ← JVM 系统属性（进程级，不是库级）
     ↓ 进程内所有走 JDK HTTP 栈的组件都会读到
     ├── LangChain4j 的 LLM 请求        ✅ 想要
     ├── nacos-client 拉配置/注册/心跳   ❌ 误伤
     └── 未来任何其他 HTTP 调用          ❌ 同样误伤
```

- **Nacos 客户端与 Server 的通信包含 HTTP 请求**（配置拉取、服务注册、心跳），走 JDK HTTP 栈 → 被全局代理转发到本机 Clash → Clash 处理内网地址 `192.168.157.129:30048` 失败 → 启动时同步注册失败 → **应用 fail-fast 退出**；
- `-Dhttp.nonProxyHosts=localhost|127.*|192.168.*` 是**排除名单**：命中的地址直连，不命中才走代理——外网 `agentrouter.org` 走代理 ✅，内网 Nacos 直连 ✅；
- **前端类比**：相当于浏览器设了系统代理，所有标签页一起走；`nonProxyHosts` 就是"内网地址直连"的例外规则。

**⚠️ 澄清"是不是 LangChain4j 导致 Nacos 报错"（2026-10-19 学员追问）**：

**不是。** 两者是独立变量：

| 阶段 | LLM 客户端 | 代理设置层级 | Nacos |
|---|---|---|---|
| 场景⑦ 及之前 | 无 LLM 调用 | 不用代理 | ✅ |
| 场景⑧ 手写版初验 | 手写 HttpClient | **代码层**（只给 LLM 的 HttpClient 设 ProxySelector） | ✅ **不受影响** |
| 场景⑧ 切 LangChain4j 首试 | LangChain4j | **JVM 全局**（`-Dhttps.proxyHost`，未排除内网） | ❌ 报错 |
| 修正后 | LangChain4j | JVM 全局 + `nonProxyHosts` | ✅ |

**报错的唯一条件是"代理设在 JVM 全局且未排除内网"**；LangChain4j 只是"逼我们用全局代理"的推手（它的代码层代理实测没生效 → 被迫改用全局代理 → 才踩到 Nacos）。若 LangChain4j 的代码层代理生效，此坑不会出现。

> 记忆法：**客户端选型影响"代码怎么写"；代理层级影响"谁会跟着走代理"——只有后者会误伤 Nacos。**

**三种代理作用域方案**：

| 方案 | 覆盖范围 | 适用 | 本项目状态 |
|---|---|---|---|
| JVM 全局代理 + `nonProxyHosts` | 整个进程（除名单外） | 快速验证 | ✅ LangChain4j 版当前使用 |
| 代码层代理（`ProxySelector`） | 只有 LLM 请求 | 最干净 | ✅ 手写版已验证生效（`client-impl=http`） |
| 运维层 `HTTP_PROXY`/`NO_PROXY` | 容器/进程，由平台统一管 | 生产标准 | ⬜ 部署阶段采用 |

### 8.4 两种实现的最终分工

| 实现 | 触发条件 | 代理方式 | 适用 |
|---|---|---|---|
| `LangChain4jLlmClient`（默认） | `app.llm.client-impl=langchain4j` | JVM 参数 + nonProxyHosts | 想用框架能力（结构化输出、工具调用、RAG） |
| `OpenAiCompatibleLlmClient` | `client-impl=http` | 代码层 `app.llm.proxy-host/port` | 代理需要严格隔离、或框架行为不可控时 |
| `SimulatedLlmClient` | `app.llm.simulated=true` | — | 验证超时/失败/降级 |

治理层 `LlmCallGuard` 对三者完全无感——这正是接口抽象的价值。

## 十三、附讲：`@ConfigurationProperties` 配置绑定（Q5，2026-10-19 学员提问）

### 13.1 一句话本质

```java
@ConfigurationProperties(prefix = "app.llm")
public record LlmProperties(String baseUrl, String apiKey, ...) { }
```

**"把这个类的字段，和配置文件里 `app.llm.*` 的键按名字对上号"**——Spring 启动时读 yml，逐个赋值，再把对象注册成 bean 供人注入。

### 13.2 三段式：声明 → 注册 → 调用（缺一不可）

| 阶段 | 位置 | 作用 |
|---|---|---|
| ① **声明** | `LlmProperties` 上的 `@ConfigurationProperties(prefix = "app.llm")` | "我要接收 app.llm.* 的配置" |
| ② **注册** | `PropertiesConfiguration` 上的 `@EnableConfigurationProperties(LlmProperties.class)` | **没有这一步，注解等于白写**——Spring 不会创建该 bean |
| ③ **调用** | 需要它的类在构造器里加参数（如 `LlmPlanGenerator(..., LlmProperties props)`） | 拿到绑定好的对象 |

> 又是 J7 的主线：**注解 = 声明（申请书），框架 = 执行者（外包工）**。

### 13.3 键名映射规则（松散绑定）

| yml 写法 | Java 字段 | 结果 |
|---|---|---|
| `base-url`（kebab-case） | `baseUrl`（camelCase） | ✅ 自动匹配 |
| `base_url` / `BASE_URL` | `baseUrl` | ✅ 也认 |
| `timeout-seconds: "20"` | `int timeoutSeconds` | ✅ 字符串自动转 int |
| `simulated: false` | `boolean simulated` | ✅ 自动转 boolean |

### 13.4 两个必须知道的缺省行为（坑）

1. **yml 没写的 key → 字段拿到 `null` / `0` / `false`，不报错**。
   例：`clientImpl` 未配置时为 `null`，所以 `LlmClientConfiguration` 里写了 `clientImpl == null ? "langchain4j" : ...` 兜底；
2. **键名写错 → 静默不匹配 → 字段为 `null`**（直到运行时才炸）。
   例：把 `base-url` 写成 `baseurl`，`baseUrl` 就是 `null`——最容易踩的"静默失败"。

### 13.5 为什么用 record 而不是普通 class

| | record | 普通 class |
|---|---|---|
| 赋值 | 规范构造器一次性赋值 | 需要 setter |
| 可变性 | **不可变**（配置本就该只读） | 可变 |
| 代码量 | 字段一行，getter 自动生成 | 字段 + getter/setter |

Spring Boot 3 支持 **record 构造器绑定**：13 个参数按名字与配置键匹配。⚠️ **record 不要再手写第二个构造器**，否则可能破坏绑定。

### 13.6 现场验证

启动日志的两行就是绑定成功的证据：

```text
LLM 使用【LangChain4j】实现：baseUrl=https://agentrouter.org/v1，model=deepseek-v4-flash
```

绑定失败（如键名写错）时这里会打印 `null`，随后 LangChain4j 构建抛异常——可临时把 `base-url` 改成 `baseurl` 试一次，亲眼看"静默失败"。
