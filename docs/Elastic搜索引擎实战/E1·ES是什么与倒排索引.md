## 1. 从"前端 filter"到"亿级搜索"：问题是怎么变大的

### 1.1 前端本地搜索（你写过的）

```js
// 数据在前端内存里，量小（几千条）——随便过滤
const results = reports.filter(r => r.title.includes(keyword));
```

### 1.2 数据搬到了后端数据库，用 LIKE

```sql
-- 报告表 100 万行，title 上还建了索引——但 LIKE '%关键词%' 照样全表扫描
SELECT * FROM research_report WHERE title LIKE '%多线程%';
```

**为什么 LIKE 的索引失效**（面试必问）：B+ 树索引只能**前缀匹配**（`LIKE '多线程%'` 能用索引）——`%关键词%` 前面有通配符，B+ 树没法定位起点，只能**全表扫描**（O(n)）。数据一多，接口从 10ms 变 10 秒。

### 1.3 问题的四层升级（LIKE 注定解决不了的部分）

| 层 | 问题 | LIKE 的表现 |
|---|------|------|
| ① 性能 | 数据量百万/亿级 | 全表扫描，越搜越慢 |
| ② **分词** | 用户搜"数据库"，内容写"数据 库""MySQL" | 字符串包含判断，切不开词、对不上词 |
| ③ **相关度** | 哪个结果更匹配？(标题命中 vs 正文命中) | 只有"匹配/不匹配"两态，没法排序 |
| ④ **语义** | 同义词（手机/移动电话）、拼写容错、拼音 | 全部做不到 |

**这四层升级，就是"搜索需求"从 CRUD 里独立出来、需要专门引擎（ES）的原因。**

## 2. ES 是什么：一句话 + 四大能力

> **Elasticsearch = 基于 Lucene 的分布式搜索引擎**——把数据写成"词 → 文档"的倒排索引，查询时查字典而不是扫全表；天生分布式（分片/副本），能支撑亿级数据 + 高并发的搜索。

**四大能力**：

| 能力 | 说明 | 典型场景 |
|------|------|---------|
| **全文检索** | 分词 + 相关度打分 + 高亮 + 模糊/同义词/拼音 | 站内搜索、电商搜索 |
| **聚合分析** | 类似 GROUP BY 的统计（且快得多） | 报表、按分类统计 |
| **地理位置** | GEO 查询（附近的店/人） | 本地生活 |
| **日志分析** | **ELK** = Elasticsearch + Logstash + Kibana | 企业日志平台（"在 Kibana 里搜日志"） |

## 3. 核心原理：倒排索引（本课重点）

### 3.1 正排 vs 倒排：换个方向就是"字典"

```text
【正排索引】文档 → 词（数据库/文档的天然顺序）
  文档1: "Spring 教程"      文档2: "Redis 教程"
  查"教程"：逐文档看内容里有没有 → 全表扫描 O(n)

【倒排索引】词 → 文档列表（★ ES 的灵魂）
  "spring" → [文档1]
  "redis"  → [文档2]
  "教程"   → [文档1, 文档2]      ← 查"教程"：查一次字典直接命中集合

这就是"倒排"的由来：索引的方向反过来了——不是"文档→词"，而是"词→文档"。
```

**倒排索引的存储形态**（直觉版）：

```text
词项字典（Term Dictionary，按字典序排好——可二分/前缀压缩）
  "redis"  → 文档列表 [2]              ← 叫 posting list（倒排表）
  "spring" → [1]
  "教程"   → [1, 2]
  "数据"   → [1, 3, 7, ...]
```

> **前端类比**：你为了加速搜索写过的预处理代码——

```js
// 建一个 Map<词, 文档 id 列表> 当"索引"
const index = new Map();
docs.forEach(doc => {
  wordsOf(doc).forEach(word => {       // ← 分词（wordsOf = 分词器）
    if (!index.has(word)) index.set(word, []);
    index.get(word).push(doc.id);
  });
});
// 搜索：查 Map（O(1)）而不是 filter 全表（O(n)）
const hits = index.get(keyword) || [];
```

**ES 就是把这个"自己写的 Map"工业化**：分好词、压缩存储、分片到多台机器、并发查询、按相关度打分。

### 3.2 分词器（analyzer）：倒排索引的"预处理工厂"

倒排索引的 key 是"词"，但原文是连续文本——所以**写入和查询都要先分词**：

```text
原文："Spring Boot 多线程实战"
分词（英文按空格+小写+词干、中文按词典切）：
  spring / boot / 多线程 / 实战     ← 这些才是索引的 key

用户搜索："多线程"  → 同样分词 → "多线程" → 命中该文档 ✓
用户搜索："线程"    → 分词 → "线程" → 若词典没切出这个词 → 可能匹配不到（这就是"分词器选型"的重要性）
```

| 语言 | 分词器 | 说明 |
|------|--------|------|
| 英文 | standard（空格/标点切 + 小写 + 停用词） | 开箱即用 |
| **中文** | **ik_max_word / ik_smart**（需安装 ik 插件） | 中文没有空格——必须用词典切词。`ik_max_word` 切得细（召回高），`ik_smart` 切得粗（精度高） |

**两个关键结论**（写入与查询必须用"同一套分词规则"——又是 J10 的"两端方言一致"）：

1. 索引时怎么分词，查询时就怎么分词——否则"词"对不上；
2. **不同字段可能要不同分词**：`title` 用 ik（搜索），`status` 用 keyword（精确匹配）——见 §四 text vs keyword。

### 3.3 一次查询的完整旅程

```text
① 用户输入"多线程实战"
② 查询词用【同一分词器】切：多线程 / 实战 / 多 / 线程 / 实战...
③ 逐个查倒排表：多线程→[1,5]、实战→[1,3]
④ 合并结果、按相关度打分排序（BM25 算法——词频 + 稀有度：越稀有越值钱的词命中，分越高）
⑤ 返回按分排序的文档列表（可选高亮命中词）
```

**打分一句话**：`BM25 ≈ 词频（TF）× 稀有度（IDF）× 字段权重`——"标题命中"比"正文命中"权重高，就是靠字段权重调的。

## 4. 概念对照表：index / document / mapping / text vs keyword

| ES 概念 | 数据库对照 | 前端 JSON 对照 | 本项目将来 |
|---------|-----------|---------------|-----------|
| **index（索引）** | ≈ **一张表**（★ 不是 DB 的索引！） | 一个文档集合 | `research_reports` 索引 |
| **document（文档）** | ≈ 一行记录 | 一个 JSON 对象 | 一份报告 |
| **field（字段）** | ≈ 一列 | 对象的 key | title / content / createdAt |
| **mapping（映射）** | ≈ 表结构 schema | TS 的 interface | 字段类型 + 分词器配置 |
| **_id** | ≈ 主键 | — | 用 taskId 当 _id（幂等更新） |
| **shard（分片）** | ≈ 分库分表 | — | 大索引切多片分散存储 |
| **replica（副本）** | ≈ 主从 | — | 容灾 + 读扩展 |

### ★ 初学者第一大坑：text vs keyword

```text
text   = 会分词 → 用于全文搜索（title、content）
         代价：不能直接做精确匹配/排序/聚合（"多线程实战" 被切碎成词了）

keyword = 不分词（整串原子值）→ 用于精确匹配/排序/聚合（status、tag、id）
         例：status="COMPLETED" 用 keyword 才能精确查；用 text 会被切成 complet/complet...
```

| 你想做的事 | 字段该用哪个 |
|-----------|-------------|
| 搜索关键词出现在 title/content 里 | **text**（+ ik 分词器） |
| 精确查 `status = 'COMPLETED'` | **keyword** |
| 按状态聚合计数（GROUP BY status） | **keyword** |
| 按时间排序 | date（数值型） |

**同一个字段的两个视角**（ES 的花活）：`fields` 子字段——`title` 主体用 text 搜索，同时保留 `.keyword` 子字段做排序/聚合：

```json
"title": {
  "type": "text",
  "analyzer": "ik_max_word",
  "fields": { "keyword": { "type": "keyword" } }     // title.keyword 可排序/聚合
}
```

## 5. 边界：ES 不是数据库（MySQL + ES 标准架构）

| 维度 | MySQL | Elasticsearch |
|------|-------|--------------|
| 事务 | ✅ ACID | ❌ **没有事务** |
| 实时性 | 实时 | **近实时**（写入后 1 秒 refresh 才能搜到） |
| 频繁更新 | 随意 | ❌ 每次更新=重写索引段，很贵 |
| 强一致 | ✅ | ❌ 副本异步同步（可能读到旧数据） |
| 角色 | **事实源（唯一真相）** | **搜索副本（可重建的索引）** |

**标准架构（面试必答）**：

```text
写：业务写 MySQL（事务保证真相）→ 同步链路 → 更新 ES 索引
读：简单查询/详情 → MySQL（或缓存）
    搜索/聚合   → ES
```

**同步链路是 ES 工程的最大难点**（E5 专门讲）：

| 方式 | 原理 | 一致性 | 复杂度 |
|------|------|--------|--------|
| 双写 | 业务代码里写库后又写 ES | 差（ES 失败→不一致） | 低 |
| **MQ 异步**（★ 推荐起点） | 写库 → 发消息 → 消费者更新 ES | 最终一致（可重试） | 中 |
| binlog CDC | 监听 MySQL binlog（Canal/Debezium）→ 同步 | 最终一致（不侵入业务） | 高 |
| 定时全量重建 | 每天凌晨重建（配 E7 分片广播） | 最终一致 | 低但延迟大 |

> **一句话边界**：**ES 里的数据"可以全部丢掉重建"**——这句话就是"它只是索引，不是真相"的判据。如果某些数据你不敢让它丢，那它必须在 MySQL。

## 6. 与本项目的三个场景

| 场景 | 需求 | ES 的角色 | 关联课程 |
|------|------|-----------|---------|
| ① **研究报告全文搜索** | 搜"多线程"命中相关报告的标题/正文，按相关度排序 | 报告索引（title/content 用 ik 分词） | 场景⑦（现状：MySQL + 缓存） |
| ② **知识库检索（RAG 增强）** | 向量相似 + 关键词混合检索 | ES 8.x 支持 kNN 向量字段 + 关键词双路召回 | 项目 RAG 链路 |
| ③ **任务执行日志搜索** | 按 taskId/时间/关键词排查"任务干了什么" | 日志索引（自动按天滚动 index） | 场景⑥（任务链路） |

**与现有架构的组合**（不是替换）：

```text
MySQL（真相）：报告写入、状态机、事务
Redis（缓存） ：单条报告详情（场景⑦）
Kafka（通道） ：MySQL → ES 的同步消息（E5 用场景⑥ 的 Kafka）
ES（索引）    ：搜索/聚合/高亮
```

## 7. 十四个常见误解速查

| # | 误解 | 真相 |
|---|------|------|
| 1 | "ES 的 index = 数据库索引" | ❌ ES 的 index ≈ **表**；"索引"在 ES 语境是"文档集合" |
| 2 | "ES 能当数据库用" | ❌ 无事务、近实时、更新贵——它只是**索引副本** |
| 3 | "写完立刻能搜到" | ❌ 近实时：默认 1 秒 refresh 后可见 |
| 4 | "text 字段能直接排序/聚合" | ❌ 被分词切碎——排序/聚合要用 keyword（或 `.keyword` 子字段） |
| 5 | "中文搜索开箱即用" | ❌ 必须装 ik 分词器，且写入/查询用同一套 |
| 6 | "ES 有事务，能回滚" | ❌ 没有事务；多文档写入是"部分成功"语义 |
| 7 | "更新一条数据很便宜" | ❌ 底层是"标记删除+新增段落"，频繁更新 → 段合并压力 |
| 8 | "分片越多越快" | ❌ 分片有开销（每片一个 Lucene 实例）——按数据量规划（单分片 10~50GB 经验值） |
| 9 | "副本只是备份" | ❌ 副本也**分担读请求**（读扩展） |
| 10 | "LIKE 加索引就能快" | ❌ `%kw%` 前缀通配 → B+ 树索引失效 → 全表扫描 |
| 11 | "ES 装好就能高可用" | ❌ 单节点无副本；高可用要≥3 节点（副本才能分配） |
| 12 | "DELETE 会立即释放空间" | ❌ 标记删除，段合并后才真正回收 |
| 13 | "搜索相关度无所谓，能搜到就行" | ❌ 电商/内容场景相关度=转化率；BM25 打分 + 字段权重是核心调优点 |
| 14 | "ES 挂了业务就挂" | ❌ 设计上应可降级（搜索降级为 MySQL 前缀搜索/缓存兜底） |

## 8. 面试速答

```text
Q：ES 是什么？为什么不用 MySQL 做搜索？
A：基于 Lucene 的分布式搜索引擎。MySQL 的 LIKE '%kw%' 前缀通配导致 B+ 树索引失效→全表扫描，
   且无分词/无相关度/无同义词。ES 用倒排索引（词→文档列表）+ 分词器 + BM25 打分解决。

Q：倒排索引是什么？
A：把"文档→词"反过来存成"词→文档列表"（posting list），查询变成查字典；
   写入时分词建索引，查询时同样分词后查表，再按相关度合并排序。

Q：text 和 keyword 的区别？
A：text 会分词（全文搜索用，不能精确匹配/聚合）；keyword 不分词（精确匹配/排序/聚合用）。
   常用 text + fields.keyword 子字段兼顾两者。

Q：ES 和 MySQL 怎么配合？数据怎么同步？
A：MySQL 存真相（事务），ES 存搜索索引（可重建）；同步用 MQ 异步/binlog CDC/定时全量，
   最终一致 + 对账兜底。ES 挂了搜索可降级，业务不能挂。

Q：为什么说 ES 不是数据库？
A：无事务、近实时（1s refresh）、更新是重写段、副本异步（可能读旧）、数据可丢可重建——
   它的定位是"索引/检索层"，不是事实源。
```

## 10. 一句话总结

```text
ES = 给数据建的巨大字典：写入时把文本切词存成"词→文档列表"（倒排索引），
查询时查字典 + 打分排序，而不是扫全表（LIKE 的死穴）。
它擅长搜索/聚合/Geo，不擅长事务/频繁更新——所以 MySQL 存真相，ES 存索引，Kafka 做同步。
```
