# 数据库表视角教程

这份文档不从 Controller 和 Service 出发，而是从“数据库里到底写了什么”来带你理解后端运行过程。

你可以把它理解成：  
**每推进一个业务步骤，后端往哪些表里写了什么，为什么要这么写。**

## 一、先看全局：有哪些核心表

当前后端最核心的表有 8 张：

1. `research_task`
2. `research_plan`
3. `research_step`
4. `step_execution`
5. `source_document`
6. `research_report`
7. `task_event_log`
8. `human_confirmation`

它们分别对应的职责如下：

### 1. research_task

任务主表，记录整个研究任务的主状态。

你可以把它理解为：

- 任务是谁
- 当前做到哪一步
- 当前是什么状态
- 是同步还是异步
- 有没有结束、有没有失败

关键字段：

- `id`
- `task_no`
- `title`
- `goal`
- `execution_mode`
- `status`
- `current_stage`
- `current_step_id`
- `requires_confirmation`
- `started_at`
- `completed_at`
- `error_message`

### 2. research_plan

研究计划表，记录某次任务生成的计划内容。

关键字段：

- `task_id`
- `version`
- `plan_summary`
- `plan_objective`
- `status`
- `confirmation_status`
- `raw_plan_payload`

### 3. research_step

研究步骤表，表示某个计划拆出来的有序步骤。

关键字段：

- `task_id`
- `plan_id`
- `step_no`
- `step_type`
- `title`
- `description`
- `input_payload`
- `expected_output`
- `status`

### 4. step_execution

步骤执行记录表，记录每一步真正执行时的运行信息。

关键字段：

- `task_id`
- `step_id`
- `attempt_no`
- `executor_type`
- `tool_name`
- `status`
- `input_payload`
- `output_payload`
- `error_message`
- `started_at`
- `finished_at`
- `duration_ms`

### 5. source_document

来源资料表，用来保存搜索结果和抓取得到的正文资料。

关键字段：

- `task_id`
- `step_id`
- `source_type`
- `url`
- `domain`
- `title`
- `snippet`
- `raw_content`
- `fetch_status`
- `relevance_score`
- `citation_ready`

### 6. research_report

研究报告表，保存最终对外展示的结果。

关键字段：

- `task_id`
- `summary`
- `key_findings`
- `final_recommendation`
- `report_markdown`
- `report_json`
- `status`
- `generated_at`

### 7. task_event_log

任务事件日志表，保存任务生命周期中的关键事件。

关键字段：

- `task_id`
- `step_id`
- `event_type`
- `event_message`
- `operator_type`
- `operator_id`
- `created_at`

### 8. human_confirmation

人工确认表，保存计划确认或步骤确认相关记录。

关键字段：

- `task_id`
- `step_id`
- `confirmation_type`
- `status`
- `request_message`
- `response_message`
- `requested_at`
- `responded_at`

## 二、创建任务时，哪些表会被写

当你创建一个研究任务时，数据库不是只写一张表。

### 第一步：写 research_task

入口方法：

- `ResearchTaskCommandService#createTask`

这时候会先插入一条任务主记录。

这条记录主要表示：

- 任务已经创建
- 现在处于规划阶段
- 还没有开始真正执行

典型状态：

- `status = QUEUED`
- `current_stage = PLANNING`

### 第二步：写 research_plan

随后进入：

- `ResearchPlanningService#generateInitialPlan`

系统会生成一条计划记录，告诉你：

- 这次任务的计划摘要是什么
- 计划目标是什么
- 计划目前还没确认

典型状态：

- `status = GENERATED`
- `confirmation_status = PENDING`

### 第三步：写 research_step

紧接着系统会批量插入多条步骤记录。

当前固定步骤链是：

1. 搜索候选资料
2. 抓取资料正文
3. 总结研究发现
4. 提取引用信息
5. 生成研究报告

典型状态是：

- 第一步：`READY`
- 后续步骤：`PENDING`

### 第四步：写 human_confirmation

还会插入一条人工确认记录，表示：

- 当前任务生成了计划
- 正在等待用户批准

典型状态：

- `status = PENDING`

### 第五步：更新 research_task

最后还会回写任务主表：

- `status = WAITING_FOR_CONFIRMATION`
- `requires_confirmation = true`

### 第六步：写 task_event_log

同时还会新增一条事件日志，类似：

- 已生成研究计划并等待人工确认

所以只看创建任务这一步，实际已经动了：

- `research_task`
- `research_plan`
- `research_step`
- `human_confirmation`
- `task_event_log`

## 三、确认计划时，哪些表会被写

用户点击“确认计划”后，入口在：

- `ResearchTaskControlService#confirmPlan`

### 如果用户批准

会更新以下表：

#### 1. research_plan

计划状态更新为：

- `status = CONFIRMED`
- `confirmation_status = APPROVED`

#### 2. human_confirmation

确认记录更新为：

- `status = APPROVED`
- `responded_at` 填充时间
- `response_message` 保存用户反馈

#### 3. research_task

任务主表更新为：

- `status = RUNNING`
- `current_stage = EXECUTING`
- `requires_confirmation = false`

#### 4. task_event_log

写入一条用户事件：

- 用户已确认研究计划，任务进入执行阶段

### 如果用户拒绝

会更新：

- `research_plan`
- `human_confirmation`
- `research_task`
- `task_event_log`

只是状态会变成：

- 计划被拒绝
- 任务被取消

## 四、执行每个步骤时，哪些表会被写

这部分最关键，入口在：

- `ResearchTaskOrchestrator#executeTask`

每一步执行都会动到不止一张表。

### 1. 先更新 research_task

执行某一步前，系统会先更新任务主表：

- `current_step_id` 指向当前步骤
- `status = RUNNING`
- `current_stage` 根据步骤类型切到 `EXECUTING` 或 `REPORTING`

这让前端和后端都知道：

- 当前任务正在执行哪一步

### 2. 写 step_execution

然后会插入一条步骤执行记录：

- `status = RUNNING`
- `started_at` 记录开始时间

这是执行过程里最关键的“过程证据表”。

### 3. 写 task_event_log

接着写一条事件日志：

- 开始执行步骤：xxx

### 4. 如果工具有来源资料，写 source_document

例如：

- `SEARCH` 步骤会产出候选来源
- `FETCH` 步骤会产出抓取正文

这些结果会被保存到：

- `source_document`

不同来源会用不同字段区分：

- `source_type`
- `fetch_status`
- `citation_ready`

### 5. 执行成功后的写入

如果步骤成功：

#### step_execution

更新为：

- `status = SUCCESS`
- `output_payload`
- `finished_at`
- `duration_ms`

#### research_step

当前步骤更新为：

- `status = COMPLETED`

#### 下一个 research_step

下一步如果原来是 `PENDING`，会被推进到：

- `status = READY`

#### task_event_log

新增一条：

- 步骤执行完成：xxx

### 6. 执行失败后的写入

如果步骤失败：

#### step_execution

更新为：

- `status = FAILED`
- `error_message`
- `finished_at`
- `duration_ms`

#### research_step

当前步骤更新为：

- `status = FAILED`

#### research_task

任务主表更新为：

- `status = FAILED`
- `error_message`
- `completed_at`

#### task_event_log

新增一条：

- 步骤执行失败：xxx

## 五、不同步骤对 source_document 的影响

`source_document` 是这个项目很值得重点看的表，因为它把“研究过程中的资料”真正留下来了。

### 1. SEARCH 步骤

通常会先写入候选资料，例如：

- URL
- 标题
- 摘要
- 来源域名
- 相关度

这时候很多记录还只是“候选来源”。

### 2. FETCH 步骤

会把选中的来源进一步补充正文：

- `raw_content`
- `content_hash`
- `fetch_status`

### 3. CITATION_EXTRACT 步骤

编排器会把已抓取来源进一步更新为：

- `citation_ready = true`

这表示这些资料已经可以进入最终报告引用。

## 六、生成报告时，哪些表会被写

入口：

- `ResearchReportAssemblyService#buildReport`

### 1. 读取哪些表

报告生成前，会先查：

- `source_document`
- `step_execution`

也就是说，报告本身不是直接来自任务表，而是来自前面执行过程中沉淀下来的资料和步骤输出。

### 2. 写 research_report

报告生成后，会写入：

- `summary`
- `key_findings`
- `final_recommendation`
- `report_markdown`
- `report_json`
- `status = FINAL`
- `generated_at`

### 3. 更新 research_task

当所有步骤都完成后，编排器还会把任务主表更新成：

- `status = COMPLETED`
- `current_step_id = null`
- `completed_at`

### 4. 写 task_event_log

同时会再写一条：

- 研究任务执行完成并已生成报告

## 七、task_event_log 为什么这么重要

如果你只看任务主表，你只能知道“当前状态是什么”。  
但如果你看 `task_event_log`，你会看到整个任务是怎么一步步走过来的。

它适合回答这些问题：

- 什么时候生成了计划
- 什么时候用户确认了计划
- 哪一步开始了
- 哪一步完成了
- 哪一步失败了
- 任务什么时候结束了

所以调试时建议你永远把它和 `step_execution` 一起看。

## 八、step_execution 为什么不能省

很多初学项目只会在任务表上存一个状态，但这个项目单独拆了 `step_execution`，意义很大。

它解决了这些问题：

- 能看每一步实际输入了什么
- 能看每一步输出了什么
- 能看每一步耗时多少
- 能看错误发生在哪一步
- 将来能支持重试和多次 attempt

也就是说：

- `research_step` 是“计划步骤”
- `step_execution` 是“实际运行记录”

这两个不能混为一谈。

## 九、按一次成功任务来总结落表顺序

如果一条任务完整成功，数据库大致会按这个顺序变化：

### 创建阶段

1. 插入 `research_task`
2. 插入 `research_plan`
3. 插入多条 `research_step`
4. 插入 `human_confirmation`
5. 更新 `research_task` 为等待确认
6. 插入 `task_event_log`

### 确认阶段

7. 更新 `research_plan`
8. 更新 `human_confirmation`
9. 更新 `research_task` 为运行中
10. 插入 `task_event_log`

### 执行阶段（每一步都会重复）

11. 更新 `research_task.current_step_id`
12. 插入 `step_execution`
13. 插入 `task_event_log`
14. 插入或更新 `source_document`
15. 更新 `step_execution`
16. 更新 `research_step`
17. 插入 `task_event_log`

### 报告阶段

18. 插入或更新 `research_report`
19. 更新 `research_task` 为完成
20. 插入 `task_event_log`

## 十、如果任务失败，数据库会怎么表现

失败时通常会看到：

- `research_task.status = FAILED`
- 某条 `research_step.status = FAILED`
- 某条 `step_execution.status = FAILED`
- `research_task.error_message` 有错误信息
- `task_event_log` 里能看到失败事件

这就是你排查问题时最实用的观察路径。

## 十一、如果你想亲手验证

你现在本地 `dev` 模式已经启用了 H2，可以直接打开：

- `http://localhost:8080/h2-console`

连接信息通常是：

- JDBC URL：`jdbc:h2:mem:research-agent`
- 用户名：`sa`
- 密码：空

然后你可以手动查这些表：

```sql
SELECT * FROM research_task;
SELECT * FROM research_plan;
SELECT * FROM research_step ORDER BY step_no;
SELECT * FROM step_execution ORDER BY started_at DESC;
SELECT * FROM source_document ORDER BY created_at DESC;
SELECT * FROM research_report;
SELECT * FROM task_event_log ORDER BY created_at DESC;
SELECT * FROM human_confirmation ORDER BY requested_at DESC;
```

## 十二、最值得你建立的数据库理解

读这个项目时，建议你把 8 张表分成 4 组来记：

### 1. 任务骨架

- `research_task`
- `research_plan`
- `research_step`

### 2. 运行痕迹

- `step_execution`
- `task_event_log`

### 3. 资料沉淀

- `source_document`

### 4. 最终结果与控制

- `research_report`
- `human_confirmation`

一旦你按这个方式去看，后端运行就不会再像一团散代码，而会变成一个非常清晰的“状态流 + 数据流”系统。
