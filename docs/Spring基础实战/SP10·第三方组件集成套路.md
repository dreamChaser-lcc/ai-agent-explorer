## 一、"starter 三件套"：集成一个组件要做的全部事情

```text
① 依赖（pom.xml）          —— 把库拉进来
② 配置（yml + 绑定类）     —— 告诉它连哪里、用什么参数
③ 自动配置（imports + 条件）—— 让它在满足条件时自动装配 bean
```

**三方分工**（谁写哪部分）：

| 三件套 | 谁负责 | 例子 |
|---|---|---|
| 依赖 | **你**（加 pom） | `spring-boot-starter-data-redis` |
| 配置 | **你**（写 yml，键名由库作者定） | `spring.data.redis.host` |
| 自动配置 | **库作者**（写好 imports + 条件） | `RedisAutoConfiguration` |

**你要做的其实只有两件**：加依赖 + 填配置。**自动配置是库作者写好的**——这就是 Spring Boot 的开发体验来源（SP5 讲的"引依赖 = 签字同意"）。

## 二、项目五大集成对照表

| 组件 | 依赖（pom） | 配置前缀（yml） | 自动配置类（框架提供） | 项目里的用法 | 启停方式 |
|---|---|---|---|---|---|
| **Kafka** | `spring-kafka` | `spring.kafka.*` | `KafkaAutoConfiguration` | `@KafkaListener` / `KafkaTemplate`（场景⑤⑥） | 配 `bootstrap-servers` 即启用 |
| **Redis** | `spring-boot-starter-data-redis` | `spring.data.redis.*` | `RedisAutoConfiguration` | `@Cacheable` / `RedisTemplate`（场景⑥⑦） | 配 `host` 即启用 |
| **Nacos** | `spring-cloud-starter-alibaba-nacos-config` | `spring.cloud.nacos.*` | `NacosConfigAutoConfiguration` | 配置中心（**本地已禁用**） | `spring.cloud.nacos.config.enabled` |
| **Actuator** | `spring-boot-starter-actuator` | `management.*` | `EndpointAutoConfiguration` 家族 | 端点观测（SP7） | `management.endpoints.web.exposure.include` |
| **LangChain4j** | `langchain4j-*` | `app.llm.*`（**自有前缀**） | `LangChain4jAutoConfiguration`（**未被采用**） | 手写 bean（`LlmClientConfiguration`） | `app.llm.client-impl` |

**⚠️ 最后一行是例外，也是本课重点**：LangChain4j 的自动配置**存在但我们没用**——因为需要自定义 UA，改为手写 bean（场景⑧ §八）。**这说明"自动配置不是唯一路径"**：不满意默认行为时，手写 `@Bean` 覆盖它（`@ConditionalOnMissingBean` 会让你赢）。

## 三、"引了依赖会有什么副作用"——自动配置的意外生效

自动配置的规则是"**条件满足就生效**"，而**你不一定知道自己满足了条件**：

| 现象 | 项目实例 | 教训 |
|---|---|---|
| **远程配置突然覆盖本地** | Nacos 配置中心连通 → 拉到集群版配置（PG）→ 覆盖本地 H2 → 启动失败（SP1 坑 1） | 依赖带来的**能力**会在条件满足时自动生效 |
| 默认 bean 抢占 | 引 Redis starter → 自动创建 `RedisTemplate` | 想自定义就用 `@Bean` 覆盖（`@ConditionalOnMissingBean` 让你赢） |
| 默认参数与预期不符 | HikariCP 默认 10 连接（SP9） | 用 `/actuator/metrics` 看实际值，别假设 |

**判断依据**：`/actuator/conditions`——**每个自动配置类的条件评估结果都在里面**（SP7 实测 299 positive / 342 negative）。

## 四、排查手册：bean 不存在 / 有两个

| 症状 | 第一步 | 第二步 |
|---|---|---|
| 某个 bean 注入失败 | `/actuator/conditions` 找对应 AutoConfiguration 是否 **negative** | 看 `negativeMatches` 的原因：缺 class？缺配置？条件不满足？ |
| 启动报 `NoUniqueBeanDefinitionException` | 看异常里的 bean 名列表和依赖链 | `@Primary` 标默认 / `@Qualifier` 精确指定 / **排查"名字巧合"**（SP1 实验③） |
| 自动配置没生效 | 启动加 `--debug` 看条件报告 | 检查 imports 清单、`@ConditionalOnProperty` 的值 |
| 配置不生效 | 查配置优先级（SP6）：环境变量/命令行 > 远程 > 本地 yml | `/actuator/env` 看某个 key 的**所有来源** |

## 五、自己造一个集成：5 步 checklist

```text
① 依赖            pom 里加（内部模块可省）
② XxxProperties   @ConfigurationProperties + 默认值
③ XxxAutoConfiguration  @AutoConfiguration + @EnableConfigurationProperties + @Bean + @ConditionalOnMissingBean
④ imports 清单    META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（一行）
⑤ 条件注解        @ConditionalOnClass / @ConditionalOnProperty（决定"什么时候才装配"）
```

**完整模板就是 SP5 的 `com.aiexplorer.starterdemo` 四件套**（`GreetingProperties` / `GreetingService` / `GreetingAutoConfiguration` / imports）。

## 六、Spring 线收官：10 课知识地图

```text
模块一 · Spring Framework 核心
  SP1 IoC 容器与 Bean 生命周期   ← 一切的基础：bean 从哪来、活多久
  SP2 AOP 与动态代理             ← 增强手段：切面靠代理
  SP3 MVC 请求处理全流程         ← Web 入口：Filter → DispatcherServlet → Controller
  SP4 事务传播与失效             ← 数据一致性：一个事务一条命

模块二 · Spring Boot 工程
  SP5 启动流程与自动配置         ← 工程化核心：imports + 条件
  SP6 配置体系与 Profile         ← 外部化配置：优先级决定"谁生效"
  SP7 Actuator 与打包部署        ← 可观测 + 交付：fat jar 与端点
  SP8 Filter 与 Interceptor      ← 请求链路拦截：两层钩子的分工

模块三 · 数据访问与集成
  SP9 数据访问全景与连接池       ← 一次 save 经过谁：连接池是瓶颈所在
  SP10 第三方组件集成套路        ← 收口：starter 三件套 + 副作用排查
```

**贯穿全线的三条主线**：

1. **"声明 → 注册 → 调用"**（J7 的主线）：注解只是申请书，框架才是执行者；
2. **"代理"**：AOP、事务、缓存、`@Transactional` 全在代理上（SP2/SP4/SP8 反复出现）；
3. **"条件与优先级"**：自动配置靠条件、配置取值靠优先级——**"为什么没生效"永远先查这两处**。

## 八、思考题（自查 + 参考答案）

1. 引了 `spring-boot-starter-data-redis` 但没配 `spring.data.redis.host`，会发生什么？<br>
   **参考答案**：自动配置会装配 `RedisTemplate` bean（条件通常是 `@ConditionalOnClass` 而非"必须有 host"），但**第一次真正访问 Redis 时才会连接失败**——这就是"自动配置只看条件，不验证可用性"的典型坑。正确做法：要么配好 host，要么排除自动配置（`@SpringBootApplication(exclude = RedisAutoConfiguration.class)`）。
2. 为什么 LangChain4j 的自动配置我们没用？<br>
   **参考答案**：自动装配的 `ChatModel` 无法设置中转站要求的 `User-Agent`（需要 `customHeaders`），所以**手写 `@Bean` 覆盖**它——`@ConditionalOnMissingBean` 让你的 bean 优先。**自动配置不是唯一路径，而是"默认路径"**。
3. `/actuator/conditions` 的 `negativeMatches` 有什么用？<br>
   **参考答案**：它列出"**哪些自动配置没生效、为什么没生效**"（缺 class / 缺配置 / 条件不满足）——排查"bean 为什么不存在"最快的手段（SP7 实测 342 个 negative）。
4. 想让自己的集成"引了就能用"，最少要哪几个文件？<br>
   **参考答案**：`XxxProperties`（配置绑定）+ `XxxAutoConfiguration`（条件装配）+ `META-INF/spring/...AutoConfiguration.imports`（清单），再加条件注解（`@ConditionalOnClass` / `@ConditionalOnProperty`）——五步见 §五。

```text
KafkaAutoConfiguration#kafkaTransactionManager / #kafkaRetryTopicConfiguration / #kafkaJaasInitializer

```

### 9.2 关键 bean 核对（`/actuator/beans`，199 KB JSON）

| 组件 | 条件评估 | 关键 bean | 结论 |
|---|---|---|---|
| **Kafka** | positive | `kafkaTemplate` ✅ | 自动配置真的装配了 |
| **Redis** | positive | `redisTemplate` / `stringRedisTemplate` ✅ | 同上 |
| **Nacos 配置** | **negative** | `nacosConfigManager` ❌ | **开关禁用 → bean 不存在** |
| **LangChain4j** | 自动配置未采用 | `chatModel` ❌ / `llmClient` ✅ | **手写 bean 覆盖**（`@ConditionalOnMissingBean`） |
| **数据源** | — | `dataSource` ✅（HikariCP） | SP9 的连接池 |

**两个铁证**：

1. **`@ConditionalOnProperty` 直接决定 bean 存在性**——禁用 Nacos config → 对应 AutoConfiguration 变 negative → `nacosConfigManager` 根本不存在；
2. **LangChain4j 是"自动配置被手写 bean 取代"的活标本**——`chatModel` 不存在、`llmClient` 存在，且应用功能完全正常。

### 9.3 操作坑（记录备查）

`/actuator/beans` 的 JSON 在 PowerShell `Invoke-RestMethod` 下**解析不出 bean 名**（`$b.contexts.application.beans` 取不到属性），换 `curl.exe -s` + 正则字符串计数才可靠。以后核对 bean 存在性用后者。
