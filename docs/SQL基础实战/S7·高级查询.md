## 一、窗口函数：给每一行"贴一列"，而不是合并行

**先看它和 GROUP BY 的核心差别**：

```text
GROUP BY：分桶 → 每个桶压成一行（明细消失）
窗口函数：分桶后 → 每一行都保留，只在旁边贴一列结果
```

前端类比：

```js
// GROUP BY ≈ 压缩成统计表
// 窗口函数 ≈ map 里带上"我在组内的名次"，行数不变
rows.map((item, index) => ({ ...item, rank: index + 1 }))
```

**语法骨架**：

```sql
SELECT
    函数名() OVER (              -- ★ 窗口函数：在"某个视野"里算一个值，贴在当前行旁边（行数不变）
        PARTITION BY 分桶列      -- 第 1 层：跟谁比（省略 = 全表一个大窗口）
        ORDER BY 排序列          -- 第 2 层：从哪算起（省略 = 视野是整组；给了 = "从开头到当前行"）
    ) AS 结果别名
FROM 表名;
```

### ★ 图解：同一张表、只改 OVER 括号（**Q9**，2026-10-18 增补，全部实测）

**原始表（5 行）**：

```text
student | subject | score
张三    | 数学    | 90
李四    | 数学    | 90
王五    | 英语    | 85
赵六    | 英语    | 85
钱七    | 数学    | 70
```

**第一认知：行数不变**——下面四组查询全部 **5 行进、5 行出**。窗口函数从不删行，只在每行旁边**贴一列**（GROUP BY 才是"压行"）。

**A. `OVER ()` = 每行贴"全表统计"**

```sql
SELECT
    student, subject, score,
    COUNT(*)       OVER ()        AS total_rows,   -- 空括号 = 整张表一个窗口 → 每行都贴"总行数"
    ROUND(AVG(score) OVER (), 1)  AS avg_all       -- 同上 → 每行都贴"全班平均分"
FROM s7_score
ORDER BY score DESC;
```

```text
student | subject | score | total_rows | avg_all
张三    | 数学    | 90    | 5          | 84.0
李四    | 数学    | 90    | 5          | 84.0
王五    | 英语    | 85    | 5          | 84.0
赵六    | 英语    | 85    | 5          | 84.0
钱七    | 数学    | 70    | 5          | 84.0
```

空括号 = 视野是整张表 → 每行都贴"全班 5 人、平均 84"。

**B. `OVER (PARTITION BY subject)` = 每行贴"本组统计"**

```sql
SELECT
    student, subject, score,
    COUNT(*) OVER (PARTITION BY subject)           AS subject_count,  -- 视野 = 本科目的所有行
    ROUND(AVG(score) OVER (PARTITION BY subject), 1) AS subject_avg   -- 同上 → 本科目平均分
FROM s7_score
ORDER BY subject, score DESC;
```

```text
student | subject | score | subject_count | subject_avg
张三    | 数学    | 90    | 3             | 83.3   ← 数学组 3 人
李四    | 数学    | 90    | 3             | 83.3
钱七    | 数学    | 70    | 3             | 83.3
王五    | 英语    | 85    | 2             | 85.0   ← 英语组 2 人
赵六    | 英语    | 85    | 2             | 85.0
```

**C. `OVER (ORDER BY score DESC)` = 每行贴"从第一名到我这行"的累计**

```sql
SELECT
    student, subject, score,
    SUM(score) OVER (
        ORDER BY score DESC, student   -- 有 ORDER BY → 视野缩成"从第一名到当前行"（累计）
    ) AS running_total                 -- 结果：90 / 180 / 265 / 350 / 420
FROM s7_score
ORDER BY score DESC, student;
```

```text
student | score | running_total
张三    | 90    | 90      ← 只有我
李四    | 90    | 180     ← 我和前面
王五    | 85    | 265
赵六    | 85    | 350
钱七    | 70    | 420     ← 到这里全班总和
```

配 `SUM` = 累计分；配 `ROW_NUMBER` = 名次。**排名函数必须带 ORDER BY，原因就在这。**

**"窗口"到底是什么**：每一行**抬头往外看一圈**，看到的那片范围就是它的"窗口"，在窗口内算一个值贴在自己身上。

| OVER 括号 | 这一行的视野 | 白话 |
|---|---|---|
| `OVER ()` | 整张表 | 看全班 |
| `OVER (PARTITION BY subject)` | 同科目的行 | 看本科目同学 |
| `OVER (ORDER BY score DESC)` | 从第一名到我自己 | 看我前面的排名 |

**与 GROUP BY 的正面对照（实测）**：

```text
GROUP BY subject    → 2 行（明细被压掉）
数学 | 3 | 83.3
英语 | 2 | 85.0

PARTITION BY subject → 5 行（明细保留 + 贴统计列）
张三 | 数学 | 90 | 3 | 83.3
...
```

前端场景：列表每行要显示"分数 + 本科目平均分"用来标红低于平均——GROUP BY 做不到（明细没了），窗口函数一行搞定。

> **口诀：GROUP BY 是"汇总成表"，窗口函数是"贴标签不删行"。**

### ★ 排名三兄弟的本质：台阶比喻 + 决定性实验（**Q10**，2026-10-18 增补）

**三者不是"三种排名风格"，是三种"计数方式"**——把成绩想成台阶（90 站第 1 级、85 第 2 级、70 第 3 级）：

| 人 | 成绩 | 第几级台阶 | **ROW_NUMBER**<br>纯排队号 | **RANK**<br>位置序号 | **DENSE_RANK**<br>台阶号 |
|---|---|---|---|---|---|
| 张三 | 90 | 1 | 1 | **1** | **1** |
| 李四 | 90 | 1 | 2 | **1** | **1** |
| 王五 | 85 | 2 | 3 | **3** ← 跳号 | **2** ← 连号 |
| 赵六 | 85 | 2 | 4 | **3** | **2** |
| 钱七 | 70 | 3 | 5 | **5** | **3** |

- **DENSE_RANK = 台阶号**：只数"第几级台阶"，1/2/3 连号，不管每级站几个人；
- **RANK = 位置序号**：数"人是第几个站上去的"——第 1 级站了 2 人，占掉**位置 1、2**，第 2 级的第一人就是**位置 3**（跳号不是 bug，是两个人真占了两个位置）；
- **ROW_NUMBER = 排队号**：不管台阶，一人一号（取号机），1~5 绝不重复。

**决定性实验（实测原文）——同样"取第一名"**：

```text
RANK()       ... WHERE rnk = 1   → 2 行（张三、李四并列第一）
DENSE_RANK() ... WHERE drnk = 1  → 2 行（同样并列）
ROW_NUMBER() ... WHERE rn = 1    → 1 行（只有张三）
```

★ **这就是"每组取最新一条"必须用 `ROW_NUMBER` 的原因**：只有它保证恰好一行；`RANK` 遇到并列（如两条事件时间相同）会把一行变多行，业务逻辑崩。

**实战选择口诀**：

| 需求 | 用谁 | 原因 |
|---|---|---|
| 取唯一一条（最新/去重/分页） | `ROW_NUMBER` | 唯一能保证"绝不并列" |
| 显示并列名次（排行榜） | `RANK` | 并列同名次，符合名次语义 |
| 统计档位（共几个等级） | `DENSE_RANK` | 台阶连号，`MAX(drnk)` = 档位数 |

前端类比：`ROW_NUMBER` ≈ `arr.map((it, i) => i + 1)`；`RANK` ≈ 运动会名次榜（并列冠军→没亚军→下一个季军）；`DENSE_RANK` ≈ 段位等级（两个最强王者，下一个是星耀=第 2 档）。

### 三个排名函数（并列时表现不同）

假设成绩：`90, 90, 85`

| 函数 | 结果 | 规则 |
|---|---|---|
| `ROW_NUMBER()` | 1, 2, 3 | 强行排队，**绝不并列** |
| `RANK()` | 1, 1, 3 | 并列占位（下一个跳号） |
| `DENSE_RANK()` | 1, 1, 2 | 并列不占位（下一个连号） |

```sql
SELECT
    student,
    score,
    ROW_NUMBER() OVER (ORDER BY score DESC) AS rn,    -- 排队号：1,2,3,4,5（绝不并列）
    RANK()       OVER (ORDER BY score DESC) AS rnk,   -- 位置序号：1,1,3,3,5（并列占位 → 跳号）
    DENSE_RANK() OVER (ORDER BY score DESC) AS drnk   -- 台阶号：1,1,2,2,3（并列不占位 → 连号）
FROM s7_score
ORDER BY score DESC;                                  -- 外层排序只管显示，不影响上面算出的名次
```

## 二、两大实战套路（面试常客）

### 套路 1：每组取最新一条（TOP 1 per group）

**项目场景**：任务列表要给每个任务显示"最近一条动态"。

```sql
SELECT * FROM (
    SELECT
        e.task_id,
        e.event_type,
        e.event_message,
        e.created_at,
        ROW_NUMBER() OVER (             -- 给每个任务的事件编"时间倒序"号
            PARTITION BY task_id        -- 按任务分桶：每个任务各自排名，互不干扰
            ORDER BY created_at DESC    -- 最新的排第 1
        ) AS rn
    FROM task_event_log e
) t                                     -- 派生表必须起别名（外层才能引用 rn）
WHERE rn = 1;                           -- 只留每桶第一名 = 每组最新一条
```

**逐行翻译**：

1. 内层：按 `task_id` 分桶，桶内按时间**倒序**编 1,2,3——最新一条永远是 `rn = 1`；
2. 外层：只留 `rn = 1` → 每个任务恰好一条。

**★ 为什么必须套子查询**：执行顺序是 `FROM → WHERE → 窗口函数 → ORDER BY`（S1 的执行顺序表升级版）——`WHERE` 跑的时候 `rn` 还没算出来，所以 `WHERE rn = 1` 写在同一层会报错/查不到。**窗口函数的别名只能在"更外层"使用。**

### 套路 2：组内占比（窗口聚合 + GROUP BY 配合）

```sql
SELECT
    status,
    COUNT(*) AS cnt,                            -- 分子：本桶行数（GROUP BY 已把明细压成每桶一行）
    ROUND(
        COUNT(*) * 100.0                        -- ×100 变百分比（写 100.0 避免整数除法丢掉小数）
        / SUM(COUNT(*)) OVER (),                -- 分母：所有桶的总数（OVER 空括号 = 全表汇总）
        1                                       -- 保留 1 位小数
    ) AS percent
FROM research_task
GROUP BY status                                 -- 先分组：15 行 → 3 桶
ORDER BY cnt DESC;
```

`SUM(COUNT(*)) OVER ()` = 不带 PARTITION 的窗口 = **全表汇总**（所有桶的 cnt 总和），拿来当分母。`OVER ()` 空括号 = 整个结果集是一个大窗口。

（`ROUND(x, 1)` = 保留 1 位小数，前端类比 `toFixed(1)`。）

## 二·补、结合项目真实表的三组实战（2026-10-18 应学员"有结合表给我解答吗"增补）

> 说明：真实 H2 文件库被运行中的应用独占（文件锁），本节用**同结构、同分布**数据实测（15 任务、12/2/1 状态、每任务 1~2 条事件）；SQL 在 H2 控制台对真实表跑，形态完全一致。

### 例 1：`task_event_log` 上"每条事件贴两个标签"

```sql
SELECT
    SUBSTRING(CAST(e.task_id AS VARCHAR), 1, 8) AS task_prefix,  -- 只取 UUID 前 8 位便于阅读
    e.event_type,
    CAST(e.created_at AS VARCHAR) AS event_at,                   -- 时间转文本，方便肉眼对照
    ROW_NUMBER() OVER (
        PARTITION BY e.task_id              -- 每个任务内各自排名
        ORDER BY e.created_at DESC          -- 最新的第 1
    ) AS rn,                                -- 第几条事件（最新 = 1）
    COUNT(*) OVER (
        PARTITION BY e.task_id              -- 注意：这里【没有 ORDER BY】
    ) AS event_count                        -- 本任务事件总数（整组视野 → 每行都贴同一个数）
FROM task_event_log e
ORDER BY e.task_id, rn;
```

```text
task_prefix | event_type     | event_at         | rn | event_count
2db8366d    | STATUS_CHANGED | 2026-10-14 18:57 | 1  | 2   ← 同一任务：最新一条
2db8366d    | PLAN_GENERATED | 2026-10-14 17:57 | 2  | 2   ← 同一任务：较早一条
0b7923a1    | PLAN_GENERATED | 2026-10-07 17:57 | 1  | 1   ← 只有 1 条事件
5ea5bb0c    | PLAN_GENERATED | 2026-10-04 17:57 | 1  | 1
```

**★★ Q9 视野规则的实战验证**：同一个 `task_id` 两行事件 `rn = 1、2`（按时间倒序编号）；`event_count` 两行**都是 2**——`COUNT(*) OVER (PARTITION BY task_id)` **没有 ORDER BY**，视野是**整组**。

把 `event_count` 改成 `COUNT(*) OVER (PARTITION BY task_id ORDER BY created_at DESC)`，结果就从 `2, 2` 变成 `1, 2`——**加 ORDER BY，视野从"整组"缩成"从开头到当前行"**。排序方向决定累计方向。

### 例 2：任务列表 + 最新动态（前端列表页真正要的数据）

```sql
SELECT
    t.task_no,                          -- 主表：任务
    t.status,
    e.event_type AS latest_event        -- 从派生表取"最新一条事件"（无事件则为 null）
FROM research_task t
LEFT JOIN (                             -- LEFT：没有事件的任务也要出现（S2 老规矩）
    SELECT
        task_id, event_type, created_at,
        ROW_NUMBER() OVER (
            PARTITION BY task_id        -- 每个任务内部排名
            ORDER BY created_at DESC    -- 最新的第 1
        ) AS rn
    FROM task_event_log
) e
    ON e.task_id = t.id                 -- 关联规则：事件属于这个任务
   AND e.rn = 1                         -- 且只认"最新那条"
ORDER BY t.task_no;
```

```text
task_no   | status                   | latest_event
TASK-0001 | WAITING_FOR_CONFIRMATION | STATUS_CHANGED
TASK-0002 | WAITING_FOR_CONFIRMATION | STATUS_CHANGED
...
```

内层给每个任务的事件按时间倒序编号；外层 JOIN 只认 `rn = 1` → **每个任务恰好一行"最近动态"**。`LEFT JOIN` 保证无事件的任务也出现（动态列 null，S2 老规矩）。

### 例 3：状态占比（GROUP BY + 窗口求和）

```sql
SELECT
    status,
    COUNT(*) AS cnt,                    -- 每个状态的桶大小
    ROUND(
        COUNT(*) * 100.0                -- 分子：本桶数量
        / SUM(COUNT(*)) OVER (),        -- 分母：3 个桶的数量之和（12+2+1=15）
        1
    ) AS percent
FROM research_task
GROUP BY status;                        -- 先压成 3 行，再开窗求总和
```

```text
status                   | cnt | percent
WAITING_FOR_CONFIRMATION | 12  | 80.0
CANCELLED                | 2   | 13.3
COMPLETED                | 1   | 6.7
```

`GROUP BY` 先把 15 行压成 3 行；`SUM(COUNT(*)) OVER ()` 再把 3 行的 cnt 求和（12+2+1=15）当分母——**聚合之后再开窗**，窗口函数执行在 GROUP BY 之后。前端饼图数据一行 SQL 出。

## 三、CASE WHEN：SQL 的三元表达式

**两种形态**：

```sql
-- ① 简单形式（等值判断，像 switch）：判断对象写在 CASE 后面
SELECT
    status,
    CASE status
        WHEN 'COMPLETED' THEN '已完成'    -- 命中这个值 → 返回这个结果
        WHEN 'CANCELLED' THEN '已取消'
        ELSE '其他'                      -- 兜底（省略时无匹配则返回 NULL）
    END AS status_label                 -- 整块起别名，当普通列用（可参与 WHERE/GROUP BY/ORDER BY）
FROM research_task;

-- ② 搜索形式（任意条件，像 if / else if）：每个 WHEN 后跟一个条件表达式
SELECT
    title,
    CASE
        WHEN priority >= 5 THEN '高'      -- 条件为真就走这里（按顺序判断，命中即停）
        WHEN priority >= 1 THEN '中'
        ELSE '低'
    END AS priority_level
FROM research_task;
```

前端等价：`status === 'COMPLETED' ? '已完成' : ...`。

**两大用途**：

1. **翻译显示标签**（接口返回中文）：配合 S3 的 `GROUP BY` 出报表；
2. **条件统计**（一个查询数出多个口径）：

```sql
SELECT
    status,
    COUNT(*) AS total,                                    -- 本状态总行数
    SUM(                                                  -- 把"命中 1 / 不命中 0"加起来 = 满足条件的行数
        CASE WHEN error_message IS NOT NULL THEN 1 ELSE 0 END
    ) AS error_count                                      -- 本状态下有错误信息的任务数
FROM research_task
GROUP BY status;
```

`SUM(CASE WHEN 条件 THEN 1 ELSE 0 END)` = **条件计数**——比"每种条件各查一次"快得多，报表 SQL 的标配。

## 四、CTE（`WITH`）：给查询起中间变量

**语法**：

```sql
WITH 名字 AS (                    -- ① 声明一个中间结果（相当于 const 名字 = ...）
    SELECT ...                    --    里面可以是任意查询（子查询能写的它都能写）
)                                 --    多个 CTE 用逗号分隔：WITH a AS (...), b AS (...)
SELECT ... FROM 名字 WHERE ...;    -- ② 后面把"名字"当普通表用
```

前端类比：

```js
const ranked = rankedEvents(...);   // WITH 里的子查询 = 一个中间变量
return ranked.filter(r => r.rn === 1);
```

**为什么值钱**：把嵌套子查询的"洋葱"拉平成"变量表"，可读性提升一个档；多个 CTE 用逗号分隔；还能**递归**。

把套路 1 改写成 CTE 版（更清晰）：

```sql
WITH ranked_events AS (                       -- ① 中间结果：每条事件打上"第几条"的号
    SELECT
        e.task_id, e.event_type, e.created_at,
        ROW_NUMBER() OVER (
            PARTITION BY e.task_id            -- 每个任务内部排名
            ORDER BY e.created_at DESC        -- 最新的第 1
        ) AS rn
    FROM task_event_log e
)
SELECT task_id, event_type, created_at        -- ② 把中间结果当表查
FROM ranked_events
WHERE rn = 1;                                 -- 只留最新那条（与套路 1 子查询版结果完全一致）
```

### 递归 CTE（`WITH RECURSIVE`）：树结构的专用武器

**项目场景**：`research_step.depends_on_step_id` 是自引用（S2 自连接讲过）——"步骤 A 依赖 B，B 依赖 C"形成链条。查"完整依赖链（含层级和路径）"就要递归。

**实测原文**（H2 2.3.232，见文末附录）：

```text
id | node_name | depth | path
1  | root      | 0     | root
2  | alpha     | 1     | root > alpha
3  | beta      | 2     | root > alpha > beta
4  | gamma     | 1     | root > gamma
```

**结构三件套**：

```sql
WITH RECURSIVE chain (id, node_name, depth, path) AS (   -- 声明"会长大的表"，列名先起好

    -- ① 种子查询（锚点 / Anchor）：只执行一次，放入起点
    SELECT id, node_name, 0, node_name
    FROM s7_node
    WHERE parent_id IS NULL                              -- 根 = 没有父亲的那行（depth 记 0）

    UNION ALL                                            -- ② 把下一批结果【追加】进结果集（不是覆盖）

    -- ③ 递归查询（Recursive Member）：拿【上一轮新增的行】JOIN 原表，找它们的子节点
    SELECT
        n.id,
        n.node_name,
        c.depth + 1,                                     -- 层数 +1
        c.path || ' > ' || n.node_name                   -- 路径拼接（H2/PG 用 ||，MySQL 用 CONCAT）
    FROM s7_node n
    JOIN chain c ON n.parent_id = c.id                   -- c = 上一轮结果（自我引用）
    -- 这里可以加 WHERE 做【额外过滤】（如只递归前几层）
    -- ★ 真正的终止 = 这一轮查不到任何新行 → 结果集不再增长 → 自动停
)
SELECT * FROM chain ORDER BY id;                          -- ④ 最终把长大后的表当普通表查
```

**读法**：`chain` 是"不断长大的结果表"——先放根节点（锚点），然后每一轮拿上一轮新增的行去 JOIN 原表找子节点。**没有新行时自动停**（终止条件不需要手写）。

**★ 关于"终止条件"的校正**（2026-10-19）：递归部分写 `WHERE` **不是必需的**，它只是额外过滤（如只递归前几层）。**真正的终止是"这一轮查不到新行"**——结果集不再增长就停。**只有数据可能成环时**（A→B→A）才需要 `depth < N` 之类的兜底条件防死循环；本项目 `depends_on_step_id` 这种有向无环依赖一般不需要。

前端类比：广度优先遍历（BFS）自己喂自己——`let frontier = [root]; while (frontier.length) { ... }`。

## 五、执行顺序再升级（本课最容易踩的坑）

```text
FROM → WHERE → GROUP BY → 聚合 → HAVING → 【窗口函数】 → SELECT → ORDER BY → LIMIT
```

由此得到两条铁律：

1. **`WHERE` 里不能用窗口函数别名**（`rn` 此时不存在）→ 必须套子查询/CTE（套路 1 的"为什么"）；
2. **`ORDER BY` 里可以用**（它排在窗口函数之后）。

## 七、动手练习（H2 控制台）

```sql
-- ============ 练习 1：排名三兄弟（造并列分数才有对比价值）============
DROP TABLE IF EXISTS s7_score;               -- 先删旧表（可重复执行，避免重复插入）
CREATE TABLE s7_score (
    id UUID PRIMARY KEY,                     -- 主键：随机 UUID
    student VARCHAR(32),                     -- 学生名
    subject VARCHAR(16),                     -- 科目
    score INTEGER                            -- 分数（有并列才看得出三兄弟差别）
);
INSERT INTO s7_score (id, student, subject, score) VALUES
 (RANDOM_UUID(), '张三', '数学', 90),
 (RANDOM_UUID(), '李四', '数学', 90),        -- 与张三并列 90
 (RANDOM_UUID(), '王五', '数学', 85),
 (RANDOM_UUID(), '赵六', '数学', 85),        -- 与王五并列 85
 (RANDOM_UUID(), '钱七', '数学', 70);

SELECT
    student, score,
    ROW_NUMBER() OVER (ORDER BY score DESC) AS rn,    -- 排队号：1,2,3,4,5
    RANK()       OVER (ORDER BY score DESC) AS rnk,   -- 位置序号：1,1,3,3,5（跳号）
    DENSE_RANK() OVER (ORDER BY score DESC) AS drnk   -- 台阶号：1,1,2,2,3（连号）
FROM s7_score
ORDER BY score DESC;
-- 验收点：90/90 处 rn=1,2 而 rnk=1,1；85 处 rnk 跳到 3、drnk=2

-- ============ 练习 2：每组取最新一条（真实表 task_event_log）============
SELECT * FROM (
    SELECT
        e.task_id, e.event_type, e.event_message, e.created_at,
        ROW_NUMBER() OVER (
            PARTITION BY task_id           -- 每个任务各自排名
            ORDER BY created_at DESC       -- 最新的第 1
        ) AS rn
    FROM task_event_log e
) t                                         -- 派生表必须起别名
WHERE rn = 1                                -- 只要每桶第一名
ORDER BY created_at DESC;
-- 验收点：每个 task_id 恰好一行（= 该任务最近一条事件）

-- ============ 练习 3：故意在同层引用 rn（看报错，理解执行顺序）============
SELECT
    task_id, event_type, created_at,
    ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY created_at DESC) AS rn
    -- ↑ 窗口函数在这一步才算出 rn
FROM task_event_log
WHERE rn = 1;
-- ↑ WHERE 先于窗口函数执行 → 此时 rn 不存在
-- 预期报错：Column "rn" not found（第五节的铁律 1）

-- ============ 练习 4：CASE WHEN 翻译状态 + 条件计数 ============
SELECT
    status,
    CASE status
        WHEN 'COMPLETED' THEN '已完成'
        WHEN 'CANCELLED' THEN '已取消'
        WHEN 'WAITING_FOR_CONFIRMATION' THEN '等待确认'
        ELSE '其他'                          -- 兜底
    END AS status_label,                     -- 翻译后的显示标签
    COUNT(*) AS task_count,                  -- 本状态任务数
    SUM(CASE WHEN error_message IS NOT NULL THEN 1 ELSE 0 END) AS error_count
    -- ↑ 条件计数：命中 1、不命中 0，相加即"有错误的任务数"
FROM research_task
GROUP BY status                              -- 先分桶，再对每桶做上面三件事
ORDER BY task_count DESC;

-- ============ 练习 5：CTE 重写套路 1（与练习 2 结果必须一致）============
WITH ranked_events AS (                      -- ① 中间结果：每条事件打"第几条"
    SELECT
        e.task_id, e.event_type, e.created_at,
        ROW_NUMBER() OVER (
            PARTITION BY e.task_id           -- 每个任务内部排名
            ORDER BY e.created_at DESC       -- 最新的第 1
        ) AS rn
    FROM task_event_log e
)
SELECT task_id, event_type, created_at       -- ② 当普通表查
FROM ranked_events
WHERE rn = 1;                                -- 只留最新（应与练习 2 完全一致）

-- ============ 练习 6：递归 CTE（树结构；对应项目的步骤依赖链）============
DROP TABLE IF EXISTS s7_node;
CREATE TABLE s7_node (
    id INT PRIMARY KEY,                      -- 节点编号
    parent_id INT NULL,                      -- 父节点（NULL = 根）
    node_name VARCHAR(32) NOT NULL
);
INSERT INTO s7_node (id, parent_id, node_name) VALUES
 (1, NULL, 'root'),                          -- 根
 (2, 1,    'alpha'),                         -- root 的子
 (3, 2,    'beta'),                          -- alpha 的子（第 3 层）
 (4, 1,    'gamma');                         -- root 的另一个子

WITH RECURSIVE chain (id, node_name, depth, path) AS (
    -- ① 锚点：根节点（只跑一次）
    SELECT id, node_name, 0, node_name
    FROM s7_node
    WHERE parent_id IS NULL

    UNION ALL                                 -- ② 追加下一批

    -- ③ 递归：上一轮结果 JOIN 原表 → 找子节点
    SELECT
        n.id, n.node_name,
        c.depth + 1,                          -- 层数 +1
        c.path || ' > ' || n.node_name        -- 路径拼接
    FROM s7_node n
    JOIN chain c ON n.parent_id = c.id        -- 自我引用
)
SELECT id, node_name, depth, path FROM chain ORDER BY id;   -- ④ 当普通表查
-- 验收点：4 行，depth 0/1/2/1，path 逐级拼接（与附录实测输出一致）

-- ============ 练习 7：清理（不留垃圾表）============
DROP TABLE IF EXISTS s7_score;
DROP TABLE IF EXISTS s7_node;
```

**验收标准**：
1. 练习 1 能指着 90/90 那两行讲清三个函数的差别；
2. 练习 2 每个 task_id 只有一行，且是最新时间那条；
3. 练习 3 亲眼看到 `rn` 不可用的报错（执行顺序的体感）；
4. 练习 5 与练习 2 结果完全一致（CTE 与子查询等价）；
5. 练习 6 的 depth/path 与附录实测输出一致，能说出"锚点 + 递归 + UNION ALL"各自的作用。

FROM task_event_log e
WHERE NOT EXISTS (SELECT 1 FROM research_task t WHERE t.id = e.task_id);
