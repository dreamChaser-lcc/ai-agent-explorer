## 一、窗口函数：给每一行"贴一列"，而不是合并行

**先看它和 GROUP BY 的核心差别**：

```text
GROUP BY：分桶 → 每个桶压成一行（明细消失）
窗口函数：分桶后 → 每一行都保留，只在旁边贴一列结果
```

前端类比：

```js
// GROUP BY ≈ 压缩成统计表
// 窗口函数 ≈ map 里带上"我在组内的名次"，行数不变
rows.map((item, index) => ({ ...item, rank: index + 1 }))
```

**语法骨架**：

```sql
函数名() OVER (PARTITION BY 分桶列 ORDER BY 排序列)
                └── 类似 GROUP BY，但【不合并行】  └── 决定名次
```

### ★ 图解：同一张表、只改 OVER 括号（**Q9**，2026-10-18 增补，全部实测）

**原始表（5 行）**：

```text
student | subject | score
张三    | 数学    | 90
李四    | 数学    | 90
王五    | 英语    | 85
赵六    | 英语    | 85
钱七    | 数学    | 70
```

**第一认知：行数不变**——下面四组查询全部 **5 行进、5 行出**。窗口函数从不删行，只在每行旁边**贴一列**（GROUP BY 才是"压行"）。

**A. `OVER ()` = 每行贴"全表统计"**

```text
student | subject | score | total_rows | avg_all
张三    | 数学    | 90    | 5          | 84.0
李四    | 数学    | 90    | 5          | 84.0
王五    | 英语    | 85    | 5          | 84.0
赵六    | 英语    | 85    | 5          | 84.0
钱七    | 数学    | 70    | 5          | 84.0
```

空括号 = 视野是整张表 → 每行都贴"全班 5 人、平均 84"。

**B. `OVER (PARTITION BY subject)` = 每行贴"本组统计"**

```text
student | subject | score | subject_count | subject_avg
张三    | 数学    | 90    | 3             | 83.3   ← 数学组 3 人
李四    | 数学    | 90    | 3             | 83.3
钱七    | 数学    | 70    | 3             | 83.3
王五    | 英语    | 85    | 2             | 85.0   ← 英语组 2 人
赵六    | 英语    | 85    | 2             | 85.0
```

**C. `OVER (ORDER BY score DESC)` = 每行贴"从第一名到我这行"的累计**

```text
student | score | running_total
张三    | 90    | 90      ← 只有我
李四    | 90    | 180     ← 我和前面
王五    | 85    | 265
赵六    | 85    | 350
钱七    | 70    | 420     ← 到这里全班总和
```

配 `SUM` = 累计分；配 `ROW_NUMBER` = 名次。**排名函数必须带 ORDER BY，原因就在这。**

**"窗口"到底是什么**：每一行**抬头往外看一圈**，看到的那片范围就是它的"窗口"，在窗口内算一个值贴在自己身上。

| OVER 括号 | 这一行的视野 | 白话 |
|---|---|---|
| `OVER ()` | 整张表 | 看全班 |
| `OVER (PARTITION BY subject)` | 同科目的行 | 看本科目同学 |
| `OVER (ORDER BY score DESC)` | 从第一名到我自己 | 看我前面的排名 |

**与 GROUP BY 的正面对照（实测）**：

```text
GROUP BY subject    → 2 行（明细被压掉）
数学 | 3 | 83.3
英语 | 2 | 85.0

PARTITION BY subject → 5 行（明细保留 + 贴统计列）
张三 | 数学 | 90 | 3 | 83.3
...
```

前端场景：列表每行要显示"分数 + 本科目平均分"用来标红低于平均——GROUP BY 做不到（明细没了），窗口函数一行搞定。

> **口诀：GROUP BY 是"汇总成表"，窗口函数是"贴标签不删行"。**

### ★ 排名三兄弟的本质：台阶比喻 + 决定性实验（**Q10**，2026-10-18 增补）

**三者不是"三种排名风格"，是三种"计数方式"**——把成绩想成台阶（90 站第 1 级、85 第 2 级、70 第 3 级）：

| 人 | 成绩 | 第几级台阶 | **ROW_NUMBER**<br>纯排队号 | **RANK**<br>位置序号 | **DENSE_RANK**<br>台阶号 |
|---|---|---|---|---|---|
| 张三 | 90 | 1 | 1 | **1** | **1** |
| 李四 | 90 | 1 | 2 | **1** | **1** |
| 王五 | 85 | 2 | 3 | **3** ← 跳号 | **2** ← 连号 |
| 赵六 | 85 | 2 | 4 | **3** | **2** |
| 钱七 | 70 | 3 | 5 | **5** | **3** |

- **DENSE_RANK = 台阶号**：只数"第几级台阶"，1/2/3 连号，不管每级站几个人；
- **RANK = 位置序号**：数"人是第几个站上去的"——第 1 级站了 2 人，占掉**位置 1、2**，第 2 级的第一人就是**位置 3**（跳号不是 bug，是两个人真占了两个位置）；
- **ROW_NUMBER = 排队号**：不管台阶，一人一号（取号机），1~5 绝不重复。

**决定性实验（实测原文）——同样"取第一名"**：

```text
RANK()       ... WHERE rnk = 1   → 2 行（张三、李四并列第一）
DENSE_RANK() ... WHERE drnk = 1  → 2 行（同样并列）
ROW_NUMBER() ... WHERE rn = 1    → 1 行（只有张三）
```

★ **这就是"每组取最新一条"必须用 `ROW_NUMBER` 的原因**：只有它保证恰好一行；`RANK` 遇到并列（如两条事件时间相同）会把一行变多行，业务逻辑崩。

**实战选择口诀**：

| 需求 | 用谁 | 原因 |
|---|---|---|
| 取唯一一条（最新/去重/分页） | `ROW_NUMBER` | 唯一能保证"绝不并列" |
| 显示并列名次（排行榜） | `RANK` | 并列同名次，符合名次语义 |
| 统计档位（共几个等级） | `DENSE_RANK` | 台阶连号，`MAX(drnk)` = 档位数 |

前端类比：`ROW_NUMBER` ≈ `arr.map((it, i) => i + 1)`；`RANK` ≈ 运动会名次榜（并列冠军→没亚军→下一个季军）；`DENSE_RANK` ≈ 段位等级（两个最强王者，下一个是星耀=第 2 档）。

### 三个排名函数（并列时表现不同）

假设成绩：`90, 90, 85`

| 函数 | 结果 | 规则 |
|---|---|---|
| `ROW_NUMBER()` | 1, 2, 3 | 强行排队，**绝不并列** |
| `RANK()` | 1, 1, 3 | 并列占位（下一个跳号） |
| `DENSE_RANK()` | 1, 1, 2 | 并列不占位（下一个连号） |

```sql
SELECT student, score,
       ROW_NUMBER() OVER (ORDER BY score DESC) AS rn,
       RANK()       OVER (ORDER BY score DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY score DESC) AS drnk
FROM s7_score
ORDER BY score DESC;
```

## 二、两大实战套路（面试常客）

### 套路 1：每组取最新一条（TOP 1 per group）

**项目场景**：任务列表要给每个任务显示"最近一条动态"。

```sql
SELECT * FROM (
    SELECT e.task_id, e.event_type, e.event_message, e.created_at,
           ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY created_at DESC) AS rn
    FROM task_event_log e
) t
WHERE rn = 1;
```

**逐行翻译**：

1. 内层：按 `task_id` 分桶，桶内按时间**倒序**编 1,2,3——最新一条永远是 `rn = 1`；
2. 外层：只留 `rn = 1` → 每个任务恰好一条。

**★ 为什么必须套子查询**：执行顺序是 `FROM → WHERE → 窗口函数 → ORDER BY`（S1 的执行顺序表升级版）——`WHERE` 跑的时候 `rn` 还没算出来，所以 `WHERE rn = 1` 写在同一层会报错/查不到。**窗口函数的别名只能在"更外层"使用。**

### 套路 2：组内占比（窗口聚合 + GROUP BY 配合）

```sql
SELECT status,
       COUNT(*) AS cnt,
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS percent
FROM research_task
GROUP BY status
ORDER BY cnt DESC;
```

`SUM(COUNT(*)) OVER ()` = 不带 PARTITION 的窗口 = **全表汇总**（所有桶的 cnt 总和），拿来当分母。`OVER ()` 空括号 = 整个结果集是一个大窗口。

（`ROUND(x, 1)` = 保留 1 位小数，前端类比 `toFixed(1)`。）

## 二·补、结合项目真实表的三组实战（2026-10-18 应学员"有结合表给我解答吗"增补）

> 说明：真实 H2 文件库被运行中的应用独占（文件锁），本节用**同结构、同分布**数据实测（15 任务、12/2/1 状态、每任务 1~2 条事件）；SQL 在 H2 控制台对真实表跑，形态完全一致。

### 例 1：`task_event_log` 上"每条事件贴两个标签"

```sql
SELECT SUBSTRING(CAST(e.task_id AS VARCHAR),1,8) AS task_prefix, e.event_type,
       CAST(e.created_at AS VARCHAR) AS event_at,
       ROW_NUMBER() OVER (PARTITION BY e.task_id ORDER BY e.created_at DESC) AS rn,
       COUNT(*)     OVER (PARTITION BY e.task_id) AS event_count
FROM task_event_log e
ORDER BY e.task_id, rn;
```

```text
task_prefix | event_type     | event_at         | rn | event_count
2db8366d    | STATUS_CHANGED | 2026-10-14 18:57 | 1  | 2   ← 同一任务：最新一条
2db8366d    | PLAN_GENERATED | 2026-10-14 17:57 | 2  | 2   ← 同一任务：较早一条
0b7923a1    | PLAN_GENERATED | 2026-10-07 17:57 | 1  | 1   ← 只有 1 条事件
5ea5bb0c    | PLAN_GENERATED | 2026-10-04 17:57 | 1  | 1
```

**★★ Q9 视野规则的实战验证**：同一个 `task_id` 两行事件 `rn = 1、2`（按时间倒序编号）；`event_count` 两行**都是 2**——`COUNT(*) OVER (PARTITION BY task_id)` **没有 ORDER BY**，视野是**整组**。

把 `event_count` 改成 `COUNT(*) OVER (PARTITION BY task_id ORDER BY created_at DESC)`，结果就从 `2, 2` 变成 `1, 2`——**加 ORDER BY，视野从"整组"缩成"从开头到当前行"**。排序方向决定累计方向。

### 例 2：任务列表 + 最新动态（前端列表页真正要的数据）

```sql
SELECT t.task_no, t.status, e.event_type AS latest_event
FROM research_task t
LEFT JOIN (
    SELECT task_id, event_type, created_at,
           ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY created_at DESC) AS rn
    FROM task_event_log
) e ON e.task_id = t.id AND e.rn = 1
ORDER BY t.task_no;
```

```text
task_no   | status                   | latest_event
TASK-0001 | WAITING_FOR_CONFIRMATION | STATUS_CHANGED
TASK-0002 | WAITING_FOR_CONFIRMATION | STATUS_CHANGED
...
```

内层给每个任务的事件按时间倒序编号；外层 JOIN 只认 `rn = 1` → **每个任务恰好一行"最近动态"**。`LEFT JOIN` 保证无事件的任务也出现（动态列 null，S2 老规矩）。

### 例 3：状态占比（GROUP BY + 窗口求和）

```sql
SELECT status, COUNT(*) AS cnt,
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS percent
FROM research_task
GROUP BY status;
```

```text
status                   | cnt | percent
WAITING_FOR_CONFIRMATION | 12  | 80.0
CANCELLED                | 2   | 13.3
COMPLETED                | 1   | 6.7
```

`GROUP BY` 先把 15 行压成 3 行；`SUM(COUNT(*)) OVER ()` 再把 3 行的 cnt 求和（12+2+1=15）当分母——**聚合之后再开窗**，窗口函数执行在 GROUP BY 之后。前端饼图数据一行 SQL 出。

## 三、CASE WHEN：SQL 的三元表达式

**两种形态**：

```sql
-- ① 简单形式（等值判断，像 switch）
CASE status
  WHEN 'COMPLETED' THEN '已完成'
  WHEN 'CANCELLED' THEN '已取消'
  ELSE '其他'
END

-- ② 搜索形式（任意条件，像 if/else if）
CASE
  WHEN priority >= 5 THEN '高'
  WHEN priority >= 1 THEN '中'
  ELSE '低'
END
```

前端等价：`status === 'COMPLETED' ? '已完成' : ...`。

**两大用途**：

1. **翻译显示标签**（接口返回中文）：配合 S3 的 `GROUP BY` 出报表；
2. **条件统计**（一个查询数出多个口径）：

```sql
SELECT status,
       COUNT(*) AS total,
       SUM(CASE WHEN error_message IS NOT NULL THEN 1 ELSE 0 END) AS error_count
FROM research_task
GROUP BY status;
```

`SUM(CASE WHEN 条件 THEN 1 ELSE 0 END)` = **条件计数**——比"每种条件各查一次"快得多，报表 SQL 的标配。

## 四、CTE（`WITH`）：给查询起中间变量

**语法**：

```sql
WITH 名字 AS (
    SELECT ...
)
SELECT ... FROM 名字 WHERE ...;
```

前端类比：

```js
const ranked = rankedEvents(...);   // WITH 里的子查询 = 一个中间变量
return ranked.filter(r => r.rn === 1);
```

**为什么值钱**：把嵌套子查询的"洋葱"拉平成"变量表"，可读性提升一个档；多个 CTE 用逗号分隔；还能**递归**。

把套路 1 改写成 CTE 版（更清晰）：

```sql
WITH ranked_events AS (
    SELECT e.task_id, e.event_type, e.created_at,
           ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY created_at DESC) AS rn
    FROM task_event_log e
)
SELECT task_id, event_type, created_at
FROM ranked_events
WHERE rn = 1;
```

### 递归 CTE（`WITH RECURSIVE`）：树结构的专用武器

**项目场景**：`research_step.depends_on_step_id` 是自引用（S2 自连接讲过）——"步骤 A 依赖 B，B 依赖 C"形成链条。查"完整依赖链（含层级和路径）"就要递归。

**实测原文**（H2 2.3.232，见文末附录）：

```text
id | node_name | depth | path
1  | root      | 0     | root
2  | alpha     | 1     | root > alpha
3  | beta      | 2     | root > alpha > beta
4  | gamma     | 1     | root > gamma
```

**结构三件套**：

```sql
WITH RECURSIVE chain (id, node_name, depth, path) AS (
    -- ① 锚点：起点（谁是根）
    SELECT id, node_name, 0, node_name
    FROM s7_node WHERE parent_id IS NULL

    UNION ALL

    -- ② 递归部分：拿【上一层的结果】JOIN 原表，找下一层
    SELECT n.id, n.node_name, c.depth + 1, c.path || ' > ' || n.node_name
    FROM s7_node n
    JOIN chain c ON n.parent_id = c.id
)
SELECT * FROM chain ORDER BY id;
```

**读法**：`chain` 是"不断长大的结果表"——先放根节点（锚点），然后每一轮拿上一轮新增的行去 JOIN 原表找子节点。**没有新行时自动停**（终止条件不需要手写）。

前端类比：广度优先遍历（BFS）自己喂自己——`let frontier = [root]; while (frontier.length) { ... }`。

## 五、执行顺序再升级（本课最容易踩的坑）

```text
FROM → WHERE → GROUP BY → 聚合 → HAVING → 【窗口函数】 → SELECT → ORDER BY → LIMIT
```

由此得到两条铁律：

1. **`WHERE` 里不能用窗口函数别名**（`rn` 此时不存在）→ 必须套子查询/CTE（套路 1 的"为什么"）；
2. **`ORDER BY` 里可以用**（它排在窗口函数之后）。

## 七、动手练习（H2 控制台）

```sql
-- 练习 1：排名三兄弟（造并列分数才有对比价值）
DROP TABLE IF EXISTS s7_score;
CREATE TABLE s7_score (id UUID PRIMARY KEY, student VARCHAR(32), subject VARCHAR(16), score INTEGER);
INSERT INTO s7_score (id, student, subject, score) VALUES
 (RANDOM_UUID(), '张三', '数学', 90),
 (RANDOM_UUID(), '李四', '数学', 90),
 (RANDOM_UUID(), '王五', '数学', 85),
 (RANDOM_UUID(), '赵六', '数学', 85),
 (RANDOM_UUID(), '钱七', '数学', 70);

SELECT student, score,
       ROW_NUMBER() OVER (ORDER BY score DESC) AS rn,
       RANK()       OVER (ORDER BY score DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY score DESC) AS drnk
FROM s7_score ORDER BY score DESC;
-- 验收点：90/90 处 rn=1,2 而 rnk=1,1；85 处 rnk 跳到 3、drnk=2

-- 练习 2：每组取最新一条（真实表 task_event_log）
SELECT * FROM (
    SELECT e.task_id, e.event_type, e.event_message, e.created_at,
           ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY created_at DESC) AS rn
    FROM task_event_log e
) t WHERE rn = 1
ORDER BY created_at DESC;
-- 验收点：每个 task_id 恰好一行（= 该任务最近一条事件）

-- 练习 3：故意在同层引用 rn（看它报错，理解执行顺序）
SELECT task_id, event_type, created_at,
       ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY created_at DESC) AS rn
FROM task_event_log
WHERE rn = 1;
-- 预期报错：Column "rn" not found —— WHERE 执行时 rn 还没算（第五节的铁律 1）

-- 练习 4：CASE WHEN 翻译状态 + 条件计数
SELECT status,
       CASE status
         WHEN 'COMPLETED' THEN '已完成'
         WHEN 'CANCELLED' THEN '已取消'
         WHEN 'WAITING_FOR_CONFIRMATION' THEN '等待确认'
         ELSE '其他'
       END AS status_label,
       COUNT(*) AS task_count,
       SUM(CASE WHEN error_message IS NOT NULL THEN 1 ELSE 0 END) AS error_count
FROM research_task
GROUP BY status
ORDER BY task_count DESC;

-- 练习 5：CTE 重写套路 1（与练习 2 结果必须一致）
WITH ranked_events AS (
    SELECT e.task_id, e.event_type, e.created_at,
           ROW_NUMBER() OVER (PARTITION BY e.task_id ORDER BY e.created_at DESC) AS rn
    FROM task_event_log e
)
SELECT task_id, event_type, created_at FROM ranked_events WHERE rn = 1;

-- 练习 6：递归 CTE（树结构；对应项目的步骤依赖链）
DROP TABLE IF EXISTS s7_node;
CREATE TABLE s7_node (id INT PRIMARY KEY, parent_id INT NULL, node_name VARCHAR(32) NOT NULL);
INSERT INTO s7_node (id, parent_id, node_name) VALUES
 (1, NULL, 'root'), (2, 1, 'alpha'), (3, 2, 'beta'), (4, 1, 'gamma');

WITH RECURSIVE chain (id, node_name, depth, path) AS (
    SELECT id, node_name, 0, node_name FROM s7_node WHERE parent_id IS NULL
    UNION ALL
    SELECT n.id, n.node_name, c.depth + 1, c.path || ' > ' || n.node_name
    FROM s7_node n JOIN chain c ON n.parent_id = c.id
)
SELECT id, node_name, depth, path FROM chain ORDER BY id;
-- 验收点：4 行，depth 0/1/2/1，path 逐级拼接（与文末实测输出一致）

-- 练习 7：清理
DROP TABLE IF EXISTS s7_score;
DROP TABLE IF EXISTS s7_node;
```
