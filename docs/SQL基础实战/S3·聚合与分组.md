# S3 · 聚合与分组（COUNT / SUM / AVG + GROUP BY + HAVING）

> **本课目标**：从"查一行行明细"升级到"查统计结果"——聚合函数家族、GROUP BY 分桶、HAVING 过滤组、JOIN + 聚合的组合拳（以及那个必踩的计数坑）。
> **教材**：`backend/src/main/resources/mapper/ResearchTaskMapper.xml` 的 `countPage`（项目在跑的聚合 SQL）
> **前置**：S1（SELECT / WHERE / 执行顺序）、S2（JOIN）

---

## 一、前端类比：聚合 ≈ JS 的统计函数

你写过这种统计代码：

```js
const total = allTasks.length;                                  // COUNT(*)
const failed = allTasks.filter(t => t.status === 'FAILED').length;  // COUNT + WHERE
const avgPriority = allTasks.reduce((s, t) => s + t.priority, 0) / allTasks.length;  // AVG
```

SQL 的聚合函数就是这些统计的数据库版——**数据不过网，数据库内部算完只返回一个数**：

```sql
SELECT COUNT(*), AVG(priority) FROM research_task;   -- 一次查询，两个统计
```

**关键转变**：聚合查询的返回**不再是"一行行明细"，而是"统计数字"**——15 行数据聚合成 1 行结果。

---

## 二、聚合函数家族（6 个）

| 函数 | 干什么 | JS 等价 | 注意 |
|---|---|---|---|
| `COUNT(*)` | 数**行数**（含 NULL 行） | `arr.length` | 最常用 |
| `COUNT(列)` | 数该列**非 NULL** 的个数 | `arr.filter(t => t.x != null).length` | ★ NULL 不计数（后面有大坑） |
| `COUNT(DISTINCT 列)` | 数**去重后**的个数 | `new Set(arr.map(t => t.x)).size` | |
| `SUM(列)` | 求和 | `reduce((s,t) => s + t.x, 0)` | 只能数值列 |
| `AVG(列)` | 平均值 | `sum / count` | **NULL 行不参与平均** |
| `MIN(列)` / `MAX(列)` | 最小/最大 | `Math.min(...arr)` / `Math.max(...)` | 数值/时间/字符串都行 |

**项目教材：`countPage`**（`ResearchTaskMapper.xml` 第 35–43 行）：

```sql
SELECT COUNT(*)
FROM research_task
WHERE status = 'RUNNING'   -- 动态拼接，status 传了才拼
```

不带 `GROUP BY` 的聚合 = **全表（过滤后）聚成一行**——这就是分页接口"总数"的来源（配合 `LIMIT/OFFSET` 算出 totalPages）。

## 三、GROUP BY：分桶统计（本课主角）

需求："**每种状态**各有多少任务？"——先把数据按状态**分桶**，再对每桶 `COUNT`：

```sql
SELECT status, COUNT(*) AS task_count
FROM research_task
GROUP BY status;
```

结果长这样：

```text
status                     | task_count
---------------------------+-----------
WAITING_FOR_CONFIRMATION   |     7
COMPLETED                  |     6
CANCELLED                  |     2
```

JS 完全等价物（对照着读，一遍就懂）：

```js
// 1. 分桶：按 status 把任务塞进各自的桶
const buckets = {};
for (const t of allTasks) {
  (buckets[t.status] ??= []).push(t);
}
// 2. 对每桶统计
const result = Object.entries(buckets)
  .map(([status, list]) => ({ status, task_count: list.length }));
```

**GROUP BY 干的事 = 前端手写的分桶循环；SELECT 里的聚合函数 = 对每桶做的统计。**

### ★ 铁律：SELECT 只能放"分组列 + 聚合函数"

```sql
-- ✗ 报错：title 既不在 GROUP BY 里，也不在聚合函数里
SELECT status, title, COUNT(*) FROM research_task GROUP BY status;
```

为什么？分桶之后，一个桶里有 7 个任务、7 个不同的 `title`——数据库不知道该显示哪个，干脆报错。**桶的身份证是 `status`，桶的统计数字是 `COUNT(*)`，其他列无处安放。**

（想绕过？`MAX(title)` 之类的聚合可以硬放——但那是"桶里最大的 title"，先想清楚是不是真要这个。）

## 四、执行顺序：完整版（S1 版本升级）

```text
FROM / JOIN   ① 定表、连接
WHERE         ② 过滤行（原始明细）
GROUP BY      ③ 分桶
聚合计算       ④ 每桶算 COUNT/SUM/AVG...
HAVING        ⑤ 过滤桶（聚合结果）
SELECT        ⑥ 挑列/算别名
ORDER BY      ⑦ 排序（可用聚合别名）
LIMIT         ⑧ 截取
```

这个顺序直接解释了下面两个规则。

---

## 五、WHERE vs HAVING：一个滤行，一个滤桶

需求："统计**已创建之后**的任务中，**数量 ≥ 2** 的状态有哪些？"

```sql
SELECT status, COUNT(*) AS task_count
FROM research_task
WHERE created_at >= '2026-10-01'      -- ② 先滤行：只留 10 月后的任务（还没分桶）
GROUP BY status                        -- ③ 再分桶
HAVING COUNT(*) >= 2                   -- ⑤ 再滤桶：桶里数量不足 2 的扔掉
ORDER BY task_count DESC;
```

| | WHERE | HAVING |
|---|---|---|
| 过滤对象 | **行**（原始明细） | **组**（聚合结果） |
| 执行时机 | 分桶**前**（②） | 分桶**后**（⑤） |
| 能用聚合函数？ | ✗（聚合还没算） | ✓（`HAVING COUNT(*) >= 2`） |
| 前端类比 | 分桶前 `.filter()` | 分桶后 `.filter(([k,list]) => list.length >= 2)` |

**记忆口诀：WHERE 管进桶的货，HAVING 管留下的桶。**

## 六、JOIN + GROUP BY 组合拳（与 S2 无缝衔接）

需求："**每个任务**各有多少个步骤？"

```sql
SELECT t.title AS task_title, COUNT(s.id) AS step_count
FROM research_task t
LEFT JOIN research_step s ON s.task_id = t.id   -- LEFT：没步骤的任务也要出现
GROUP BY t.id, t.title
ORDER BY step_count DESC;
```

三个要点：

1. **先 JOIN 膨胀（S2 的扁平行），再分桶统计**——每个任务的步骤行被聚到同一个桶里；
2. **`GROUP BY t.id, t.title`**：PostgreSQL/H2 语义下，SELECT 里的非聚合列必须出现在 GROUP BY。用 `t.id`（主键，唯一）当分组键最稳，`t.title` 跟着一起列出；
3. ★ **本课最大的坑：为什么是 `COUNT(s.id)` 不是 `COUNT(*)`？**

```text
LEFT JOIN 之后没步骤的任务也是 1 行（s.id = null）：

COUNT(*)      → 数行数 → 没步骤的任务也数出 1   ← 错！
COUNT(s.id)   → 数非 NULL → null 不计入 → 0   ← 对！
```

**S2 的"LEFT JOIN 无匹配填 NULL" + S3 的"COUNT(列) 不数 NULL"两条知识在这里会师**——不用 `COUNT(s.id)` 的话，每个没步骤的任务都被谎报为"有 1 个步骤"。

## 八、动手练习（H2 控制台）

```sql
-- 练习 1：每种状态多少任务（分桶统计入门）
SELECT status, COUNT(*) AS task_count
FROM research_task
GROUP BY status
ORDER BY task_count DESC;

-- 练习 2：COUNT(*) vs COUNT(列)——NULL 不计数的差异
SELECT COUNT(*) AS total_rows,
       COUNT(error_message) AS has_error,
       COUNT(created_by) AS has_creator
FROM research_task;
-- 预期：total_rows = 15，另外两个明显更小（大多数是 null）

-- 练习 3：每个任务几个步骤（JOIN + GROUP BY 组合拳）
-- 注意用 COUNT(s.id)，想想为什么（第六节）
SELECT t.title AS task_title, COUNT(s.id) AS step_count
FROM research_task t
LEFT JOIN research_step s ON s.task_id = t.id
GROUP BY t.id, t.title
ORDER BY step_count DESC;

-- 练习 4：把练习 3 的 COUNT(s.id) 改成 COUNT(*)，对比两种结果的差额
-- 差额 = 没有步骤的任务（被 COUNT(*) 谎报为 1 的那批）

-- 练习 5：HAVING 滤桶——步骤数 ≥ 5 的任务
SELECT t.title AS task_title, COUNT(s.id) AS step_count
FROM research_task t
LEFT JOIN research_step s ON s.task_id = t.id
GROUP BY t.id, t.title
HAVING COUNT(s.id) >= 5
ORDER BY step_count DESC;

-- 练习 6：复刻项目 countPage（对照 mapper 第 35-43 行）
SELECT COUNT(*) FROM research_task WHERE status = 'COMPLETED';

-- 练习 7（可选）：多桶维度 + AVG/MAX
SELECT t.title AS task_title, COUNT(e.id) AS execution_count,
       MAX(e.duration_ms) AS slowest_ms
FROM research_task t
LEFT JOIN step_execution e ON e.task_id = t.id
GROUP BY t.id, t.title
ORDER BY slowest_ms DESC NULLS LAST;
```

**验收标准**：
1. 练习 1 能说出哪桶最大；
2. 练习 2 能解释 `total_rows` 和 `has_error` 的差额是什么（error_message IS NULL 的行数）；
3. 练习 4 能指出 COUNT(*) 版本里"被谎报为 1"的具体任务；
4. 练习 6 结果 = 列表接口里 COMPLETED 状态的总数（可对照前端页面）。

## 九、验证记录（2026-10-15/16，7 练习全绿 + 全课程最佳侦探故事）

| 练习 | 结果 | 判定 |
|---|---|---|
| ① 分桶 | `WAITING_FOR_CONFIRMATION=12` / `CANCELLED=2` / `COMPLETED=1` | ✅ |
| ② COUNT(*) vs COUNT(列) | 首跑 `15/15/15`（异常！）→ 侦探三连破案 → 重跑 **`15/0/15`** | ✅ 详见下方侦探实录 |
| ③ 组合拳 COUNT(s.id) | 15 个任务全部 5 步 | ✅ |
| ④ 改 COUNT(*) 对比 | 与③**完全相同** | ✅ 数据现状掩盖坑（解读二） |
| ⑤ HAVING >= 5 | 15 桶全过（全是 5 步，无桶被筛掉） | ✅ |
| ⑥ 复刻 countPage | `?column? = 1`（无别名的默认列名），与①的 `COMPLETED=1` **交叉验证一致** | ✅ |
| ⑦ 多桶 + MAX | MQ Test `execution_count=5, slowest_ms=29`；其余 14 行 `0/null` | ✅ 三个亮点（解读三） |

### ★ 侦探实录（练习②的 15/15/15 之谜）

首跑 `has_error=15` 与 S1 记录（error_message 全 NULL）矛盾——不猜，跑侦探三连：

1. **侦探①**：`error_message IS NULL` = **15**（全空）；`created_by IS NULL` = **0**（全非空）；
2. **侦探②抽样**：`error_message` 全 `null`；`created_by` 全 `'demo-user'`（真实值，非空串）；
3. **查证代码**：`ResearchTaskController` 第 103 行 `createTask(request, "demo-user")`——后端**硬编码**写入（MVP 无用户系统），`created_by` 从第一个任务起就非 NULL；
4. **重跑练习②** = `15 / 0 / 15`，与侦探①完全吻合，案闭。

**三条结论入档**：
- `COUNT(列)` 不数 NULL 的正反实证：全 NULL 的 `error_message` 数出 **0**，全非空的 `created_by` 数出 **15**；
- **可空 ≠ 一定空**：同是 `NULL` 约束，`created_by` 被应用层填满、`error_message` 老实空着（S5 伏笔）；
- **查证 > 记忆，证据面前人人平等**：S1 答疑时"created_by 大概率全 null"是 AI 未查证的推测——被侦探 SQL 纠正。推测必须验证，包括 AI 说的。

### ★ 解读二：COUNT(*) 的坑被数据现状掩盖（S2 解读一重演）

练习③④结果相同、练习⑤无桶被筛——因为当前库里**每个任务恰好 5 步**，LEFT JOIN 无一行填 NULL，`COUNT(*)` 无谎报机会。哪天来了"刚创建、没步骤"的任务，`COUNT(*)` 版就谎报 1。**数据现状会掩盖写法缺陷，选型要看业务语义。**

### ★ 解读三：练习⑦的三个亮点

1. 14 行 `execution_count = 0`：`COUNT(e.id)` 对 LEFT JOIN 无匹配正确数出 **0**（`COUNT(*)` 会谎报 1）——第六节大坑的**正面实证**；
2. 两个同名"MQ Test"各占一行：分桶键是 `t.id` 不是 `title`，**同名任务是两个桶**；
3. 全 NULL 桶的 `MAX(duration_ms)` 返回 `null`，`NULLS LAST` 把它压到队尾——聚合忽略 NULL 的实物。
