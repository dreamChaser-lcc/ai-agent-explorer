## 一、DDL vs DML：改"结构"和改"数据"是两本证

| 家族 | 语句 | 动的是 | 类比 |
|---|---|---|---|
| **DML**（S4 学的） | INSERT / UPDATE / DELETE | 表里的**行** | 改文档内容 |
| **DDL**（本课主角） | CREATE / ALTER / DROP | 表**本身**（结构） | 改文档的模板/字段定义 |

**结构的改动影响所有行**——`ALTER TABLE 加一列` = 全表每行同时多出一个格子（老行填默认值或 NULL）。所以 DDL 在生产是重炮，发得比 DML 更谨慎。

## 二、列定义四要素 + 类型家族对照 JS

每一列的完整形态：**列名 + 类型 + 约束 + 默认值**：

```sql
created_by VARCHAR(128) NULL,
version   BIGINT       NOT NULL DEFAULT 0,
```

类型家族全谱（本项目实际用到的每一种）：

| SQL 类型 | 项目实例 | JS 类比 | 备注 |
|---|---|---|---|
| `UUID` | `id`、所有 `task_id` | `string`（Java 侧是 UUID 对象） | 全局唯一标识 |
| `VARCHAR(n)` | `task_no VARCHAR(64)`、`title VARCHAR(255)` | `string`（带长度上限） | 超长直接报错 |
| `TEXT` | `goal`、`error_message` | `string`（不限长） | 长文本 |
| `INTEGER` | `priority`、`attempt_no` | `number`（整数） | ±21 亿 |
| `BIGINT` | `version`、`duration_ms` | `number`（大整数） | ±922 兆 |
| `DOUBLE` | `relevance_score` | `number`（浮点） | |
| `BOOLEAN` | `requires_confirmation` | `boolean` | |
| `TIMESTAMP WITH TIME ZONE` | `created_at` 系 | `Date` | 绝对时间点（S1 答疑：时区指纹） |
| `JSON` | `event_payload`、`input_payload` | `object` | 存 JSON 文本，数据库能查询 |

**选型直觉**：能小不大（`INTEGER` 够就别 `BIGINT`）、文本定长用 `VARCHAR` 不定长用 `TEXT`、时间一律带时区。

## 三、约束五件套（+2 个本项目没用的）

| 约束 | 干什么 | 项目实例 |
|---|---|---|
| `PRIMARY KEY` | **身份证**：唯一 + 非空，自动建索引 | `id UUID PRIMARY KEY` |
| `NOT NULL` / `NULL` | 必填 / 选填（S1 答疑已透） | 全表可见 |
| `UNIQUE` | 不许重复（允许多个 NULL——场景④的幂等基石） | `task_no VARCHAR(64) NOT NULL UNIQUE` |
| `DEFAULT` | 不给值时的兜底 | `version BIGINT NOT NULL DEFAULT 0` |
| `CHECK` | 值范围检查——**本项目未用** | 如 `CHECK (priority >= 0)`，了解即可 |
| `FOREIGN KEY` | 物理外键——**本项目未用**（逻辑外键，关联靠应用层 + 手写 ON，S2 讲过） | — |

**UNIQUE 的两种写法**（效果等价，都会建唯一索引）：

```sql
-- 写法 1：列内联（建表时顺手声明）
task_no VARCHAR(64) NOT NULL UNIQUE

-- 写法 2：独立命名索引（schema 第 35 行，场景④用的）
CREATE UNIQUE INDEX IF NOT EXISTS uq_research_task_idempotency_key
    ON research_task (idempotency_key);
```

独立写法的优势：**能起名**（报错信息里认得出是哪条约束）、**能多列组合**（`UNIQUE(a, b)`）、**能给后加的列补约束**（幂等键列就是 `ALTER` 加的，只能事后建索引）。

## 四、逐行精读 `research_task`（约束全家桶活教材）

```sql
CREATE TABLE IF NOT EXISTS research_task (
    id UUID PRIMARY KEY,                                   -- 主键：自动唯一+非空+索引
    task_no VARCHAR(64) NOT NULL UNIQUE,                   -- 业务编号：必填且全局唯一
    title VARCHAR(255) NOT NULL,                           -- 系统必给
    goal TEXT NOT NULL,                                    -- 系统必给
    execution_mode VARCHAR(32) NOT NULL,                   -- 系统必给
    status VARCHAR(64) NOT NULL,                           -- 状态机（场景②）
    current_stage VARCHAR(64) NOT NULL,                    -- 系统必给
    current_step_id UUID NULL,                             -- "还没开始执行"
    requires_confirmation BOOLEAN NOT NULL DEFAULT FALSE,  -- DEFAULT 兜底
    priority INTEGER NOT NULL DEFAULT 0,                   -- DEFAULT 兜底
    error_message TEXT NULL,                               -- "还没失败"（S3 侦探主角）
    created_by VARCHAR(128) NULL,                          -- 可空但被 demo-user 填满（S3 侦探）
    started_at TIMESTAMP WITH TIME ZONE NULL,              -- "还没开始"
    completed_at TIMESTAMP WITH TIME ZONE NULL,            -- "还没完成"
    version BIGINT NOT NULL DEFAULT 0,                     -- 乐观锁（S4 两幕主角）
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,          -- 每行必有
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL           -- 每行必有
);
```

一眼看穿的设计规律（把一路攒的知识对号入座）：

- **系统必定能给的** → `NOT NULL`（task_no/title/status...）
- **业务上"还没发生"的** → `NULL`（current_step_id/error_message/started_at/completed_at）
- **可空但被应用层填满的** → `created_by`（demo-user 硬编码）
- **并发防护** → `version ... DEFAULT 0`
- **审计底座** → `created_at/updated_at NOT NULL`（行一落地就有）

## 五、ALTER 与 IF NOT EXISTS：表结构怎么"安全地长大"

schema 第 21–25 行：

```sql
-- 兼容已有库：老库（表已存在）缺 version 列时补上（IF NOT EXISTS → 本文件可重复执行）
ALTER TABLE research_task ADD COLUMN IF NOT EXISTS version BIGINT DEFAULT 0 NOT NULL;

-- 场景④：幂等键列（客户端带来的"请求唯一标记"——重复提交在数据库层被拦下）
ALTER TABLE research_task ADD COLUMN IF NOT EXISTS idempotency_key VARCHAR(128);
```

两个要点：

1. **`IF NOT EXISTS` = 幂等**：脚本跑一百遍结果一样（已有就不动）。整个 `schema-dev.sql` 从 `CREATE TABLE IF NOT EXISTS` 到 `CREATE INDEX IF NOT EXISTS` 全靠这个特性实现"**可重复执行的初始化脚本**"——dev 模式每次启动都跑一遍（`application-dev.yml` 的 `sql.init.mode: always`），不炸；
2. **给老行加 NOT NULL 列的套路**：`version` 加列时带 `DEFAULT 0`——老行自动填 0，不用回填脚本。若加 NOT NULL 又不给 DEFAULT，老库会报错（老行没值）。

## 八、动手练习（H2 控制台：读元数据 + 建表全周期）

**第一组：元数据三连**（`INFORMATION_SCHEMA` = "查表结构本身的表"——数据库的自描述目录）

```sql
-- 练习 1：research_task 的列定义全景（类型/可空/默认值）
-- ★ H2 2.3.232 实测：本视图没有 TYPE_NAME / COLUMN_TYPE 列！
--   类型文本就在 DATA_TYPE 列（character varying / uuid / timestamp with time zone ...）
--   长度在 CHARACTER_MAXIMUM_LENGTH
--   元数据是版本敏感区：报"列不存在"先 SELECT * FROM INFORMATION_SCHEMA.COLUMNS ... LIMIT 1 看列头
SELECT COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH, IS_NULLABLE, COLUMN_DEFAULT
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'research_task'
ORDER BY ORDINAL_POSITION;
-- 验收点：version 看到 DEFAULT 0；created_by 的 IS_NULLABLE = YES；
--        TEXT 列显示为 character varying(1000000000)（H2 里 TEXT 别名 = 超长 VARCHAR）

-- 练习 2：对比两列的"命运"
SELECT COLUMN_NAME, IS_NULLABLE FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'research_task' AND COLUMN_NAME IN ('task_no', 'error_message');
-- 验收点：task_no = NO（必填），error_message = YES（还没失败）

-- 练习 3：这张表身上有哪些约束
SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE FROM INFORMATION_SCHEMA.TABLE_CONSTRAINTS
WHERE TABLE_NAME = 'research_task';
-- 验收点：能看到 PRIMARY KEY；task_no 的 UNIQUE 也在列

-- 练习 3 与练习 4 必须合起来看：
--   ③ 约束视图只有 2 个（PRIMARY KEY + task_no 的 UNIQUE）；
--   ✗ 幂等键的 UNIQUE 不在这里——它用 CREATE UNIQUE INDEX 建的独立索引，只出现在④
--   ✓ UNIQUE 约束会自动拥有一份索引（约束管不许重，索引顺便让按它查询变快）

-- 练习 4：这张表身上有哪些索引（主键自带一个）
SELECT INDEX_NAME, INDEX_TYPE_NAME FROM INFORMATION_SCHEMA.INDEXES
WHERE TABLE_NAME = 'research_task';
-- 验收点：共 5 个 = PRIMARY_KEY_1（主键自带）+ CONSTRAINT_1F_INDEX_1（task_no UNIQUE 自动生成）
--        + idx_created_at + idx_status + uq_research_task_idempotency_key（独立唯一索引）
-- ★ 应学员实测修正：初版写"共 4 个"漏数了 UNIQUE 自动索引——约束与索引是一体两面
```

**第二组：建表全周期**（亲手把本课所有语法串一遍；最后 DROP 清理，不留垃圾）

```sql
-- 练习 5：建表（五件套全用上）
CREATE TABLE IF NOT EXISTS s5_lab (
    id UUID PRIMARY KEY,
    lab_name VARCHAR(64) NOT NULL UNIQUE,
    score INTEGER NOT NULL DEFAULT 0,
    note TEXT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);

-- 练习 6：INSERT 验证 DEFAULT 和 NULL 的分工（score/note 都不给）
INSERT INTO s5_lab (id, lab_name, created_at)
VALUES (RANDOM_UUID(), '第一号实验室', CURRENT_TIMESTAMP);
SELECT lab_name, score, note FROM s5_lab;
-- 验收点：score = 0（DEFAULT 兜底），note = NULL（选填空着）

-- 练习 7：UNIQUE 拦截实测（原样再插一次同名）
INSERT INTO s5_lab (id, lab_name, created_at)
VALUES (RANDOM_UUID(), '第一号实验室', CURRENT_TIMESTAMP);
-- 预期报错：Unique index or primary key violation——数据库是并发的最终仲裁者（场景④同款）

-- 练习 8：ALTER 长大 + 元数据确认
ALTER TABLE s5_lab ADD COLUMN IF NOT EXISTS extra_flag BOOLEAN DEFAULT FALSE;
SELECT COLUMN_NAME, DATA_TYPE, IS_NULLABLE FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 's5_lab' ORDER BY ORDINAL_POSITION;
-- 验收点：extra_flag 出现在清单末尾；老行（就一行）的 extra_flag 自动填 FALSE/默认

-- 练习 9：DROP 清理（DDL 的"删表"，比 DELETE 更重——连结构一起删）
DROP TABLE IF EXISTS s5_lab;
SELECT COUNT(*) FROM INFORMATION_SCHEMA.TABLES WHERE TABLE_NAME = 's5_lab';
-- 验收点：清理后计数 = 0
```

**验收标准**：
1. 练习 1 的输出能和第四节逐行精读对上（类型、可空、默认三列都能解释）；
2. 练习 6 能说出 score=0 与 note=null 的机制差异；
3. 练习 7 的报错信息里能看到约束/索引名字（理解"数据库是并发仲裁者"）；
4. 练习 9 清理后计数归零，库不留垃圾。

### ★ 深挖一：练习⑦的报错原文解剖（一报三课）

```text
Unique index or primary key violation: "public.CONSTRAINT_INDEX_C ON public.s5_lab(lab_name NULLS LAST) VALUES ( /* 1 */ U&'\7b2c\4e00\53f7\5b9e\9a8c\5ba4' )" [23505-232]
```

1. **`23505`** = SQLSTATE 的 `unique_violation`——**应用层 409 Conflict 的源头错误码**（场景④幂等兜底捕获的就是这个）。看到 23505 就要想到"数据库在做并发仲裁"；
2. **`CONSTRAINT_INDEX_C`** = 列内联 `UNIQUE` 没起名，数据库**自动生成的丑名字**。对比独立写法 `uq_research_task_idempotency_key`——**重要约束必须起名**，否则报错信息、排障、运维沟通全靠猜；
3. **`U&'\7b2c...'`** = H2 把非 ASCII 字符转义成 Unicode 码点（`\7b2c\4e00\53f7...` 即"第一号实验室"）——报错里中文变乱码不是数据坏了，是转义显示。

### ★ 深挖二：元数据三次踩坑实录（AI 的"查证 > 记忆"现身说法）

练习①的 SQL 连撞两堵墙：`TYPE_NAME` 列不存在（H2 1.x 旧列）→ 改猜 `COLUMN_TYPE` 又不存在 → **真连 `h2-2.3.232.jar` 实测**，才确认：H2 2.x 的**类型文本就在 `DATA_TYPE` 列**（`character varying` / `uuid` / `timestamp with time zone`），长度在 `CHARACTER_MAXIMUM_LENGTH`。

**三条入档**：
- 元数据（`INFORMATION_SCHEMA`）是**版本敏感区**，跨版本列名会消失/改名——**别背列名，先 `SELECT * ... LIMIT 1` 看列头**；
- **面试/文档里的"H2 元数据列"默认按 1.x 记忆是靠不住的**，连库查一遍只要 30 秒；
- 本课教学原则"查证 > 记忆"连 AI 自己都要被它审判——前两次猜列名就是活体反面教材。

### ★ 深挖三：练习③↔④ 的"两个侧面"

约束视图只列 `TABLE_CONSTRAINTS`（PRIMARY KEY / UNIQUE 约束），**独立 `CREATE UNIQUE INDEX` 不在其中**；索引视图列全 5 个索引。**查"这张表被什么管着"必须两个视图合看**；而 `UNIQUE` 约束自带索引的事实说明——**约束和索引是一体两面**：约束管"不许重复"，索引顺手把"按它查询"变快（`WHERE task_no = ?` 和 `WHERE idempotency_key = ?` 都是索引查询）。
