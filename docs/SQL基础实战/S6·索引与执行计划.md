## 一、前端类比：索引 = 预先建好的 Map

```js
// 全表扫描：每次查都要遍历整个数组 → O(n)
const task = allTasks.find(t => t.taskNo === 'TASK-0001');

// 建索引：先花时间建 Map（一次），之后查询 O(1)
const taskByNo = new Map(allTasks.map(t => [t.taskNo, t]));
const task = taskByNo.get('TASK-0001');
```

**数据库索引就是这个 `Map`**——预先排好序的"目录"，键是列值，值是行在磁盘上的位置。查询时先查目录（几步跳转），再直接取那一行，不用从头翻到尾。

**代价也一模一样**：

| | 收益 | 成本 |
|---|---|---|
| 前端 Map | 查询 O(1) | 建 Map 要 O(n)、占内存、数据变了要重建 |
| 数据库索引 | 查询从 O(n) → O(log n) | **每次 INSERT/UPDATE/DELETE 都要维护索引**、占磁盘 |

> **心法：索引是给"读"买的加速包，账单寄给"写"**。一个高频写入的表挂 10 个索引，写性能会被索引维护拖垮——**索引不是越多越好**。

---

## 二、索引为什么既快又有序

数据库索引的底层结构是 **B-tree**（一种始终有序的树），这带来三种能力：

1. **等值查询快**：`WHERE code = 'CODE-5000'`——沿树找，log(n) 步；
2. **范围查询快**：`WHERE created_at BETWEEN ... AND ...`——有序结构上"扫一段"即可；
3. **天然有序 → 免排序**：`ORDER BY 索引列` 不用额外排序（数据反正是按索引顺序取的）——本项目列表页 `ORDER BY created_at DESC LIMIT 10` 就吃这个红利。

图书馆类比：书架上的书**按分类排好**（索引），找"计算机类第 3 排"直接走过去；没排过的书（无索引）只能一箱一箱翻。

## 四、怎么读 H2 的 EXPLAIN（实测三种输出）

`EXPLAIN SELECT ...` 返回一列 `PLAN`，里面的 **`/* ... */` 注释就是"访问路径"的判决书**。三种关键形态：

```text
-- ① 全表扫（没走索引）：看到 表名.tableScan
FROM "public"."s6_lab"
    /* public.s6_lab.tableScan */
WHERE "code" = 'CODE-5000'

-- ② 走索引：看到 索引名 + 它吃掉的条件
FROM "public"."s6_lab"
    /* public.idx_s6_lab_code: code = 'CODE-5000' */
WHERE "code" = 'CODE-5000'

-- ③ 走索引且免排序：看到 index sorted
FROM "public"."s6_lab"
    /* public.idx_s6_lab_code */
ORDER BY 2
FETCH FIRST 10 ROWS ONLY
/* index sorted */
```

（`FETCH FIRST 10 ROWS ONLY` 是 LIMIT 10 的标准 SQL 写法，`ORDER BY 2` 指第二列。）

**读法三句话**：`tableScan` = 全表扫（坏）；索引名出现 = 走索引（好）；`index sorted` = 排序都省了（更好）。

## 四·补、完整 EXPLAIN 输出逐行讲解（2026-10-18 应学员要求增补）

以下四段输出全部是 **H2 2.3.232 原始输出 + 实测复现**，逐段批注。

### 例 1：全表扫（无索引的等值查询）

```text
PLAN
SELECT
    "public"."s6_lab"."id",
    "public"."s6_lab"."code",
    "public"."s6_lab"."created_at"
FROM "public"."s6_lab"
    /* public.s6_lab.tableScan */
WHERE "code" = 'CODE-5000'
```

| 行 | 含义 |
|---|---|
| `PLAN` | 结果集的列名——EXPLAIN 只返回一列，整段文本都在这一列里 |
| `SELECT` + 3 行缩进列名 | 复述你要的输出列（你写 `SELECT *`，计划里展开成实际 3 列）。`"public"` 是 schema 名（相当于库里的"命名空间"） |
| `FROM "public"."s6_lab"` | 从哪张表取数 |
| `/* public.s6_lab.tableScan */` | ★ **判决书：全表扫描**——10000 行从第一行翻到最后一行，逐行判断 `code = 'CODE-5000'` |
| `WHERE "code" = 'CODE-5000'` | 复述你的过滤条件（执行时才逐行算） |

### 例 2：走索引（同一条 SQL，建索引之后）

```text
PLAN
SELECT
    "public"."s6_lab"."id",
    "public"."s6_lab"."code",
    "public"."s6_lab"."created_at"
FROM "public"."s6_lab"
    /* public.idx_s6_lab_code: code = 'CODE-5000' */
WHERE "code" = 'CODE-5000'
```

与例 1 **唯一的差别就在那行注释**：

- `tableScan` 消失了，换成 `idx_s6_lab_code`（索引名）；
- **冒号后面的 `code = 'CODE-5000'` 是关键**——它表示"索引消化了这个条件"：查目录直接定位到那一行，`WHERE` 不再需要逐行判断。

> **读计划的最好姿势 = 对比法**：同一条 SQL，改一件事（建索引 / 换写法）前后各 `EXPLAIN` 一次，只盯 `/* */` 的变化。

### 例 3：走索引 + 免排序（ORDER BY ... LIMIT）

```text
PLAN
SELECT
    "id",
    "code"
FROM "public"."s6_lab"
    /* public.idx_s6_lab_code */
ORDER BY 2
FETCH FIRST 10 ROWS ONLY
/* index sorted */
```

| 行 | 含义 |
|---|---|
| `SELECT` 只有 2 列 | 你只选了 `id, code`（和例 1/2 的 `*` 不同） |
| `/* public.idx_s6_lab_code */` | 走索引，但**冒号后没有条件**——说明索引这次不负责过滤（没有 WHERE），只负责**提供顺序** |
| `ORDER BY 2` | 按"第 2 个输出列"（= `code`）排序——数据库内部用列序号简写 |
| `FETCH FIRST 10 ROWS ONLY` | 你的 `LIMIT 10` 的标准 SQL 形态 |
| `/* index sorted */` | ★ **排序由索引顺序直接提供**，没有额外排序步骤。索引本身就是有序的 → 按序读 10 行就停 |

> **注释有无冒号条件 = 索引的不同角色**：`idx: 条件` → 索引在**过滤**；只有 `idx` → 索引在**供排序**。

### 例 4：LIKE 前缀改写（本课最漂亮的一段）

```text
PLAN
SELECT
    "public"."s6_lab"."id",
    "public"."s6_lab"."code",
    "public"."s6_lab"."created_at"
FROM "public"."s6_lab"
    /* public.idx_s6_lab_code: code >= 'CODE-5'
        AND code < 'CODE-6'
     */
WHERE "code" LIKE 'CODE-5%'
```

- `WHERE` 行仍显示你写的 `LIKE 'CODE-5%'`（**复述原句**）；
- 但注释里实际执行的条件变成了 **`code >= 'CODE-5' AND code < 'CODE-6'`**——数据库把前缀 LIKE **重写成了范围查询**：
  - `'CODE-5%'` = "以 CODE-5 开头的所有串"；
  - 索引有序 → 它们在树上排成连续一段，起点 `'CODE-5'`，终点是下一个前缀 `'CODE-6'`；
  - `'CODE-6'` 本身不匹配（所以是 `<` 而不是 `<=`）。
- 对比练习 4（`LIKE '%5000'`，没有字头 → 无法切段 → `tableScan`）：**一正一反，字头原理实锤**。

### 读计划心法（四步）

1. 先找 `/* ... */` —— 判决书都在注释里；
2. `表名.tableScan` = 全表扫；`索引名` = 走索引；
3. 索引名后**有冒号条件** = 索引在过滤；**只有名字** = 索引在供排序；
4. 最后找 `/* index sorted */` —— 有它 = 排序也省了。

## 五、索引失效的四大经典场景（前两个已实测）

### ① 前置通配符 `LIKE '%xxx'` —— 实测失效

```sql
EXPLAIN SELECT * FROM s6_lab WHERE code LIKE '%5000';
-- 实测：/* public.s6_lab.tableScan */ ← 索引白建了
```

**为什么**：索引按"字头"排序（像字典）。`'%5000'` 是"任何结尾"，字典不知道从哪翻起，只能整本翻。**后置通配符 `'CODE-5%'`（有字头）才有可能用索引**——具体以你的 EXPLAIN 输出为准。

### ② 对索引列做函数/运算 —— 实测失效

```sql
EXPLAIN SELECT * FROM s6_lab WHERE LOWER(code) = 'code-5000';
-- 实测：/* public.s6_lab.tableScan */ ← 索引用不上
```

**为什么**：索引存的是 `code` 原值，不是 `LOWER(code)` 的结果。要对列"做点什么"再比，数据库只能把每一行都算一遍。

**同类陷阱**：`WHERE YEAR(created_at) = 2026`、`WHERE priority + 1 = 5`。
**改写心法**：把运算挪到"值的另一侧"——

```sql
-- ✗ 函数包住索引列
WHERE YEAR(created_at) = 2026
-- ✓ 索引列裸露，条件变成范围
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
```

### ③ `OR` 连接了非索引列

`WHERE status = 'COMPLETED' OR title LIKE '%AI%'`——`title` 没索引，整条走全表扫。改写思路：拆成两条查询 UNION，或给高频 OR 列补索引。

### ④ 隐式类型转换

`WHERE task_no = 123`（task_no 是 VARCHAR）→ 数据库要逐行把字符串转成数字再比，索引失效。**类型对齐**：字符串列比较就用字符串值。

### ★ 总口诀：索引列必须"裸着"出现在比较的一侧

索引是给"**索引列本身**"准备的目录——只要列被函数包住、被运算包住、被通配符包住字头，目录就失效。

## 五·补、索引类型全景 + 执行计划的价值（2026-10-18 应学员提问增补）

### A. 索引按「结构」分（决定它能服务什么查询）

| 类型 | 擅长 | 不擅长 | 前端类比 | 谁提供 |
|---|---|---|---|---|
| **B-tree**（本课/本项目主角） | 等值 + **范围** + **排序** | — | 有序字典 | MySQL/PG/H2 默认全是它 |
| **哈希** | **只有等值**（O(1) 定位） | 范围、排序 | `Map.get()` | MySQL（MEMORY 表 / 自适应哈希）、PG `USING HASH`、H2 `CREATE HASH INDEX` |
| **全文（倒排索引）** | 文本分词搜索 | 精确/范围 | 搜索引擎 | MySQL FULLTEXT、PG GIN、ES |
| **空间（R-tree/GiST）** | 地理位置范围 | 普通列 | 地图"附近的人" | MySQL SPATIAL、PG GiST |
| **位图 bitmap** | 低基数（取值少）列的过滤 | 高并发写 | 课表"谁选了这门课" | Oracle；PG 的 Bitmap Scan 是执行策略 |

> **H2 实测补充**：`CREATE HASH INDEX idx ON t(code)` 语法在 H2 2.3.232 可用；但实测范围查询（`code > 'CODE-5000'`）**也显示使用该索引**——这是 H2 存储引擎的实现细节，**不能外推**。MySQL/PG 的哈希索引明确只支持等值。**某库真实行为 = 该库文档 + 本库 EXPLAIN 实测**。

### B. 索引按「组织/使用方式」分（不是结构类型，但常被混着说）

| 概念 | 一句话 | 关键点 |
|---|---|---|
| **聚簇索引** Clustered | 行数据按索引键**物理排序**存放（InnoDB 的主键索引 = 表本身） | 一张表只能有一个 |
| **二级索引** Secondary | 独立结构，叶子存主键；查其他列要"**回表**" | InnoDB 常识 |
| **覆盖索引** Covering | 查询所需列**全在索引里** → 不用回表 | 纯性能红利 |
| **复合（联合）索引** | 多列合成一个 B-tree，**最左前缀**原则 | 电话簿按"姓+名"排：按姓能查，只按名查不了 |
| **唯一索引** | S5 学过：约束 + 索引一体两面 | |
| **表达式索引** | 对函数结果建索引（PG：`CREATE INDEX ON t (LOWER(code))`） | **专治第五节的"函数包列失效"** |
| **部分索引** Partial | 带 `WHERE` 的索引（PG） | 只索引"关心的子集" |

**最左前缀实测**（H2 2.3.232）：`CREATE INDEX idx_ih_status_code ON ih(status, code)` 后，`WHERE status = 'A'`（只命中第一列）照样走 `idx_ih_status_code`；若只写 `WHERE code = ?`（跳过最左列），一般就用不上了。

### C. 执行计划到底能干嘛（五个用途）

**本质**：SQL 是声明式的（S1）——"要什么"你定，"怎么做"由数据库定。**执行计划 = 数据库做决策的账本**；它展示的是**它选的路径**，不是你的意图。

1. **验索引**：走没走、走的哪个（本课主体）——别猜，看 `/* */`；
2. **找慢查询病因**：`tableScan`、无索引的连接、额外排序——慢的根源都写在计划里；
3. **A/B 对比写法**：同一需求两种 SQL（子查询 vs JOIN、OR vs UNION）各跑一次，挑计划好的；
4. **量化扫描量**：`EXPLAIN ANALYZE` 真跑并给实际数据——实测等值查询输出 `/* scanCount: 2 */`（只扫 2 行，不是 10000）；
5. **预判增长风险**：计划随数据量变化（见本课第一节实测：15 行 vs 10000 行），上线前评估。

**⚠️ 两个命令的安全边界**：

| 命令 | 执行吗 | 用途 |
|---|---|---|
| `EXPLAIN` | **不执行**，只出方案 | 安全，随便跑 |
| `EXPLAIN ANALYZE` | **真执行一遍** | 量化实际扫描/耗时；**UPDATE/DELETE 上慎用**（真会改数据） |

**排障工作流**：慢查询 → `EXPLAIN` 看计划 → 改索引 / 改写 SQL（挪运算、去前置通配符、拆 OR）→ **再 `EXPLAIN` A/B 对比** → `EXPLAIN ANALYZE` 量化收尾。

## 六、数据量小的时候，优化器用不用索引？

**讲义初版预判**："15 行小表很可能会 tableScan"——**2026-10-18 实测推翻了它**：

```text
-- research_task 只有 15 行，实测仍然走索引！
FROM "public"."research_task"
    /* public.idx_research_task_status: status = 'COMPLETED' */
WHERE "status" = 'COMPLETED'
```

**结论修正**：小表是否放弃索引是**各数据库优化器的自由**（取决于统计信息与代价模型），H2 2.3.232 即使 15 行也选索引；MySQL/PG 的行为可能不同、且随数据量变化。

**唯一可靠的做法：跑 `EXPLAIN` 看输出，不凭经验预判**——这也是本课反复出现的"查证 > 记忆"（连讲义的预判都被实测打脸，入档为证）。

## 八、动手练习（H2 控制台；全部 SQL 已实测可跑）

```sql
-- 练习 1：造 10000 行实验表（ROW_NUMBER 造序，避开 SYSTEM_RANGE 的 X 列大小写坑）
CREATE TABLE IF NOT EXISTS s6_lab (
    id UUID PRIMARY KEY,
    code VARCHAR(32),
    created_at TIMESTAMP WITH TIME ZONE
);
INSERT INTO s6_lab (id, code, created_at)
SELECT RANDOM_UUID(), 'CODE-' || CAST(ROW_NUMBER() OVER () AS VARCHAR), CURRENT_TIMESTAMP
FROM SYSTEM_RANGE(1, 10000);
SELECT COUNT(*) FROM s6_lab;   -- 预期 10000

-- 练习 2：无索引等值查询
EXPLAIN SELECT * FROM s6_lab WHERE code = 'CODE-5000';
-- 预期：/* public.s6_lab.tableScan */

-- 练习 3：建索引后再看
CREATE INDEX IF NOT EXISTS idx_s6_lab_code ON s6_lab(code);
EXPLAIN SELECT * FROM s6_lab WHERE code = 'CODE-5000';
-- 预期：/* public.idx_s6_lab_code: code = 'CODE-5000' */

-- 练习 4：前置通配符失效
EXPLAIN SELECT * FROM s6_lab WHERE code LIKE '%5000';
-- 预期：tableScan

-- 练习 5：函数作用于列失效
EXPLAIN SELECT * FROM s6_lab WHERE LOWER(code) = 'code-5000';
-- 预期：tableScan

-- 练习 6：ORDER BY 免排序
EXPLAIN SELECT id, code FROM s6_lab ORDER BY code LIMIT 10;
-- 预期：/* public.idx_s6_lab_code */ + /* index sorted */

-- 练习 7（自己探）：后置通配符能不能走索引？以你的输出为准
EXPLAIN SELECT * FROM s6_lab WHERE code LIKE 'CODE-5%';

-- 练习 8（对比真实表）：15 行的 research_task，观察优化器的选择
EXPLAIN SELECT * FROM research_task WHERE status = 'COMPLETED';
EXPLAIN SELECT id, task_no, title FROM research_task ORDER BY created_at DESC LIMIT 10;
-- 2026-10-18 实测：两条都走索引（status 索引 / created_at 索引 + index sorted）
-- ★ 讲义初版预判"15 行可能 tableScan"被推翻——优化器行为以 EXPLAIN 为准（第六节已修正）

-- 练习 9：清理
DROP TABLE IF EXISTS s6_lab;
```

**验收标准**：
1. 练习 2 与 3 的对比能指着 `/* ... */` 说出"走没走索引"；
2. 练习 4/5 能解释"为什么索引失效"（字头 / 函数包住列）；
3. 练习 6 能看到 `index sorted` 并说出"免排序"的含义；
4. 练习 8 的实测结果能正确解释（走索引 ≠ 数据量小就没用）。

| ③ 建索引后同句 | `/* public.idx_s6_lab_code: code = 'CODE-5000' */` | ✅ 只差一行注释，对比法成立 |
| ④ `LIKE '%5000'` | `tableScan` | ✅ 前置通配符失效 |
| ⑤ `LOWER(code) = ...` | `tableScan` | ✅ 函数包住索引列失效 |
| ⑥ `ORDER BY code LIMIT 10` | `idx_s6_lab_code` + `ORDER BY 2` + `FETCH FIRST 10 ROWS ONLY` + `/* index sorted */` | ✅ 走索引且免排序 |
| ⑦ `LIKE 'CODE-5%'` | ★ 计划改写成 `code >= 'CODE-5' AND code < 'CODE-6'`，走索引 | ✅ **字头原理的数学形态实锤**（与④正反对照） |
| ⑧ 真实表 15 行对比 | `status` 查询走 `idx_research_task_status`；`ORDER BY created_at DESC LIMIT 10` 走索引 + `index sorted` | ✅ **推翻讲义初版预判**（详见深挖二） |
| ⑨ DROP 清理 | 执行成功 | ✅ |

### ★ 深挖一：练习⑦ 揭开"字头"的底牌

```text
/* public.idx_s6_lab_code: code >= 'CODE-5'
    AND code < 'CODE-6'  */
WHERE "code" LIKE 'CODE-5%'
```

数据库把**前缀 LIKE 重写成范围查询**：所有以 `'CODE-5'` 开头的串在有序索引上排成连续一段，起点 `'CODE-5'`、终点下一个前缀 `'CODE-6'` 之前（`<` 不含 `'CODE-6'` 本身）。

**这就是"有字头能查目录、没字头只能整本翻"的数学形态**——练习④（`'%5000'`，无段可切 → tableScan）与练习⑦一正一反，原理彻底闭环。

### ★ 深挖二：三笔"实测打脸讲义"的入档记录（查证 > 记忆，连讲义也不例外）

1. **S5**：元数据列名 `TYPE_NAME`/`COLUMN_TYPE` 连猜两次皆错，真连 h2 jar 才查出 `DATA_TYPE`；
2. **S6 第六节**：讲义初版预判"15 行小表很可能 tableScan"——实测 `research_task`（15 行）**仍然走索引**。结论修正为：小表是否放弃索引是各优化器的自由，**以 EXPLAIN 输出为准，不凭经验预判**；
3. **S6 讲义全篇的正确姿势**：EXPLAIN 输出格式**先实测再落笔**（`tableScan` / 索引名+条件 / `index sorted` 三形态全部来自真实执行），因此讲义里没有"大概长这样"——这是反面教训换来的正面执行。

### ★ 深挖三：读计划心法四步（沉淀）

1. 先找 `/* ... */`（判决书）；
2. `表名.tableScan` = 全表扫；`索引名` = 走索引；
3. 索引名**后有冒号条件** = 索引在过滤；**只有名字** = 索引在供排序；
4. 最后找 `/* index sorted */` —— 有 = 排序也省了。

## 附、五问速答卡（2026-10-18 应学员"都答不上来"直接给的答案）

**① 哈希索引为什么做不了范围查询？**
哈希把键算成"格子编号"直接跳过去——只保留"键 → 位置"，**丢掉了顺序**；范围查询的灵魂就是顺序。
类比：哈希 = 快递柜（有取件码能开格，但格子无先后，没法要"5000~6000 号的包裹"）；B-tree = 图书馆书架（按编号有序，区间直接走过去拿）。

**② `EXPLAIN` vs `EXPLAIN ANALYZE`？**
前者只看作战计划**不执行**（出发前看导航）；后者**真跑一遍**再给实际数据（开一趟回来读行车记录，如 `scanCount`）。⚠️ `EXPLAIN ANALYZE` 会真执行，UPDATE/DELETE 上慎用。

**③ 复合索引 `(status, code)`，为什么只按 `code` 查用不上？**
复合索引是**多级排序**：先按 status 排，相同才按 code 排——跳过第一级就找不到入口。
类比：电话簿按"姓+名"排；你只知道名"伟"不知姓，每个姓下面都可能有"伟"，只能一段段翻完 = 全表翻。
规则：**必须从最左列开始连续用**——`(status)` ✓ / `(status, code)` ✓ / 只有 `(code)` ✗。

**④ B-tree 为什么能免排序？**
数据在索引里**本身就按该列有序**；`ORDER BY 索引列` 要的顺序 = 索引的物理顺序，顺着读即可。
反例：`ORDER BY 无索引列` 必须把所有行取出再重排一遍（数据量大极贵）。

**⑤ `/* idx: 条件 */` 与 `/* idx */`（无冒号）区别？**

| 形态 | 索引的角色 |
|---|---|
| `/* idx: code = 'x' */` **有冒号** | **筛子**——用索引直接定位符合 WHERE 的行 |
| `/* idx */` **无冒号**（常配 `index sorted`） | **排序器**——无过滤条件，只按索引顺序供 ORDER BY |

看懂计划先分这两类角色，骨架就抓住了。
