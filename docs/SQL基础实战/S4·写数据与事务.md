# S4 · 写数据与事务（INSERT / UPDATE / DELETE + 事务）

> **本课目标**：从"只读"升级到"会写"——INSERT 的列值对应、UPDATE/DELETE 的 WHERE 血案、事务的草稿箱模型、乐观锁 UPDATE（场景②的原理）。
> **教材**：`backend/src/main/resources/mapper/TaskEventLogMapper.xml` 的 `insert`（项目在跑的写 SQL）
> **前置**：S1（WHERE）、S3（COUNT）
> **⚠️ 本课纪律**：前 three 课错了顶多查不出来，本课错了会**真改真删数据**——所有练习按讲义顺序做，危险实验必须在事务保护下进行。

---

## 一、前端类比：三种写 = 三种请求

| SQL | 干什么 | 前端类比 |
|---|---|---|
| `INSERT INTO` | 新增一行 | `POST /api/tasks`（创建资源） |
| `UPDATE ... SET` | 改已有行 | `PUT /api/tasks/{id}`（更新资源） |
| `DELETE FROM` | 删行 | `DELETE /api/tasks/{id}` |

查（SELECT）是"拿数据"，写（INSERT/UPDATE/DELETE）是"改数据"——**改错不可撤销**（除非有事务，见第五节），所以写比查危险一个量级。

## 二、INSERT：项目教材逐行精读

`TaskEventLogMapper.xml` 第 8–19 行（项目每次任务事件都在跑这条）：

```sql
INSERT INTO task_event_log (id, task_id, step_id, event_type, event_message,
                            event_payload, operator_type, operator_id, created_at)
VALUES (#{id}, #{taskId}, #{stepId}, #{eventType}, #{eventMessage},
        CAST(#{eventPayload, typeHandler=...} AS JSON),
        #{operatorType}, #{operatorId}, #{createdAt})
```

| 片段 | 人话 |
|---|---|
| `INSERT INTO 表 (列清单)` | 声明"要往哪些列写"——**列的顺序就是后面值的顺序** |
| `VALUES (值清单)` | 与列清单**一一对应**（数量、顺序都不能错） |
| `#{id}` | MyBatis 参数占位符——**预编译**，详见下方「SQL 注入与预编译」 |
| `CAST(... AS JSON)` | 把 Java 对象序列化后的文本，转成数据库 JSON 类型存入 |
| 主键 `id` 由 Java 生成 | **不是数据库自增**——Service 层先生成 UUID 再传入（`RANDOM_UUID()` 思路相同） |

**三个规则**：

1. **没写的列 = 填默认值或 NULL**：`step_id` 没在 VALUES 给值就是 NULL（它是可空列，合法）；若漏了 NOT NULL 且无默认值的列，直接报错；
2. **可以只写部分列**——前提是其余列"可空或有默认"；
3. **批量插入**：`VALUES (...), (...), (...)` 一条语句插多行（比循环单插快得多）。

### ★ SQL 注入与预编译（2026-10-16 应学员提问增补；S1 逐行翻译漏了 `#{status}`，在此补齐）

**`#{}` 是什么**：MyBatis 的参数占位符，工作方式是**模板和参数分开两次发送**：

```text
第 1 次发送（骨架）：SELECT ... FROM research_task WHERE status = ?    ← 结构已编译锁死
第 2 次发送（值）  ：参数 'RUNNING'                                    ← 只当"值"填进 ? 的位置
```

**先看反面——字符串拼接 SQL 为什么会出事**（SQL 注入 = 后端版的 XSS）：

```java
// 危险写法：用户输入直接拼进 SQL
String sql = "SELECT * FROM users WHERE name = '" + userInput + "'";
```

攻击者输入 `' OR '1'='1`，拼出来的 SQL：

```sql
SELECT * FROM users WHERE name = '' OR '1'='1'   -- 恒真 → 全表泄露！
```

更狠的输入 `'; DROP TABLE users; --` 直接删库。**用户输入被当成了 SQL 代码执行**——和前端 XSS（用户输入 `<script>` 被当 HTML 执行）是同一个错误模式。

**预编译为什么能防**：数据库先编译 `WHERE name = ?` 这个**骨架**——`?` 的位置从编译那一刻起就定性为"一个值"，语法结构锁死。之后传来的任何内容**只能被当作值**，永远不会再被解析成 SQL 代码。攻击者输入的 `' OR '1'='1` 整个成为"名字的值"，匹配不到任何行，攻击落空。

**前端对照记忆**：

| 后端 | 前端 | 后果 |
|---|---|---|
| 字符串拼接 SQL | `innerHTML = userInput` | XSS / 注入 |
| 预编译参数 `#{}` | `textContent = userInput` | 永远当文本，安全 |

项目里所有 mapper 的 `#{xxx}` 都是预编译写法——**永远不要用 `${xxx}`**（MyBatis 的字符串替换占位符，等价于拼接，注入口）。

## 三、UPDATE：改行 + WHERE 是保命绳

```sql
UPDATE research_task
SET priority = 5, updated_at = CURRENT_TIMESTAMP
WHERE id = '某个任务id';
```

- `SET 列 = 值`：要改什么（可多列，逗号分隔）；
- `WHERE`：改**哪些行**——**忘 WHERE = 全表每行都改**，血案第一现场。

**项目真实用法：乐观锁 UPDATE**（场景②的原理）：

```sql
UPDATE research_task
SET priority = 9, version = version + 1
WHERE id = '某id' AND version = 0;   -- 双条件：id 对，且"我看到的版本"没被人动过
```

判断结果看**影响行数**：

- `1 行受影响` → 改成功了，同时 version 变成 1；
- `0 行受影响` → **id 对但 version 对不上 = 有别人先改过了** → 拒绝覆盖，返回 409 冲突。

这就是"乐观锁"的全部：不加锁，提交时校验版本号，冲突靠影响行数发现。**同一个 UPDATE 跑两遍，第二遍必然 0 行**——版本号已经被第一遍抬走了。

## 四、DELETE：删行，一句话警告

```sql
DELETE FROM task_event_log WHERE id = '某id';   -- 删一行
DELETE FROM task_event_log;                      -- ✗ 删全表！（忘 WHERE）
```

**防护习惯**：DELETE/UPDATE 之前，先用**同样的 WHERE 跑一遍 SELECT（或 COUNT）**，确认要动的就是这几行，再执行写操作。`TRUNCATE TABLE` 是"清空全表"的快捷方式（更快但不可带 WHERE），生产环境见到的第一反应应该是报警。

## 五、事务：草稿箱模型（本课核心）

前端没有直接对应物，最接近的类比：**购物车结算**——扣库存、扣余额、生成订单，三步**必须同生共死**：任何一步失败，全部当没发生过。这就是事务（Transaction）。

```sql
SET AUTOCOMMIT FALSE;      -- 关掉"每句自动提交"，进入草稿模式（H2 写法）

UPDATE ...;                -- 草稿 1
DELETE ...;                -- 草稿 2
SELECT ...;                -- 自己看一眼草稿（只有你能看到，别人看不到未提交的修改）

COMMIT;                    -- 全部保存（正式生效）
-- 或
ROLLBACK;                  -- 全部丢弃（回到 SET AUTOCOMMIT FALSE 之前的样子）

SET AUTOCOMMIT TRUE;       -- 恢复自动提交
```

**三个关键认知**：

1. **原子性**：事务内的多条写语句是一个整体——COMMIT 一起生效，ROLLBACK 一起消失。没有"改了一半"这种状态；
2. **草稿可见性**：未 COMMIT 的修改只有当前连接看得见（其他连接/页面查到的还是旧数据）；
3. **项目对照**：`@Transactional`（场景②状态机、场景⑤审计）= Spring 框架替你管这套 BEGIN/COMMIT/ROLLBACK——方法正常返回 → 自动 COMMIT；抛异常 → 自动 ROLLBACK。你写注解，框架当事务管家（好莱坞原则又见面了）。

## 六、危险操作防护三板斧

1. **先 COUNT 后动手**：UPDATE/DELETE 的 WHERE 先拿来 `SELECT COUNT(*)`，数字不对不动笔；
2. **草稿模式试写**：拿不准就 `SET AUTOCOMMIT FALSE` 里先改，SELECT 检查，对再 COMMIT，不对 ROLLBACK；
3. **UPDATE 带版本号**：改共享数据用乐观锁写法（`AND version = ?`），把"覆盖别人"变成"0 行受影响"。

## 八、动手练习（H2 控制台，按顺序做）

```sql
-- 练习 1：INSERT——复刻项目 insert 的迷你版
-- 先抄一个真实任务 id：
SELECT id, title FROM research_task LIMIT 1;
-- 再插入一条手工事件日志：
INSERT INTO task_event_log (id, task_id, event_type, event_message, operator_type, created_at)
VALUES (RANDOM_UUID(), '把上面查到的id贴这里', 'MANUAL_TEST', 'S4 课堂实验事件', 'HUMAN', CURRENT_TIMESTAMP);
-- 验证：
SELECT event_type, event_message, created_at FROM task_event_log
WHERE task_id = '同一个id' ORDER BY created_at DESC LIMIT 3;

-- 练习 2：UPDATE + WHERE（安全的定点修改）
UPDATE research_task SET priority = 5 WHERE title = 'MQ Test';
-- 看"影响行数"提示；再 SELECT 验证：
SELECT title, priority FROM research_task WHERE priority = 5;

-- 练习 3：危险实验（事务保护下的"忘 WHERE 惨案"）——逐条执行！
SET AUTOCOMMIT FALSE;
UPDATE research_task SET priority = 99;                              -- 血案：没有 WHERE！
SELECT COUNT(*) FROM research_task WHERE priority = 99;              -- 15：全表遭殃确认
SELECT title, priority FROM research_task LIMIT 3;                   -- 亲眼看看 99
ROLLBACK;                                                            -- 全部丢弃
SELECT COUNT(*) FROM research_task WHERE priority = 99;              -- 0：复活确认
SET AUTOCOMMIT TRUE;                                                 -- 恢复自动提交

-- 练习 4：乐观锁 UPDATE（同一句跑两遍，看影响行数 1 → 0）
UPDATE research_task
SET priority = 9, version = version + 1
WHERE id = '挑一个任务的id' AND version = 0;
-- 再原样跑第二遍 → 影响行数 0（version 已被抬走）——这就是"乐观锁冲突"

-- 练习 5：DELETE 测试数据（清理练习 1 插入的日志）
DELETE FROM task_event_log WHERE event_type = 'MANUAL_TEST';
SELECT COUNT(*) FROM task_event_log WHERE event_type = 'MANUAL_TEST';  -- 0：删干净确认
```

**验收标准**：
1. 练习 1 能说出"列清单和值清单一一对应"以及主键为什么不是数据库生成的；
2. 练习 3 四个数字（15 → 15 → 0 → 恢复）能讲清 COMMIT/ROLLBACK 的原子性；
3. 练习 4 两次影响行数 1、0 能解释"第二遍为什么失败"；
4. 练习 5 删除后 COUNT = 0。
