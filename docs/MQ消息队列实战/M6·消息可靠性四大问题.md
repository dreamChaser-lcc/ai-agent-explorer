# M6 · 消息可靠性四大问题专题（丢失 / 重复 / 顺序 / 积压 + 一致性）

> **一课目标**：把 M4 的"三问"拆成可诊断的四个问题（+ 一个被忽略的第五问题：一致性），
> 每个问题：**现象 → 根因 → 方案 → 项目现状 → 验证实验**。
> **前置**：M1（概念）/ M3（offset·ISR·Rebalance）/ M4（acks·幂等·有序）
> **本课补的遗留**：场景⑥ 一直挂着的 ⬜「outbox / 事务消息」（第六节给出实现设计）。

---

## 一、四大问题总览（先看矩阵）

| 问题 | 你会看到的现象 | 一句话根因 | 主要对策 |
|---|---|---|---|
| **丢失** | 消息发了却没被处理 | 三处任一断了：生产未确认 / Broker 未落盘 / 消费未提交就失败 | acks=all + 多副本 + 处理后才提交 |
| **重复** | 同一任务被执行两次 | at-least-once + 重试/Rebalance/提交失败 | 生产幂等 + 消费幂等 |
| **顺序** | 取消跑在开始前 | 重试乱序 / 分区散落 / 并发消费 | key 收窄 + in.flight≤5 + 单分区串行 |
| **积压** | LAG 越涨越大 | 消费速率 < 生产速率 | 扩消费者（≤分区）/ 加分区 / 优化 / 降级 |
| **一致性** | 库里有单、消息没发（或相反） | 业务事务与消息发送不是一个原子操作 | **outbox 表 / 事务消息**（第六节） |

```text
★ 判断顺序：先看 LAG（是积压吗）→ 再看重复（幂等日志）→ 再看丢失（对账）→ 最后看一致性（对账+补偿）
```

## 二、问题 1：消息丢失（三个环节，逐个堵）

### 2.1 环节 1：生产端（发了但没到 Broker）

```text
坑：acks=0（发出去不管）/ 未重试 / 发送异常被吞
症状：日志有"已发送"，但 broker 端没有该消息（LOG-END-OFFSET 不增长）

堵法：
  acks=all + retries 大 + delivery.timeout.ms 兜底
  send 的回调要处理失败（不要 fire-and-forget）
```

```java
// ❌ 只记日志、不看结果（丢了不知道）
kafkaTemplate.send(topic, key, value);
log.info("[MQ] 已发送");

// ✅ 处理回调（失败可重试/告警/落库补偿）
kafkaTemplate.send(topic, key, value).whenComplete((r, e) -> {
    if (e != null) {
        log.error("[MQ] 发送失败 topic={} key={}", topic, key, e);
        // → 落 outbox 表重试 / 告警 / 标记任务失败（第六节）
    }
});
```

### 2.2 环节 2：Broker 端（收到了但没存住）

```text
坑：replicas=1（单副本，磁盘坏就丢）/ min.insync.replicas=1（acks=all 退化成 acks=1）
    / unclean.leader.election.enable=true（让落后副本当 leader）

堵法（生产）：replication.factor >= 3 + min.insync.replicas = 2
              + unclean.leader.election.enable = false

本项目：单节点开发环境（replicas=1）——可接受，生产必须 3 副本（M4 已讲）
```

### 2.3 环节 3：消费端（处理了但没提交 / 没处理就提交）

```text
坑 1：enable-auto-commit=true（poll 到就提交）→ 处理失败也不重投 → 丢
坑 2：catch 异常后静默 return（假装成功）→ 提交了 → 丢
坑 3：异步处理（丢给线程池后立即提交 offset）→ 处理还没完成就提交了 → 丢

堵法：ack-mode=record（处理成功才提交）+ 不吞异常 + 异步处理要等结果再提交（MANUAL）
```

**项目自检**：

```text
✅ ack-mode: record（M4 已修）
✅ 消费失败不 catch 吞掉（异常向上抛 → 不提交 → 重投）
⚠ executeTask 内部若把子步骤丢线程池且不等待 → 存在"提前提交"风险（M6 可检查）
```

### 2.4 丢失的验证实验

```powershell
# 思路：先用极短的 max.poll.interval.ms 制造"处理超时"，看消息是否重投（不丢）
# 或：消费端故意抛异常 → 看 LAG 是否持续（未提交 → 重投）
```

## 三、问题 2：消息重复（重复不可怕，不幂等才可怕）

### 3.1 重复的四个源头

```text
① 生产重试：ack 丢了 → 重发 → broker 收到两条（幂等生产者可解）
② Rebalance：分区易主 → 新消费者从上次 offset 重读
③ 提交失败：处理成功但 commit 抛异常 → 重投
④ 业务重放：人工重置 offset / 补偿脚本（本项目演示过 --from-beginning）
```

### 3.2 消费幂等的三种实现（按代价从低到高）

| 方案 | 做法 | 适用 |
|---|---|---|
| **状态守卫**（项目已用） | 终态任务直接跳过（shouldStop） | 天然幂等（状态机） |
| **唯一约束**（项目场景④） | 唯一索引 + 捕获 DuplicateKeyException | 插入型业务 |
| **幂等表** | (业务键, 消息id) 记录已处理，处理后插入 | 无法天然幂等的业务 |

```text
★ 幂等键选谁：
   · 消息自带业务 id（taskId）→ 用业务键
   · 没有 → 生产端带 UUID，消费端存"已处理 UUID"
```

### 3.3 项目实测回顾（场景⑥）

```text
重放 1 条已处理的消息 → 10ms 内被状态守卫拦下（日志："重复消费拦截"）
三次重放实验：消费零副作用 ✅
（详见 docs/业务场景实战/⑥异步升级Kafka.md）
```

## 四、问题 3：顺序（三个条件缺一不可）

```text
条件 1：生产端 max.in.flight.requests.per.connection <= 5 且 enable.idempotence=true
        （in.flight > 5 时，重试的第 1 条可能晚于第 2 条到达 → 乱序）
条件 2：同一业务键的消息进同一分区（key = taskId ✓）
条件 3：同一分区只被一个消费者串行处理（Kafka 天然保证）
```

**反例推演（如果 key 用随机值）**：

```text
消息 A（开始）→ hash 随机 → 分区 1
消息 B（取消）→ hash 随机 → 分区 0
消费者并行处理 → B 可能先于 A 执行 → 状态机被破坏（取消后又开始执行）
```

**项目的保序证据**：M3/M4 实测 20 条同 key 消息 → 全部进 partition 2（单分区串行）✓

## 五、问题 4：积压（LAG 治理）

### 5.1 诊断三看

```text
① LAG 曲线（持续涨 = 跟不上；突然涨 = 生产突增或消费者停）
② 消费者实例数 vs 分区数（实例 < 分区 → 有分区没人吃；实例 > 分区 → 有人闲着）
③ 单条处理耗时（用日志/监控：本项目 ≈ 2.7 秒/条实测）
```

### 5.2 四手段（M4 已讲，这里给决策树）

```text
LAG 涨 → 实例数 < 分区数？ ──是──→ 扩实例（到分区数为止）
                            └─否─→ 单条耗时能降？ ──能──→ 优化/拆分/并行子任务
                                                 └─不能─→ 加分区（接受 key 落点变化）
                                                          └─还不够→ 降级/采样/死信人工
```

### 5.3 本项目实测（M4 数据）

```text
灌 20 条 → LAG 20 → 17（8 秒处理 3 条，≈2.7s/条）
说明：长任务消费慢是【设计使然】，需要靠"扩分区 + 扩消费者"或"拆分任务"提吞吐
```

## 六、★ 第五问题：一致性（outbox / 事务消息）——场景⑥ 的 ⬜ 遗留

### 6.1 问题本质

```text
业务写库（任务入库）与发消息是两个独立操作：
  · 先写库后发消息：库成功、发消息失败 → 有任务永远不执行（孤儿任务）
  · 先发消息后写库：消息发了、库回滚 → 消费者去执行不存在的任务
本项目现状：afterCommit（事务提交后才发）→ 解决"回滚了却发了"，
            但【发送失败】仍会丢（有任务没人执行）→ 需要 outbox 兜底
```

### 6.2 三种方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. afterCommit 直发**（现状） | 事务提交后同步发消息 | 简单，解决"回滚却发了" | 发送失败 = 丢失；无重试 |
| **B. 本地消息表 outbox**（推荐） | 消息先写库表（同事务）→ 后台任务扫表投递 → 标已发 | 不丢（表里有重试）；幂等友好 | 多一张表 + 投递器 + 延迟 |
| **C. Kafka 事务消息** | 生产端事务 + 消费端 read_committed | 链路内原子 | 复杂、性能降、只能覆盖 Kafka 内部 |

### 6.3 outbox 实现设计（本项目可直接落地）

**表结构**（与业务同库，同事务写入）：

```sql
CREATE TABLE task_outbox (
    id           UUID PRIMARY KEY,
    task_id      UUID NOT NULL,              -- 业务键
    event_type   VARCHAR(32) NOT NULL,       -- TASK_EXECUTION_REQUESTED
    payload      VARCHAR(512) NOT NULL,      -- 消息体（本项目 = taskId）
    status       VARCHAR(16) NOT NULL,       -- PENDING / SENT / FAILED
    retry_count  INT NOT NULL DEFAULT 0,
    create_time  TIMESTAMP WITH TIME ZONE NOT NULL,
    update_time  TIMESTAMP WITH TIME ZONE
);
CREATE INDEX idx_task_outbox_status ON task_outbox (status, create_time);
```

**写入（与业务同事务）**：

```java
@Transactional
public void createTask(...) {
    taskRepository.save(task);                      // 业务写库
    outboxRepository.save(TaskOutbox.pending(task)); // ★ 消息也写库（同一事务，要么都成功要么都失败）
}                                                   // 不再在事务里直接发 Kafka
```

**投递器（后台扫表 + 发送 + 标记）**：

```java
@Scheduled(fixedDelay = 1000)
public void dispatch() {
    List<TaskOutbox> pending = outboxRepository.findTop100ByStatusOrderByCreateTimeAsc(PENDING);
    for (TaskOutbox msg : pending) {
        try {
            kafkaTemplate.send(TOPIC, msg.getTaskId().toString(), msg.getPayload()).get(3, SECONDS);
            outboxRepository.markSent(msg.getId());      // 发送成功才标记
        } catch (Exception e) {
            outboxRepository.markRetry(msg.getId());     // 失败 → retry_count++，下一轮再试
        }
    }
}
```

**消费端幂等**：消息可能重复投递（SENT 标记失败时会重发）→ 消费侧已有三层守卫 ✓

**方案 B 的完整闭环**：

```text
业务事务（task + outbox 同时写）→ 提交成功
  → 投递器扫到 PENDING → 发 Kafka → 标记 SENT
  → 发送失败 → retry_count++ → 下轮重试（直到成功或告警）
  → 消费端三层守卫兜重复
= 不丢（表里有重试）+ 不重（幂等守卫）+ 最终一致
```

### 6.4 什么场景需要 outbox

```text
✅ 需要：任务不能丢、且允许秒级延迟（本项目"任务执行"就是）
❌ 不需要：可丢的埋点/日志类消息（afterCommit 直发足够）
```

## 七、四大问题 + 一致性速查表（一页带走）

| 问题 | 现象 | 根因 | 方案 | 项目现状 |
|---|---|---|---|---|
| 丢失 | 消息没被处理 | 生产未确认/Broker 单副本/消费提前提交 | acks=all + 多副本 + 处理后才提交 | ✅ 已配（单节点限开发） |
| 重复 | 任务执行两次 | 重试/Rebalance/提交失败 | 生产幂等 + 消费幂等 | ✅ 三层守卫 |
| 顺序 | 取消早于开始 | 重试乱序/分区散落 | key + in.flight≤5 + 单分区 | ✅ key=taskId |
| 积压 | LAG 涨 | 消费慢/实例少/分区少 | 扩实例→加分区→优化→降级 | ✅ 已配长任务三件套 |
| 一致性 | 有任务不执行 | 业务与消息非原子 | **outbox 表** | ⬜ 本课设计（待实现） |

## 八、自测题（答案）

```text
Q1 消费端"处理成功但 commit 失败"会造成什么？怎么兜？
Q2 为什么"生产端幂等"救不了"消费端重复"？
Q3 积压时加分区有什么副作用？什么情况下不能加？
Q4 outbox 方案里，消息为什么必须和业务写同一个事务？
Q5 什么时候可以不用 outbox（直接 afterCommit 发）？
```

### 答案

```text
Q1 消息会被重投（重复消费）；兜法 = 消费幂等（状态守卫/唯一约束/幂等表）。
Q2 幂等生产者只去重"生产端重试"（同 PID+分区+序列号）；Rebalance 重投/提交失败
   是另一条路径，必须在消费端兜。
Q3 副作用：key 哈希落点改变 → 同 key 历史消息可能分布到不同分区 → 顺序受影响；
   不能加的情况：业务强依赖分区内顺序且无法容忍迁移乱序（需停写迁移或双写过渡）。
Q4 为了保证"业务成功 ⇔ 消息存在"的原子性：同事务写 → 要么都成功（消息必会被投递）
   要么都失败（不留孤儿任务），避免"库有单、消息没有"。
Q5 消息可丢且延迟敏感时（埋点/日志/统计）；或已有其他补偿机制（对账任务）。
```

## 九、一句话

```text
丢失 = 三个环节逐个堵（acks + 副本 + 处理后才提交）
重复 = 不怕重，怕不幂等（生产幂等 + 消费幂等）
顺序 = key 收窄 + in.flight≤5 + 单分区串行
积压 = 扩实例（≤分区）→ 加分区 → 优化 → 降级
一致性 = 消息和业务写同一个事务（outbox），投递器负责重试 —— 这才叫"不丢"
```
