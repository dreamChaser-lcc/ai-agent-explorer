# M7 · 选型与架构决策（Kafka vs RabbitMQ vs RocketMQ）

> **一课目标**：给得出"这个场景该用哪个 MQ"的答案，并能说清理由（面试高频 + 架构决策必备）。
> **前置**：M1–M6 全部（本课是收网）
> **产出一张决策树 + 本项目结论**

---

## 一、三者定位一句话

```text
Kafka     = 高吞吐的【事件流平台】（分区日志，可回放，大数据生态）
RabbitMQ  = 灵活路由的【消息中间件】（Exchange 路由 + DLX + TTL 延迟，业务消息）
RocketMQ  = 阿里系【业务消息中间件】（事务消息 + 顺序消息 + 延迟消息，Kafka 的"业务化改良"）
```

## 二、硬指标对比表（选型看这些）

| 维度 | Kafka | RabbitMQ | RocketMQ |
|---|---|---|---|
| 吞吐（单机） | **十万~百万/秒** | 万级/秒 | 十万级/秒 |
| 延迟 | 毫秒~几十毫秒（批量刷盘） | **微秒~毫秒** | 毫秒 |
| 消息模型 | 分区日志（Pull） | 队列（Push） | 队列（Pull） |
| 消息保留 | **按时间/大小保留，可重放** | 消费即删（无重放） | 保留（可回溯） |
| 顺序 | 分区内有序 | 队列内有序 | 分区内有序 |
| 路由能力 | 弱（Topic/key） | **强（4 种 Exchange）** | 中（Tag 过滤） |
| 延迟消息 | ❌ 需自造 | **✅ TTL+DLX** | **✅ 原生（18 级）** |
| 事务消息 | ✅（生产端事务） | ❌（需 outbox） | **✅ 原生（半消息+回查）** |
| 消息回溯 | ✅ 重置 offset | ❌ | ✅ |
| 运维复杂度 | 高（分区/ISR/Rebalance） | 中 | 中高 |
| 社区/生态 | **最大**（大数据全家桶） | 大（Spring 生态好） | 国内大厂多 |
| 适用规模 | 大数据量、事件流 | 业务消息、中小吞吐 | 电商/金融交易类 |

## 三、决策树（按问题顺序问自己）

```text
Q1 消息需要"重放历史"吗？（回放、补偿、事件溯源）
   ├─ 需要 → Kafka（唯一原生支持，重置 offset 即可）
   └─ 不需要 → Q2

Q2 需要"延迟消息"（如 30 分钟自动关单）吗？
   ├─ 需要 → RabbitMQ（TTL+DLX 最省事）或 RocketMQ（原生）
   └─ 不需要 → Q3

Q3 需要"复杂路由"（一条消息按规则进不同队列/多种消费者各取所需）吗？
   ├─ 需要 → RabbitMQ（4 种 Exchange）
   └─ 不需要 → Q4

Q4 吞吐量级？（单条消息大不大、峰值多高）
   ├─ 十万+/秒 或 大数据管道 → Kafka
   ├─ 万级/秒 业务消息 → RabbitMQ 足够
   └─ 电商交易（要事务消息/顺序/延迟全家桶）→ RocketMQ

Q5 团队熟悉度 / 运维成本？
   └─ 已有一套生态就用熟悉的（避免为选型而选型）
```

## 四、场景映射表（一眼选型）

| 业务场景 | 推荐 | 理由 |
|---|---|---|
| 日志采集 / 埋点上报 / 监控指标 | **Kafka** | 高吞吐 + 顺序 + 可回放 |
| 大数据管道（Flink/Spark 上游） | **Kafka** | 生态标准 |
| **任务异步执行**（本项目场景⑥） | **Kafka** | 只发轻消息 + 需要回放/重试 + 量不大但要求可靠 |
| 订单 30 分钟未支付自动关闭 | **RabbitMQ** | 延迟消息原生（TTL+DLX） |
| 一条事件通知多个系统（订单创建→库存/积分/物流） | **RabbitMQ** | fanout/topic 路由，加消费者零改动 |
| 电商交易（下单/扣库存/支付） | **RocketMQ** | 事务消息 + 顺序消息 + 延迟 |
| 削峰填谷（秒杀下单） | **Kafka/RocketMQ** | 高吞吐排队 |
| RPC 异步化（调用第三方慢接口） | **RabbitMQ** | 低延迟 + 简单路由 |
| 事件溯源（状态由事件重建） | **Kafka** | 分区日志天生适合 |

## 五、常见反模式（选错的代价）

```text
❌ 用 Kafka 做延迟队列：
   自造"延时 topic + 定时扫描"，扫描间隔决定精度（秒级抖动）+ 复杂度高
   → 简单需求用 RabbitMQ 一条 TTL+DLX 就解决

❌ 用 RabbitMQ 做日志采集：
   消费即删、无回放 → 丢一条就永久丢；万级吞吐撑不住埋点洪峰
   → 日志/埋点必须 Kafka

❌ 为"路由灵活"上 Kafka 多 topic：
   每个消费者一个 topic → topic 数量爆炸（元数据/连接开销）
   → 需要广播/路由就用 RabbitMQ，或一个 topic 多消费组（Kafka 的正确广播姿势）

❌ 单节点 Kafka 上生产：
   replicas=1 → 磁盘坏就丢；单 broker 无高可用（本项目刻意标注"开发环境"）

❌ 事务消息当万能药：
   跨系统一致性最好用 outbox（M6），Kafka 事务只覆盖其内部链路
```

## 六、本项目结论（为什么是 Kafka，什么时候引入 RabbitMQ）

**现状：只用 Kafka（场景⑥）**

```text
用 Kafka 的理由（逐条对上场景）：
  ① 任务执行是"事件流"：提交 → 异步执行 → 状态推进（天然事件模型）
  ② 轻消息 + 需要回放：出问题重置 offset 重放（调试/补偿方便）
  ③ 高可靠要求：acks=all + 幂等 + DLT（M4/M5 已配齐）
  ④ 与 Spring 集成成熟：@KafkaListener 已在项目跑通
  ⑤ 未来扩展（LLM 流式事件、审计流）天然适配 Kafka
```

**什么情况下应该引入 RabbitMQ？**

```text
① 需要延迟消息（如"任务 30 分钟未开始则自动取消"）—— Kafk a 自造成本高
② 需要复杂路由（一个事件要按类型分发到多条业务线）
③ 低延迟 + 简单任务分发（RPC 异步化场景，RabbitMQ 更轻）
★ 引入前提：先确认 Kafka 不能覆盖（避免"双 MQ"运维负担）
```

**一句话选型结论**：

```text
核心链路（任务执行）= Kafka（吞吐 + 回放 + 可靠）
延迟/路由类需求 = 未来按需引入 RabbitMQ（TTL+DLX 最合适）
```

## 七、面试高频问答（背这几条）

```text
Q：为什么选 Kafka 不选 RabbitMQ？
A：①需要回放/补偿（分区日志）②吞吐要求 ③已有事件流模型；
   反过来说：如果只要延迟队列/灵活路由，RabbitMQ 更合适（别硬上 Kafka）。

Q：Kafka 能做延迟消息吗？
A：不能原生做。要么自造（延时 topic + 定时扫描），要么用 RabbitMQ/RocketMQ。
   本项目延迟需求就用 RabbitMQ 或定时任务（CleanupScheduler 已在做类似事）。

Q：消息不丢怎么保证？
A：三端：生产 acks=all / Broker 多副本 / 消费处理后才提交；加 outbox 兜"发消息失败"。
   见 M4/M6。

Q：Kafka 的 Rebalance 是什么，怎么减少？
A：分区重新分配（消费者增减/超时触发，整组 STW）；减少：调大 max.poll.interval、
   控制 max-poll-records、用 CooperativeSticky 分配器、避免频繁启停。

Q：Kafka 事务能解决"消息与数据库一致性"吗？
A：只能覆盖 Kafka 内部链路（produce 原子），跨系统（DB + MQ）要用 outbox（M6）。
```

## 八、自测题（答案）

```text
Q1 日志采集为什么必须 Kafka？
Q2 30 分钟未支付关单用哪个 MQ？怎么实现？
Q3 一条"订单创建"要通知 5 个系统，Kafka 和 RabbitMQ 各怎么做？哪个更合适？
Q4 为什么"单节点 Kafka 上生产"是反模式？
Q5 本项目未来什么需求会促使引入 RabbitMQ？
```

### 答案

```text
Q1 消费即删 + 无回放 + 万级吞吐撑不住洪峰；Kafka 高吞吐 + 保留可回放 + 生态标准。
Q2 RabbitMQ：TTL（x-message-ttl=30min）+ DLX（过期进目标队列）→ 消费者收"关单"消息。
   （RocketMQ 原生延迟也能做，但 RabbitMQ 最轻）
Q3 Kafka：一个 topic + 5 个消费组（各读各的 offset，广播）✓ 也行；
   RabbitMQ：fanout 交换机 + 5 个队列（物理广播）。
   数据量小、要路由/独立队列 → RabbitMQ 更直观；大数据量/已有 Kafka → 多消费组更省。
Q4 磁盘坏 = 数据直接丢；broker 挂 = 服务不可用（无副本可切换）；
   acks=all 在单副本下退化为 acks=1（M4 讲过）。
Q5 需要延迟消息（任务超时取消）或复杂路由（多业务线分发）时。
```

## 九、一句话

```text
没有最好的 MQ，只有最合适的：
要吞吐/回放/事件流 → Kafka；要路由/延迟/低延迟业务消息 → RabbitMQ；
要事务+顺序+延迟全家桶（电商交易）→ RocketMQ。
选型的本质：先问"消息要不要重放、要不要延迟、要不要路由"，答案自然浮现。
```
