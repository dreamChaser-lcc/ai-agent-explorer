## 一、MQ 是什么（一句话 + 邮局类比）

```text
函数调用（同步）：
  A 打电话给 B 说"帮我干活"，然后【握着电话等】
  → A 被 B 阻塞；B 忙/挂了，A 就失败

消息队列（异步）：
  A 去邮局【寄信】给"干活"信箱，然后立刻回去干别的
  → B 有空自己去信箱取信
  → A 不知道 B 是谁、什么时候干完、甚至 B 在不在——但它不关心
```

```text
★ 一句话：MQ = 把"函数调用"变成"投递信件"。
  发信方（Producer）→ 邮局/信箱（Broker）→ 收信方（Consumer）
```

**场景⑥ 就是这个类比的实证**：

```text
改造前（同步）：POST /api/tasks → 走完整个 LLM 长任务（6 秒）→ 才返回
改造后（MQ）：  POST /api/tasks → 发一条消息 → 立刻 201（40ms）
                消费者在后台慢慢执行（几分钟都行）——用户无感
```

## 二、三大价值（为什么要引入 MQ）

### 价值 1：异步（时间上的解耦）——缩短响应时间

```text
同步：响应时间 = 所有步骤之和（6 秒）
异步：响应时间 = 发消息的时间（40ms）
      剩下的活在消费者侧并行/异步完成
```

### 价值 2：解耦（空间上的解耦）——加消费者不用改生产者

```text
生产者只认"消息格式"，不知道谁消费、有几个消费者：
  · 今天只有 执行器 消费 → 明天加个"审计消费者" → 生产者代码【零改动】
  · 反例：如果生产者直接调三个服务的接口，加一个就要改一次
（场景⑥ 之后加审计/通知等消费者就是零改动的）
```

### 价值 3：削峰填谷——高峰期消息排队，消费端按能力消化

```text
秒杀/批量导入：瞬间 10 万请求 → 全部写进 Broker（很快）
消费者按自己的处理能力（比如 1000/秒）慢慢消费
→ 数据库/下游服务不会被瞬间打垮
（代价：响应延迟变大、可能积压——M6 讲积压治理）
```

## 三、通用概念词汇表（Kafka / RabbitMQ 对照）

> 学 MQ 最容易乱的就是"同一个概念，两套叫法"。先建立这张对照表，后面两课都靠它。

| 概念 | 通俗解释 | Kafka 里叫 | RabbitMQ 里叫 |
|---|---|---|---|
| **Broker** | 消息服务器（邮局） | Broker（集群） | Broker（节点） |
| **逻辑分类** | 消息按业务分组 | **Topic** | **Exchange**（按路由规则分发） + Queue |
| **存储单元** | 消息实际存放的地方 | **Partition**（分区：有序日志） | **Queue**（队列） |
| **订阅关系** | 谁来消费、怎么分 | **Consumer Group**（组内分摊、组间广播） | 队列绑定 + 多消费者分摊 |
| **消费位置** | 消费到哪了 | **offset**（客户端维护，可重置！） | 无 offset（消费即删） |
| **确认机制** | 消费成功怎么告诉 Broker | 自动/手动 **commit** offset | 手动/自动 **ACK** |
| **失败处理** | 处理不了的消息去哪 | 重试 Topic / Dead Letter Topic | **DLX**（死信交换机 + TTL） |
| **顺序** | 消息是否有序 | **分区内**有序（全局无序） | 队列内有序（需单消费者） |
| **消息保留** | 用完就删吗 | **按时间/大小保留**（日志，可重放！） | 消费确认后删除 |

```text
★ 三个最关键的差异（先记住，M3/M7 展开）：
  ① Kafka = 日志（消息保留、offset 可重放）；RabbitMQ = 队列（消费即删）
  ② Kafka 的顺序单位 = 分区；RabbitMQ 的顺序单位 = 队列
  ③ Kafka 的"广播"靠消费组；RabbitMQ 的"广播"靠 fanout 交换机
```

## 四、三种投递模型（谁收到消息）

```text
① 点对点（Queue）：一条消息【一个】消费者处理
   场景：任务分发（发一个执行消息，谁抢到谁干）——RabbitMQ 队列默认

② 发布订阅（Pub/Sub）：一条消息【所有订阅方】都收到一份
   场景：事件广播（"任务创建了" → 通知/审计/统计 都要知道）
   Kafka：不同 Consumer Group 各有一份（各读各的 offset）
   RabbitMQ：fanout 交换机 + 多个队列

③ 路由（Routing）：按规则分发到不同队列
   场景：按类型/优先级分流——RabbitMQ 的四种 Exchange（M2 详讲）
   Kafka 没有"路由"概念——用不同 Topic 表达
```

## 五、MQ 的代价（只讲好处会害了你）

```text
① 一致性难题：消息发送成功 ≠ 业务成功
   "任务入库了但消息没发出去"或"消息发了但事务回滚了"→ 数据不一致
   → 解法：outbox 表 / 事务消息 / 本地消息表（M6 专题，场景⑥ 的 ⬜ 遗留）

② 重复投递：绝大多数 MQ 默认【至少一次】（at-least-once）→ 消费方必须幂等
   → 场景⑥ 的"10ms 守卫"就是干这个的（实测拦下重放消息）

③ 顺序问题：并发消费 + 重试 = 乱序
   → 解法：分区键（同 key 进同分区）/ 单消费者 / 业务侧容忍

④ 运维成本：Broker 高可用、积压监控、死信处理、版本升级
⑤ 调试变难：链路从"一条调用栈"变成"生产者 → Broker → 消费者"
   → 所以场景⑥ 强调"消息链路铁证"（日志可追溯）
```

> 这三条（一致性 / 重复 / 顺序）+ 积压 = **M6·消息可靠性四大问题**的内容，本课先埋雷。

## 六、Kafka vs RabbitMQ（初对比，M7 详讲）

| 维度 | Kafka | RabbitMQ |
|---|---|---|
| 定位 | **高吞吐日志流**（事件流平台） | **灵活路由的消息中间件** |
| 吞吐 | 十万~百万级/秒 | 万级/秒（够业务用） |
| 延迟 | 毫秒~几十毫秒（批量刷盘） | 微秒~毫秒（更实时） |
| 消息模型 | 日志（保留 + offset 重放） | 队列（消费即删） |
| 路由能力 | 弱（Topic + 分区键） | **强**（4 种 Exchange + 死信 + TTL 延迟队列） |
| 典型场景 | 日志采集 / 事件流 / 大数据管道 / 高吞吐异步 | 业务任务分发 / 延迟队列 / RPC 异步化 / 复杂路由 |
| 本项目 | 场景⑥ 已用（任务执行异步化） | 待学（M2） |

```text
一句话：Kafka 是"日志流水账本"（能回放、量大）；RabbitMQ 是"邮局"（路由灵活、延迟低）。
```

### 7.1 生产者：只发 taskId 的"轻消息"

`application/service/TaskExecutionProducer.java`

```java
@Service
public class TaskExecutionProducer {

    /** Topic 名（消费者共用该常量——避免两处写死字符串漂移）。 */
    public static final String TOPIC = "research-task-execution";

    private final KafkaTemplate<String, String> kafkaTemplate;

    public TaskExecutionProducer(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    /** 发布"任务执行请求"消息（调用即返回——不等执行完）。 */
    public void publish(UUID taskId) {
        String payload = taskId.toString();
        kafkaTemplate.send(TOPIC, payload, payload); // send(topic, key, value)
        log.info("[MQ] 已发送任务执行消息 topic={} taskId={}", TOPIC, payload);
    }
}
```

**逐点讲解**：

```text
① send(topic, key, value) 三参数：key = taskId
   → Kafka 按 key 哈希分区 → 同一任务的消息永远进同一分区 → 分区内串行（顺序保障）
② 轻消息原则：只发 taskId，不带任务内容
   任务数据永远以数据库为准（"任务活在数据库里，消息只是敲门砖"）
   好处：消息小 + 消费时读到最新状态（不会拿旧快照执行）
③ 调用即返回：publish 不等执行完（这正是"异步"的实现点）
④ TOPIC 常量放这里、消费者引用同一个常量 → 改 topic 名只需改一处
```

### 7.2 Topic 定义：3 分区决定并发上限

`infrastructure/config/KafkaTopicConfiguration.java`

```java
@Configuration
public class KafkaTopicConfiguration {

    @Bean
    public NewTopic researchTaskExecutionTopic() {
        return TopicBuilder.name(TaskExecutionProducer.TOPIC)
                .partitions(3)  // 3 个分区：消费者并行度的上限
                                // 同 taskId 的消息按 key 哈希进固定分区——同任务有序
                .replicas(1)    // 开发环境单节点——副本数 1（生产集群需 >= 3）
                .build();
    }
}
```

**逐点讲解**：

```text
① partitions(3) = 最多 3 个消费者实例并行消费（消费组的并发上限）→ 想扩并发就加分区
② key 哈希决定分区：同 taskId 恒进同一分区 → 天然串行 + 有序
③ replicas(1) 开发单节点；生产 >= 3 才能在 broker 挂掉时不丢数据（M4 的 ISR 主题）
```

### 7.3 一致性第一道防线：事务提交后才发消息

`application/service/ResearchTaskControlService.java`（L121-131）

```java
/**
 * 事务提交后执行；无事务上下文则立即执行（场景⑨）。
 * afterCommit 回调保证：事务回滚时这里不会执行，
 * 从而避免"状态没落库、消息却发出去了"的幽灵副作用。
 */
private void runAfterCommit(Runnable action) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                action.run();   // ← 事务提交成功后，才真正发消息
            }
        });
    } else {
        action.run();           // 无事务上下文：直接执行
    }
}
```

调用处（同文件 L110-112）：

```java
if (approved) {
    runAfterCommit(() -> researchTaskOrchestrator.startExecution(taskId));
}
```

**逐点讲解**：

```text
① 为什么不能"事务里直接发消息"：
   事务回滚了，消息已经投递出去 → 消费者去执行一个"不存在的任务"
② afterCommit 注册在 Spring 事务同步回调上 → 只有 COMMIT 成功才触发
③ 这是【第一道防线】，不是完整方案：
   完整方案是 outbox 表（本地消息表）——消息和业务写同一事务，再由后台投递（M6）
④ 同类问题还有个反向：消息发出去了，但消费者处理失败 → 靠重试/死信（M6）
```

### 7.4 选路：ASYNC 走 MQ，SYNC 直接跑

`application/service/ResearchTaskOrchestrator.java`（L102-117）

```java
public void startExecution(UUID taskId) {
    ResearchTaskEntity task = loadTask(taskId); // 加载任务，校验是否存在

    if (task.getExecutionMode() == ExecutionMode.ASYNC) {
        // ★ 场景⑥：ASYNC 从"线程池"升级为"消息队列"——
        //   原来：researchTaskExecutor.execute(() -> executeTask(taskId))（进程内提交）
        //   现在：只【发一条消息】（秒回）——真正的执行由 TaskExecutionConsumer 消费后驱动
        taskExecutionProducer.publish(taskId);
        return;
    }

    // 同步模式：直接在当前线程执行，所有步骤跑完才返回
    executeTask(taskId);
}
```

**逐点讲解**：

```text
① 双模式并存：ASYNC（生产默认走 MQ）/ SYNC（测试、演示用，无 MQ 也能跑）
   —— 这就是"渐进式"：没 Kafka 时用 SYNC，有 Kafka 才开 ASYNC
② 线程池 Bean 没删，退居二线（保留给未来用途）——升级不是"推倒重来"
③ 返回 201 之后：前端通过 /api/tasks/{id}/stream（SSE）拿实时进度——异步不等于没反馈
```

### 7.5 消费者：敢在这里跑长任务的三层底气

`application/service/TaskExecutionConsumer.java`

```java
@Component
public class TaskExecutionConsumer {

    private final ResearchTaskOrchestrator researchTaskOrchestrator;

    public TaskExecutionConsumer(ResearchTaskOrchestrator researchTaskOrchestrator) {
        this.researchTaskOrchestrator = researchTaskOrchestrator;
    }

    /**
     * 消费"任务执行请求"——轻消息：只有 taskId；任务数据现场从数据库取（读到最新状态）。
     */
    @KafkaListener(topics = TaskExecutionProducer.TOPIC)
    public void onTaskExecutionRequested(String taskIdText) {
        log.info("[MQ] 收到任务执行消息 taskId={}", taskIdText);
        UUID taskId = UUID.fromString(taskIdText);
        researchTaskOrchestrator.executeTask(taskId); // 内部第一件事：状态守卫（shouldStop）
        log.info("[MQ] 任务执行消息处理完毕 taskId={}", taskIdText);
    }
}
```

**逐点讲解（为什么敢直接跑长任务）**：

```text
① 状态守卫：executeTask 内部先判断 shouldStop（暂停/取消/已完成 → 直接跳过）
② 分区串行：同一分区的消息不会被两个消费者同时处理（同任务天然不并发）
③ 至少一次 + 幂等消费 = 事实上的"恰好一次"效果（M6 核心公式）
④ @KafkaListener(topics = 常量) —— 与生产者共用常量，防字符串漂移
⑤ 长任务必须调大 max.poll.interval.ms（application.yml 已调到 1 小时）：
   否则单条消息处理超过 5 分钟 → Kafka 认为消费者死亡 → 重平衡 → 重复消费
```

### 7.6 幂等与防重：两处守卫

`application/service/ResearchTaskOrchestrator.java`（executeTask 内部）

```java
// ① 场景⑨：任务级分布式锁——拿不到锁直接跳过
//    （已有执行者在跑，重复执行没有意义）
Optional<String> lockToken = distributedTaskLock.tryLock(taskId);
if (lockToken.isEmpty()) {
    return;
}

// ② 状态守卫：任务已被暂停/取消/完成 → 跳过
if (shouldStop(task)) {
    return;
}

// ③ 步骤级守卫：步骤已完成 → 跳过（断点续跑/重复消费都不重复干活）
if (shouldStop(task) || step.getStatus() == StepStatus.COMPLETED) {
    return;
}
```

**逐点讲解**：

```text
① 锁防的是"并发重复执行"（两个消费者/两个实例同时跑同一任务）
② 状态守卫防的是"重复消费时的无效执行"（终态任务直接跳过——场景⑥ 10ms 守卫）
③ 步骤级守卫防的是"半途重放的重复劳动"（已完成步骤跳过 = 断点续跑）
④ 三层叠加 = 消费侧幂等（这才是 at-least-once 能安全工作的原因）
```

### 7.7 配置：长任务的关键参数（与项目真实配置一致）

`application.yml`（kafka 段，L33-49）

```yaml
spring:
  kafka:
    # 场景⑥：Kafka 接入（任务消息化——异步执行从"线程池"升级为"消息队列"）
    # 开发环境：本地 docker 单节点（KRaft 模式）
    bootstrap-servers: ${KAFKA_BOOTSTRAP:localhost:9092}
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.apache.kafka.common.serialization.StringSerializer
    consumer:
      group-id: research-agent-backend
      # 新消费者组从【最早】消息开始读（学习环境友好：能看到历史消息——"重放"演示的前提）
      auto-offset-reset: earliest
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      properties:
        # ★ 长任务护航：默认 5 分钟（max.poll.interval.ms）会被误判"消费者死亡"
        #   → 触发重平衡 → 重复消费。调大到 1 小时（配合"至少一次 + 状态守卫"的容错设计）
        max.poll.interval.ms: 3600000
```

**逐点讲解**：

```text
① group-id: research-agent-backend —— 消费组名
   同组多实例分摊分区；换个 group-id 就是"新订阅"（各自从头/从最新消费）
② auto-offset-reset: earliest —— 新消费组从最早消息读
   学习环境友好：能看到历史消息（"重放"演示的前提）
③ max.poll.interval.ms: 3600000 —— 长任务的命门
   默认 5 分钟：一条消息处理超时 → Kafka 认为消费者死亡 → 重平衡 → 重复消费
④ String 序列化（生产/消费）—— 练习里消息体就是 taskId 字符串（轻消息）
```

**本项目的两个"未配置项"（M4 会回来优化）**：

```text
① ack-mode：项目没显式配 → 用 Spring Kafka 默认 BATCH（一批处理完提交一次）
   长任务更推荐 record（每处理一条提交一次，减少重复窗口）——M4 讲取舍
② max-poll-records：项目没配 → 默认 500（一次拉一批）
   长任务场景建议调小（如 1），避免"一批里一条失败导致整批重投"——M4 讲
```
## 八、自测题（完整答案）

### Q1 三大价值分别对应什么场景？

```text
异步（时间解耦）：POST /api/tasks 从 6 秒变 40ms（发消息即返回）——场景⑥
解耦（空间解耦）：生产者只认消息格式，加"审计消费者"不用改生产者——场景⑥ 后续扩展
削峰（流量整形）：高峰期消息堆在 Broker，消费者按能力消费——批量导入/秒杀
```

### Q2 Kafka 的 Partition 与 RabbitMQ 的 Queue 本质区别？

```text
Kafka Partition = 一段【只追加的日志】：
  · 消息按保留策略（时间/大小）保存，不因消费而删除
  · offset 由客户端维护 → 可以【重放历史消息】（重置 offset 重读）
  · 支持多消费者各自读同一分区（不同消费组）

RabbitMQ Queue = 一个【消费即删】的队列：
  · 消费者 ACK 后消息被删除（或进死信）
  · 没有"重读历史"概念（要重放只能重新投递）
  · 一条消息在同一队列内只被一个消费者消费

→ 一句话：Partition 是"可回放的账本"，Queue 是"发完就撕的便签"。
   这决定了 Kafka 适合事件流/回放/大数据，RabbitMQ 适合业务任务分发。
```

### Q3 "消费组"在 Kafka 里解决什么问题？RabbitMQ 里对应什么？

```text
Kafka Consumer Group：
  · 组内分摊：同一个组的多个实例，各消费不同分区的消息（水平扩展）
  · 组间广播：不同消费组各自独立消费全量消息（发布订阅）
  → 一个消费者组 = 一份完整的"订阅"

RabbitMQ 对应：
  · 组内分摊 → 同一个 Queue 挂多个消费者（默认轮询分发）
  · 组间广播 → fanout 交换机 + 多个 Queue（每个 Queue 一份）

→ 差异：Kafka 的"组"是客户端逻辑概念（broker 只管分区分配）；
   RabbitMQ 靠"多个队列"物理实现广播。
```

### Q4 为什么 MQ 默认是"至少一次"而不是"恰好一次"？

```text
因为"确认"和"删除"是两步，网络随时可能断在中间：

  消费者处理完 → ACK 发出 → 【ACK 丢失】→ Broker 认为没消费 → 重投
  → 消息被处理了两次（at-least-once）

反过来"至多一次"（先 ACK 再处理）：
  ACK 后消费者崩溃 → 消息丢了（at-most-once）——更不可接受

★ 工程上：宁可重复不可丢失（业务数据丢了无法恢复，重复可以靠幂等消除）
→ 所以默认 at-least-once + 消费侧幂等 = 事实上的 exactly-once
（Kafka 的"事务 + 幂等生产者"能做到精确一次，但只在其内部链路，且成本高——M4 讲）
```

### Q5 场景⑥ 里 key = taskId 是为了什么？

```text
为了【顺序】：
① Kafka 按 key 哈希决定分区 → 同一 taskId 的消息永远进同一分区
② 同一分区内消息【串行】消费 → 同任务的消息不会并发处理、不会乱序
③ 不同任务分散到不同分区 → 并发度不受影响

反例：如果 key 用 UUID 随机或 null → 同一任务的多条消息可能乱序到达
     → "开始执行"可能晚于"取消执行" → 状态机被破坏
```

## 九、一句话

```text
MQ = 把调用变成投递：异步、解耦、削峰是它的价值；
一致性、重复、顺序、积压是它的代价。
Kafka = 可重放的日志流水账；RabbitMQ = 路由灵活的邮局。
学 MQ 不是学"怎么发消息"，是学"怎么在不可靠的投递上建可靠系统"。
```
